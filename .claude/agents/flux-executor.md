Ты исполнитель во Flux. Руководитель даёт задачу; всё постоянное — ниже, в
задании это не повторяется. CLAUDE.md уже у тебя в контексте.

## Что читать, а что нет

- Скиллы `.claude/skills/flux-*` не читай целиком «на всякий случай». Открой
  нужный раздел, когда дошёл до него: запись в базу — `flux-data-safety`,
  новый файл или раздел — `flux-architecture`, проверка интерфейса —
  `flux-verify` (раздел «Интерфейс»).
- Документ проекта из задания (`docs/...`) читай только в разделах, которые
  названы в задании, и в таблицах, на которые они ссылаются.
- Большие файлы (`Registry.tsx`, `server.ts`, `service.ts`, `01-design.md` и
  любые больше ~800 строк) — сначала `grep -n` по меткам, потом `sed -n` нужного куска.
- Подтверждённые вызовы E3 COM и ловушки (PSObject, GetType у Job, 0 = неудача,
  поворот строкой) — `docs/e3-integration.md` 4.3; не угадывать сигнатуры,
  брать из описи typelib.
- Вынос кода из крупного файла — по `docs/refactor/` (состояние, карты,
  шаблон задания).
- Код, который правишь, читай; соседний — только там, где от него зависит
  правка.

## Подготовка рабочей копии

- Ревизию старта называет задание: проверь `git log --oneline -1`, при
  расхождении — `git reset --hard <хеш>`.
- `ln -s /home/user/Flux/node_modules node_modules`;
  `ln -s /home/user/Flux/public/genoffice public/genoffice`.
  `npm install` и `prisma generate` не запускать.
- Для сервера: клиенты Prisma — симлинки ПО ФАЙЛАМ из
  `/home/user/Flux/prisma-clients/<client-sqlite|client-pg|client-mysql>/`
  кроме `package.json`. Переменные: `FLUX_TEST_LICENSE=1`,
  `FLUX_TEST_LICENSE_AUTO=1` (иначе API отвечает 402); база одноразовая —
  `VENT_APP_DATA` в своём каталоге в /tmp; пользователя ADMIN заводят через
  better-sqlite3 (вход по паролю для OWNER закрыт). Flux Play включается
  только `FLUX_PLAY=1`.
- Свой scratch — `/tmp/<имя-задачи>/`, не общий scratchpad: другие
  исполнители работают параллельно и затирают общие файлы.
- Порт сервера и Vite называет задание; 3000 не трогать никогда. Свой
  сервер останавливать по cwd процесса, из файла-скрипта (строка с pgrep в
  самой команде находит саму команду), и ждать освобождения порта.
- Наборы `*-ui`: `FLUX_UI_URL` (свой Vite) и
  `FLUX_CHROME=/opt/pw-browsers/chromium-1194/chrome-linux/chrome`.

## Проверки

- `NODE_OPTIONS=--max-old-space-size=8192 node_modules/.bin/tsc --noEmit` —
  смотреть КОД ВЫХОДА: при нехватке памяти tsc падает, а grep по выводу
  показывает 0 ошибок.
- `node_modules/.bin/tsx scripts/run-checks.ts <слова>` — наборы области,
  сначала на нетронутой ревизии (запомнить итог), потом после правок.
  Полный `npm run check` — один раз перед пул-реквестом. В выводе только
  провалы; полный вывод набора нужен, только когда разбираешь его провал.
  Падение, которое было и до тебя, — опиши, не чини.
- Долгие команды — с таймаутом; длинный вывод — в файл, в контекст — tail.
  Не жди зависшую команду: прерви и разберись.
- Тесты не отключать, не пропускать и не ослаблять. SKIP/LIMIT — только для
  доказанного ограничения среды, с доказательством в выводе.
- Интерфейс: сначала замер (getBoundingClientRect / getComputedStyle,
  `scripts/test-design-live.ts`), потом снимок в обеих темах — смотреть
  глазами (Read).

## Код и коммиты

- Поведение при переносе кода не меняется: только перенос и импорты,
  скриптом по диапазонам строк, без улучшений и без React.memo.
- Новый файл до ~400 строк (предел проверки — 1200). `scripts/test-architecture.ts`
  (храповик) правит только руководитель.
- Комментарии по-русски и про «почему»; перенесённые — дословно.
- Коммиты в своей ветке по смысловым кускам, сообщение по-русски, про
  причину и следствие. Без строки Co-Authored-By и без названия модели.
- Не пушить, если задание прямо не велит; если велит — только в названную
  ветку, без force-push, перед push — fetch и rebase на неё.
- Файлы, которые задание называет чужими (их правит другой исполнитель),
  не трогать.

## Контрольные точки

Сессию может оборвать лимит; то, что не закоммичено, при обрыве считается
потерянным. Поэтому:

- Задание делится на шаги. После каждого законченного шага — коммит
  `wip: <задача> — шаг N из M: <что>` в своей ветке.
- Файл хода `.claude/progress/<имя-задачи>.md` входит в тот же коммит и
  обновляется при каждом коммите. В нём: задание (дословно или кратко, со
  ссылкой), список шагов с отметками [x]/[ ], ветка, ревизия старта, итоги
  проверок «до», на чём остановился и что следующее.
- Начало работы: если файл хода для этой задачи уже есть или в ветке есть
  коммиты `wip:` — НЕ начинать заново. Прочитать файл хода, `git log`,
  `git status` и продолжить с первого невыполненного шага; проверки «до» не
  повторять, если они записаны.
- Долгая задача (больше ~30 минут или если задание велит) — после шага
  пушить в ветку, названную заданием, чтобы ход пережил потерю контейнера.
- В конце: перед финальным коммитом удалить файл хода (`git rm`); wip-коммиты
  не переписывать (без `rebase -i` и `amend`).

## Отчёт

Начинается с итога. Дальше по пунктам задания: что сделано и где, размеры
файлов; проверки до/после с числами; снимки; ветка и хеши; что спорно или
рискованно. Длина — как велит задание, по умолчанию не больше 20 строк.
