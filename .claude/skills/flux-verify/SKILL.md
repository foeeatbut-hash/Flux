# Проверка работы

## Наборы проверок

Логика, у которой есть правильный ответ, проверяется скриптом. Запуск:

```bash
npx tsx scripts/test-<имя>.ts
```

Что уже есть: `test-capture` (распознавание захвата и конфликты),
`test-constructor-fn` (своды по проекту), `test-architecture` (границы между
слоями и размер файлов, см. skill `flux-architecture`), `test-blank-parser`,
`test-normalize`, `test-doc-import`, `test-nlp`, `test-assistant`,
`test-api`, `test-flow`, `test-mail`, `test-ribbon` (состав лент
редакторов) и `test-layout` (`api`, `flow` и `layout`
требуют поднятого сервера, см. ниже).

Формат — простой и одинаковый, без фреймворка: счётчик, функция сравнения,
названия проверок по-русски и по существу.

```ts
const eq = (name: string, got: any, want: any) => { /* … */ };
eq('разделитель между цифрами значим', normCode('бл2.1') === normCode('бл21'), false);
console.log(`\n${ok} проверок пройдено, ${fail} провалено`);
process.exit(fail ? 1 : 0);
```

Название проверки должно говорить, **что именно** сломается: «разные номера не
считаются похожими» лучше, чем «тест 4».

Проверки пишутся до того, как объявить готовым. На этом проекте они уже
несколько раз ловили дефекты, которые выглядели правильно в коде: слипание
`бл2.1` с `бл21`, привязку `AHU-21` к `AHU-211`, потерю кодов с цифры.

## Типы и сборка

```bash
npx tsc --noEmit    # ноль ошибок; любая новая — своя, чинить
npx vite build
npm run build:electron
```

## Интерфейс

Для нового экрана — снимок и просмотр, а не «выглядит правильно». Схема:
поднять `vite preview`, открыть страницу в Chromium через `playwright-core`,
снять снимок, посмотреть.

```js
const b = await chromium.launch({
  executablePath: '/opt/pw-browsers/chromium-1194/chrome-linux/chrome',
  args: ['--no-sandbox'],
});
```

Проверять обе темы (`colorScheme: 'light' | 'dark'`), горизонтальную прокрутку
(`document.documentElement.scrollWidth - clientWidth` должно быть 0) и ошибки в
консоли (`pageerror`, `console` типа `error`).

Если верстка ведёт себя странно — **измерять**, а не гадать: `getBoundingClientRect`,
`getComputedStyle`. Так нашлось, что кнопка с классом `.ok` обнуляла ширину
бейджам `.badge.ok` — столкновение имён в каскаде, на глаз неотличимое от
случайности.

## Сервер здесь поднимается — этим надо пользоваться

Раньше здесь было записано, что сервер в контейнере не запускается. Это
неверно: `npx tsx server.ts` поднимает Express на порту 3000, создаёт SQLite в
`database/`, синхронизирует схему и засевает администратора `RaupovKhKh` с
паролем `1122`. Через полминуты по API можно работать по-настоящему.

```bash
nohup npx tsx server.ts > /tmp/srv.log 2>&1 &
until curl -s localhost:3000/api/health >/dev/null; do sleep 3; done
npx tsx scripts/test-api.ts
```

`scripts/test-api.ts` — дымовая проверка HTTP-слоя: вход, отказ по чужому и
подделанному токену, основные списки, запись и удаление. Гонять её обязательно
до и после переноса маршрутов из `server.ts` в `server/routes/*` — перенос
легко сделать «почти правильно».

Осторожно с `pkill -f "tsx server.ts"`: строка совпадает с собственной командной
строкой оболочки, и она убьёт сама себя. Писать `pkill -f "tsx serv[e]r.ts"`.

## Интерфейс живьём, включая вход

Программа открывается в браузере по тому же адресу. Лицензия проверяется
подписью, приватного ключа в репозитории нет и быть не должно — для проверки
интерфейса подменяется **только ответ проверки**, код программы не трогается:

```js
await page.route('**/api/license/status', r => r.fulfill({
  status: 200, contentType: 'application/json',
  body: JSON.stringify({ licensed: true, machineId: 'T', expiresAt: Date.now() + 9e8, daysLeft: 30, reason: '' }),
}));
```

Дальше — вход `RaupovKhKh` / `1122`, выбор проекта, разделы открываются кликом
по плитке на Главной или по левому меню. Так проверяются все 14 разделов на
ошибки в консоли и на переливы вёрстки.

Двух живых собеседников делать не нужно: `scripts/test-chat-privacy.ts` поднимает
три сокета (отправитель, получатель, посторонний) и проверяет, кому пришло.

## Раскладка при сжатии: мерить панель, а не окно

`scripts/test-layout.ts` обходит все разделы и меряет геометрию каждого
элемента на экране: вылет за пределы места, обрыв подписи без многоточия,
схлопывание в ноль, кнопки мельче 20 px.

Ключевое: раздел живёт **в своём окне, а не во весь экран**. Окно бывает
любого размера — половина стола, четверть, ужатое до 820 px, — и раздел обязан
держаться в нём, а не в экране. Отсюда два правила:

- в разметке разделов правил окна (`sm:`, `md:`, `lg:`, `xl:`) быть не должно —
  вместо них запросы к контейнеру: `@[900px]:grid-cols-3`. Контейнером окно
  объявлено в `WindowsLayer.tsx` одной строкой `@container`, и та же метка
  `data-window-body` служит корнем измерения для проверки. Правила окна
  остаются законными только в оболочке и всплывающих окнах — они и правда
  живут в окне;
- мерить надо ОКНО, а не стол. Проба берёт корнем `[data-window-body]`:
  раздел отступает от него, и ширина стола ему ничего не говорит. Именно так
  выяснилось, что Блокнот мерил свою высоту от окна (`100vh`) и выходил вдвое
  выше своего места.

Раньше проходов было два — одна панель и четыре, — потому что панельная
оболочка давала разделу то целый экран, то его четверть. Панелей больше нет:
окно и есть панель, только двигается, и узкий случай даёт узкий экран.

Список объяснённых исключений в файле держать коротким. Каждый пункт — с
причиной, иначе за год он разрастётся и проверка перестанет что-либо значить.

Проверка меряет то, что лежит в базе, — и потому зависит от данных. Заголовок
заметки вылезал за карточку на 34 px только при заметке с названием по
умолчанию («Новая заметка»), а в засеянных данных такой нет: обход её не видел,
пока заметку не завели руками. Отсюда два вывода: свои пробные записи после
прогона удалять обязательно (иначе провалы окажутся своими же), а найденную
причину закреплять проверкой в наборе `architecture`, которая смотрит разметку
и от данных не зависит. Для этого случая — `truncate` на flex-контейнере.

## Правила доступа проверяются вдвоём, а не в одиночку

`scripts/test-mail-shared.ts` заводит второго сотрудника, входит от его имени и
смотрит на одни и те же данные с двух сторон. Иначе главное свойство общего
ящика не проверить: «прочитано» там личное, и что письмо, открытое одним,
осталось непрочитанным у второго, видно только при двух живых сеансах.

Тем же способом проверяется и обратное — что чужой личный ящик не виден
никому: и в списке, и по прямому обращению с чужим `accountId`. Проверка «я не
вижу своего чужого» бессмысленна, нужен именно второй вход.

Пароль второму сотруднику набор ставит сам и не полагается на засеянный: иначе
прогон зависит от того, что лежало в базе.

## Сценарии вместо обхода «нажмём всё подряд»

`scripts/test-flow.ts` проходит путь инженера через интерфейс и сверяет
результат с базой: завели тег в «Тегах» — он обязан появиться в базе, в списке
закупок и в счётчике позиций; удалили — исчезнуть отовсюду; создали заметку и
напечатали текст — текст обязан оказаться на сервере.

Обход «нажмём каждую кнопку и посмотрим» так не работает. Он не знает, что
должно произойти, и выдаёт за дефекты собственные промахи. Проверено на этом
проекте — почти все его находки оказались его же artefact'ами:

- на Главной боковое меню свёрнуто в нулевую ширину, но кнопки остаются в
  разметке: клик уходит в невидимую и отваливается по таймауту;
- React при перерисовке создаёт узлы заново — метки, проставленные заранее,
  теряются, и все кнопки выглядят «недоступными»;
- сравнение длины разметки не видит перестановку строк местами;
- панель редактора выглядит мёртвой, если в тексте нет курсора;
- «кнопка перекрыта» бывает обычным всплытием события на вложенный span.

Разделы держатся смонтированными (keep-alive), поэтому селектор находит поля
скрытых разделов. Брать надо **первое видимое**, иначе ввод уходит в невидимое
поле соседнего экрана.

Убирать за собой обязательно, и **сначала закрывать браузер, потом удалять
данные**: редактор досохраняет текст с задержкой, и запись, удалённая при живой
странице, появляется снова.

## Чему нельзя верить при проверке интерфейса

`document.body.innerText.includes(текст)` — **не** доказательство, что сообщение
отправилось: набранный текст лежит в поле ввода и тоже попадает в `innerText`.
Так уже был получен ложный «✓» на пустой переписке. Проверять надо две вещи
сразу: запись в базе через API и наличие текста в ленте **вне** полей ввода.

Набирать текст `page.keyboard.type()` в сфокусированное поле, а не подменять
`textContent` — редактор на `contenteditable` не заметит подмены и Enter уйдёт
в пустоту.

## Почта: сервера снаружи нет, а проверять надо

Порт 993 из контейнера закрыт, живой ящик не подключить. Это не повод не
проверять раздел: письма кладутся прямо в базу (`MailAccount`, `MailFolder`,
`MailMessage`, `MailAttachment`), и дальше работает весь путь — список,
цепочки, чтение, поиск, отметки. Так и нашлись оба дефекта показа тела письма.

Обязательно засевать письмо с **заведомо вредоносным HTML**: скриптом,
картинкой по внешней ссылке, ссылкой `javascript:` и плашкой `position:fixed`.
Проверять два признака сразу: в отчёте Playwright нет запросов на чужие
адреса, а `contentDocument` у iframe письма недоступен снаружи — это и есть
доказательство, что песочница на месте.

Разбор адресов, цепочек и правила безопасности тела покрыты `test-mail.ts` и
проверяются без браузера.

Остаётся непроверяемым: захват с экрана целиком (нужен Electron и буфер обмена)
и сборка exe.

Для такого честная формулировка: «проверено разбором кода, типами и сборкой; на
живых данных не наблюдал». Не выдавать рассуждение за наблюдение — если в
отчёте сказано «работает», это должно означать, что я это видел.
