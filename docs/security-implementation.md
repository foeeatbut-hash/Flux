# Защита и подключение Flux

Этот документ описывает итог реализации. Исходные решения и мотивация этапов A–E сохранены в `security-plan-stage2.md`. Ручная проверка текущих исходников, её результаты и оставшиеся ограничения приведены в [manual-security-review-2026-10-03.md](manual-security-review-2026-10-03.md).

В исходниках Flux закреплены четыре публичных ключа из комплекта владельца. Уже созданное хранилище Flux-Owner сохраняется; повторно создавать ключи не нужно. При первоначальном развёртывании нового комплекта передают сборщику только `flux-public-keys.json`, затем вручную устанавливают сборку с соответствующими ключами и перевыпускают лицензии. Закрытые ключи и зашифрованные `.flux-owner` файлы для сборки не используются. Новые portable EXE с текущими изменениями пока не выпущены.

## Полномочия и лицензии

Исходники отдельного приложения владельца находятся в `tools/flux-owner`.
Наличие программы не предоставляет права владельца: для входа и подписи нужен
закрытый ключ, соответствующий закреплённым открытым ключам. Начальная настройка
описана в `tools/flux-owner/README.md`; опубликованные ранее EXE не получают
изменения исходников автоматически.

Первый профиль OWNER создаётся только после одноразового подписанного запроса входа. Вход паролем для него запрещён. Автоматического администратора с известным паролем больше нет. Владелец управляет подключением к БД, системными ролями, расписанием копирования и подписанными обновлениями. Администратору отдельно выдаются права работы с сотрудниками, активации лицензий и ручной резервной копии; назначить другого администратора может владелец.

Лицензия FLUX2 связана с установкой компании и логинами сотрудников. Истёкшая лицензия оставляет чтение с пояснением о продлении. Сервер запрещает изменения через HTTP и сокеты, включая сохранение Office, а не только скрывает кнопки. Подписанный список FLUXREV1 содержит накопленные отзывы и растущий номер. Работающий процесс помнит принятый список и отклоняет его удаление или откат; новый процесс не знает записи, уже удалённые из БД, поэтому восстановление старой БД после перезапуска может вернуть их действие.

Сессии живут восемь часов. Смена пароля, роли, разрешений или активности отказывает прежнему токену; выход отзывает отдельную сессию в общей БД. Браузер использует HttpOnly cookie и подписанный CSRF, Electron хранит токен через safeStorage в главном процессе. Старый bearer из localStorage удаляется. Открытые сокеты повторно проверяют права и лицензию; связи сущностей с проектом проверяются до обработчиков, а содержимое проектных событий берётся из БД.

## Сервер и обновления

Для выбранного развёртывания используется существующая MariaDB компании. Настольный Flux запускает свой API на рабочей станции и подключает его к общей БД. Flux Owner принимает SQL URI, запускает отдельный portable Flux в режиме `--flux-company-server` на loopback и входит в его API подписанным запросом. Блокировка GUI не мешает этому серверному процессу; отдельные сессии используют разные порты и временные каталоги. Настольный Flux сохраняет URI в конфигурации рабочей станции без шифрования DPAPI. Owner не сохраняет URI между подключениями: после отключения или нового запуска его нужно ввести снова; пароль не записывается в хранилище Owner, статус или реестр. Установка программы на NAS для этого варианта не требуется. Он предполагает доверенные рабочие станции, которым разрешён прямой доступ к общей БД.

Пользовательский вариант подключения сейчас только direct DB: настольные Flux и Flux Owner принимают URI MariaDB/MySQL. Отдельный внешний HTTP API сервер для пользователей не предусмотрен; внутренний API настольного приложения работает на loopback. Текущая инструкция — `company-server.md`.

У direct DB есть существенная граница доверия: SQL-реквизиты используются на рабочих станциях, и права учётной записи действуют непосредственно в базе. Это не защищает абсолютно от патча клиентской программы или администратора БД с достаточными правами; выдавайте отдельной записи только нужные права и ограничивайте сетевой доступ.

Flux-Owner подписывает файл выпуска отдельным ключом и загружает его в БД. Публикация проверяет подпись, полную длину и хеш всех кусочков; внешняя ссылка вместо файла не принимается. Сотрудники получают только чтение сведений о выпуске и скачивание. Изменение БД не даёт подписать собственный EXE.

Без обязательного внешнего сервиса нельзя гарантировать защиту от администратора сервера с root: он может заменить сам код проверки. В текущем варианте компания работает автономно, закрытые ключи остаются у владельца. Сертификат подписи Windows отдельно подтверждает издателя для Windows; он не заменяет подпись обновлений Flux и не требуется для этих протоколов.

## Проверки и границы

Проверены подписи, повторный вход по nonce, отзыв, конфликтные активации, отказ production-режима от тестовых ключей, сессии/CSRF, права пользователей, принадлежность сущностей проектам и публикация через кусочки БД. В исходниках намеренно лежат непроизводственные приватные тестовые ключи в fixtures; исходный тестовый сервер принимает их только при явной настройке, а portable Flux им не доверяет.

Первый запуск, Windows safeStorage и безоконный сервер необходимо дополнительно проверить на Windows после закрепления открытых ключей. Доступ к серверу компании из облачной среды не проверен: требуется сеть компании или VPN. Корпоративные настройки и данные при этих проверках не изменялись.
