# Постепенный перевод частей Flux на Rust

Статус: идея · обновлено 4 ноября 2026

Решение владельца (4 ноября 2026): переписывать на Rust постепенно и только
то, что от этого выигрывает — скорость, память, надёжность нативной части.
Программа целиком не переписывается: интерфейс остаётся веб-интерфейсом
(React, редакторы GenOffice), сервер — на TypeScript. Узкие места там — база,
сеть и логика, а не язык; перепись дала бы месяцы без новых функций и заново
пойманные ошибки.

## Правило отбора

Часть переводится на Rust, только если выполнены все три условия:

1. **Есть замеренная проблема** — время, память, падения, — а не «на Rust
   быстрее». Замер до и после записывается в PR.
2. **Часть отделена договором**: вход и выход — данные (JSON, файл, поток), а не
   общие объекты программы. Тогда её можно заменить целиком и сравнить на тех
   же входах.
3. **Есть набор проверок на настоящих данных**, который гоняется на старой и
   новой версии и даёт одинаковый результат (кроме исправленных ошибок).

Старую версию не удаляют, пока новая не прошла Windows CI и приёмку владельца;
переключение — настройкой, откат — ею же.

## Что уже есть в программе

- **Движок Excel на Rust** — большие книги в Таблицах (окно ячеек, потоковое
  чтение); собирается в GitHub Actions под Windows x64
  (`docs/office-engine-choice.md`, `docs/office-genoffice-plan.md`). Это
  образец сборки и поставки.
- **Нативный помощник Проводника** — C# через `Add-Type` в долгоживущем
  процессе (`electron/nativeShellSource.ts`, `electron/nativeShellHost.ts`);
  замена файла при сохранении — `electron/filesystem/replace.ts`, PowerShell на
  каждое сохранение (`docs/plan.md`, раздел 1).
- **Модули расчётов через WebAssembly** — уже предусмотрены
  (`docs/roadmap/modules.md`): Rust — один из языков модуля.

## Этапы

1. **Нативный помощник Windows** (первый кандидат). Сохранение файла, корзина,
   миниатюры, меню Оболочки, длинные пути `\\?\` — одним долгоживущим
   процессом на Rust (`windows-rs`) вместо PowerShell и C# через `Add-Type`.
   Польза: сохранение без запуска PowerShell, нет компиляции C# при старте,
   длинные пути. Готово, когда `scripts/test-windows-files-native.ts`
   проходит на Windows CI с новым помощником, а время сохранения замерено до и
   после. Закрывает пункт «Быстрое сохранение в Windows» из `docs/plan.md`.
2. **Разбор больших файлов — по замеру.** XML Веза (`server/vezaXml.ts`),
   выгрузки E3, импорт бланков: переводить только тот разбор, который на
   настоящих файлах заказчика тормозит или ест память. Форма — модуль
   N-API (`napi-rs`) с тем же входом и выходом; набор проверок — существующие
   `scripts/test-veza-xml.ts` и соседи, плюс сверка результата старого и
   нового разбора на папке настоящих файлов.
3. **Модули расчётов** — Rust как язык модуля через WebAssembly, по плану
   `modules.md`; отдельной переписи программы не требует.

## Что не переводить

- Интерфейс и редакторы GenOffice — веб-библиотеки, замены на Rust нет.
- Сервер API и работа с базой (Prisma, три СУБД) — выигрыша нет, риск большой.
- Оболочка Tauri вместо Electron — **не сейчас**: потребует переписать главный
  процесс (Проводник, мост к E3, обновления) и проверить редакторы во
  встроенном браузере Windows (WebView2). Вернуться, если размер или память
  Electron станут проблемой у пользователей; тогда этот план правится.

## Вопросы владельцу

1. Начинаем с этапа 1 (помощник Проводника), когда до него дойдёт очередь
   `docs/plan.md`? *По умолчанию:* да.
2. Есть ли у вас файлы, на которых программа сейчас заметно тормозит (большие
   XML, выгрузки E3, книги Excel)? Они нужны для замеров этапа 2.
