# Модули внутри Flux и Flux Studio

Статус: в работе (этап 2 влит, #139; следующий — этап 3) · обновлено 7 ноября 2026

Задание на разработку для внешнего исполнителя (порядок PR и критерии
приёмки) — [studio-handoff.md](../studio-handoff.md).

Любые подпрограммы разных разработчиков — расчётные и любые другие — живут
внутри Flux как **модули**. Во Flux одна **универсальная оболочка**: окно
модуля, место в «Пуске», вход из карточек. Модуль сам объявляет, где он
появляется. Логику и интерфейс модуля ведёт разработчик через отдельную
программу — **Flux Studio** (свой portable, одна на все модули и всех
разработчиков). Обновление, выложенное из Studio, сразу доходит до всех
Flux через общую базу; новый portable Flux для этого не выпускается.
Данные Flux модуль только читает: ничего во Flux не правит.

## Главный принцип: Flux — операционная система для модулей

Решение владельца (4 ноября 2026): Flux для модулей — как Windows для
программ. Разработчик пишет модуль, как пишут программу под Windows, и он
работает во Flux полноценно. Отсюда устройство:

| Windows | Flux |
|---|---|
| Win32/WinRT API | **API Flux** — один для всех модулей: данные Flux, окна, «Пуск», карточки, уведомления, открытие и сохранение файлов через Проводник, печать и выгрузка, подключения к внешним программам (E3, API по адресу), фоновые задачи |
| Установка программы | выпуск модуля через общую базу, сразу у всех |
| Подпись кода (Authenticode) | подпись разработчика + сертификат владельца |
| Разрешения приложений (камера, файлы, сеть) | разрешения в `manifest.json`: какие данные, какие подключения; владелец разрешает один раз |
| Программа не ломает Windows и другие программы | изоляция: ошибка модуля не роняет Flux и чужие модули |
| Новая версия Windows не ломает старые программы | API и договор с номером версии; Flux держит текущую и предыдущую |

API Flux растёт вместе с Flux: всё, что Flux умеет сам, со временем
становится доступно модулям через API с разрешением. Запись в данные Flux —
такая же часть API, но пока закрыта решением владельца (п. 4 ниже) и
открывается по разрешению, когда владелец решит.

## Решение владельца (6 ноября 2026)

Модули подписываются тем же ключом владельца, что и обновления Flux (`keys.update`); отдельного ключа модулей нет. Подписи не спутать: у выпуска, запроса, сертификата, отзыва отката и перевода в рабочий канал разные приставки (`FLUXMOD1`, `FLUXMODREQ1`, `FLUXMODCERT1`, `FLUXMODREV1`, `FLUXMODPIN1`, `FLUXMODCHANNEL1`).

## Решение владельца (7 ноября 2026): языки и нагрузка

Логика подпрограмм пишется **только** на: TypeScript/JavaScript, Python
(Pyodide) и WebAssembly для C, C++, Rust, Go и C#. Других языков (Fortran, Java,
Lua и т. п.) и «отдельного процесса» для них не добавлять. Flux должен работать
**легко для компьютера, точно и надёжно**: всё вне главного потока, не больше
«ядра − 1» (до 4) расчётов разом, фон уступает открытому окну, простой — 0 %
процессора, числа float64 (целое больше 2^53 — строкой, NaN и бесконечность —
ошибка), детерминизм (случайность только от зерна). Реализовано в этапе 3а.

## Решение владельца (9 ноября 2026): запрос разрешения у человека и журнал подпрограмм

Дополняет «Подключения к внешним программам». **Разрешение двухступенчатое:**
владелец допускает подключение выпуску при публикации (объявление в подписанном
`manifest.json` — это допуск), а человек при **первом обращении** подпрограммы к
программе видит запрос и решает сам — как в Windows или на телефоне, для обычного
человека, а не программиста.

1. **Окно запроса:** «„<подпрограмма>“ хочет подключиться к <понятное имя программы>»,
   значок, одна строка простым языком о том, что подпрограмма будет делать.
2. **Выбор:** «Разрешить всегда», «Только сейчас» (фокус по умолчанию), «Не разрешать»
   (Esc). «Всегда» и «Не разрешать» запоминаются для этой подпрограммы, этого
   подключения, этого человека на этом компьютере; «только сейчас» — до закрытия окна подпрограммы.
3. **«Подробнее»:** что именно разрешается (читать / изменять / отправлять данные, в какую
   программу), чего подпрограмма не получит, кто выпустил и когда проверил владелец;
   технические сведения (COM-объект, порт, путь) — ещё ниже, свёрнуто «Для специалиста».
4. **Тексты для человека задаёт разработчик** в `manifest.json` (`app`, `does`, `access` —
   обязательны), проверяет владелец («Запросы на публикацию» показывают их как увидит
   человек); пустые и технические тексты не пропускает схема манифеста.
5. **Управление:** страница подпрограммы в Store («Разрешения») и «Настройки → Подпрограммы»:
   «Разрешено / Спрашивать / Запрещено», «Сбросить все». Администратор может запретить
   подключение роли — политика хранится и проверяется (сервер и главный процесс) и сильнее выбора человека.
6. **Новая версия с новым адресом или более широким доступом** (было «читать», стало «изменять»)
   спрашивает снова: прежний выбор привязан к тексту разрешения.
7. **Отказ:** подпрограмма получает ошибку `NOT_ALLOWED` и работает без подключения; в окне — плашка
   «Нет доступа к … — Разрешить…».
8. **Без связи** сохранённые решения и запрос работают: решение хранит главный процесс.

**Журнал всего, что делают подпрограммы** (не только подключений): запуск и закрытие,
расчёты, чтения данных Flux (вид и объём), запросы разрешений и решения, подключения
(к чему, метод, длительность, объём, итог), строки самой подпрограммы через `flux.log`
(info/warn/error, не чаще 5 в секунду, до 200 знаков), сбои. Без данных проектов и содержимого вызовов.
Хранится на компьютере кольцом (5000 записей, 14 дней) и уходит на сервер пачками (30 дней,
200 000 строк). Смотрят владелец и администратор (с именами, фильтры, CSV), разработчик —
только свои подпрограммы и **без людей**. Журнал можно приложить к обращению (флажок в панели «Сообщить о проблеме», строки видны до отправки, до 30 строк, без людей и проектов); правила политики задаёт администратор во вкладке «Подключения» Store.

## Решения владельца (4 ноября 2026)

1. Программа разработчика называется **Flux Studio** (было «Flux SDK»).
2. ВЕРОСА ни при чём: в плане нет ни первого модуля, ни примера под
   конкретную подпрограмму. Первый модуль — простой пример разработчика.
3. Любой разработчик делает свою подпрограмму в Flux Studio — любую, не
   только расчётную. Поэтому оболочка не добавляется владельцем в portable
   под каждую программу: во Flux одна универсальная оболочка (окно модуля,
   место в «Пуске», вход из карточек), а модуль сам объявляет, где
   появляется. Цепочка доверия остаётся: владелец выдаёт сертификат
   разработчику, Flux запускает только подписанное. Решение 29 октября
   «оболочку добавляет владелец» заменено этим.
4. Данные Flux — только на чтение. Пока модуль может брать любые данные Flux
   через договор (проекты, оборудование и его параметры, теги, спецификации,
   каталог, файлы Проводника, ВДР и т. п.), но ничего во Flux не правит.
   Записи из модуля нет; результат модуль показывает в своём окне и, если
   нужно, отдаёт пользователю файлом. Запись — возможное развитие позже,
   отдельным решением владельца.
5. **Вход в Studio — как во Flux.** Studio подключается к той же общей базе
   тем же способом, что обычный Flux, и работает по той же лицензии. Профиль
   разработчика заводит владелец/администратор там же, где все профили Flux;
   в Studio видны те же профили. Для этого — новая должность (роль)
   **«Разработчик»** с правами `module.develop` (и `module.publish`, если
   выдано); войти в Studio может только профиль с этим правом. Отдельной
   учётной системы у Studio нет.

## Решения владельца (29 октября 2026)

- Разработчики модулей — внутренние программисты компании.
- Оболочку подпрограммы и её связи с данными проекта добавляет владелец в
  portable Flux, один раз на программу. *Заменено решением 4 ноября 2026:
  одна универсальная оболочка.*
- Логику и интерфейс внутри оболочки меняет разработчик через Studio.
  Выкладывает сам, когда угодно, или передаёт пакет владельцу, и тот
  выкладывает.
- Всё хранится и раздаётся через общую базу (SQL), отдельного сервера нет.
- В Studio есть панель для настройки интерфейса подпрограммы.
- Логика может быть на любом языке, оболочка — на TypeScript.
- Название — **Flux Studio** (с 4 ноября; было Flux SDK). Studio —
  универсальная программа: для любых модулей любых разработчиков.
- Studio выпускается **вместе с каждой версией portable Flux** и проверяет,
  что модуль правильно работает со связками Flux: проекты, теги,
  оборудование, файлы Проводника, спецификации, выпуск документов.
- В Studio — панель разработчика с инструментами для интерфейса или
  написание всего кодом.
- В Studio встроена методология дизайна и интерфейса Flux: кнопки, строки,
  поля, таблицы во всех модулях одинаковые.

## Что есть в программе (разведка кода, 29 октября 2026)

### Раздача обновлений через базу — готовый образец
- `server/updates.ts`: таблицы `AppUpdate` (версия, поколение, состояние
  `uploading → ready → published`, подпись, размер, sha256, число кусков) и
  `AppUpdateChunk` (куски до 2 МБ, размер — от `max_allowed_packet`,
  `server/limits.ts:34–54`; при сбое кусок делится пополам). Выпуски
  неизменяемы, есть отзыв и журнал.
- Подпись Ed25519, формат `FLUXUPD1.<манифест>.<подпись>`
  (`electron/updateSignature.ts:48–60`), открытый ключ зашит в exe
  (`electron/updateKey.ts`), закрытый — у владельца
  (`tools/update-sign.mjs`). Проверяется на сервере и на клиенте перед
  установкой; откат на старую версию запрещён.
- Клиент узнаёт о выпуске опросом `GET /api/updates/latest`
  (`src/store/updateStore.ts:110`); кампании назначают выпуск устройствам
  (`server/routes/updateCampaigns.ts`, подписанные команды, делегирование).
- Для модулей переиспользуется: «метаданные + куски в базе», проверка
  sha256 по кускам, формат подписи (свой префикс и ключ), состояния,
  поколения, отзыв, кампании. Не переиспользуется: проверка MZ, замена exe,
  запрет отката.

### Изоляция — готовый образец моста
- Главное окно: `nodeIntegration: false`, `contextIsolation: true`,
  `sandbox` по умолчанию (`electron/main.ts:63–82`). IPC — белые списки
  каналов (`electron/ipcAllow.ts`), каналов для модулей нет.
- Редакторы Flux Office (GenOffice) открываются в `<iframe>`
  (`src/components/office/OfficeAppEditor.tsx:464` и др.) и говорят с Flux
  через `postMessage` `{flux:'office', id, op, payload}`
  (`src/lib/officeBridge.ts:11–25`, проверка источника `fromOwnFrame`).
  Это образец моста, **но** у iframe нет атрибута `sandbox` и он того же
  источника, что Flux: изоляция держится только на CSP внутри страницы.
  Для чужого кода этого мало.
- CSP главного окна не задана (в `index.html` и сессии Electron не найдена).

### Подключения к внешним программам (решение владельца, 4 ноября 2026)

Модуль — **часть Flux**, а не отдельная программа: открывается в окне Flux, в
«Пуске» и карточках, в оформлении Flux, с данными Flux. Изоляция защищает от
ошибок и чужого кода, но не отрезает модуль от внешних программ: модуль
**просит подключение у Flux, Flux его открывает, и дальше модуль работает с API
программы сам**, любыми его методами.

- Модуль объявляет в `manifest.json`, какие подключения ему нужны: E3 (COM),
  адрес и порт по HTTP/WebSocket (например, сервер API другой программы по IP),
  при необходимости другие способы (COM-объект по имени, локальный сервис).
- Владелец разрешает подключения модулю один раз — вместе с сертификатом
  разработчика или выпуском; без разрешения подключение не открывается.
- Flux открывает подключение и становится **сквозным каналом**: вызовы модуля
  к API программы проходят через Flux как есть, без того чтобы каждый метод
  описывать в portable. Flux проверяет только, что подключение разрешено, и
  пишет журнал (кто, когда, к чему подключался).
- Способы подключения (COM, HTTP по адресу, WebSocket и т. п.) — это общий
  набор Flux, один на все модули: добавить новый способ — выпуск Flux;
  пользоваться им — выпуск модуля.
- Что по-прежнему закрыто без отдельного решения: правка данных Flux, сеть на
  адреса, не объявленные и не разрешённые модулю, запуск exe на компьютере.

### Права
- Роли: OWNER, ADMIN, MANAGER, ENGINEER_VENT, ENGINEER_AUTO, SERVICE; свои
  роли создаются (`src/lib/roles.ts`, таблица `Role`). Права по функциям —
  `src/lib/permissions.ts`, проверка `permAllows` (`server.ts:705`).
- «Разработчик каталога» — не роль, а права `catalog.*` (по умолчанию
  запрещены). Так же стоит сделать права модулей.

## Как это устроено

### Две части: оболочка во Flux и содержимое в базе

| | Оболочка (в portable Flux) | Содержимое (в общей базе) |
|---|---|---|
| Кто меняет | владелец (оболочка) | разработчик модуля через Studio |
| Как обновляется | новый portable | выпуск из Studio, сразу у всех |
| Что внутри | универсальная оболочка: окно модуля, место в «Пуске», вход из карточек, договор, мост, исполнитель, проверка подписи | интерфейс, логика, справочные данные модуля, контрольные примеры |

### Договор
Оболочка задаёт договор — версионированный перечень:
- **что читает:** проект, позиция оборудования с параметрами и составом,
  теги, спецификации, каталог, файлы Проводника, ВДР и другие данные Flux —
  только на чтение;
- **что пишет:** ничего во Flux; результат расчёта модуль показывает в своём
  окне (см. «Результат расчёта»);
- **события:** «открыт из карточки», «проект сменился», «данные позиции
  изменились»;
- **схемы входа и выхода** (JSON Schema) — оболочка проверяет каждое
  сообщение модуля по схеме.

Договор имеет номер версии. Модуль объявляет, с какой версией договора он
работает. Flux поддерживает текущую и предыдущую версию; модуль, которому
нужна более новая, не запускается: «Обновите Flux до версии …». Новое поле
или связь — новая версия договора и новый portable.

### Пакет модуля
Описание (имя, версия, автор, версия договора, права, языки), интерфейс,
логика, справочные данные, контрольные примеры, подпись. Хранится как
выпуск — по образцу `AppUpdate`/`AppUpdateChunk`, отдельными таблицами
`ModuleRelease`/`ModuleChunk`.

### Цепочка доверия — главное условие
У каждого Flux есть реквизиты SQL общей базы
([company-server.md](../company-server.md)). Значит, **любой**
пользователь технически может записать в таблицу модулей что угодно.
Поэтому Flux не доверяет таблице, а доверяет только подписи:
1. Корень — ключ владельца, зашитый в exe (как `electron/updateKey.ts`).
2. Владелец выдаёт разработчику сертификат: «ключ разработчика X может
   подписывать модули» (подписан ключом владельца, лежит в базе).
3. Разработчик подписывает выпуск своим ключом в Studio.
4. Flux перед запуском проверяет: подпись выпуска → сертификат
   разработчика → ключ владельца; sha256 всех кусков. Что-то не сходится —
   модуль не запускается, предыдущая проверенная версия продолжает
   работать.
5. Отзыв сертификата — запись, подписанная владельцем; выпуски отозванного
   ключа перестают запускаться.

### Изоляция
- Модуль открывается в iframe **другого источника**
  (`flux-module://<id>/`, свой протокол Electron) с
  `sandbox="allow-scripts"` без `allow-same-origin`, со своей CSP
  `default-src 'none'` + только свои файлы. Нет доступа к Node, Electron,
  IPC, cookie и хранилищу Flux, сети.
- Связь — только `postMessage` по образцу `officeBridge.ts`, но каждое
  сообщение проверяется по схеме договора; лишние поля отбрасываются.
- Расчёт — в Web Worker внутри iframe, с пределом времени (например,
  30 с) и памяти; зависший worker останавливается.
- Модуль ничего не пишет в базу. Данные Flux он получает через оболочку по
  договору, только на чтение и с правами пользователя. Модуль не может
  больше, чем пользователь.
- Упавший модуль закрывает только своё окно.

### Интерфейс: панель в Studio
- Основной путь — **описание формы** (JSON): группы, поля, таблицы,
  графики, привязки к данным. Оболочка рисует её компонентами Flux — модули
  выглядят частью программы и меняются вместе с её оформлением.
- Визуальный редактор этой формы в Studio: перетащить поле, привязать к
  входу или выходу расчёта.
- Для того, что формой не собрать (своя схема установки, график
  характеристики) — свой код страницы внутри той же изоляции.
- Просмотр сразу в оболочке на тестовых данных.

### Как связаны форма, код и данные (решение руководителя, 4 ноября 2026)

Чтобы визуальный редактор, код и данные не расходились, у модуля **один
источник на каждую часть**, а редакторы Studio — лишь разные виды одного файла:

| Файл пакета | Что в нём | Чем правится |
|---|---|---|
| `manifest.json` | имя, версия, версия договора, где появляется («Пуск», карточка оборудования, тега), какие данные читает | форма свойств в Studio |
| `form.json` | интерфейс: группы, поля, таблицы, графики, кнопки — компонентами Flux | визуальный редактор **и** текстовый редактор — оба правят этот же JSON |
| `logic/*.ts` (или `.py`, `.wasm`) | обработчики и расчёт | редактор кода в Studio (Monaco) |
| `examples/*.json` | контрольные примеры | таблица примеров в Studio |

**Привязки** — строки-пути внутри `form.json`, а не код:
- `flux.equipment.params.airflow`, `flux.tag.identifier` — данные Flux по
  договору, только чтение; при событии «данные изменились» поле обновляется
  само;
- `calc.out.pressure` — выход расчёта; `state.<имя>` — своё состояние модуля
  (ввод пользователя в окне модуля, не пишется во Flux);
- события — имена обработчиков: `"onClick": "recalc"`,
  `"onDataChanged": "recalc"` → функция `recalc` в `logic/`.

**Код** получает один объект API: `flux.read(…)`, `flux.on('changed', …)`,
`state`, `calc`. Для него из схем договора генерируются типы (`.d.ts`) — в
редакторе Studio есть автодополнение, а при выпуске Studio проверяет каждую
привязку и вызов: неизвестный путь или поле не по договору — выпуск не уходит.

**Своя страница** (то, что формой не собрать: схема установки, график
характеристики) — компонент `custom` внутри `form.json` со своим HTML/TS в той
же изоляции и с тем же API.

Чего не делать: визуальный редактор **не генерирует код** (обратный разбор
сгенерированного кода ломается при первой ручной правке); модуль **не
получает React и компоненты Flux напрямую** — только набор компонентов
модулей, версионированный вместе с договором, чтобы обновление Flux не
ломало чужие модули.

### Логика на любом языке
Для оболочки расчёт — чёрный ящик: на вход JSON, на выход JSON по схеме
договора.

| Способ | Языки | Что выкладывается | Плюсы | Минусы |
|---|---|---|---|---|
| Исходник в Studio | TypeScript/JavaScript | текст кода | проще всего, отладка в Studio | только JS/TS |
| Python в песочнице (Pyodide) | Python, numpy/scipy | текст кода | инженеры часто считают на Python | первый запуск дольше; **Pyodide (~10–30 МБ) кладётся в portable**, а не берётся из интернета — CSP и офлайн |
| WebAssembly | C, C++, Rust, Go (TinyGo), C# (.NET, WASI-команда) | готовый `.wasm` | быстро, изолировано, одинаково на всех ПК | сборку настраивает разработчик |
| Отдельный процесс | любой: C#, Delphi, VB, старый exe | `.exe`/`.dll`, JSON через stdin/stdout | старый расчёт как есть | только Windows; **без песочницы** — exe из базы, запущенный на ПК, — это выполнение кода с правами пользователя; только после одобрения владельца и с подписью кода (Authenticode), иначе SmartScreen и антивирус блокируют |

По умолчанию — первые три. Отдельный процесс — исключение для старых
расчётов, каждый выпуск — с одобрением владельца.

### Контрольные примеры
- Набор «вход → ожидаемый выход с допуском» (например, ±0,5 % по давлению).
- Studio прогоняет их перед выпуском; не сошлось — выпуск не уходит.
- Те же примеры — при переносе логики на другой язык.
- Flux при первом запуске нового выпуска прогоняет короткий набор
  (несколько примеров) — ловит расхождения конкретного компьютера (редко,
  но бывает у exe и при разных версиях библиотек).

### Результат расчёта
- Модуль показывает результат в своём окне. Во Flux он не записывается:
  ни в карточку позиции, ни в теги, ни в спецификацию.
- Если нужно, результат отдаётся пользователю файлом, который тот сохраняет
  сам.
- Вместе с результатом видно, на каких данных он получен: версия модуля,
  версия договора, отпечаток входа (sha256 входного JSON).
- **Устаревание:** если вход изменился (отпечаток другой) или вышла новая
  версия модуля с другим результатом на тех же входах, модуль показывает
  предупреждение «пересчитать». Пересчёт — по кнопке, не молча.

### Flux Store и обращения по подпрограммам

Этап распространения реализован; устройство, политика каналов, Store и
обращения описаны на [странице программы](../methodology/03-programs/modules.md).
Решения владельца сохраняются: автообновление по умолчанию выключено;
выпуск сначала может попасть тестировщикам, затем всем по отдельному
подписанному решению владельца без замены выпуска; обращения по модулю —
единая история, а данные проектов не передаются разработчику. Человек
выбирает адресата и согласие на диагностические вложения; автоматический
счётчик сбоев обезличен. Похожие обращения не склеиваются автоматически;
«У меня тоже» учитывает затронутых. Известные проблемы могут содержать обход,
а выпущенное исправление предлагается автору через обновление. Оценки и отзывы
внутренние. Откат версии доступен без связи, а отзыв выпуска останавливает
его у установивших. Изменения разрешений при установке показываются человеку.

Остаётся на последующие этапы:
- постоянные данные модуля, копия перед обновлением, восстановление и выбор
  удаления данных при удалении подпрограммы;
- вкладка ошибок и графики сбоев по версиям в Studio, редактор и проверки
  перед отправкой, а также подключения к внешним программам;
- снимки окна модуля с редактированием, расширенный журнал и стеки с привязкой
  к исходникам, если они потребуются в полном диагностическом пакете Studio.

### Запрос на публикацию и проверка владельцем (решение владельца, 5 ноября 2026)

Всё, что разработчики выпускают, сначала приходит **владельцу Studio**: он
проверяет код и связь с Flux, при необходимости правит и только потом
выпускает в Store. Без этого ни один выпуск до пользователей не доходит.

**Разработчик: «Отправить на публикацию».**
1. В Studio оформляет выпуск: версия, «что нового», снимки, разрешения,
   требования, канал, который просит (тестовый или рабочий).
2. Studio прогоняет проверки (договор, привязки, контрольные примеры,
   методология). Не прошло — отправить нельзя.
3. Запрос уходит владельцу **со всем, что относится к подпрограмме**:
   - **весь исходный код** (не только собранное): TypeScript, Python,
     исходники C/C++/Rust/Go/C# для WebAssembly; для WebAssembly Studio
     собирает `.wasm` из исходников сама, чтобы владелец проверял ровно тот
     код, который будет работать (хеш сборки сверяется);
   - `manifest.json`, `form.json`, свои данные и справочники, контрольные
     примеры, снимки;
   - **разница с прошлой версией** по каждому файлу;
   - **разница в разрешениях и подключениях** («новое: читает ВДР,
     подключение к api.example по адресу …») — выделена отдельно;
   - отчёт проверок Studio, версия API и Flux, на которых собрано;
   - комментарий разработчика к владельцу.
4. Запрос подписан ключом разработчика — видно, кто и что прислал.
   Отправленный запрос не меняется: новая правка — новый запрос
   (или «Обновить запрос»), прежний сохраняется в истории.

**Владелец: раздел «Запросы на публикацию» в Studio.**
- Очередь со счётчиком и уведомлением: подпрограмма, разработчик, версия,
  что нового, флаги «расширены разрешения», «новая подпрограмма», «есть
  открытые ошибки „не могу продолжить“».
- Просмотр кода: дерево файлов, разница с прошлой версией построчно,
  поиск; отдельная вкладка «Связь с Flux» — какие данные читает, какие
  подключения открывает, какие события слушает, какие привязки в форме.
- **Проверить в работе:** запуск подпрограммы в Studio на тестовой базе и в
  тестовом Flux, контрольные примеры, снимки обеих тем.
- **Замечания к строкам кода** — как в обзоре кода; уходят разработчику.
- Решения:
  - **«Вернуть на доработку»** — с замечаниями; разработчик правит и
    отправляет новый запрос, обсуждение сохраняется;
  - **«Внести изменения сам»** — владелец правит код в редакторе Studio;
    правки видны разработчику отдельной разницей «изменения владельца» с
    комментарием, и следующая версия разработчика строится уже на них
    (Studio не даст потерять их при его следующей отправке);
  - **«Отклонить»** — с причиной;
  - **«Выпустить»** — выбор канала (тестовый / рабочий, постепенно), дата
    выпуска (сразу или в выбранное время); выпуск подписывает **владелец**
    и он уходит в Store.
- История по каждой подпрограмме: все запросы, решения, правки владельца,
  кто что выпустил.

**Цепочка доверия с проверкой владельца.** Flux запускает только выпуск,
подписанный ключом владельца (`electron/updateKey.ts` — корень). Подпись
разработчика стоит на запросе и показывает автора, но сама по себе выпуск не
запускает. Так даже разработчик с сертификатом не может выложить
непроверенный код.

**Помощники владельца (позже, по решению владельца).** Право
`module.review`: проверять запросы и возвращать на доработку; выпускать —
только владелец, пока он не решит иначе.

**Срочный отзыв** не ждёт очереди: владелец отзывает выпуск сразу (раздел
«Flux Store», «Отозвать выпуск»).

### Публикация
1. Разработчик в Studio: проверки, «Отправить на публикацию» (выше).
2. Владелец проверяет, при необходимости правит, подписывает и выпускает.
3. Выпуск уходит в базу (`uploading → ready`), затем в канал:
   - «тестовый» — видят назначенные люди;
   - «рабочий» — все.
4. Выпуск появляется в Flux Store; у кого подпрограмма установлена — во
   вкладке «Обновления», ставится по решению человека (см. «Flux Store»).
   Открытый модуль предлагает перезапуститься на новую версию; расчёт,
   идущий в этот момент, не прерывается.
5. Откат — перевести рабочий канал на прошлый выпуск (в отличие от
   обновлений exe, откат модуля разрешён — выпуски неизменяемы и
   подписаны).

### Если общая база недоступна
- Каждый Flux хранит у себя загруженные и проверенные выпуски модулей;
  модуль работает на последней версии.
- Новые выпуски не приходят до восстановления связи; потом догружаются.
- Разработчик работает в Studio на тестовой базе; выкладка ждёт связи.
- Модуль работает на кэше выпуска; данные Flux читаются по связи. Записи во
  Flux нет, поэтому в офлайн-режиме модуль только показывает результат.

### Flux Studio (portable разработчика)

**Одна на всех.** Studio не привязана к одной подпрограмме: разработчик видит модули,
на которые у него есть сертификат, и может завести новый (с одобрения
владельца — он выдаёт сертификат).

**Выходит вместе с Flux.** Studio собирается из того же репозитория в той
же сборке CI, что portable Flux, с тем же номером версии (Flux 1.21.0 —
Studio 1.21.0). Общий код: оболочка, мост, договор, компоненты интерфейса,
API. Поэтому то, что разработчик видит в Studio, ровно то, что увидит
пользователь во Flux этой версии.
- Выпуск модуля помечается версией Studio, в которой он собран, и
  минимальной версией Flux.
- Studio старее Flux в общей базе — предупреждение «обновите Studio»:
  договор мог измениться.

**Вход и ключи.** Тот же вход, что во Flux: та же общая база, лицензия и
профили; пускают профиль с правом `module.develop` (роль «Разработчик»,
решение 4 ноября, п. 5). Закрытый ключ
разработчика — в защищённом хранилище ОС (`safeStorage`), не в базе.

**Тестовая база.** SQLite с образцами проектов: проекты, теги с
иерархией, системы и установки, файлы в
Проводнике, спецификации, ВДР. Из Studio в рабочую базу пишется только
выпуск модуля.

**Проверка связок — набор тестов внутри Studio.** Тот же набор идёт в CI
Flux, поэтому изменение Flux, ломающее договор, видно до выпуска portable.
Studio прогоняет его для модуля перед каждым выпуском:

| Связка | Что проверяется |
|---|---|
| Проект | модуль открывается в проекте, без проекта — понятное сообщение; смена проекта — данные перечитаны |
| Оборудование | вход из карточки позиции; чтение параметров и состава; позиция не меняется |
| Теги | чтение тега позиции и иерархии; модуль не создаёт и не меняет теги |
| Файлы и Проводник | модуль читает только разрешённые файлы проекта; отчёт отдаётся пользователю файлом |
| Спецификации и выпуск | спецификация и выпуск документов читаются; результат расчёта в них не попадает |
| Права | под пользователем без прав чтение данных отклоняется |
| Офлайн | без общей базы модуль работает на кэше выпуска; данные Flux — по связи |
| Изоляция | нет доступа к cookie, хранилищу Flux, IPC, сети |
| Время и память | расчёт укладывается в пределы |
| Контрольные примеры | все сходятся в допуске |
| Интерфейс | проверки методологии (ниже) |

Не прошёл хоть один — выпуск не уходит. Отчёт прикладывается к выпуску и
виден владельцу.

**Панель разработчика.** Два пути, можно смешивать:
- *Инструменты:* палитра компонентов Flux (кнопки, поля, списки, таблицы,
  вкладки, группы, графики, схема установки), перетаскивание на форму,
  привязка к входу и выходу расчёта, свойства компонента (подпись,
  единицы, допустимые значения, обязательность), условия видимости,
  проверка ввода, предпросмотр в светлой и тёмной теме и в узком окне.
- *Код:* то же описание формы правится текстом (JSON), а произвольная
  страница — кодом (TypeScript/HTML) внутри изоляции. Редактор с
  подсветкой, подсказками по договору и компонентам, отладка расчёта на
  тестовой базе с точками останова и журналом сообщений моста.

**Методология дизайна внутри Studio.** Чтобы модули были неотличимы от
Flux:
- Компоненты — те же, что в словаре компонентов
  [01-design.md](../methodology/01-design.md) (раздел 5); меры, шрифт,
  цвет, поверхности — разделы 1–4; тексты интерфейса — раздел 6. Своего
  набора кнопок у модуля нет: палитра Studio — это и есть компоненты Flux.
- Методология встроена в Studio справкой: у каждого компонента — когда
  применять и пример.
- Проверочный список (раздел 8 `01-design.md`) — автоматическая проверка
  перед выпуском: цвета только из токенов, нет горизонтальной прокрутки,
  обе темы, подписи по правилам текста, размеры по мерам. Для страниц,
  написанных кодом, — те же проверки снимком.
- Меняется методология во Flux — меняется и в Studio со следующей версией;
  модули, собранные формой, перерисовываются сами.

**Публикация.** Каналы, история, откат, обращения пользователей по модулю.

## Первый модуль: E3Flux

Связка с E3.series сейчас встроена в portable Flux: каждая правка требует
нового выпуска Flux. Решение 4 ноября: E3Flux переводится в модуль Studio,
и его правки выходят как выпуски модуля, без выпуска Flux.

- **Чтение данных Flux.** E3Flux читает оборудование, параметры, теги,
  проекты через договор — только на чтение, как любой модуль. Данные в окне
  всегда актуальны: оболочка передаёт модулю события «данные изменились»
  (по существующим `entity:changed` и живым обновлениям), модуль перечитывает.
- **Доступ к E3 через подключение.** Модуль просит у Flux подключение к
  E3 (возможность «E3», выданная модулю владельцем); Flux открывает его через
  COM в главном процессе, и дальше модуль сам вызывает **любые** методы API
  E3 через это подключение (см. «Подключения к внешним программам»). Набор
  действий в portable не зашивается — новые вызовы E3 выходят выпуском
  модуля. Логика E3Flux (что и как выгружать, сопоставление) — в модуле.
- **Своё хранилище.** Связи «позиция ↔ блок в схеме E3» и план выгрузки
  хранятся в данных модуля, а не в оборудовании и тегах Flux — правило
  «данные Flux только на чтение» сохраняется. Существующие таблицы связей E3
  переносятся под модуль либо модулю дают писать только в них (вопрос
  владельцу 3).
- **Опора:** [e3-integration.md](../e3-integration.md) (раздел 4.3 —
  подтверждённые вызовы COM и подводные камни; раздел 13 — решения владельца
  и этапы A–G), [e3-link.md](e3-link.md), страница программы
  [e3flux.md](../methodology/03-programs/e3flux.md).

### Дальнейшие пределы исполнения
- Этап 3а: память WebAssembly и Pyodide ограничена максимумом `WebAssembly.Memory`,
  время — остановкой Worker, число расчётов — общей очередью. Жёсткой квоты ЦП и
  кучи у TypeScript-Worker по-прежнему нет (браузерный API её не даёт).

### 5. Flux Studio: сборка вместе с Flux, вход, публикация
- Вторая цель сборки в том же CI с тем же номером версии; общий код
  оболочки, моста и компонентов.
- Вход, ключ разработчика, тестовая база с образцами, публикация, история.

### 6. Studio: проверка связок
- Набор тестов связок (таблица выше) — в Studio и в CI Flux.
- Выпуск не уходит без прохождения; отчёт прикладывается к выпуску.

### 7. Studio: панель разработчика и методология
- Палитра компонентов Flux, визуальный редактор формы, свойства,
  предпросмотр в темах; редактор кода и отладка.
- Справка по методологии и автоматический проверочный список раздела 8.

### 8. Перенос существующей логики (по необходимости)
- Перенос расчёта, который уже есть в другом виде, и его справочных данных;
  контрольные примеры, допуски.
- Большие справочные данные — куски, как у выпусков.

### 9. Python и WebAssembly
- Внедрено в этапе 3а (см. «Внедрено»). numpy 2.2.5 включён в сборку (решение владельца 9 ноября). Дисковый кэш компиляции wasm невозможен — см. страницу программы.

### 10. Отдельный процесс (по необходимости)
- Только если есть расчёт, который нельзя перенести; подпись кода,
  одобрение владельца на каждый выпуск.

### 11. Перенос E3Flux в модуль
- Вынести связку из portable в модуль Studio: договор на чтение, мост к E3
  как возможность договора, событие «данные изменились».
- Связи и план выгрузки — в данных модуля; существующие таблицы связей — по
  решению владельца (вопрос 3).
- Готово: правка E3Flux выходит как выпуск модуля без выпуска Flux; сценарии
  из `e3-integration.md` проходят без регрессий.

## Что может пойти не так

| Риск | Как избежать |
|---|---|
| Выпуск подложен прямой записью SQL | цепочка доверия и проверка подписи на клиенте |
| Модуль читает данные Flux мимо договора | другой источник, `sandbox`, CSP |
| Модуль портит данные Flux | записи из модуля нет; данные Flux — только на чтение через договор |
| Новый выпуск молча меняет прошлые расчёты | результат показывается с версией модуля и отпечатком входа; «пересчитать» по кнопке |
| Модуль новее Flux (нужна новая версия договора) | проверка версии договора, понятное сообщение |
| Разработчик ушёл из компании | отзыв сертификата; модуль остаётся работать на последнем выпуске, новый разработчик получает сертификат |
| Зависший или тяжёлый расчёт вешает Flux | Web Worker, предел времени и памяти |
| Pyodide или библиотеки из интернета | всё в portable, сеть модулю закрыта |
| exe-модуль — выполнение кода на ПК | только с подписью кода и одобрением владельца |
| Разные результаты на разных ПК | контрольные примеры при первом запуске выпуска |
| Обновление пришло посреди расчёта | расчёт завершается на старой версии, предложение перезапуска |
| Новая версия Flux ломает модуль | проверка связок в CI Flux до выпуска portable; модуль помечен минимальной версией Flux |
| Studio старее Flux | одна версия у обоих, предупреждение «обновите Studio» |
| Модуль выглядит не как Flux | палитра — только компоненты Flux, автоматический проверочный список |

## Порядок относительно других планов

- Номер установки для кампаний выпусков сейчас берётся из лицензии
  (`licenseInstallationId`). Модулям он нужен — на этапе 3 вынести его в
  свой модуль, ничего больше в лицензии не трогая (см. возможное развитие
  [license-removal.md](license-removal.md)).
- Поле «платформа» у выпусков продумать сразу (WebAssembly, Python и TS —
  одни на все ОС; exe — только Windows), см. возможное развитие
  [linux.md](linux.md).

## Внедрено

**PR 1 — этапы 1–2:** договор v1 на чтение, общая оболочка с входами по манифесту, изоляция `flux-module://` и мост с проверкой сообщений, Worker с пределом времени и встроенный пример. Загрузки выпусков из базы пока нет. Устройство и границы проверок — [Модули Flux](../methodology/03-programs/modules.md).

**Этап 2 (PR #139):** выпуски и проверка владельцем, права и роль «Разработчик»,
каналы, Flux Store, обращения по подпрограммам; описание — на
[странице программы](../methodology/03-programs/modules.md). Влит в `main`;
следующий этап — 3 (все языки и подключения), остальные остаются в плане.

**Этап 3а (языки и пределы исполнения):** Python (Pyodide в portable, общая среда),
WebAssembly для C, C++, Rust, Go (TinyGo) и C# (WASI-команда), единый вызов «JSON →
JSON», поля `language`/`sourceLanguage`/`platform` в манифесте и подписи выпуска,
контрольные примеры при первом запуске на компьютере, общая очередь расчётов,
пределы времени и памяти. Подключения к внешним программам — часть 3б. Устройство
и числа — [страница программы](../methodology/03-programs/modules.md).

**Этап 3б (подключения к внешним программам, журнал подпрограмм):** раздел `connections`
в `manifest.json` (COM по имени объекта, HTTP и WebSocket по адресу, порту и префиксу пути; `app`,
`does`, `access` — тексты для человека), в подписанном выпуске и в разнице запроса владельца
(«новое: подключение к …»); окно запроса у человека, решения в главном процессе; сквозной канал
(`electron/moduleConnections.ts`): адрес берётся из объявления, проверяется после разрешения имени,
редиректы не выполняются, cookie Flux не передаются, пределы частоты, одновременных вызовов,
открытых подключений, размера и времени; COM — общий способ на помощнике PowerShell
(`electron/moduleCom.ts`; запуск программ и сеть в обход адресов через COM закрыты списком).
Журнал подпрограмм (кольцо на компьютере, таблица `ModuleJournal` на трёх СУБД, просмотр
владельцем, администратором и разработчиком без людей); примеры `connections-http` и
`connections-com`. Устройство и границы — [страница программы](../methodology/03-programs/modules.md).
