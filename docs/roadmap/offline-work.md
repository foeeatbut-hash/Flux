# Работа при недоступном сервере

Статус: в работе ([plan.md](../plan.md), раздел 7) · обновлено 5 ноября 2026

Если вся работа идёт только через общую базу и она недоступна, встают все.
Цель: у каждого на компьютере облегчённая копия данных его проектов; при
сбое люди продолжают работать, изменения копятся локально и сверяются после
восстановления связи. Конфликтные изменения не вносятся, пока люди их не
разрешат. Выпуск ревизий и отправка документов без сервера запрещены.

## Решения владельца (29 октября 2026)

- Делать: всё должно работать и без сервера с общей базой. Есть связь —
  работа онлайн, локальная копия обновляется; нет связи — работа на
  последней локальной копии.
- Копируются только проекты, с которыми человек работает.
- На время отказа правки сохраняются локально как черновики во всех
  программах; после восстановления сливаются, конфликты разбирают люди, и
  до решения конфликтные правки в общую базу не попадают.

Ответы на открытые вопросы (владелец, 29 октября 2026):

- **Срок офлайна — без предела.** Техническая граница не нужна. Чем дольше
  копия не обновлялась, тем больше правок коллег накопится и тем больше
  будет конфликтов; поэтому плашка показывает возраст копии («данные на
  …, 3 дня назад»). Права проверяются заново при сверке: уволенный или
  лишённый прав сотрудник свои офлайн-правки не внесёт.
- **Шифрование** — на усмотрение разработки. Первая версия: копия в профиле
  пользователя, защита — средствами ОС (BitLocker); шифрование файла базы —
  если потребует IT.
- **Спор решают сами сотрудники**, внёсшие правки: экран конфликта и
  переписка в мессенджере. Руководитель проекта в разбор не встраивается.
- **Импорт офлайн разрешён как обычно.** Позиции одного файла помечаются
  одной группой: при сверке видно, что они пришли из одного бланка;
  непересекающиеся применяются, конфликтные идут на разбор.
- **Аварийного выпуска нет.** Без сервера можно выгрузить черновик документа
  с пометкой «ЧЕРНОВИК» без номера ревизии; официальный выпуск — после
  восстановления связи.
- **Кэш — максимальный.** В копию входят данные и все файлы проектов в
  работе (бланки, расчёты, выпущенные документы, вложения). Руководства
  каталога — по открытию. Предел один: на диске остаётся не меньше 10 %
  свободного места. Объём копии виден в настройках.

## Решения владельца (5 ноября 2026)

- **Копия обновляется постоянно, пока связь есть**, а не в момент обрыва:
  обрыв всегда застаёт свежую копию.
- **Вход без связи — со второго раза.** Если человек хоть раз вошёл на этом
  компьютере при связи, дальше он входит и без связи (2.6). Первый вход —
  только при связи.
- **Лицензия и права хранятся автономно.** Подписанные ключи лицензий и
  список отзыва (сейчас в `AppSetting`, `server/licenseService.ts`)
  копируются в локальную копию; проверка лицензии — по подписи и доверенному
  времени, без общей базы. Права и роль человека — из копии (2.2). Отзыв
  лицензии, снятие прав или блокировка, сделанные во время обрыва, вступают
  в силу при возвращении связи — и тогда же его офлайн-правки проходят сверку
  прав (4.3).
- **Всё это касается и Flux Studio** ([modules.md](modules.md)): вход
  разработчика без связи — так же со второго раза; модули работают на кэше
  проверенных выпусков; данные Flux модуль читает из локальной копии; выкладка
  нового выпуска ждёт связи и при возвращении сверяется (раздел «Каталог
  расхождений», группа «Studio и модули»).
- **Обработчик на сервере сверяет всё и сам решает, что можно решить.**
  Непересекающиеся правки применяются автоматически; спорные — на разбор
  людям (раздел 5). Каталог ниже — полный список случаев, который обработчик
  обязан различать; новый найденный случай дописывается сюда.

## Что есть в программе (разведка кода, 29 октября 2026)

### Устройство
- Каждый настольный Flux поднимает свой API на loopback и ходит напрямую в
  общую MariaDB/PostgreSQL (`server/databaseClient.ts`,
  [company-server.md](../company-server.md)). «Сервер упал» = «общая база
  недоступна».
- Тот же API работает с локальной SQLite (режим `LOCAL`). Схем три, ведутся
  вручную (`prisma/schema.prisma`, `.mariadb.`, `.postgresql.`); при старте
  схема докатывается структурно (`server/schema-sync.ts`,
  `server/localSchema.ts`), **номера версии схемы нет**.
- **Автопереключения на SQLite сейчас нет намеренно** —
  `server/databaseClient.ts:12`: ошибка общей базы не должна создавать
  независимую локальную базу под видом базы компании. Офлайн-копия должна
  уважать это: она всегда помечена как копия конкретной общей базы и никогда
  не становится «базой компании».
- При провале старта `prisma = null` и все `/api` отвечают 503
  (`server.ts:449–458, 513–521, 715`). Переподключения посреди работы нет:
  запросы просто падают, текст ошибки — `server/dbError.ts:64–66`.

### Связь и опрос
- `src/lib/dbStatus.ts`: опрос 15 с при норме, 4 с при сбое; состояния
  `checking | ok | slow | db-down | offline`; `offline` — со второго промаха.
- `/api/health` (`server/routes/system.ts:57–70`) спрашивает **свой
  встроенный сервер**, тот делает `user.count()`; `db-down` — это и есть
  «нет общей базы», `offline` — «не отвечает сам встроенный сервер».

### Запись в базу
- **309 маршрутов записи.** Сверка версии клиента есть только у части:
  теги (`PUT /api/tags/:id` через `server/tagWrite.ts`), атрибуты и решения
  E3 (`expectedVersion`), источники и привязки оборудования, документы
  Office (`sourceSha`, `baseHash`), каталог, Конструктор (409 «позицию уже
  изменил другой сотрудник», `builder.ts:269`), справочники.
- **Без сверки:** ВДР (14 маршрутов, ни одной транзакции), проекты,
  правка оборудования, Проводник, чат, данные проекта, заметки, календарь,
  архивы и другие.
- `equipmentCore.ts` сверяет `version` внутри одного запроса — от гонок
  внутри запроса, а не от устаревших данных у клиента.
- Идемпотентность (повтор без двойного эффекта) есть только у обращений
  (`clientRequestId`, `FeedbackMutationReceipt`) и импорта
  (`ImportJob.idemKey`).

### Номера
- ID сущностей — `server/entityIds.ts`: `PRJ-000001`,
  `<проект>-TAG|EQ|SYS|MB|DICT-000001`; счётчик в `AppSetting`, выдача в
  транзакции `Serializable` с повторами; номер расходуется навсегда.
- Ревизия ВДР — `nextRevision` (`vdr.ts:126`), читается без блокировки;
  `revision-up` (:367–387) пишет без транзакции; `issue-revision`
  (:628–675) — два отдельных вызова без транзакции; `PUT` реестра (:349)
  целиком заменяет `revisions` и `columnsConfig`.
- Ревизия документа Office — `max+1` вне транзакции
  (`officeRevisions.ts:39–41`), **уникального ограничения нет** — только
  индекс (`schema.prisma:1192`). Два одновременных выпуска могут получить
  один номер.
- У `Tag.identifier` **уникального ограничения нет** — уникальность кода
  проверяется в коде (`tags.ts:156–168`, `/tag-check`). База дубль не
  отсечёт.

### Файлы
- Файлы проекта (бланки, расчёты, документы) — в базе: `FileNode`, куски в
  `FileChunk`, старые — base64 в `FileNode.content`. Версии для отката —
  `FileVersion.data` (20 последних), ревизии Office —
  `OfficeDocumentRevision.data`. Вложения каталога — куски в `AppSetting`.
  Вложения почты — на диске клиента.

### Между пользователями
- `broadcast()` (`server/context.ts:58`) шлёт событие только окнам **того
  же компьютера**. `vdr:changed`, `entity:changed` коллегам не доходят:
  они видят изменения только при перечитывании.
- Через общую базу ходят: шина совместной правки Office
  (`server/officeBus.ts`, опрос 700 мс), присутствие (`server/presence.ts`),
  очередь уведомлений (`server/feedback/outbox.ts`), чат (сокет + опрос
  12 с), уведомления (опрос 60 с).
- **Журнала изменений с порядковым номером нет.** `SystemChangeLog` —
  текст «кто что изменил», без машинного описания.

### Побочные эффекты записи
- История тегов пишется **после** `writeTag`, не в его транзакции
  (`tags.ts:437–441`), при сбое только логируется.
- `bumpElementsOfTags` (`server/equipmentVersion.ts:26`) поднимает версию
  оборудования при смене кода тега.
- Журналы: `ActionLog`, `SystemChangeLog`, `EquipmentHistory`.
- Каскадные удаления: проект → теги, системы, папки, справочники, чаты,
  документы Конструктора; система → моноблоки → позиции → история; папка →
  файлы → куски; реестр ВДР → строки.

### Вход и сессии
- Пароль — scrypt в `User.password` (`server/routes/auth.ts:41–75`).
  Токен сессии — HMAC с секретом машины (`server.ts:527–540`), 8 часов.
- `validate()` (`server/authSessions.ts:106–120`) **на каждый запрос**
  читает из базы `User`, `Role.permissions` и отзыв сессии, без кэша.

### Черновики
- Общего механизма локальных черновиков нет. Есть серверные: ревизии
  Office `DRAFT`, строки ВДР `DRAFT`, черновики каталога, черновик импорта
  оборудования, `MailDraft`; локальные — только черновики обращений
  (IndexedDB, `src/feedback/draftDb.ts`).
- Мессенджер хранит в сообщении только `linkedElementId` (позиция
  оборудования) и `linkedProjectId` (`schema.prisma:565`); ссылок на другие
  объекты нет.

## Главные решения устройства

1. **Две разные задачи — два разных механизма.**
   - *Вниз* (сервер → копия): копирование **строк** по журналу изменений.
   - *Вверх* (копия → сервер): повтор **действий пользователя** через те же
     маршруты API, а не заливка строк. Тогда сервер сам пересчитывает
     производное (история тегов, версии оборудования, журналы), проверяет
     права и правила. Заливка строк обошла бы всё это и испортила бы
     производные данные.
2. **Версия записи — целое число, а не `updatedAt`.** MariaDB по умолчанию
   хранит время с точностью до секунды или миллисекунды, SQLite — строкой,
   PostgreSQL — до микросекунды. Сравнение `updatedAt` между копией и
   сервером даст ложные конфликты или пропустит настоящие. Нужна колонка
   `version Int` у каждой синхронизируемой модели, `+1` при каждой записи (у
   `ComponentElement` она уже есть).
3. **Копия — не база компании.** Файл копии хранит, чьей общей базы он
   копия (идентификатор базы); подключиться к нему как к самостоятельной
   базе нельзя; при смене общей базы копия удаляется.
4. **Время — серверное.** Часы на компьютерах расходятся. Время применения
   ставит сервер; время на компьютере — только для показа «внесено офлайн
   в 14:32».

## Этапы

Порядок выбран так, чтобы каждый этап приносил пользу сам по себе и не
ломал работу онлайн.

### 0. Целостность записи — нужна и без офлайна

Без этого этапа сверка после подключения невозможна, а часть ошибок
случается уже сейчас при одновременной работе.

0.1. **ВДР — сделано 4.11.2026** (`server/vdrWrite.ts`, `scripts/test-vdr-concurrency.ts`). `revision-up`, `issue-revision`, `PUT` реестра — в
транзакции, с ожидаемой ревизией от клиента; чужая — 409 «ревизию B
выпустил Иванов в 14:32»; `PUT` сливает поля, а не заменяет `revisions` и
`columnsConfig` целиком (по образцу `server/tagWrite.ts`).

0.2. **Ревизии Office.** Номер — в той же транзакции, что запись;
уникальное ограничение `[documentId, revision]`. **Перед добавлением —
найти существующие дубли** (план и предпросмотр, `flux-data-safety`):
ограничение на базе с дублями не создастся, старт упадёт.

0.3. **Код тега — уникальность в базе.** Колонка нормализованного кода
(регистр, пробелы — по правилам `resolveTag`) и уникальное ограничение
`[projectId, код]`. Тоже сначала поиск и разбор существующих дублей.
**Ловушка:** MariaDB сравнивает строки без учёта регистра (зависит от
collation), SQLite — с учётом. Нормализованная колонка снимает разницу.

0.4. **Целая версия у синхронизируемых моделей:** Project, Tag,
EquipmentSystem, Monoblock, ComponentElement (есть), DocRegister,
DocRegisterItem, ConstructorDoc, FileNode, Dictionary, DictionaryItem,
TagTemplate. Колонка добавляется во все три схемы; заполнение — 1.

0.5. **Сверка версии в маршрутах этих моделей.** Клиент присылает версию,
которую видел; чужая — 409 с текущим состоянием, кто и когда. Начать с
самых ценных данных: ВДР, Конструктор, оборудование, теги (остальные
маршруты тегов), проекты, Проводник. Справочник маршрутов — отчёт
разведки выше.

0.6. **Ключ идемпотентности** (`X-Flux-Op-Id`) у этих же маршрутов: повтор
с тем же ключом возвращает прежний ответ, а не делает второй раз (образец —
`FeedbackMutationReceipt`).

0.7. **История тегов — в одной транзакции с записью.** Сейчас при сбое
запись проходит, а история теряется.

Готово: два одновременных выпуска — одна ревизия и понятный отказ; правка
по устаревшим данным — 409, а не перезапись; повтор запроса не дублирует.
Проверки на гонку для каждого пункта.

### 1. Журнал изменений на сервере

1.1. Таблица `ChangeFeed`: порядковый номер, проект, модель, ID, версия,
вид (создание/изменение/удаление), кто, когда (сервер).

1.2. Запись в журнал — в **той же транзакции**, что изменение. Способ —
расширение клиента Prisma (`$extends`), перехватывающее create/update/
upsert/delete по синхронизируемым моделям.
**Ловушки:**
- `updateMany`/`deleteMany` (например, `bumpElementsOfTags`) не возвращают
  ID — для них расширение сначала выбирает ID, потом пишет журнал;
- сырой SQL (`$executeRaw`, таблицы `ensureTables`, `localSchema.ts`) мимо
  расширения проходит — найти все такие записи и либо перевести на Prisma,
  либо писать журнал вручную; проверка «каждая запись в синхронизируемую
  таблицу оставляет след в журнале»;
- каскадное удаление делает база — расширение его не видит. Журнал
  удаления родителя должен содержать удалённых детей (выбрать до удаления).

1.3. **Ловушка порядка.** Номер выдаётся при вставке, а видна строка после
фиксации транзакции. Транзакция с номером 101 может зафиксироваться позже
транзакции с номером 102. Читатель, запомнивший «дошёл до 102», навсегда
пропустит 101. Решение: читатель перечитывает «хвост» — всё, что новее
отметки минус окно (например, 30 секунд или 500 номеров), и отбрасывает
уже применённое по паре «модель, ID, версия».

1.4. **Первый потребитель — живые обновления у коллег.** Встроенный
сервер каждого Flux опрашивает журнал (как `officeBus.ts`, раз в 1–2 с) и
рассылает своим окнам `entity:changed`. Коллеги начинают видеть изменения
сразу, а не при перечитывании. Это польза уже до офлайна.

1.5. Очистка журнала: строки старше N дней удаляются; копия, отставшая
сильнее, перекачивает проект целиком.

Готово: правка у одного — через 1–2 с видна у другого; ни одна запись не
теряется при параллельных транзакциях (проверка на гонку).

### 2. Локальная копия только для чтения

Первый офлайн, который уже полезен: при сбое можно смотреть, искать и
выгружать.

2.1. Файл копии — SQLite той же схемы в профиле пользователя, с отметкой
«копия базы <идентификатор>, программа <версия>, схема <отпечаток>».

2.2. Состав: проекты, где человек участник и которые «в работе»; их теги,
оборудование, системы, спецификации, ВДР, справочники, файлы (`FileNode`,
`FileChunk`, `FileVersion`, `OfficeDocumentRevision`); каталог (без
руководств — по открытию); пользователи (имена для показа) и **его**
учётная запись с ролью и правами.

2.3. Первое наполнение — снимок проекта целиком, по частям, с
возобновлением после обрыва. Дальше — по журналу (этап 1) фоном.

2.4. Предел места: на диске остаётся ≥ 10 % свободного. Не хватает — сначала
не скачиваются файлы старых ревизий, потом — вложения; данные (теги,
оборудование) — всегда. В настройках — объём и состав копии.

2.5. Переключение: состояние `db-down` держится 3 опроса подряд →
встроенный сервер переключает чтение на копию; плашка «Нет связи с
сервером. Данные на 14:32 (3 дня назад). Только просмотр». Все записи —
отказ с понятным текстом. Связь вернулась → обратно на общую базу,
догрузка журнала.

2.6. **Вход офлайн.** `validate()` читает `User`/`Role` из копии. Если
человек не входил на этом компьютере онлайн (нет его записи в копии) —
офлайн-вход невозможен, сказать прямо.
**Ловушка безопасности:** в копии лежит хеш пароля. Хранить только хеш
этого пользователя, а не всех; копия — в профиле пользователя Windows.
Отзыв сессии и смена пароля, сделанные коллегой, офлайн не видны — при
возвращении связи сессия проверяется заново.

2.7. **Ловушка схемы.** Коллеги обновили Flux, схема общей базы новее, чем
у этого клиента. Копия создаётся по схеме *этого* клиента; неизвестные
колонки не копируются. При возвращении связи — сверка отпечатка схемы;
если программа старее базы, онлайн работает как сейчас (докатка
добавляет, но не удаляет), а копия пересоздаётся после обновления.

Готово: при отключённой базе видно всё по своим проектам, работают поиск,
выгрузки Excel и черновики PDF; при возвращении — работа онлайн без
перезапуска.

### 3. Офлайн-правки: журнал действий

3.1. Каждое действие записи, сделанное офлайн, сохраняется как запрос к API:
маршрут, тело, ключ идемпотентности, версии записей, на которых работал
человек, время на компьютере, группа (например, «импорт файла
blank.xlsx»).

3.2. Тот же запрос применяется к локальной копии, чтобы человек видел свою
правку. Локальная версия помечается «не отправлено».

3.3. **Новые записи** получают временный ID (`ВР-<компьютер>-<n>`).
Следующие действия, ссылающиеся на них (привязать тег к новой позиции),
хранят временный ID. При отправке сервер выдаёт настоящий ID, клиент ведёт
таблицу «временный → настоящий» и подставляет его в следующие запросы.
**Ловушка:** временный ID мог попасть в текст (название, комментарий,
имя файла выгрузки) — показать предупреждение, текст не менять.

3.4. Удаление офлайн — тоже действие в журнале.
**Ловушка каскада:** офлайн удалена система, а коллега онлайн добавил в
неё моноблок. Повтор удаления на сервере каскадом снесёт чужую работу.
Правило: удаление проходит, только если удаляемое и **все его потомки** не
менялись и не появлялись после версии, которую видел человек; иначе —
конфликт.

3.5. Что офлайн запрещено (кнопки неактивны с пояснением): выпуск ревизий
документов и ВДР, номера документов, отправка документов и писем,
создание и удаление проектов, участники и права, пользователи, панель
разработчика каталога, совместная правка Office (шина в общей базе),
выгрузка в E3 (связи `E3Binding` должны совпадать у всех).
Разрешено: теги, оборудование, импорт, спецификации (позиции), черновики
документов, ВДР (строки, без выпуска), справочники проекта, файлы
Проводника, заметки, сообщения чата (уйдут после подключения).

3.6. **Документы Office офлайн.** Правка — над локальной копией файла.
Слить два docx/xlsx автоматически нельзя. Если файл менял и коллега —
конфликт на уровне файла: «оставить мой», «оставить коллеги», «сохранить
оба» (мой — новой версией с пометкой «копия <имя>»).

3.7. Журнал переживает перезапуск и выключение компьютера (пишется на
диск сразу, в той же транзакции локальной копии).

### 4. Отправка после подключения

4.1. Сначала копия догружает журнал сервера (этап 1).

4.2. **Предварительная сверка у себя** по свежей копии: каждое действие
классифицируется — применится / сольётся / конфликт / отказ по правам.
Человек видит итог «94 применятся, 4 сольются, 2 конфликта» и нажимает
«Отправить». Автоматически ничего не уходит.

4.3. Отправка — по одному действию по порядку, с ключом идемпотентности.
Сервер сверяет версию и права **на момент применения** (а не по
предварительной сверке — за секунду всё могло измениться).

4.4. Разбор ответа:

| Ответ сервера | Что делает клиент |
|---|---|
| успех | отмечает отправленным, подставляет настоящие ID |
| 409, меняли другие поля | сливает по правилам (как `tagWrite.ts`) и повторяет |
| 409, то же поле / удалено / дубль кода | конфликт (этап 5), зависимые действия ждут |
| 403 | отказ по правам, видно человеку |
| нет связи | пауза, продолжение с того же места |

4.5. **Зависимости.** Действие, ссылающееся на запись из конфликтного
действия (привязка к тегу, который ушёл в конфликт), ждёт его разрешения.
Независимые идут дальше.

4.6. Группы (импорт одного файла): непересекающиеся позиции применяются,
конфликтные — на разбор; в истории видно, что всё из одного файла.

4.7. После отправки — копия обновляется по журналу, локальные пометки «не
отправлено» исчезают.

Готово: 1000 действий с обрывом посередине — ничего не потеряно и не
применено дважды; зависимое не уходит раньше того, от чего зависит.

### 5. Конфликты

5.1. Конфликт хранится **на сервере** (таблица конфликтов): чьё действие,
против какой правки, поле, три значения (исходное, моё, коллеги), кто и
когда. Так его видят оба, даже если первый закрыл программу.

5.2. На сервере остаётся прежнее значение; правка из конфликта не внесена.
Остальные видят у поля значок «есть неразрешённый конфликт».

5.3. Уведомление обоим (через очередь уведомлений, `outbox.ts`) с кнопкой
«Перейти к конфликту».

5.4. Экран: три значения, кто и когда; действия «Принять вариант
коллеги» (моё действие отменяется), «Оставить мой» (коллеге —
подтверждение), «Объединить» (текстовые поля — правка вручную), «Написать
коллеге». Решают сами сотрудники.

5.5. **Ловушка «пинг-понг»:** оба нажали «Оставить мой». Правило: «Оставить
мой» не применяет значение, а отправляет предложение; применяется, когда
второй принял, или когда второй сам выбрал «Принять вариант коллеги».

5.6. **Ловушка «третий»:** пока двое спорят, третий меняет то же поле
онлайн. Конфликт обновляется: показываются уже три варианта, решение
принимается заново.

5.7. Раздел «Конфликты» со счётчиком на панели задач; конфликт без
движения — напоминание раз в день.

### 6. Мессенджер

6.1. Ссылка на объект в сообщении: сейчас есть только `linkedElementId` и
`linkedProjectId`. Нужен общий вид ссылки (`тип + ID`: тег, позиция,
документ, строка ВДР, конфликт) в схеме сообщения и открытие по клику.

6.2. «Написать коллеге» из экрана конфликта: чат с этим человеком,
готовый текст и ссылка на конфликт.

6.3. Офлайн сообщения копятся и уходят после подключения тем же журналом
действий.

### 7. Документы и выпуск

7.1. Выпуск ревизий — только онлайн, номер — сервер, по очереди
(этап 0.1–0.2).

7.2. Офлайн — выгрузка черновика с пометкой «ЧЕРНОВИК» без номера.

7.3. Перед выпуском после офлайна: если входящие в документ позиции
изменились за время офлайна — предупреждение с разницей.

7.4. Пока один готовит выпуск, другим видна пометка «Иванов готовит
ревизию B» (через присутствие, `presence.ts`) — не блокировка, снимается
по времени.

### 8. История и откат

8.1. Каждая отправка офлайн-правок — группа в истории: «офлайн-правки
Петрова, 14:32–16:10, 98 действий, отправлено в 16:12».

8.2. Откат группы — существующим механизмом отката массовых операций;
откат сам проходит сверку версий (если после отправки запись меняли — откат
этой записи становится конфликтом, а не перезаписью).

### 9. Проверки

Каждая — автоматическая, на двух клиентах и общей базе (MariaDB и
PostgreSQL), Windows CI обязательно:
- одно поле с двух сторон; разные поля одной записи;
- удаление против правки; удаление родителя при новом потомке;
- дубль кода тега офлайн у двоих;
- временные ID и цепочка зависимых действий;
- обрыв посреди отправки, повтор, двойная отправка;
- 1000 действий; офлайн 7+ дней с очисткой журнала;
- права отозваны за время офлайна; пользователь отключён;
- коллега обновил Flux (схема новее);
- одновременный выпуск ревизии ВДР и Office;
- документ Office правили оба;
- диск почти заполнен;
- выключение компьютера посреди записи в журнал.

### 10. Внедрение

10.1. Выпуск с этапами 0–1 (польза: целостность и живые обновления).

10.2. Выпуск с этапом 2 (просмотр офлайн) — на всех.

10.3. Этапы 3–8 под настройкой «Работа без сервера», пилот на одном
проекте, замер: сколько действий, конфликтов, время разбора.

10.4. Включение для всех.

Параллельно — резервирование самой общей базы (реплика MariaDB/
PostgreSQL), чтобы офлайн требовался реже.

## Что может пойти не так — сводка

| Риск | Где решается |
|---|---|
| Ложные или пропущенные конфликты из-за точности `updatedAt` | целая версия, 0.4 |
| Дубль номера ревизии | транзакция и уникальное ограничение, 0.1–0.2 |
| Дубль кода тега у двоих офлайн | уникальность в базе, 0.3; конфликт «дубль», 4.4 |
| Ограничение не создаётся из-за старых дублей | поиск и разбор дублей до ограничения, 0.2–0.3 |
| Пропуск изменения при параллельных транзакциях | перечитывание хвоста журнала, 1.3 |
| Запись мимо журнала (сырой SQL, updateMany, каскад) | 1.2 и проверка «каждая запись оставляет след» |
| Повтор действия применился дважды | ключ идемпотентности, 0.6 |
| Каскад удаления сносит чужую работу | правило удаления с потомками, 3.4 |
| Производные данные расходятся (история, версии) | вверх — действия, а не строки, решение 1 |
| Копию приняли за базу компании | отметка базы, решение 3 |
| Хеш пароля на ноутбуке | только свой, в профиле, 2.6 |
| Схема копии и сервера разошлись | отпечаток схемы, 2.7 |
| Два docx не сливаются | конфликт на уровне файла, 3.6 |
| «Пинг-понг» при разборе | «Оставить мой» — предложение, 5.5 |
| Временный ID в тексте | предупреждение, 3.3 |
| Часы компьютеров расходятся | серверное время, решение 4 |
