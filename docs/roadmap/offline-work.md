# Работа при недоступном сервере

Статус: в работе ([plan.md](../plan.md), раздел 7) · обновлено 29 октября 2026

Если вся работа идёт только через общую базу и она недоступна, встают все.
Цель: у каждого на компьютере облегчённая копия данных его проектов; при
сбое люди продолжают работать, изменения копятся локально и сверяются после
восстановления связи. Конфликтные изменения не вносятся, пока люди их не
разрешат. Выпуск ревизий и отправка документов без сервера запрещены.

## Решения владельца (29 октября 2026)

- Делать: всё должно работать и без сервера с общей базой. Есть связь —
  работа онлайн, локальная копия обновляется; нет связи — работа на
  последней локальной копии.
- Копируются только проекты, с которыми человек работает.
- На время отказа правки сохраняются локально как черновики во всех
  программах; после восстановления сливаются, конфликты разбирают люди, и
  до решения конфликтные правки в общую базу не попадают.

Предварительные ответы на открытые вопросы (владелец может поменять):
офлайн до 7 дней, дольше — сначала обновить копию; шифрование — пока
BitLocker, шифрование файла базы позже; спор решает руководитель проекта;
импорт офлайн — одним пакетом; аварийного выпуска в первой версии нет; кэш
вложений — 2 ГБ.

## Что уже есть в программе

- Каждый настольный Flux поднимает свой API на loopback и подключается
  напрямую к общей MariaDB/PostgreSQL (`server/databaseClient.ts`,
  [company-server.md](../company-server.md)). «Сервер упал» на деле значит
  «общая база недоступна».
- Тот же API работает с локальной SQLite той же схемы (режим `LOCAL`), так
  что локальная копия может быть обычной базой Flux.
- Опрос связи с базой — `src/store/dbStatusStore.ts`.
- Сверка версии и слияние полей при записи тега — `server/tagWrite.ts`;
  `expectedVersion` и ответ 409 — `server/routes/e3Attributes.ts`.
- Номера записей выдаются по порядку — `server/entityIds.ts`.
- Предпросмотр, план с классами конфликтов и откат массовых операций —
  skill `flux-data-safety`, `src/capture/plan.ts`.
- Выпущенный документ не перезаписывается — `server/officeRevisions.ts`.
- Внутренний мессенджер.

## Этапы

### 0. Сверка версий во всех путях записи (нужна и без офлайна)
Сверка после подключения — тот же механизм «записать, если запись всё ещё
та, что я видел». Пройти все маршруты записи (ВДР, выпуск документов,
спецификации, оборудование, проекты), отметить, где сверки нет, и добавить
по образцу тегов. Ответ о конфликте называет, кто и когда изменил.

Известный дефект: `server/routes/vdr.ts` — `revision-up` читает и пишет без
транзакции и сверки (два почти одновременных выпуска дают один номер,
запись истории теряется), `PUT /api/vdr/registers/:id` целиком заменяет
`revisions` и `columnsConfig`.

Готово: два одновременных выпуска дают одну ревизию и один понятный отказ;
одновременная правка одного поля — конфликт, а не тихая перезапись.

### 1. Локальная копия
- Хранится: проекты, где человек участник и которые «в работе»; теги,
  оборудование, спецификации, ВДР, справочник, нужная часть каталога.
- Не хранится: PDF, руководства, вложения — подгружаются при открытии, кэш с
  пределом (1–2 ГБ), старое вытесняется. Пользователи и права — только то,
  что нужно для работы.
- Обновление: первый раз — снимок проекта, дальше только изменения. На
  сервере нужен журнал изменений с порядковым номером: по `updatedAt` не
  видно удалений. Клиент помнит, до какого номера дошёл. Фоном — раз в
  минуту или по сигналу об изменении.
- Решить: шифрование копии (BitLocker или шифрованный файл базы); срок
  жизни копии — после N дней без связи сначала обновить.

### 2. Переход в офлайн и обратно
- Порог (например, 3 неудачные проверки подряд), чтобы не прыгать при
  коротком сбое.
- Встроенный API переключается на локальную копию. Постоянная плашка: «Нет
  связи с сервером. Данные на 14:32. Изменения сохраняются у вас».
- Офлайн запрещено (кнопки недоступны с пояснением): выпуск ревизий, номера
  документов, ревизии ВДР, отправка документов, удаление проектов,
  пользователи и права, панель разработчика каталога.
- Решить: крупный импорт офлайн — предлагается разрешить одним пакетом.

### 3. Журнал офлайн-правок
- Операция, а не копия таблиц: номер, кто, когда, запись, поле, «было»,
  «стало», версия, на которой работал.
- Новые записи получают временный номер (`ВР-…`); при сверке сервер выдаёт
  настоящий и заменяет ссылки: связи родитель — потомок, позиции
  спецификации, ВДР.
- Удаление — операция «удалить», а не стирание.
- Импорт и массовые правки — одна группа, применяется или откладывается
  целиком. Зависимая операция ждёт ту, от которой зависит.

### 4. Сверка после подключения
1. Сначала локальная копия подтягивает изменения сервера.
2. Человек видит итог до отправки: «94 применятся, 4 сольются, 2 конфликта»
   и нажимает «Отправить».
3. Сервер применяет по одной операции со сверкой версии.

| Ситуация | Результат |
|---|---|
| Запись на сервере не менялась | применяется |
| Меняли разные поля одной записи | сливается |
| Меняли одно поле | конфликт |
| Один удалил, другой изменил | конфликт |
| Двое создали тег с одним кодом | конфликт «дубль» |
| Прав на запись больше нет | отказ с пояснением |

Повтор после обрыва безопасен: сервер помнит номера принятых операций.
Готово: 1000 правок с обрывом посередине — ничего не потеряно и не применено
дважды.

### 5. Конфликты
- Пока конфликт не разрешён, на сервере прежнее значение; правка ни одной
  стороны не вносится.
- Уведомление обоим с кнопкой «Перейти к конфликту». Экран: исходное
  значение, моё, коллеги, кто и когда. Действия: «Принять вариант коллеги»,
  «Оставить мой» (уходит коллеге на подтверждение), «Объединить» для
  текста, «Написать коллеге».
- Остальные видят у поля значок неразрешённого конфликта.
- Раздел «Конфликты» со счётчиком.
- Решить: кто решает, если двое не договорились (предлагается руководитель
  проекта; конфликт без движения N дней уходит к нему).

### 6. Мессенджер
«Написать коллеге» открывает чат с готовым текстом и ссылкой на конфликт;
клик по ссылке открывает экран конфликта. Проверить, умеет ли мессенджер
ссылки на объекты программы.

### 7. Документы, выпуск, ВДР
- Офлайн — только черновики. После подключения черновик сверяется с
  изменившимися данными; изменились входящие позиции — предупреждение перед
  выпуском.
- Одновременный выпуск при живом сервере: номер выдаёт сервер по очереди.
  Второй видит «Ревизию B выпустил Иванов в 14:32:04, ваш выпуск не
  выполнен», разницу между B и своими правками и варианты: «Выпустить мои
  правки ревизией C» (черновик поверх B), «Отменить мои правки», «Написать».
- Пока один готовит выпуск, другим видна пометка «Иванов готовит ревизию B»
  — предупреждение, не блокировка, снимается по времени.
- Выпущенное не меняется, исправление — следующей ревизией.
- Решить: нужен ли аварийный «временный выпуск» без сервера — вопрос
  регламента.

### 8. История и откат
Каждая сверка — группа в истории («офлайн-правки Петрова, 14:32–16:10, 98
операций»), откатывается целиком существующим механизмом. В истории записи
видно «внесено офлайн, отправлено в 16:12».

### 9. Проверки
Двое правят одно поле; удаление против правки; дубль кода; временные номера
и замена ссылок; обрыв посреди отправки; 1000 правок; офлайн несколько дней;
права изменились за время офлайна; одновременный выпуск ревизии. Обязательно
— Windows CI.

### 10. Внедрение
Пилот на одном проекте с настройкой «Работа без сервера», замер правок и
конфликтов, затем включение для всех.

Параллельно — резервирование самой общей базы (реплика), чтобы офлайн
требовался реже.
