# API Flux для программ

Состояние: идея, записана по решению владельца 11 ноября 2026. Порядок не
назначен; устройство ещё будет продумываться. Главное требование владельца:
**новая функция Flux или программы не должна заставлять переделывать уже
внедрённое** — API расширяется, а не меняется.

## Что есть сейчас

Программа живёт в изоляции и не ходит в базу и на сервер. Данные она
просит у Flux через мост по договору (`docs/roadmap/modules.md`, разделы
«Договор», «Изоляция»). Сегодня мост только читает.

## Направление

- **Один API по разделам Flux:** `flux.tags`, `flux.equipment`,
  `flux.files` (Проводник), `flux.documents` (ВДР, Документооборот),
  `flux.specs`, `flux.project`, `flux.users`. В каждом — чтение, поиск,
  подписка на изменения.
- **Разрешения в описании программы** («читать теги», «создавать файлы
  в Проводнике»): владелец видит их при выпуске, пользователь — при
  установке из Store. Сверх списка мост ничего не даёт.
- **Права пользователя сильнее разрешений:** программа действует от
  имени запустившего и не может больше, чем он. Проверка — на сервере.
- **Запись только через план и предпросмотр** (навык `flux-data-safety`):
  программа отдаёт план изменений, Flux показывает его человеку и после
  подтверждения выполняет сам — с проверками, журналом и откатом.
- **На всех языках одинаково:** TypeScript — вызовы функций; Python и
  WebAssembly — тот же API сообщениями (задача «Подключения из Python и
  WebAssembly» в `modules.md`).

## Чтобы потом не переделывать

- **Версии у каждого раздела API.** Программа указывает версию, под
  которую написана; Flux держит старые версии, Studio предупреждает об
  устаревшем. Изменение, ломающее договор, — только новой версией раздела.
- **Только добавление:** новые методы и необязательные поля; смысл
  существующих не меняется. Неизвестные поля ответа программа обязана
  пропускать.
- **Новый раздел Flux подключается записью в реестре API**, а не правкой
  моста, Studio и каждой программы: описание методов, разрешений и
  типов — в одном месте, из него строятся типы для редактора кода Studio,
  ответы тестовой базы, проверка перед отправкой и проверка CI.
- **Проверка совместимости в CI Flux:** набор договорных проверок идёт на
  каждом изменении Flux; сломанный договор виден до выпуска.
- **Разрешения расширяемы:** новое разрешение не затрагивает уже
  установленные программы; расширение прав при обновлении программы
  — с повторным согласием.

## Порядок (предварительно)

1. Чтение по всем разделам с разрешениями и версиями — вместе с первой
   настоящей программой (E3Flux), чтобы видеть, каких методов не хватает.
2. Подписка на изменения.
3. Запись через план и предпросмотр: сначала теги и файлы.

## Вопросы на проработку

Набор методов каждого раздела; формат реестра API; как долго держать

## Что уже заложено страницей программы (договор v2, 11 ноября 2026)

- **Версии и добавление, а не замена:** договор v2 добавил `ui: "page"` и `pages`; `form.json` и все сообщения моста v1 не менялись
  (старые выпуски содержат собственную копию проверки сообщений — менять смысл существующих сообщений нельзя). Новые действия
  страницы — одно сообщение `page` с полем `op`; новое действие добавляется новым `op`, старые страницы его не видят.
- **Клиент `flux.*` версионируется именем файла** (`/_flux/flux.v1.js`, `flux-ui.v1.css`): несовместимое выйдет как `v2`, а `v1`
  останется. Типы для редактора строятся из договора (`modules/page/types.ts`).
- **Интернет — только через мост** (`flux.net.fetch` поверх объявленного подключения `http`): кадр сам в сеть не ходит, CSP закрыт.
  «Любой адрес в интернете» и «локальная сеть» — отдельные, более заметные разрешения: внедрены (раздел ниже).
- **Точки расширения:** реестр разрешений в манифесте, `flux.programs.call`, диалоги Flux, разрешения «изменять …» — записываются
  записью в реестре, а не правкой моста каждой программы.

## Реестр разрешений и `flux.net.fetch(url)` (договор v3, 12 ноября 2026)

Разрешения собраны в таблицу `modules/permissions/registry.ts`: у каждого вида — проверка объявления в манифесте, строка для человека,
признак «заметное» и ключ сравнения для повторного согласия. Окно Store, отпечаток разрешений (`permissionsDigest`, его сверяет главный
процесс), «новое при обновлении» (`addedPermissions`), разница в «Запросах на публикацию» и проверка манифеста при выпуске строятся из неё.
Виды: чтение разделов (`reads`), подключения (`connections`), новые **`internet`** и **`lan`**. Будущие («программа», «изменять …») — новой
записью в таблице. Тексты строк прежних видов не меняются (по ним считается отпечаток уже установленных программ; проверка — `test-modules-permissions`).

```json
"contractVersion": 3,
"permissions": [
  { "kind": "internet", "does": "Показывает курсы валют и погоду из открытых сервисов" },
  { "kind": "lan", "does": "Находит принтеры и контроллеры в сети предприятия" }
]
```

- **Манифест.** `permissions` необязателен, до 16 записей; `does` — текст для человека (те же правила, что у `does` подключений:
  12–240 знаков, не меньше трёх слов, без адресов и разметки); повтор той же пары запрещён. Строгая схема старого Flux отвергла бы
  новое поле, поэтому выпуск с `permissions` — **`contractVersion: 3`**, и старый Flux скажет «Обновите Flux» (`unmetRequirements`).
  v1 и v2 без изменений. Раздел относится к программе со своим экраном (`flux.net.fetch` есть на странице).
- **Вызов.** `flux.net.fetch(url, init)` — когда первый аргумент полный адрес `http(s)://…`; прежняя форма `(connection, path, init)` не
  менялась. На мосту — новое сообщение `net` с `call: { url, method, headers?, body?, encoding? }` (метод внутри `call`, как у
  `connect`: на верхнем уровне `POST` мост принял бы за запись в данные Flux). Ответ приходит прежними `connect-result` / `connect-error`.
- **Проверка в главном процессе** (`ModuleConnections.net`, `electron/moduleNet.ts`, `modules/permissions/netAddress.ts`): форма вызова,
  выпуск, `permissions` проверенного манифеста, политика администратора, пределы; имя разрешается, проверяются **все** адреса, соединение
  идёт с проверенным (подмена DNS между проверкой и подключением невозможна). Публичный адрес — нужен `internet`; частная сеть
  (10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7) — `lan`; петля, «этот компьютер», 0.0.0.0, метаданные облака, link-local,
  широковещательные и групповые закрыты **всегда**, а `localhost` и `*.localhost` — по имени; петля открывается только явным подключением
  `connections`. Пределы, запрет редиректов (3xx возвращается как есть), отсутствие cookie, журнал (метод и имя сервера, без пути
  и тела) — прежние, этапа 3б. WebSocket по полному адресу в эту часть не входит.
- **Согласие.** При установке и обновлении — путь Store: строки `internet` и `lan` заметные (рамка и значок «!» в окне установки;
  «новое: любой адрес в интернете» в разнице владельца). Версия с добавленным разрешением в автообновление не попадает: Store
  останавливается и спрашивает. Спрашивать во время работы не нужно: человек уже согласился при установке.
- **Политика администратора.** Правило в `connection-policy` с именем подключения `@internet` или `@lan` (знак `@` не даёт совпасть с
  подключением из манифеста) запрещает роли соответствующее разрешение сильнее согласия при установке: отказ `NOT_ALLOWED`.
  Управление — вкладка «Подключения» Store.
- **Studio.** Типы `flux.d.ts` содержат обе формы `fetch`; проверка перед отправкой (`page-net`) требует `permissions` для адреса в
  коде, называет заведомо закрытые адреса и лишнее разрешение, а `permissions` без `contractVersion: 3` и у программы с формой — ошибка;
  пробный запуск (`runNet`) идёт по тем же правилам, что Flux, и ходит в сеть по-настоящему.

## Добавлено к v2: `flux.openFile` (12 ноября 2026)

Программа просит у человека файл, а не читает диск сама. Это ровно то, что в таблице «Что есть» стояло как «диалоги Flux»,
в первой, самой нужной части: чтение файла пользователя. Добавлением: новое действие страницы `op: "file-pick"`, старые не менялись.

```js
try {
  const file = await flux.openFile({ accept: ['.csv', '.txt'] });   // имена расширений — подсказка диалогу
  file.name;      // «данные.csv» — только имя, без папок
  file.size;      // байт, до 512 КиБ
  file.text();    // содержимое строкой (UTF-8)
  file.bytes();   // содержимое байтами
} catch (e) {
  if (e.code === 'CANCELLED') { /* человек закрыл диалог — это не ошибка */ }
}
```

- **Диалог показывает Flux** — главный процесс (`electron/modulePickFile.ts`), а не программа и не её окно. В заголовке стоит название
  программы. Окно Studio при запуске программы делает то же через свой главный процесс; в браузерной версии Flux —
  обычное окно выбора файла браузера.
- **Программа получает имя и содержимое только выбранного файла.** Путь, папка и соседние файлы не доходят; имя на мосту
  дополнительно очищается от путей. Больше 512 КиБ — ошибка `LIMIT`, файл не читается.
- **Ошибки:** `CANCELLED` (человек отказался), `LIMIT` (слишком большой файл либо второй диалог раньше, чем через секунду),
  `DENIED` (программа без страницы, неверный список расширений, хост без выбора файла), `FAILED` (файл не удалось прочитать).
- **Только добавление:** прежние сообщения и их проверка не менялись; старый Flux, не знающий `file-pick`, отвечает `DENIED`
  (проверка сообщения схемой отвергает неизвестное действие). Чтобы программа не падала там, пусть ловит ошибку и предлагает
  вставить данные вручную. Клиент остался `flux.v1.js`: несовместимого изменения нет.
- **Запись по-прежнему только через человека:** имя действия не похоже на запись (`file-pick`), мост по-прежнему отвергает
  записывающие слова. Файл для чтения не равен разрешению на чтение папки: следующий шаг (`flux.files`) решается отдельно.
- **Пробный запуск владельца** файла не выдаёт: программа получает `CANCELLED` и строку в журнале; настоящая проверка — в запуске
  Studio разработчика и во Flux.
