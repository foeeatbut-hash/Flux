# Расчётные программы внутри Flux

Статус: идея · обновлено 29 октября 2026

Расчётные программы (подбор вентиляторов, установок, клапанов и другие)
встраиваются во Flux как модули. Логику и интерфейс модуля ведёт другой
разработчик и выкладывает обновления сам, через отдельную программу
разработчика. Обновление модуля сразу доходит до всех Flux без выпуска
нового portable. Основной exe и его обновления остаются за владельцем; база
данных одна.

## Что уже есть в программе

- Обновления самого Flux лежат в общей базе неизменяемыми подписанными
  выпусками, публикует их только Owner (`server/updates.ts`,
  `server/routes/updateCampaigns.ts`). Подпись проверяется локально и в
  главном процессе Electron. Модули могут распространяться так же — через
  общую базу, без внешнего сервера.
- Каталог уже публикует данные без выпуска exe: «Панель разработчика» →
  «Записи», «Источники», «Проверка», «Публикация»
  ([03-programs/catalog.md](../methodology/03-programs/catalog.md)). Это
  образец процесса «черновик → проверка → выпуск».
- Оборудование, теги и спецификации — источник входных данных для расчёта
  и место, куда пишется результат.
- Мост к внешним программам Windows (COM для E3,
  [e3-integration.md](../e3-integration.md)) — образец, если расчётная
  программа остаётся отдельным exe.
- Ключ владельца и подписи — `license/ownerKey.ts`.

## Как это устроено

### Модуль
Пакет: описание (имя, версия, автор, совместимая версия Flux, нужные права),
интерфейс (веб-страница) и логика расчёта. Хранится в общей базе как
неизменяемый подписанный выпуск — по образцу обновлений Flux.

### Два вида модулей
1. **Встроенный.** Расчёт переписан как веб-модуль (TypeScript или
   WebAssembly, если логика на C/C++/Fortran). Работает везде, где
   работает Flux, обновляется через базу.
2. **Мост к готовому exe.** Если расчётную программу переписывать нельзя
   (чужая, лицензионная), модуль запускает её на компьютере пользователя,
   передаёт входные данные и забирает результат. Обновляется сам модуль;
   сама расчётная программа ставится как обычно. Проверить лицензию
   программы на такой способ использования.

### Песочница — главное условие безопасности
Код стороннего разработчика не получает доступа к базе, файлам и сети
напрямую. Сейчас настольный Flux подключается к общей базе с реквизитами
SQL ([company-server.md](../company-server.md)), и код модуля с такими
реквизитами мог бы сделать с базой что угодно. Поэтому:

- модуль работает в изолированном окне (отдельный процесс или iframe без
  доступа к Node и Electron);
- с Flux он общается только через API модулей: «прочитать параметры
  позиции», «записать результат расчёта», «показать уведомление»;
- права модуль объявляет в описании («читает оборудование проекта», «пишет
  в поле „Результаты подбора"»), при установке их видно, и Flux пропускает
  только объявленное;
- запись результата идёт тем же путём, что и любая запись в базу:
  предпросмотр, сверка версии, история, откат (`flux-data-safety`).

### Публикация и обновление
1. Разработчик готовит выпуск в программе разработчика и подписывает своим
   ключом.
2. Выпуск попадает в базу как черновик и проходит автоматические проверки:
   подпись, совместимость с версией Flux, объявленные права, контрольные
   расчёты (набор входов и ожидаемых результатов, который разработчик
   прикладывает).
3. Владелец (или назначенный им ответственный) одобряет выпуск. Права
   модуля расширились — одобрение обязательно. Можно настроить канал
   «тестовый» для части пользователей.
4. Одобренный выпуск сразу доступен всем Flux; открытый модуль предлагает
   перезапуститься на новую версию.
5. Откат — выбрать прошлый выпуск, он хранится в базе.

### Программа разработчика
- Вход своей учётной записью с ролью «разработчик модуля»; видны только
  свои модули.
- Шаблон модуля, локальный запуск с тестовой базой (не рабочей), просмотр
  внутри Flux до выкладки.
- Публикация, история выпусков, отзывы и обращения пользователей по модулю.
- Разработчику не нужен доступ к рабочей базе на запись: выпуск уходит в
  базу через API публикации, а не прямым SQL.

### Расчёт и данные проекта
- Модуль открывается из карточки оборудования или из «Пуска»; входные
  данные берутся из базы (расход, давление, размеры), а не вводятся заново.
- Результат расчёта пишется в позицию: подобранная модель, параметры, версия
  модуля, которой считали. Видно, по какой версии сделан расчёт, и можно
  пересчитать на новой.
- Обновление модуля не меняет прошлые расчёты молча: если результат на
  новой версии другой, это видно как предупреждение «пересчитать».

## Этапы

1. **API модулей и песочница.** Изолированное окно, набор вызовов чтения и
   записи, объявленные права. Первый модуль — простой встроенный расчёт,
   написанный владельцем, чтобы проверить API.
2. **Хранение и раздача через базу.** Формат пакета, подпись, неизменяемые
   выпуски, загрузка и проверка на клиенте — по образцу `server/updates.ts`.
3. **Одобрение и каналы.** Черновик → проверки → одобрение → выпуск;
   тестовый канал; откат.
4. **Программа разработчика.** Шаблон, локальный запуск, публикация.
5. **Мост к внешним exe** — если есть программы, которые нельзя переписать.
6. **Связь с данными проекта.** Расчёт из карточки оборудования, запись
   результата с версией модуля, предупреждение «пересчитать».

## Вопросы владельцу

1. Какие расчётные программы первые и можно ли переписать их логику, или
   нужен мост к готовому exe? Есть ли у них исходники и право на
   встраивание?
2. Кто одобряет выпуски модулей: только владелец или назначенные люди?
3. Сторонние разработчики — сотрудники компании или внешние? От этого
   зависят права и договор.
4. Может ли модуль менять общие данные (оборудование, теги) или только
   писать результат расчёта в отведённые поля?
5. Нужен ли тестовый канал обновлений?
