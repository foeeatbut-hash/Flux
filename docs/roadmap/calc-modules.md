# Расчётные программы внутри Flux

Статус: проработка · обновлено 29 октября 2026

Расчётные программы (ВЕРОСА — центральные кондиционеры, канальные установки
и другие) живут внутри Flux как подпрограммы. Владелец один раз добавляет в
portable «оболочку» подпрограммы и связывает её с проектом, оборудованием,
тегами и выпуском документов. Логику расчёта и интерфейс внутри оболочки
ведут внутренние программисты через отдельную программу — **Flux Студию**
(свой portable). Обновление, выложенное из Студии, сразу доходит до всех
Flux через общую базу; новый portable Flux для этого не выпускается.

## Решения владельца (29 октября 2026)

- Разработчики модулей — внутренние программисты компании.
- Оболочку подпрограммы и её связи с данными проекта добавляет владелец в
  portable Flux, один раз на программу.
- Логику и интерфейс внутри оболочки меняет разработчик через Студию.
  Выкладывает сам, когда угодно, или передаёт пакет владельцу, и тот
  выкладывает.
- Всё хранится и раздаётся через общую базу (SQL), отдельного сервера нет.
- В Студии есть панель для настройки интерфейса подпрограммы.

## Что уже есть в программе

- Обновления Flux лежат в общей базе неизменяемыми подписанными выпусками,
  публикует их Owner (`server/updates.ts`, `server/routes/updateCampaigns.ts`).
  Выпуски модулей раздаются так же.
- Каталог публикует данные без выпуска exe: «Панель разработчика» →
  «Записи», «Источники», «Проверка», «Публикация»
  ([03-programs/catalog.md](../methodology/03-programs/catalog.md)) —
  образец процесса «черновик → проверка → выпуск».
- Распознавание марок ВЕРОСА при импорте бланков (`src/import/recognize.ts`,
  `src/import/dictionary.ts`) и категория «центральные кондиционеры» в
  Оборудовании — входные данные для первого модуля уже есть.
- Запись в базу с предпросмотром, сверкой и откатом — skill
  `flux-data-safety`.

## Как это устроено

### Две части: оболочка во Flux и содержимое в базе

| | Оболочка (в portable Flux) | Содержимое (в общей базе) |
|---|---|---|
| Кто меняет | владелец | разработчик модуля через Студию |
| Как обновляется | новый portable | выпуск из Студии, сразу у всех |
| Что внутри | окно подпрограммы, место в «Пуске», связи с проектом, оборудованием, тегами, выпуском документов, API модуля | интерфейс (формы, таблицы, графики), логика расчёта, справочные данные (характеристики секций, вентиляторов, теплообменников), контрольные примеры |

Оболочка задаёт **договор**: какие данные модуль может прочитать (параметры
установки из карточки оборудования, тег, проект), что может записать
(результат подбора, состав установки, параметры в карточку) и какие события
получает («открыт из карточки», «проект сменился»). Пока договор не меняется,
разработчик свободен внутри. Понадобилось новое поле или новая связь —
это правка оболочки, то есть новый portable.

### Модуль
Пакет: описание (имя, версия, автор, совместимая версия договора), интерфейс,
логика, справочные данные, контрольные примеры. Хранится в базе неизменяемым
выпуском; прошлые выпуски остаются — к ним можно откатиться.

### Интерфейс: панель в Студии
- Визуальная раскладка: группы, поля ввода, выпадающие списки, таблицы,
  схемы и графики; поля привязываются к данным модуля мышью.
- Для того, что раскладкой не собрать, — свой код страницы.
- Просмотр сразу в оболочке Flux, на тестовой базе.
- Оформление берётся из Flux (палитра и элементы, skill `flux-style`), чтобы
  модули выглядели частью программы.

### Логика
- Код расчёта на TypeScript; если готовая логика на C/C++/Fortran —
  WebAssembly.
- Контрольные примеры: набор входов и ожидаемых результатов. Выпуск не
  уходит, если пример не сходится — защита от случайной поломки расчёта.

### Ограждение от ошибок
Разработчики свои, но ошибка в модуле не должна портить общую базу:
- модуль работает в изолированном окне без прямого доступа к базе, файлам и
  Node/Electron;
- в базу пишет только через API оболочки, а запись проходит обычным путём:
  предпросмотр, сверка версии, история, откат;
- упавший модуль закрывает только своё окно, Flux продолжает работать.

### Публикация
1. Разработчик в Студии собирает выпуск: проверка договора, контрольные
   примеры.
2. Выпуск уходит в базу — сразу (у разработчика есть право публиковать)
   или файлом владельцу, который выкладывает его из своего Flux/Owner.
3. Канал «тестовый» — выпуск видят только назначенные люди; потом перевод в
   «рабочий» для всех.
4. Открытый модуль предлагает перезапуститься на новую версию.
5. Откат — выбрать прошлый выпуск.

### Flux Студия (portable разработчика)
- Вход своей учётной записью с ролью «разработчик модуля»; видны только
  свои модули.
- Тестовая база для отладки, без записи в рабочие данные.
- Редактор интерфейса, редактор логики, контрольные примеры, просмотр в
  оболочке.
- Публикация, каналы, история выпусков, откат, обращения пользователей по
  модулю.
- Выпуск уходит в базу через API публикации, а не произвольным SQL.

### Расчёт и данные проекта
- Подпрограмма открывается из карточки оборудования (например, установки
  П1) или из «Пуска»; входные данные берутся из базы, а не вводятся заново.
- Результат пишется в позицию: подобранная модель, состав, параметры и
  версия модуля, которой считали.
- Новая версия модуля прошлые расчёты молча не меняет. Если на новой версии
  результат другой — у позиции предупреждение «пересчитать».
- Результат попадает в теги, спецификации и выпуск документов теми же
  путями, что и сейчас.

## Этапы

1. **Договор и оболочка для ВЕРОСА.** Перечень читаемых и записываемых
   данных, события; окно подпрограммы, место в «Пуске», вход из карточки
   центрального кондиционера.
2. **Изолированное окно и API модуля.** Первый модуль — простой расчёт,
   написанный вручную, чтобы проверить договор.
3. **Хранение и раздача выпусков через базу** по образцу `server/updates.ts`:
   формат пакета, подпись, неизменяемые выпуски, проверка на клиенте,
   откат.
4. **Flux Студия: публикация и каналы.** Вход, тестовая база, выпуск,
   тестовый и рабочий каналы.
5. **Студия: панель интерфейса** — визуальная раскладка и просмотр.
6. **Логика ВЕРОСА** — перенос расчёта и справочных данных, контрольные
   примеры.
7. **Вторая программа — канальные установки:** проверка, что договор
   подходит без переделки оболочки.

## Вопросы владельцу

1. Логика ВЕРОСА: есть исходники или документация расчёта? На каком языке?
   Это решает, переписывать на TypeScript или подключать как WebAssembly.
2. Что модуль может менять в общих данных: только свои поля результата или
   и карточку оборудования, теги?
3. Право публиковать сразу в рабочий канал — у всех разработчиков или
   только через тестовый?
4. Одна Студия для всех модулей или у каждого разработчика доступ только к
   своим?
