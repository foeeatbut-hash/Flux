# Паспорт тега

Статус: проект, 6 октября 2026.

## Решения владельца

Записаны дословно, 6 октября 2026:

- Сбор всего по тегу — **отдельная программа** («Паспорт тега»), а не
  доработка панели связей.
- «Давай пока отключим связь с ВДР».
- «Тег можно корректировать только из программы „Теги“; если там менять, он
  поменяется во всей программе, но сохранится в программе „Паспорт тега“
  история изменений».

## Почему

В программе пять разных «примечаний», и они не связаны:

- комментарии тега (`Tag.metadata.descriptions`);
- примечание закупки (`Tag.metadata.procurement.note`);
- замечания ВДР (`DocRegisterItem.remarks`);
- заметки блокнота (`UserNote`, связь по упоминанию кода);
- разобранные примечания САПР (`ComponentElement.tagNotes`).

«Карточка связей» (`WhereUsedView`, `server/insight.ts` → `whereUsed`)
показывает, где тег встречается, но без примечаний, закупки, автора и
истории. Истории изменений тега нет совсем: `ActionLog` пишет только «кто
дёрнул маршрут», без тега и без «было → стало».

Примечания остаются раздельными: примечание закупки и комментарий к тегу —
разные вещи. Паспорт собирает их в одном месте и подписывает, откуда каждое.

## Найденные ошибки, которые закрывает эта работа

1. **Затирание данных тега.** `PUT /api/tags/:id` заменяет `metadata`
   целиком тем, что прислал экран, без сверки версии. «Закупки»
   (`ProcurementManagement.tsx`, `saveProc`) сохраняют по копии тега,
   загруженной при открытии экрана. Комментарий, который коллега добавил в
   «Тегах» за это время, при смене этапа закупки молча стирается. Обратное
   тоже возможно.
2. **ВДР по коду строкой.** `DocRegisterItem.equipmentTags` ссылается на тег
   кодом. Переименование рвёт связь, хотя карточка тега обещает «связи
   сохранятся». По решению владельца связь пока отключается целиком.

## Правило записи

- Сам тег — код, наименование, марка, отдел, среда, сегменты, комментарии,
  родитель и состав — меняет только программа «Теги». Другие программы
  ссылаются на тег по `id`, поэтому изменение видно везде сразу.
- Другие программы пишут только свою часть. «Закупки» — данные закупки
  тега, отдельным запросом, который меняет только ключ `procurement` и
  ничего больше. Сервер сливает изменение с текущими данными тега, а не
  принимает целиком копию экрана.
- Запись в тег сверяет версию (`updatedAt` или счётчик). Если тег изменился
  с тех пор, как экран его прочитал, сервер отвечает конфликтом, экран
  перечитывает тег и показывает это человеку, а не затирает молча.
- Импорт и захват по-прежнему могут **создавать** теги. Изменение
  существующего тега идёт тем же путём, что и из «Тегов», и попадает в
  историю с пометкой источника («импорт оборудования», «захват»).

## История изменений

Новая таблица `TagChange`, только дописывается:

| Поле | Смысл |
|---|---|
| `id`, `tagId`, `projectId` | что и где |
| `at`, `userId` | когда и кто |
| `source` | откуда: «Теги», «Закупки», «импорт оборудования», «захват», «восстановление» |
| `kind` | создан / изменён / удалён / связь добавлена / связь убрана / комментарий добавлен / изменён / удалён |
| `field`, `before`, `after` | что было и что стало (для комментария — его текст) |

Пишет её сервер на каждом пути, который меняет тег: `server/routes/tags.ts`
(создание, правка, удаление, связи), закупки, импорт оборудования
(`equipmentTags.ts`), захват. Удалённый тег оставляет историю.

Автор создания теперь сохраняется для любого пути создания, а не только для
быстрой строки (`useQuickCreate`).

## Программа «Паспорт тега»

Свой раздел (`/tag-passport`) и пункт в Пуске: поиск тега по коду или
наименованию в текущем проекте. Открывается и с любого упоминания тега:
карточка, меню карточки на холсте, оборудование, закупки, поиск, помощник.
Пункт «Карточка связей» заменяется на «Паспорт тега».

Окно, сверху вниз:

1. **Шапка:** код, наименование, марка, отдел, среда, актуальность; «создал
   … · дата», «изменён … · дата»; кнопка «Открыть в „Тегах“» — править
   можно только там.
2. **Примечания** — все из всех разделов одним списком, по дате. У
   каждого — источник (Теги, Закупка, Заметки, САПР), автор и дата, если
   они есть, и переход к месту. Только чтение.
3. **Связи:** родитель, состав (дерево на два уровня), дубли кода.
4. **Использование:**
   - оборудование и установки;
   - закупка (этап, история этапов, поставщик, количество);
   - файлы;
   - обсуждения;
   - почта;
   - заметки.

   Группы — из `whereUsed`, пустые не показываются. ВДР здесь нет, пока
   связь отключена.
5. **История:** лента `TagChange` — кто, когда, откуда, «было → стало»;
   фильтр по виду изменения.

Данные — один запрос `GET /api/tags/:id/passport`. Он собирает тег,
примечания всех источников, `whereUsed` и историю на сервере, с теми же
правами доступа к проекту, что у остальных запросов к тегам.

## Отключение связи с ВДР

- В карточке тега убирается `TagVdrDocs`.
- В `whereUsed` для тега не возвращается группа ВДР.
- В ВДР столбец тегов строки не ведёт к тегу.
- Данные `equipmentTags` остаются в базе нетронутыми.
- Подсказка «связи сохранятся» у поля кода исправляется.

Вернуть связь можно позже, уже по `id`, а не по коду.

## Проверки

- Затирание: два клиента — «Теги» добавляют комментарий, «Закупки» по
  старой копии меняют этап; комментарий остаётся, а запись без свежей
  версии получает конфликт.
- История: каждый путь изменения (правка, связь, комментарий, закупка,
  импорт, удаление) оставляет запись с источником и «было → стало».
- Паспорт: собирает примечания всех источников и не показывает тег чужого
  проекта.
- Снимки паспорта в обеих темах.
- ВДР: у тега нет группы ВДР, в карточке нет списка ВДР.

Правила записи в базу — skill `flux-data-safety`: новая таблица только
добавляется, существующие данные не меняются и не удаляются.

## Порядок

1. Сервер:
   - `TagChange` и запись истории на всех путях;
   - слияние `metadata` с проверкой версии;
   - запрос закупки только к ключу `procurement`;
   - `GET /api/tags/:id/passport`.
2. «Закупки» переходят на свой запрос. Связь с ВДР отключается.
3. Программа «Паспорт тега» и её подключение вместо «Карточки связей».
