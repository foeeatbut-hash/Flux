# Flux на сервере компании

Клиенты Flux могут подключаться к одному адресу приложения; только сервер Flux подключается к общей базе данных. Пользователям нужен HTTPS URL приложения, например `https://flux.company.example`. Строка подключения к БД используется сервером внутри сети и не задаётся в клиентах.

## Текущее состояние и способ запуска

`server.ts` — Express + Socket.IO. По умолчанию он слушает порт `3000`; отдельно заданный `FLUX_LISTEN_HOST` имеет приоритет. Без `FLUX_EMBEDDED=1` адрес прослушивания — `0.0.0.0`, поэтому процесс доступен через сетевой интерфейс. В `main.ts` встроенный сервер помечен `FLUX_EMBEDDED=1` и слушает только `127.0.0.1`; он запускается вместе с окном.

Предпочтительный безоконный вариант при готовом Node ABI для нативных модулей:

```sh
cd Flux
npm ci
npm run build
NODE_ENV=production PORT=3000 node dist/server.cjs
```

Команда сборки уже есть в `package.json`, а `npm start` эквивалентен `node dist/server.cjs`. Перед штатным развёртыванием проверьте, что установленный Node умеет загружать `better-sqlite3` и Prisma SQLite adapter, если потребуется локальная SQLite база или сработает резервный путь создания клиента. Если используется MySQL/MariaDB, серверный клиент для этого драйвера тоже должен быть собран для целевой платформы. Нативный модуль, собранный под ABI Electron из portable EXE, нельзя считать совместимым с системным Node без проверки.

Для Windows portable доступен режим `--flux-company-server`, описанный ниже: сервер работает без окна в процессе Electron с совместимыми нативными модулями.

## База и адрес API — разные настройки

- **DB URI** (например, `mysql://USER:PASSWORD@192.168.120.176:3306/DATABASE`) — внутренний адрес MariaDB/MySQL, который читает только Flux server. Для MariaDB также понимается схема `mariadb://`. Задаётся в `config.json` сервера как `current_db_type: "REMOTE"` и `database_url`; этот секрет нельзя помещать в клиентский URL, документацию с секретами или репозиторий. Подключение должно идти к конкретному хосту БД, а не через публичный reverse proxy.
- **API URL** (например, `https://flux.company.example`) — адрес HTTPS reverse proxy перед Express, который задают на клиентах в настройке «Сервер компании». Это не URI базы данных. Не добавляйте к нему имя пользователя или пароль.

Сервер читает `config.json` в своей папке данных `pdm-app`: `%APPDATA%\pdm-app` на Windows; `~/.config/pdm-app` на Linux. В production локальная SQLite база находится там же (`database.sqlite`), если `local_db_path` не задан. Перед запуском положите `config.json` в этот каталог с выбранным режимом БД. Например, для локальной SQLite конфигурация содержит `{"current_db_type":"LOCAL","database_url":""}`. Для MariaDB нужны `{"current_db_type":"REMOTE","database_url":"mysql://USER:PASSWORD@192.168.120.176:3306/DATABASE"}`; замените значения по корпоративной схеме, не копируя пароль в клиентские настройки. Первичный запуск может создать таблицы приложения; используйте отдельного пользователя БД с правами, необходимыми для работы и синхронизации схемы.

## Сеть и TLS

Разместите HTTPS reverse proxy на поддерживаемом компанией Windows или Linux сервере и проксируйте на локальный Express `127.0.0.1:3000`. Включите WebSocket upgrade для Socket.IO и передачу `Host`, `X-Forwarded-Proto` и клиентского IP в стандартных proxy-заголовках. Flux доверяет proxy-заголовкам только от loopback; сам proxy должен находиться на том же хосте. Выпускайте/обновляйте TLS сертификат средствами компании.

Ограничьте firewall: порт приложения `3000` разрешён только с loopback (если reverse proxy локальный); `3306` открыт только между сервером Flux и сервером БД. Не публикуйте `3000` или `3306` в Интернет. Проверяйте корпоративный адрес только из сети компании или через одобренный VPN; внешний адрес без VPN не тестируйте.

## Проверка из сети компании

С Windows рабочей станции PowerShell проверьте TCP доступность сервера Flux на `192.168.120.176:3000` только если это адрес самого сервера Flux и локальная политика допускает прямую проверку порта:

```powershell
Test-NetConnection 192.168.120.176 -Port 3000
```

Для штатной конфигурации с reverse proxy проверяйте его HTTPS имя; успешный health ответ означает HTTP 200 с JSON `ok: true`:

```powershell
Invoke-RestMethod -Uri 'https://flux.company.example/api/health'
```

На самом сервере, если proxy слушает локально, проверьте backend напрямую:

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:3000/api/health'
```

Из узла Flux проверьте TCP до MariaDB/MySQL на 3306. Если адрес БД — `192.168.120.176`, используйте:

```powershell
Test-NetConnection 192.168.120.176 -Port 3306
```

Если у БД другой адрес, подставьте его вместо `192.168.120.176`.

Успешный TCP тест не подтверждает логин или права БД. После старта запросите `/api/health`: `ok: true` и `needsSetup: true` означает, что сервер и БД отвечают, но в базе пока нет пользователей; `503` означает, что сервер не смог прочитать БД. Не публикуйте вывод с секретами подключения.

## Первичная настройка владельца

В текущем дереве `license/ownerKey.ts` содержит пустые `OWNER_PUBLIC_KEY_HEX` и `OWNER_BACKUP_PUBLIC_KEY_HEX`. Пока доверенный открытый ключ не внесён из официального `FluxOwner` источника/конфигурации и не пересобрана программа, `/api/owner/challenge` ответит 503; войти владельцем и выполнить owner-only операции нельзя. Одноразовая подготовка должна быть выполнена владельцем: получить `FluxOwner` и публичную часть через официальный source-config apply workflow, применить её к исходникам и пересобрать сервер/клиенты. Точная команда этого workflow в доступном текущем коде не обнаружена, поэтому команда здесь намеренно не приводится. Закрытый ключ владельца хранится только в зашифрованном `.flux-owner` файле у владельца; он не загружается на сервер. После входа сервер создаёт единственный профиль `flux-owner` с ролью `OWNER` при первом успешном challenge-signature входе.

## Публикация обновления (только владелец)

1. На машине выпуска соберите portable EXE. Однократно создайте отдельный ключ подписания обновлений командой `node tools/update-sign.mjs keygen`; сохраните приватный ключ вне репозитория, CI и сервера. Это ключ подписания EXE, отдельный от `.flux-owner` ключа входа.
2. Подпишите выпуск: `node tools/update-sign.mjs sign release/Flux-1.2.3-x64.exe`. Рядом появится `.flux-sig` файл. Приложение проверяет версию, размер и SHA-256 по этой подписи.
3. В Flux войдите как владелец, откройте экран публикации обновления, загрузите EXE и соответствующий `.flux-sig`, укажите ту же версию и описание и опубликуйте. Сервер принимает загрузку только для владельца, записывает байты в общую БД чанками, затем сверяет подпись и публикует запись. Если загрузка не дошла целиком или подпись не совпала, публикация должна считаться неуспешной; проверьте результат в интерфейсе до объявления релиза.

## Сервер из portable

Windows portable поддерживает отдельный режим без окон:

```powershell
.\Flux-1.19.0-x64.exe --flux-company-server
```

Он запускает API в отдельном процессе Electron с совместимыми нативными модулями и пишет `company-server.log` в папку данных. По умолчанию API слушает `127.0.0.1:3000` для локального HTTPS-прокси; переменные `PORT`, `FLUX_LISTEN_HOST` и `VENT_APP_DATA` позволяют задать порт, адрес и отдельную папку сервера. Настройка БД читается из `config.json` этой папки. Режим клиента с адресом компании не запускает второй API. Для автоматического запуска настройте задачу Windows от отдельной служебной учётной записи; права и резервирование БД согласуйте с администратором компании.

Сборка проверена в Linux; запуск этого режима и службы на реальном Windows требует проверки после установки открытых ключей владельца. Без закреплённых открытых ключей сервер не разрешает первый вход владельца; это подготовительная сборка для инициализации.
