# Формат внедряемого реестра проверок

Реестры находятся в `verification/manifests/*.json`. Это паспорт сценариев,
а не утверждение, что описанные действия уже прошли тесты. Результат хранится
в отдельном отчёте прогона. Имена моделей, реальные секреты и данные сотрудников
в реестры и отчёт не включаются.

```json
{
  "version": 1,
  "group": "example",
  "programs": [{ "id": "example", "label": "Программа", "routes": ["/example"], "sources": ["src/screens/Example.tsx"] }],
  "suites": [{ "id": "example-unit", "path": "scripts/test-example.ts", "layer": "unit", "platform": "any", "resources": [], "prerequisites": [], "timeoutMs": 900000 }],
  "actions": [{ "id": "example.save", "program": "example", "label": "Сохранить", "sources": ["src/screens/Example.tsx"], "triggers": ["button", "shortcut"], "risk": "critical", "expected": ["Изменение записано и прочитано повторно"], "checks": [{ "suite": "example-unit", "layer": "unit", "claims": ["Валидатор отвергает пустое имя"] }], "manual": [{ "layer": "portable", "scenario": "Сохранить и повторно открыть файл на Windows", "expected": ["Содержимое совпадает с эталоном"] }] }],
  "connections": [{ "id": "example.to-other", "from": "example", "to": "other", "status": "implemented", "sources": ["src/screens/Example.tsx"], "expected": ["Другой клиент видит изменение"], "checks": [], "manual": [] }]
}
```

`layer`: `unit`, `component`, `api-db`, `browser-live`, `windows-native`,
`portable`. `platform`: `any`, `win32`, `linux`, `darwin`.
`risk`: `critical`, `normal`, `cosmetic`.
`prerequisites`: объекты `{ "kind": "env", "name": "FLUX_TEST_FIXTURE", "value": "1" }`
или `{ "kind": "file", "path": "public/genoffice/app.js" }`.
Динамические порты/сервисы объявляются в `resources`; наборы с общим ресурсом
исполняются последовательно. Измерения помечаются ресурсом `exclusive`.
Набор, требующий внешнего API/БД, обязан иметь проверяемую метку изолированного
стенда как prerequisite; никакого fallback к корпоративной конфигурации.

`checks` ссылается на ID набора (уникален во всех манифестах), слой должен
совпадать с описанием набора. `claims` перечисляет только утверждения, реально
проверяемые этим тестом: проверка схемы/исходного кода не доказывает работу UI.
Отсутствие автоматической проверки остаётся видимым пробелом, даже если
предусмотрен ручной сценарий. Ручные сценарии без артефакта выполнения
имеют статус NOT_RUN. Допускается ссылка на набор другой группы после сверки
всех манифестов. Планируемые связи не входят в покрытие реализованных связей.

В паспорте перечисляются фактически найденные действия, включая условные,
контекстные, клавиатурные и фоновые. Полное покрытие не заявляется по числу
записей: дополнительно сравниваются исходники, живой UI и контракты.
Исходные файлы объявляются явно; компонентные зависимости по возможности
включаются в `programs.sources`, чтобы обнаруживать новые элементы управления.

Все изменения программы, кроме необходимых тестовых фикстур, сначала
координируются с владельцем общей задачи: группы работают в одном workspace.

## Отчёт исполнения

Отчёт хранит версию приложения, Node и платформу. `scopedSourceDigest` и
`finishedScopedSourceDigest` — SHA-256 объявленных исходников, наборов,
манифестов и механизма исполнения до и после прогона. Это ограниченный набор
файлов, а не hash всего приложения или portable. Изменение этого набора во
время прогона видно через `sourceChangedDuringRun` и требует повторной проверки.

`PASS` относится к утверждениям набора; `FAIL` — к отказу/assertion/timeout;
`BLOCKED` — к отсутствующему или небезопасному стенду; `SKIP` — к явному
пропуску. Тест с частично пропущенными существенными ветвями печатает
`FLUX_VERIFY_SKIP: причина`, даже если его exit code равен нулю. Для полного
PASS нужна фикстура, реально проходящая эти ветви. Ручное действие не получает
PASS из результата соседнего unit-теста.
