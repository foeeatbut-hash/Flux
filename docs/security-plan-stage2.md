# Защита Flux: что сделано и что осталось

> Исторический план включает прежнюю цель «API-only» с внешним сервером Flux.
> Это решение больше не актуально для пользовательского подключения: настольные
> Flux и Flux Owner используют URI общей MariaDB/MySQL без внешнего HTTP-сервера.
> Текущая схема и её границы описаны в [company-server.md](company-server.md).

Документ для исполнителя, который продолжает работу над защитой. Написан так, чтобы
его можно было взять без истории разговора: цель, состояние, остаток по порядку,
решения владельца, правила репозитория.

## 1. Цель и модель угроз

Flux — личная программа владельца, сданная в аренду компании. База лежит на сервере
компании. Нужно, чтобы:

1. программой нельзя было пользоваться без лицензии, выданной владельцем;
2. профиль **владельца** был один, не зависел от паролей в коде и базе и не
   пропадал после обновления;
3. владелец создаёт администраторов и выдаёт им права выборочно; администратор не
   может ни выдать себе права владельца, ни разослать свою программу под видом
   обновления;
4. сотрудники, программисты компании и администраторы программы не могли обойти
   защиту штатными средствами.

**Честная граница.** Если у сотрудника есть исходники, root на сервере и прямой
доступ к базе, он может отключить любую проверку, которая выполняется на его же
машинах. Подпись Ed25519 при этом остаётся целой — ломают не её, а код, который её
проверяет. Реальный рычаг один: обязательная функция вне контура компании под
контролем владельца (см. раздел 6, решение 3). Всё остальное повышает стоимость
обхода и закрывает обычных сотрудников и администраторов программы.

## 2. Что уже сделано

**Слит в `main`, пул-реквест 74.** Подробности — в его описании. Кратко:

- письма не выполняют код: имя отправителя экранируется, цитата и подпись проходят
  очистку; мост окна пропускает только перечисленные каналы
  (`electron/ipcAllow.ts`); исполняемые файлы не запускаются из программы
  (`electron/runnable.ts`);
- обновления ставятся только с подписью владельца
  (`electron/updateSignature.ts`, `electron/updateKey.ts`, `tools/update-sign.mjs`),
  откат запрещён, токен не уходит при перенаправлении;
- единое правило видимости файлов `server/fileAccess.ts` и проектов
  `server/projectAccess.ts` на всех путях, включая сокеты и комнаты документов;
  «кто я» только из сессии; PATCH только по белому списку; связанные профили без
  хеша пароля;
- вход: лимит попыток, один ответ на «нет логина» и «не тот пароль», открытые пароли
  не принимаются; сокет пускает только годный профиль и закрывается при
  отключении;
- сеть: CORS только свои, большие тела только после входа, встроенный сервер
  слушает только свой компьютер, `server.cjs` и карты исходников не раздаются,
  вложения чата — по подписанной ссылке на 10 минут, пароль базы не уходит в
  ответах; всё в `server/security.ts`;
- журнал действий подключён до всех маршрутов, автор записи берётся из сессии;
- экран входа: одно поле подключения (`src/components/ConnectionPanel.tsx`,
  `src/lib/connection.ts`) вместо двух окон;
- исправлен дефект: проверка чужой базы меняла движок SQL всего сервера.

**Лежит в ветке `claude/hopeful-meitner-zb0ir5`, ещё не слито.**

- `license/node/core.ts` — формат лицензии на сотрудников: код запроса
  `FLUXREQ1.…` (администратор → владельцу), ключ `FLUX2.…` (владелец →
  администратору), правило `personLicense(login, inst, keys, now)`; предупреждение за
  14 дней. Подпись Ed25519, открытый ключ тот же, что у прежних `FLUX1`.
- `scripts/test-license-core.ts` — 17 проверок.
- `scripts/fixtures/license-test-key.txt` — **проверочный** закрытый ключ только для
  наборов; открытая половина `d1f0df97156bf12cc090411457311cc7b7bfb8344d55b8b4717a3dc32385c92c`.
  Настоящим не является.

## 3. Порядок остальной работы

Каждый этап — отдельный пул-реквест. Порядок важен: без роли владельца нельзя
правильно отдать права на лицензии и обновления.

### Этап A. Роль владельца и вход по ключ-файлу

Цель: профиль владельца, у которого нет пароля ни в коде, ни в базе, и который
нельзя отобрать обновлением.

1. **Роль `OWNER`** выше `ADMIN`. Проверка в промежуточном слое `server.ts`
   (там же `requiresAdministrator`, `PERM_ROUTES`, `AUTH_EXEMPT`): добавить
   `requiresOwner(route, method)` в `server/accessPolicy.ts`.
2. **Вход по подписи.** Сервер выдаёт одноразовое число
   (`GET /api/owner/challenge`, живёт 60 с, хранится в памяти). Клиент подписывает его
   закрытым ключом из файла владельца и присылает
   (`POST /api/owner/login {nonce, sig}`). Сервер проверяет открытым ключом,
   зашитым в сборку (`license/ownerKey.ts`, по образцу `electron/updateKey.ts`), и
   выдаёт токен сессии с ролью `OWNER`. Закрытый ключ с компьютера владельца не
   уходит; пароль нигде не вводится.
3. **На экране входа** — «Вход владельца»: выбрать файл `.flux-owner`, при желании
   фраза-пароль на файл. Подписывает окно программы (Web Crypto или главный
   процесс), сервер видит только подпись.
4. **Владелец не лежит в базе паролем.** Запись пользователя `OWNER` создаётся при
   первом входе по ключу, без поля пароля; обычный вход по паролю для неё
   отключён.
5. **Отключить начальный вход по общим учётным данным.** Новые базы не должны
   получать известный заранее пароль или профиль администратора. Уже существующие
   профили не менять автоматически; владелец базы проводит их проверку вручную.
6. **Что доступно только владельцу:** публикация и отзыв обновлений; выдача и
   изменение роли `ADMIN`; изменение и удаление `OWNER`; доверенные настройки
   (`play.publisher.key`, `security.*`, время, `license*`); путь резервных копий,
   выгрузка базы `/api/db/download`, переключение базы `/api/db/*`; права
   администраторов.
7. **Администраторы с выборочными правами.** Каталог возможностей администратора
   (`admin.users.create`, `admin.license.activate`, `admin.backup.run`,
   `admin.projects.manage`, …) в `src/lib/permissions.ts`; хранится в
   `User.permissions` и выдаётся только владельцем. Администратор без
   `admin.users.create` не создаёт профили; создать `ADMIN` или `OWNER` не может
   никто, кроме владельца.
8. **Не потерять доступ.** Открытый ключ владельца — в коде сборки, не в базе;
   ключей два: основной и запасной (закрытая половина запасного хранится отдельно,
   офлайн). Вход владельца не зависит от состояния базы и не меняется обновлением.
   Набор проверок обязан гонять вход владельца на проверочном ключе в каждом
   `npm run check`, чтобы поломка вылезла в проверке, а не у заказчика.

Тесты: `scripts/test-owner-auth.ts` — чужая подпись не входит, повтор числа не
входит, число старше 60 с не входит, `OWNER` нельзя изменить и удалить, `ADMIN` не
выдаёт `ADMIN`, администратор без права не создаёт профиль.

### Этап B. Лицензия на сотрудников, проверка на сервере

Формат готов (`license/node/core.ts`). Нужно:

1. **Номер установки.** При первом старте сервер создаёт случайный `license.install_id`
   в `AppSetting` (глобальный, ключ `license*` уже защищён от записи обычным
   маршрутом настроек). Ключ другой установки не подходит.
2. **Хранение ключей** — `AppSetting` `license.keys`; пишутся только маршрутом
   активации.
3. **Маршруты:**
   - `GET /api/license/me` — состояние лицензии вошедшего: `personLicense` плюс
     `warn` и дни;
   - `GET /api/license/request` — администратор получает один код запроса на всех
     сотрудников без лицензии;
   - `POST /api/license/activate-key` — администратор вставляет `FLUX2…`, сервер
     проверяет подпись и номер установки и сохраняет;
   - `GET /api/license/overview` — таблица «сотрудник — срок — осталось дней».
4. **Проверка на каждом запросе.** В промежуточном слое `server.ts` после
   проверки токена: нет лицензии у человека — ответ 402 с причиной. Исключения:
   `/api/health`, `/api/login`, `/api/license/*`, `/api/owner/*`, `/api/me/bootstrap`.
   `OWNER` проверке не подлежит. То же для сокетов: `socketAuth` из
   `server/security.ts` проверяет лицензию на рукопожатии, а при окончании срока
   соединение закрывается.
5. **Время.** Срок считается по надёжному времени сервера
   (`trustedNowSync`, `server.ts` около строки 931) — перевод часов назад не
   продлевает. Перепроверять срок периодически, а не только при входе (раньше
   гейт спрашивал один раз).
6. **Убрать прежнюю лицензию на компьютер:** `electron/license.ts`,
   `src/lib/license.ts`, `src/lib/licenseGate.ts`, `src/screens/LicenseGate.tsx`,
   `scripts/test-license-gate.ts`, маршруты `/api/license/status` и
   `/api/license/activate` в `server/routes/system.ts`, коды `FLUX1`. Гейт переезжает
   **после входа**: нет лицензии — экран «Нет лицензии, обратитесь к администратору»;
   у администратора — «скопировать запрос» и «вставить ключ».
7. **Предупреждение об окончании** — плашка за 14 дней (`WARN_DAYS`) с числом дней.
   Что делать после срока — решение 1 в разделе 6.
8. **Настройки → Лицензии** (только администратор с `admin.license.activate`):
   таблица, кнопки «Скопировать запрос на всех без лицензии» и «Вставить ключ».
9. **Для наборов проверок.** Сервер из исходников (`tsx server.ts`) принимает ещё и
   проверочный открытый ключ и при `FLUX_TEST_LICENSE=1` ставит себе лицензию на
   `*`; `scripts/run-checks.ts` выставляет переменную. Собранный `server.cjs` этого
   не знает (тот же приём, что `FROM_SOURCE` в `server/updates.ts`). Иначе все
   существующие наборы получат 402.

Тесты: `scripts/test-license-server.ts` — без лицензии 402, с лицензией 200, срок
вышел, ключ другой установки, подделанный ключ, сокет закрывается по сроку,
перевод часов назад.

### Этап C. Программа владельца (отдельная portable)

Заменяет `license-generator.html` (он в `.gitignore`, в репозитории его нет) и
консольный `tools/update-sign.mjs`. Всё в одном окне, минимум действий.

- **Где живёт:** `tools/flux-owner` в общем репозитории Flux и отдельная сборка
  Electron portable, приложенная к выпуску Flux. Программа запускается отдельным
  EXE и не включается в интерфейс для сотрудников. Закрытые ключи и личное
  хранилище находятся только на компьютере владельца. Форматы
  подписи берёт из `license/node/core.ts` и `electron/updateSignature.ts` (общий
  пакет или копия с проверкой совпадения).
- **Вкладки:**
  1. **Лицензии.** Вставил код запроса → список людей с галочками, название
     компании → выбрал срок (1 / 3 / 6 / 12 месяцев или дата) → «Выпустить» →
     ключ в буфере. Реестр выданного: компания, срок, дата выпуска, напоминание о
     продлении.
  2. **Обновления.** Выбрал exe → программа считает SHA-256 и подписывает → `.flux-sig`;
     по желанию тут же публикует на сервер (загрузка и запись релиза) под входом
     владельца. Одна кнопка «Подписать и опубликовать».
  3. **Ключи.** Создание ключей (лицензий, обновлений, входа владельца, запасной),
     хранилище зашифровано фразой-паролем (scrypt плюс AES-256-GCM) в
     `~/.flux-owner/`, экспорт резервной копии на отдельный носитель, показ
     открытых ключей, кнопка «Вписать открытые ключи в исходники».
  4. **Вход.** «Открыть Flux как владелец»: подписывает число сервера.
- **Отзыв лицензии.** Подписанный ключ офлайн отозвать нельзя. Варианты — решение 4
  в разделе 6.
- **Безопасность самой программы.** Закрытые ключи никогда не лежат рядом с exe и не
  попадают в репозиторий; в приложении нет сети, кроме явной публикации на сервер
  компании.

### Этап D. Подключение только через сервер

Чтобы пароль базы знал только сервер (пункт 6 первой проверки), клиенты не должны
уметь подключаться к базе напрямую.

- режим «API-only»: сервер компании (`node dist/server.cjs`) держит строку базы в
  своей среде; клиенту нужен только адрес сервера;
- `ConnectionPanel` в сборке для компании принимает только `http(s)://`; ветку с
  `mysql://` оставить за флагом «режим владельца» (для настройки сервера);
- отдельная учётная запись базы с минимальными правами для сервера, а не
  `GRANT ALL`.

### Этап E. Остальное из проверки безопасности

- **HTTPS и WSS.** Клиент отказывается от `http://` для не-локальных адресов;
  инструкция по обратному прокси; HSTS.
- **Отзываемые сессии.** Номер версии токена у пользователя; смена пароля и
  отключение профиля обнуляют его; срок короче 30 дней, с продлением.
- **Токен вне `localStorage`:** для браузерного режима — HttpOnly-cookie плюс защита
  от CSRF; для Electron — хранить в главном процессе.
- **Электронные «предохранители» (Electron Fuses) и целостность asar:**
  `@electron/fuses`: `RunAsNode` выключить (проверить, что `utilityProcess` работает),
  `EnableNodeOptionsEnvironmentVariable` и `EnableNodeCliInspectArguments`
  выключить, `EnableEmbeddedAsarIntegrityValidation` и `OnlyLoadAppFromAsar`
  включить. Подпись кода Windows (нужен сертификат — решение 6).
- **Зависимости:** `xlsx` 0.18.5 → 0.20.3 (в npm исправленной версии нет, берётся с
  `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`; в облачной среде этот сайт
  закрыт — делать там, где он доступен) и прогнать импорты; `pdfjs-dist` не ниже
  6.2.108; Electron, `engine.io`, `socket.io-parser`, `ws`, `fast-xml-parser`,
  `nodemailer` — по списку предупреждений. Сборка в GitHub Actions: действия по
  коммиту, минимальные права, обязательная проверка перед выпуском.
- **Журнал действий:** цепочка хешей записей и вынос контрольных точек за
  пределы базы.
- **Остатки по правам** (из отчётов проверки, ещё не закрыты):
  - общий страж видимости проекта (`registerProjectAccessGuard`) не покрывает
    маршруты, зарегистрированные раньше `registerProjectRoutes`, и маршруты, где
    проект определяется по номеру сущности: `PUT/DELETE /api/tags/:id`,
    `/api/systems/:id`, `/api/components/…`;
  - группы чата проектов и список групп отдаются всем;
  - ключ `procurement_templates` не имеет записи в `PERM_ROUTES` (там
    `stage_templates`);
  - события тегов и конфликтов по сокету пересылают присланные клиентом данные без
    фильтра по доступу к проекту;
  - набор `scripts/test-office-docs-live.ts` валит три проверки раздела 3 («окно
    спрашивает, что делать») — воспроизводится и на чистом `main`, к защите не
    относится, нужен отдельный разбор.

## 4. Правила репозитория (из `CLAUDE.md` и навыков `.claude/skills/flux-*`)

- Код, комментарии, сообщения коммитов и описания пул-реквестов — по-русски.
  Комментарий объясняет **почему**, а не что делает код; хорошо, если он называет
  дефект, который иначе вернётся.
- В репозиторий **не попадает**: идентификатор модели (ни в коде, ни в коммитах, ни в
  пул-реквестах); закрытые ключи (в `.gitignore` есть `*.pem`, `*.key`,
  `update-key*`, `owner-key*`, `*.flux-sig`, `license-generator.html`). Проверочные
  ключи в `scripts/fixtures/*-test-key.txt` — единственное исключение.
- Проверки: `npm run check` (около 7,5 минуты, печатает только провалы).
  Точечно: `npm run check -- <слово>`. Один набор с полным выводом:
  `npx tsx scripts/test-<имя>.ts`. Формат набора — без фреймворка, счётчик, функция
  `eq(name, got, want)`, названия по-русски и по существу.
- Типы: `npx tsc --noEmit -p .` — ноль ошибок.
- Размер файла — храповик (`scripts/test-architecture.ts`, `LEGACY`): `server.ts`
  около 1500 строк и расти не должен; новое — в `server/*.ts` и `server/routes/*.ts`.
  Общий код вне `src/`, `server/`, `electron/` лежит в корневых папках
  (`license/`, `office/`, …); то, что тянет Node (`crypto`, `fs`), — в подпапке
  `node/`.
- Права в маршрутах — одной таблицей (`PERM_ROUTES` в `server.ts`), а не в каждом
  обработчике; клиент базы берётся лениво (`getPrisma()` внутри обработчика).
- Работа с данными проекта — по навыку `flux-data-safety`: план и предпросмотр
  вместо прямой записи.
- После каждого законченного обновления — пул-реквест в `main` с русским
  заголовком, в теле: что сделано и почему, чем проверено, какие дефекты найдены по
  дороге.
- Сборка exe — по навыку `flux-release`, в GitHub Actions по метке `[build-exe]` в
  коммите. **Перед первой сборкой с подписью обновлений** владелец выполняет
  `node tools/update-sign.mjs keygen` на своём компьютере: пока в
  `electron/updateKey.ts` ключ пуст, собранная программа **не ставит обновления
  вообще**, и первый подписанный выпуск придётся поставить вручную.

## 5. Как проверить результат в конце

1. `npm run check` — ноль провалов.
2. Живой сценарий с двумя временными сотрудниками и вторым администратором:
   чужой личный файл, чужой проект, чужая группа чата, чужие уведомления — везде
   отказ без выдачи факта существования.
3. Лицензия: без ключа 402; ключ на троих — работают трое, четвёртый нет; срок вышел —
   сокеты закрылись; ключ другой установки не принят; перевод часов назад не
   продлевает.
4. Владелец: вход по ключ-файлу работает на пустой базе, на заполненной и после
   обновления; чужая подпись не входит; `ADMIN` не создаёт `ADMIN`.
5. Обновление: выпуск без подписи не публикуется; с подписью другого ключа не
   ставится; с подписью владельца и новее установленной — ставится.

## 6. Решения владельца, без которых нельзя дописать

1. **Что происходит после окончания лицензии сотрудника.** Рекомендация:
   предупреждение за 14 дней, после срока — только чтение с плашкой «обратитесь к
   владельцу», данные остаются целыми. Жёсткая блокировка рабочих данных компании
   рискует претензиями, что рабочие данные закрыты.
2. **Один общий сервер компании или сервер у каждого сотрудника.** Пока выбрано
   «не решил». При серверах у каждого пароль базы неизбежно лежит на каждом
   компьютере (этап D невозможен), а лицензию придётся проверять и в клиенте, и в
   его встроенном сервере.
3. **Нужна ли обязательная функция вне контура компании.** Без неё защита от
   того, у кого есть root на сервере, невозможна принципиально. Варианты:
   короткоживущие подписанные «билеты», которые сервер получает у службы владельца и
   без которых не работают критичные операции; или ограничить цель защитой от
   обычных сотрудников и администраторов программы.
4. **Как отзывать лицензию.** Только короткими сроками (проще), или подписанным
   списком отзыва (`FLUXREV1`), который сервер принимает вместе с ключами.
5. **Где живёт программа владельца.** Рекомендация — отдельный приватный
   репозиторий.
6. **Сертификат для подписи кода Windows** — покупается владельцем; без него exe
   остаётся неподписанным, и предупреждение Windows при запуске не уйдёт.
7. **Юридическая сторона.** Программа, написанная в рамках трудовых обязанностей,
   по статье 1295 ГК РФ обычно принадлежит работодателю, если иное не сказано в
   договоре. Закрепить права и условия аренды договором стоит до того, как на них
   будет опираться техническая защита.

## 7. Что нужно сделать самому владельцу

- закрыть репозиторий на GitHub (Settings → Danger Zone → Change visibility →
  Private); всё, что уже было опубликовано, считать утёкшим;
- сменить пароль базы и проверить учётные записи, если использовались общие пароли;
- выполнить `node tools/update-sign.mjs keygen`, сохранить копию ключа на отдельном
  носителе;
- обновить `xlsx` там, где открыт сайт SheetJS.
