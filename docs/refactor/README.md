# Рефакторинг крупных файлов

Зачем: чтобы следующая работа во Flux стоила меньше времени и контекста —
модель читает файл на 200–800 строк, а не на 4 000, а проверки идут минуты.
Роли: руководитель (Opus) решает границы, принимает шаги по отчёту и
`git diff --stat`, правит храповик и гоняет итоговые проверки; исполнители
(Sonnet, `Agent` с `isolation: worktree`) выносят по одному шагу.

## Как устроен заход

1. Карта файла — только `grep -n` по меткам-комментариям, файл целиком не
   читается. Для гигантского компонента карта и порядок записываются сюда
   отдельным файлом до первого шага.
2. Шаги раздаются по одному; параллельно — только разные файлы.
3. Шаг принимается по отчёту и `git diff --stat`; один-два куска диффа — на
   выбор. Сомнительные места из отчёта («стоял между», «заменил на то же
   самое») проверяются по коду, а не на слово.
4. Слияние — `git merge --squash` ветки исполнителя, сообщение коммита пишет
   руководитель. Храповик, `npm run check`, `tsc`, `vite build` — в конце.
5. Сборку exe ради рефакторинга не выпускать.

## Шаблон задания исполнителю

Постоянные правила (подготовка копии, порты, лицензия, проверки, коммиты)
вынесены в тип исполнителя `.claude/agents/flux-executor.md`: исполнитель
этого типа получает их сам, и задание сокращается до самой задачи —
ревизия старта, что вынести и куда, порт, чужие файлы, проверки шага.
Шаблон ниже — полный, для исполнителя без этого типа. Следующий шаг той же
области выгоднее отдать тому же исполнителю (продолжить его), чем новому:
он уже прочитал код и план.

```
Репозиторий Flux. Ты в своём git worktree.
Подготовка: `ln -s /home/user/Flux/node_modules node_modules`; если нужен
сервер — клиенты Prisma симлинкнуть ПО ФАЙЛАМ из
/home/user/Flux/prisma-clients/<client-sqlite|client-pg|client-mysql>/ кроме
package.json (он в git). npm install и prisma generate не запускать.
Прочитай CLAUDE.md и скиллы flux-architecture, flux-style (+ flux-verify,
если поднимаешь сервер; + flux-data-safety, если трогаешь запись в базу).

Шаг <N>: вынести <что именно, с метками-комментариями и примерными
строками> из <файл> в <новый файл>.
Почему: <одна фраза>.

Правила:
- Поведение не меняется. Только перенос и импорты; улучшения — нельзя.
- Перенос — скриптом, вырезая диапазоны строк, а не перепечатывая код.
- Большие файлы: сначала grep -n, потом sed -n нужного куска.
- Комментарии по-русски, про «почему»; перенесённые — дословно.
- Не трогать scripts/test-architecture.ts (храповик правит руководитель).
- Проверки: NODE_OPTIONS=--max-old-space-size=8192 node_modules/.bin/tsc
  --noEmit и смотреть КОД ВЫХОДА: при нехватке памяти tsc падает, а
  grep -c "error TS" по его выводу всё равно печатает 0.
  node_modules/.bin/tsx scripts/run-checks.ts <слова>; test-layout — отдельно
  (под общей нагрузкой бывает нестабилен). Длинный вывод — в файл, в
  контекст — tail.
- Сервер — свой, на порту 3101 (PORT=3101, FLUX_API=http://localhost:3101);
  3000 не трогать. Останавливать свой по cwd процесса, а не pkill -f
  "tsx server.ts" (убьёт чужой), и из файла-скрипта: строка с pgrep в самой
  команде находит саму команду. После kill ждать, пока порт освободится:
  сервер закрывается не мгновенно. node_modules — общий симлинк, а с ним и
  кэш Vite: после чужого перезапуска свой сервер может отдать «Invalid hook
  call» — лечится перезапуском своего.
- Коммит в своей ветке, короткое русское сообщение. Не пушить.
- Тесты не отключать и не пропускать.

Отчёт (не больше 15 строк): что вынесено и куда, размеры до/после, какие
проверки прошли, ветка и хеш, что показалось странным или рискованным.
```

Калибровка: вынос секций «Настроек» — один исполнитель,
3 минуты, ~70 тыс. токенов; четыре группы маршрутов `server.ts` с эталонным
сервером для сверки ответов — 18 минут, ~155 тыс. Шаг Registry или
DictionaryEditor с проверками раздела и снимками в обеих темах — около часа
и ~160–195 тыс. Больше двух исполнителей одновременно не пускать: общий
лимит запросов однажды остановил всех троих на несколько часов. Отчёта по
шаблону хватало для приёмки; сомнительные места исполнители называли сами,
но проверять их по коду всё равно надо.
