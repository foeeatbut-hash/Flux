# Загрузка оборудования и E3Flux — выгрузка схем в E3.series

Проект, 7 октября 2026. Две части, и вторая стоит на первой:

1. **Загрузка данных.** У каждой позиции проекта с первой загрузки есть свой
   ID: у установки, у элемента внутри неё и у элемента внутри элемента, даже
   если тега ещё нет. Этот ID не переходит к другому изделию при повторной
   загрузке. Сейчас это не так — разбор ниже.
2. **E3Flux.** Программа внутри Flux для отдела КИПиА. Она берёт подобранное
   отделом ОВ оборудование, по классификатору типовых решений подбирает
   каждому узлу установки его блок схемы в базе E3, пересчитывает
   характеристики в атрибуты E3, показывает схему на холсте и выгружает её
   в открытый E3.series. При переподборе выгружает схему заново и по ID
   заменяет то, что уже было выгружено.

Раздел 5 написан по файлам владельца: «Классификатор типовых решений» и
«Список атрибутов». Что в них нашлось и чего в них не хватает — там же.

## Часть 1. Загрузка данных: ID позиции

### 1.1 Как сейчас

Импорт (`server/equipmentImport.ts`) узнаёт позицию по пути из имён:

```
установка (по имени, с поправкой на опечатку раскладки)
  └ моноблок (по имени внутри установки)
      └ блок (по коду: «бл2.1»)
          └ подпозиция (по пути: «бл2.1/вентилятор1/двигатель1»)
```

При первом появлении пути заводится запись с постоянным ID позиции вида
`PRJ-000001-EQ-000001`; тег для этого не требуется. Правила выдачи и переноса
существующих UUID описаны в [идентичности проектов](project-identities.md).
При повторной
загрузке тот же путь находит ту же запись, и в неё пишутся новые
характеристики. Вложенность держится полем `parentElementId`, глубина любая.

Значит, ID без тега уже выдаётся на всех уровнях. Беда в другом: ID
привязан к **пути в файле**, а не к **изделию**. Пока путь не меняется, это
незаметно. Перед связью с E3 это надо исправить: схема КИП будет держаться
за ID, и если ID переедет на другое изделие, вместе с ним переедет схема.

### 1.2 Где это ломается

| # | Что случилось в расчёте | Что делает импорт сейчас | Чем плохо |
|---|---|---|---|
| Д1 | В установку вставили блок, коды сдвинулись: бывший «бл2.1» стал «бл2.2» | В «бл2.1» записываются характеристики нового блока | Тег, история и будущая связь с E3 переходят от фильтра к нагревателю. Проверки на смену типа нет: `detectTypeMismatch` вызывается только в старом разборе Excel (`server/excelParser.ts`), новый импорт её не зовёт |
| Д2 | Из двух вентиляторов блока убрали первый | «вентилятор2» исчезает, «вентилятор1» получает данные второго | Номер экземпляра выдаётся по порядку в файле, и данные сдвигаются на одну позицию |
| Д3 | Позиция пропала из нового расчёта | Ничего: запись остаётся как была, без отметки | Нельзя отличить действующее оборудование от снятого. Старый разбор помечал такие позиции `ORPHANED_TAG`, новый — нет |
| Д4 | Установку переименовали («П1» → «П1.1»), это не опечатка | Заводится новая установка, старая остаётся рядом | Теги и связи остаются на старой, у новой их нет, и снятой старая не помечена |
| Д5 | В двух файлах одной категории есть установки с одинаковым именем | `matchSystem` ищет только по имени внутри категории | Две разные установки сливаются в одну. Выгрузка в Excel их уже различает по ID, а импорт — нет |
| Д6 | Блок без параметров установки | Служебный блок `__unit__` не заводится | У установки нет записи-позиции, и связать с E3 саму установку (шкаф, щит управления) не через что |

### 1.3 Правило

**ID выдаётся изделию один раз и навсегда.** Его получает любая позиция
любого уровня: установка, моноблок, блок, подпозиция и её подпозиции. Тега
для этого не нужно. ID не используется повторно и не передаётся другому
изделию. Тег, история, ручные правки, связь с каталогом и связь с E3
привязаны к ID, а не к коду и не к тегу.

Код из файла («бл2.1») — это **адрес**, а не ID. Адрес меняется, когда
расчёт пересобирают. ID при этом остаётся прежним.

### 1.4 Сопоставление при повторной загрузке

Для каждой позиции нового файла импорт ищет запись по шагам, от надёжного к
приблизительному. На первом найденном шаге поиск заканчивается.

1. **Ключ источника.** Если в файле у узла есть свой постоянный
   идентификатор, он запоминается при первой загрузке и сравнивается при
   следующих. В выгрузках САПР ВЕЗА сейчас такого ключа не видно. Шаг
   нужен на будущее и для файлов, которые Flux сам выгружал и получает
   обратно.
2. **Тег из файла.** Тег в файле есть, и в проекте он уже стоит на позиции
   этой установки — значит, это она, даже если код другой. Так ловится Д1
   для тегированных позиций.
3. **Адрес** (как сейчас) — **с проверкой, что изделие то же.** Тип или
   роль совпадают, ключевые характеристики близки (подпись — как у
   `CatalogLearn`: тип, вид, типоразмер, мощность). Если по адресу теперь
   стоит изделие другого типа, позиция с ним не сливается.
4. **Поиск переехавших.** Позиция пропала с одного адреса, а на другом
   появилась позиция того же типа с близкими характеристиками. Импорт
   предлагает связать их: «Фильтр ФВК переехал с бл2.1 на бл2.2».

Шаги 3 и 4 только **предлагают**. Решение принимает инженер в предпросмотре
импорта (`server/equipmentPlan.ts`), по правилам `flux-data-safety`. Каждая
спорная позиция показывается в плане отдельной строкой с вариантами:

| Вариант | Что значит | Когда стоит по умолчанию |
|---|---|---|
| **То же изделие** | Новые данные пишутся в прежнюю запись (ID, тег и связь с E3 сохраняются) | Тип совпадает, характеристики близки |
| **Переподобрано** | Прежняя запись снимается, заводится новая, и между ними ставится связь «заменено на» | Тип тот же, характеристики далеки (другой типоразмер) |
| **Другое изделие** | Прежняя запись снимается, новая заводится без связи | Тип другой |

«Переподобрано» отличается от «другого изделия» для E3: позицию в схеме
можно заменить на месте, и проводка не переделывается (раздел 9).

### 1.5 Пропавшие позиции

Позиция, которой нет в новом файле, **не удаляется**. Она получает
состояние «снята» (`status = 'REMOVED'`, дата и партия импорта, которой
снята):

- в дереве оборудования она видна серой, за переключателем «показать
  снятые»;
- тег остаётся, в «Тегах» отмечается «оборудование снято»;
- если позиция есть в схеме E3, E3Flux показывает её к удалению из схемы
  (раздел 9);
- если позиция вернулась в расчёт (откатили переподбор), запись
  возвращается с тем же ID;
- **отмена импорта** (`ImportBatch`) возвращает снятые этой партией
  позиции.

Ручные позиции (`manual = true`) снятыми не становятся: файл их не знает.

### 1.6 Установка, моноблок и номера экземпляров

- **Установка — тоже позиция.** Служебный блок `__unit__` заводится всегда,
  даже без параметров: на него вешаются тег установки и связь с E3. Так
  закрывается Д6. Предпросмотр должен считать так же, иначе план и запись
  разойдутся — об этом комментарий в `importEquipmentToDB`.
- **Переименование установки (Д4)** — в плане отдельная строка: «В файле
  нет П1, появилась П1.1 с тем же составом — это она?». Да — запись
  переименовывается, ID прежний.
- **Одинаковые имена (Д5):** установка ищется по имени **и** имени файла,
  если в категории уже есть две с таким именем. Если сопоставить нельзя,
  план просит выбрать.
- **Номер экземпляра (Д2):** «вентилятор1» и «вентилятор2» сопоставляются
  не по номеру, а по шагам 2–4: тегу, типоразмеру, характеристикам. Номер
  остаётся подписью для человека.

### 1.7 Версия позиции

У `ComponentElement` уже есть `version`. Её надо поднимать при **любом**
принятом изменении: характеристик, типа, тега, состава, ручной правки.
Сейчас она растёт только при обновлении характеристик в режиме
`immediate`. E3Flux сравнивает «какую версию выгрузили» с «какая сейчас» и
по этому сравнению показывает «изменилась после выгрузки».

### 1.8 Проверки части 1

Новый набор `scripts/test-equipment-identity.ts` — повторная загрузка на
настоящих выгрузках ВЕЗА с правкой:

- сдвиг кодов (Д1): ID следует за изделием, а не за кодом;
- удаление первого из двух вентиляторов (Д2);
- пропажа позиции → «снята»; возврат → тот же ID; отмена партии → снятие
  отменено (Д3);
- переименование установки (Д4) и две установки с одним именем (Д5);
- установка без параметров получает запись (Д6);
- первая загрузка без единого тега: ID есть на всех уровнях, тег,
  поставленный потом, ложится на нужный ID;
- план и запись совпадают по каждому случаю (как сейчас сверяет
  `test-equipment-plan`).

## Часть 2. E3Flux

## 2. Кто что делает

| Кто | Где | Что делает |
|---|---|---|
| Отдел ОВ | Flux, «Оборудование» | Загружает расчёты, подбирает оборудование, ставит теги. Про E3 не знает ничего |
| Администратор каталога (КИП) | Flux, «Каталог» → «E3.series» | Ведёт типовые решения с признаками, правила признаков и атрибуты (какое значение куда пишется). Загружает их из файла |
| Инженер КИПиА | Flux → E3Flux, рядом открыт E3.series | Задаёт профиль автоматизации проекта, выбирает установку или изделие, отвечает на признаки, которых нет в подборе ОВ, раскладывает на холсте, выгружает в E3, потом достраивает схему в E3 руками и запускает свои скрипты |
| E3.series | Компьютер инженера КИП | Своя база блоков типовых решений, компонентов и атрибутов, свои скрипты (ФСА, подвал, таблица TAGов). Принимает команды Flux через COM |

## 3. Сценарий целиком

1. ОВ загрузил расчёт и подобрал оборудование: установка П1 с клапаном,
   фильтром, нагревателем и вентилятором. Теги поставлены, характеристики
   есть.
2. Инженер КИП открывает E3.series, свой проект и пустой лист.
3. Во Flux — «Оборудование» → установка П1 → **«Выгрузить в E3.series»**
   (или «Пуск» → E3Flux). Открывается окно E3Flux с выбранной установкой.
4. E3Flux подключается к запущенному E3 и показывает в шапке:
   «E3.series 2025 · проект „Корпус 3 — ВК“ · лист 12 (А3)».
5. Слева — установка П1 и её состав. У каждого узла видны название, тег,
   подобранное типовое решение («Клапан_К24_КП2_ПОК_ОП») и атрибуты E3 со
   значениями. Признаки, которых нет в подборе ОВ (ПЧ в шкафу или вне,
   датчик или реле), взяты из профиля автоматизации проекта; если профиль
   ещё пуст, E3Flux сначала спрашивает его.
6. Инженер нажимает «Разложить» (или перетаскивает блоки сам). На
   холсте справа появляется установка по ходу воздуха: «Начало
   установки», клапан, фильтр, нагреватель, вентилятор, «Конец
   установки» — в масштабе 1:1 к листу E3.
7. **«Демонстрация»**: Flux спрашивает у E3, как выглядит каждый блок, и
   холст рисует настоящие блоки, обозначения и подписи атрибутов.
8. Инженер правит: меняет подобранное решение или ответ на признак,
   двигает блоки, добавляет второе изделие или вторую установку.
9. **«Выгрузить в E3.series»**: в E3 на открытом листе появляются блоки
   типовых решений с изделиями, обозначениями и заполненными атрибутами,
   на тех же местах, что на холсте. У каждого изделия в
   `GLOBAL_ID_IN_PROJECT` — ID позиции Flux, у блока — ID узла.
   Служебные атрибуты (номер на ФСА, подвал, итоги сигналов) инженер
   получает своими скриптами E3, как сейчас.
10. Flux сохраняет запись выгрузки: что, куда, с какими значениями.
11. Через неделю ОВ переподбирает вентилятор. В карточке позиции и в
    E3Flux появляется «изменилось после выгрузки в E3». Инженер КИП
    открывает E3Flux, видит разницу «было → стало» и выгружает заново.
    Меняется только то, что изменилось. Положение блоков и проводка,
    которую инженер нарисовал руками, остаются.

## 4. Устройство

```
┌──────────── Flux: окно E3Flux (renderer) ──────────────┐
│ установки и позиции │ холст листа │ свойства позиции   │
└──────────┬───────────────────────────────┬─────────────┘
           │ HTTP (как все разделы)        │ IPC (только настольная версия)
┌──────────▼──────────────┐     ┌──────────▼───────────────────────────┐
│ Сервер Flux, общая база │     │ Electron main → мост E3              │
│ • оборудование, теги    │     │ долгоживущий помощник (C#),          │
│ • типовые решения E3    │     │ как нативный помощник Проводника     │
│ • атрибуты, профиль     │     │ (electron/nativeShellSource.ts)      │
│ • связи и выгрузки      │     └──────────┬───────────────────────────┘
└─────────────────────────┘                │ COM: CT.Application
                                ┌──────────▼───────────┐
                                │ E3.series у инженера │
                                └──────────────────────┘
```

- **С E3 говорит только компьютер инженера.** Сервер Flux к E3 не
  подключается: E3 стоит на рабочем месте, а сервер у каждого сотрудника
  свой, база общая.
- **Мост — долгоживущий помощник,** а не PowerShell на каждую команду.
  COM-вызовов на одну установку сотни, и запуск PowerShell на каждый
  растянул бы выгрузку на минуты. Шаблон уже есть: C# через Add-Type в
  `electron/nativeShellSource.ts`, тот же «нативный помощник этапа A» из
  `docs/explorer-windows11.md`.
- **Мост ничего не решает.** Он выполняет простые команды: «найди
  блок в базе», «поставь блок в точку», «запиши атрибут», «прочитай всё,
  у чего есть ID Flux». Подбор, сравнение и план
  считаются в общем модуле `e3/` — чистом TypeScript без COM, по примеру
  `equipment/`. Поэтому они проверяются в контейнере без E3.
- **Браузерная версия** (без Electron) открывает E3Flux только для
  подготовки: подбор, атрибуты, раскладка без демонстрации. Кнопки
  «Демонстрация» и «Выгрузить» неактивны, с объяснением «нужна настольная
  версия Flux на компьютере с E3.series».

### 4.1 Команды моста

Минимальный набор. Точные имена методов COM сверяются на установленной
версии E3 до начала этапа C (раздел 13).

| Команда | Что делает в E3 | Зачем |
|---|---|---|
| `status` | Какие E3 запущены, версия, открытый проект, активный лист, формат листа | Шапка E3Flux и проверки перед выгрузкой |
| `projectKey` | Читает или ставит атрибут проекта `FLUX_PROJECT` (uuid) | Узнавать проект E3 надёжнее, чем по пути к файлу: путь меняется при копировании и переносе |
| `listParts` | Блоки типовых решений, компоненты и символы базы E3; состав блока (какие изделия внутри) | Есть ли блок в базе E3, сопоставление изделий блока с подпозициями Flux (5.4) |
| `attrDefs` | Определения атрибутов базы E3 | Проверка списка атрибутов |
| `preview` | Ставит блоки на временный лист, выгружает их изображение и габариты и удаляет лист | «Демонстрация» |
| `sheetOccupancy` | Габариты того, что уже стоит на листе | Холст показывает занятые места |
| `readBound` | Все блоки с `FLUX_BLOCK` и изделия с ID Flux: решение, обозначение, лист, координаты, атрибуты | Повторная выгрузка, сверка ручных правок |
| `apply` | Выполняет план выгрузки по шагам и после каждого шага сообщает, что сделано | Выгрузка |

### 4.2 Где лежит код

Расписывается по `flux-architecture` перед этапом A. Набросок:

- `e3/` — общий чистый модуль: признаки и выбор решения, расчёт
  атрибутов, раскладка, план выгрузки и сверка;
- `server/routes/e3*.ts` — типовые решения, атрибуты, профиль, связи,
  выгрузки;
- `electron/e3Bridge*.ts` — мост и его C#-источник;
- `src/screens/e3flux/` — окно программы;
- страница `docs/methodology/03-programs/e3flux.md` — пишется до
  раскладки в коде, по шаблону раздела 03.

### 4.3 Что умеет API E3.series и что проверить

E3.series управляется через COM — тот же интерфейс, которым пользуются
скрипты отдела КИП (ФСА, подвал, таблица TAGов). Отдельная серверная
часть или обмен файлами не нужны: мост работает с уже запущенным E3 на
компьютере инженера, от его имени и с его лицензией.

| Что нужно E3Flux | Через API | Уверенность до проверки |
|---|---|---|
| Подключиться к запущенному E3, узнать проект, лист, формат | Объект приложения и проекта, листы | Высокая: на этом стоят все скрипты E3 |
| Читать и писать атрибуты изделий, блоков, листов, проекта | `GetAttributeValue` / `SetAttributeValue` у объектов | Высокая: так работают нынешние скрипты |
| Писать обозначение изделия (`Device Designation`) | Отдельный вызов имени устройства, не атрибут | Высокая |
| Читать базу E3: список блоков, компонентов, определений атрибутов | Объекты базы данных и компонентов | Средняя: зависит от того, как в базе хранятся типовые решения — как блоки базы или как файлы `.e3p` |
| Поставить типовое решение в точку листа | Вставка блока или подсхемы из базы, либо импорт `.e3p` в точку | Средняя: способ выбирается по тому, где лежат решения; **вставка символа из базы подтверждена пробой 8 октября 2026 — высокая**, для устройства по компоненту не подтверждена |
| Найти поставленное по атрибутам связи, прочитать координаты | Обход устройств и блоков проекта | Высокая |
| Изображение блока для демонстрации | Экспорт листа или области в картинку / PDF / DXF | Средняя: набор форматов экспорта зависит от версии |
| Заменить блок на месте с сохранением проводов | Удалить старый, поставить новый в ту же точку, переподключить по выводам | Средняя: переподключение проводов — самая сложная часть, проверяется отдельно |
| Запустить скрипт E3 после выгрузки | Вызов скрипта из COM | Низкая: нужно проверить; без этого инженер запускает скрипт сам, как сейчас |

Итог: всё, что нужно для подбора, выгрузки, повторной выгрузки и сверки,
идёт через API. Под вопросом только способы, а не возможность: как именно
вставляется блок, в каком формате выгружается картинка, переподключаются
ли провода. Это выясняется в первые дни этапа C на компьютере с E3.
Если какой-то вызов окажется недоступен, запасной путь — небольшой скрипт
внутри E3, который мост запускает и которому передаёт данные. Так уже
устроены скрипты отдела.

Подтверждено пробой на ПК владельца (E3.series 2023, exe 2022, PowerShell 5.1), 8 октября 2026:

- вставка символа на активный лист: `Symbol.Load(имя_символа, "1")`, затем `Symbol.Place(id_листа, x, y, "0")` вернул id нового символа (45 мс); активный лист — `Job.GetActiveSheetId`;
- чтение проекта, листов, устройств (`Job.GetAllDeviceIds(ref)`) и атрибутов — около 1,2 мс на устройство; `FLUX_PROJECT` пишется и читается обратно.

Подводные камни моста:

1. Значения из конвейера PowerShell уходят в COM как PSObject и дают DISP_E_TYPEMISMATCH — разворачивать в базовый тип.
2. У Job есть собственный метод `GetType()`: на COM-объекте E3 `.GetType()` звать нельзя, вызов — через `[System.__ComObject].InvokeMember`.
3. На неудачу E3 возвращает 0 (SetId, Load, Create), исключения нет — успех только по ненулевому результату.
4. `Component.GetVersion` возвращает версию с пробельным хвостом («1   ») — обрезать.
5. У `Symbol.Place` поворот — строка.
6. Списков компонентов и символов базы в COM API нет: база E3 — Access (`components.mdb`, `symbols.mdb`, ACE OLEDB), читать только на чтение.
7. `CT.Dispatcher` не зарегистрирован; подключение — через `Marshal.GetActiveObject("CT.Application")`.

Ещё не подтверждено: экспорт листа (`Sheet.Export` / `Sheet.ExportImage` / `Job.ExportPDF` — какие строки формата принимает) и создание устройства по компоненту (`Device.Create`, 6 аргументов).

### 4.4 Три открытых способа: варианты и выбор

Окончательно выбирается на компьютере с E3 в начале этапа C. Ниже — что
берётся первым и чем его заменить, если не выйдет.

**Как поставить типовое решение в точку листа**

| Вариант | Как | За | Против |
|---|---|---|---|
| **А. Из базы E3** | Блок хранится в базе изделий E3, мост ставит его в точку листа так же, как инженер вставляет его руками из дерева базы | Один источник, версии ведёт база E3. По описанию `GLOBAL_BLOCK_ID` («ID типовой схемы в БД изделий в Екубе») решения уже лежат в базе | Если какого-то решения в базе нет, его не поставить |
| Б. Импорт `.e3p` | Мост импортирует файл оригинала в точку листа | Не нужна запись в базе | Нужен общий доступ к файлам; файлы и база расходятся по версиям; при импорте E3 переименовывает совпавшие обозначения; медленнее |
| В. Копия из шаблонного проекта | Открыть проект со всеми решениями, скопировать блок | — | Хрупко: зависит от буфера обмена и второго открытого проекта |

**Выбор: А.** Б остаётся запасным для решения, у которого в каталоге
указан файл оригинала, а в базе его нет. В любом варианте после вставки
мост сразу переименовывает изделия блока по тегам Flux: E3 даёт им
обозначения по умолчанию («-M1»), и без переименования они совпадали бы с
соседними.

**Как получить изображение для «Демонстрации»**

| Вариант | Как | За | Против |
|---|---|---|---|
| **А. Геометрия через API** | Мост читает линии, дуги, тексты и выводы поставленного блока с координатами, Flux сам рисует их в SVG | Чёткость при любом масштабе; известны точки выводов (нужны для проводов) и места текстов (атрибуты на холсте встают туда же, где будут в E3) | Больше вызовов на блок; что-то из графики (заливки, вложенные символы) может не читаться |
| Б. Векторный экспорт | Временный лист выгружается в DXF / SVG / EMF / PDF, Flux переводит в SVG | Картинка ровно как в E3 | Нет выводов и мест текстов; формат зависит от версии E3 |
| В. Растровый экспорт | PNG / BMP области листа | Проще всего | Мутная при увеличении, ничего не знает о блоке |

**Выбор: А, с Б как дополнением.** Если геометрия читается неполно, фон
берётся из векторного экспорта, а выводы и места текстов — из API. В —
только если ни А, ни Б не работают. Результат кешируется в SVG (7.2),
поэтому цена вызовов платится один раз на решение.

**Как сохранить провода при замене блока**

Чаще всего замена не нужна: при переподборе меняется мощность или ток, а
решение остаётся тем же, и обновляются только атрибуты (С1, С2). Замена
нужна, когда сменился признак (пружина → реверс, датчик → реле), — С3.

| Вариант | Как | За | Против |
|---|---|---|---|
| **А. Замена с переподключением по выводам** | Перед удалением мост запоминает, какой провод к какому выводу старого блока подходил. Ставит новый блок в ту же точку и подключает провода к выводам с тем же именем, затем — с тем же сигналом (`!Pin_OpisaniePR_tip_signala`, `SIGNAL_TAG`), затем — в той же точке | Автоматически, понятный результат | Выводы, которых в новом блоке нет, остаются висящими |
| Б. Правка внутри блока | Сравнить состав старого и нового решения: общие изделия (двигатель) не трогать вовсе, лишние удалить, недостающие (датчик) добавить | Сохраняется больше всего, включая ручные правки внутри блока | Сложнее всего; блок перестаёт совпадать с решением базы, и следующая замена угадывает хуже |
| В. Рядом, без переподключения | Новый блок ставится рядом, старый помечается «заменён», провода переносит инженер | Ничего не ломается | Вся работа руками |

**Выбор: А, с предпросмотром.** До записи E3Flux показывает план проводов:
«провод W12: вывод 3 → вывод 3», «провод W14: вывода „КП2“ в новом блоке
нет — останется висеть». Инженер подтверждает план. Висящие провода
перечисляются в отчёте, а в E3 помечаются атрибутом, чтобы их нашёл
поиск. Если выводы не совпали совсем, E3Flux сам предлагает В. Б —
возможное развитие, когда А проверено на настоящих схемах.

Насколько хорошо работает А, зависит от того, одинаково ли названы
выводы в похожих решениях («Клапан_КР24» и «Клапан_К24»). Это видно по
базе E3: сверка 5.8 показывает, у каких пар решений выводы расходятся.

В каталоге появляется раздел **«E3.series»** с вкладками «Типовые

### 5.1 Что ставится в схему: типовое решение, а не компонент

В E3 ставится не отдельное изделие, а **типовое решение** — готовый блок
схемы (`.e3p`). Например, «Вентилятор_ПЧИД_К_РТС_ОСВ» — это вентилятор с
частотником в шкафу, датчиком 4–20 мА, дополнительной коробкой, двумя
выводами PTC и освещением секции. Внутри блока уже стоят все его изделия:
двигатель, датчик, внешние контакты.

Поэтому соответствие строится не «позиция Flux → компонент E3», а **«узел
установки Flux → типовое решение»**.

**Решение владельца (8 октября 2026), дословно:** «в классификаторе имя схемы
— это и есть название в E3». Единица вставки — само типовое решение: поле
`E3Solution.name` («Название схемы») и есть имя блока в базе E3; отдельного
«имени изделия E3» у строк «Таблицы IO» не требуется. Решение без названия
схемы — пробел `solution-no-name` (вставлять нечего).

```
Flux                                   E3
установка П1 ──────────────────────▶ «Начало_2УР_ПВ_Р» … «Конец_2УР_ПВ»
  блок «Вентилятор» (узел) ─────────▶ блок «Вентилятор_ПЧИД_К_РТС_ОСВ» (08.xx)
    вентилятор                          ├ двигатель 3Ф + PTC   ◀─ атрибуты MOTOR_*
      двигатель ─── атрибуты ─────────▶ ├ датчик 4–20 мА       ◀─ заполняет КИП
                                        └ внешние контакты
  блок «Клапан» ────────────────────▶ блок «Клапан_К24_КП2_ПОК_ОП»
    клапан → привод ─── атрибуты ─────▶ └ привод               ◀─ атрибуты DRIVE_*, SIGNAL_*
```

Колонки классификатора и что из них берёт Flux:

| Колонка файла | Во Flux | Как используется |
|---|---|---|
| Уникальный ID типового решения («08.01.38») | ID решения | Ключ. По нему решение находится при повторной загрузке файла. В E3 блок несёт его сам в `GLOBAL_BLOCK_ID` |
| Основной класс («Клапаны») | Класс решения | Связь с типом Flux (5.3) |
| Класс («Клапан с электроприводом. Возвратная пружина») | Подкласс | Группировка в выборе |

| Название схемы («Клапан_К24_КП2_ПОК_ОП») | Имя блока в базе E3 | Что ставить. Блок несёт его в `GLOBAL_BLOCK_NAME` |
| Описание схемы | Описание | Видно при выборе: человек выбирает по нему |

### 5.2 Признаки: как выбрать одно решение из сотни

Внутри класса решения различаются признаками, и признаки зашиты в
название. Словарь — лист «Обозначения». Например, у вентиляторов 123
решения: способ пуска (ПП, ПП230, ЗТ, УППИ, УППВ, ПЧИ, ПЧВ), контроль
(без, Д — датчик 4–20 мА, Р — реле перепада), коробка (К), защита
двигателя (РТС, 2РТС, ТК), БРНО, сервисный выключатель (СВ), освещение
(ОСВ), поворот (Влево).

Признак — это вопрос с вариантами ответа, например «Способ пуска
двигателя: ПП / ПП230 / ЗТ / УППИ / УППВ / ПЧИ / ПЧВ / ЕС». У каждого
типового решения в каталоге записаны **явные ответы** на признаки своего
класса.

**Откуда берутся ответы.** Признаки делятся на три вида, и это главное
для «схема формируется сама, но всё можно выбрать»:

| Вид признака | Примеры | Откуда ответ |
|---|---|---|
| **Из подбора ОВ** — свойство изделия | Напряжение привода 24 / 230 В; пружина / реверс / плавное регулирование / электромагнит / ТРУ; число приводов на клапане (1, 2, 3 — «2К24», «3КПР24»); число EC-вентиляторов в блоке (1–12); 1 фаза или 3 фазы; EC-двигатель; PTC или ТК у двигателя; нагреватель электрический или жидкостный, число ступеней; фильтр одинарный или двойной; обогрев клапана; концевые выключатели КП1 / КП2 | Характеристики, вид и состав позиции Flux — по правилу (5.3) |
| **Решение КИП по проекту** — одно на весь проект | Где ставится ПЧ или УПП: в шкафу или вне шкафа; датчик 4–20 мА или реле перепада на фильтрах и вентиляторах; ставить ли дополнительные коробки; сервисный выключатель | **Профиль автоматизации проекта** (5.6): задаётся один раз и подставляется во все позиции |
| **Раскладка** | Поворот «Влево»; одно- или двухуровневая установка | Из места на листе: вытяжная линия идёт справа налево, приток слева направо (7.1) |

**Как выбирается решение:**

1. Отбор по классу: позиция Flux «Клапан» → решения класса «Клапаны».
2. Ответы на признаки собираются из трёх источников. Порядок силы:
   ручной ответ инженера КИП → ответ из подбора ОВ → профиль проекта.
3. Остались решения, у которых все заданные признаки совпадают.
   - **Одно** — оно и ставится. В свойствах позиции видно, почему: «24 В
     (из характеристики „Напряжение“), пружина (вид привода), КП2
     (профиль проекта), обогрев клапана (характеристика „Обогрев“)».
   - **Несколько** — на какой-то признак ответа нет. E3Flux спрашивает
     именно его («Концевые выключатели: КП1 / КП2?»), а не предлагает
     выбрать из списка 20 названий.
   - **Ни одного** — такой комбинации в классификаторе нет. Показываются
     ближайшие решения и чем каждое отличается: «Клапан_К24_КП2 — нет
     обогрева клапана». Можно выбрать ближайшее или завести недостающее
     решение в каталоге.
   - **Решение есть в каталоге, а блока с таким названием в базе E3 мост
     не нашёл** — выбрать можно, а выгрузить нельзя: «Блок не найден в
     базе E3». Обычно это опечатка в названии или новое решение, ещё не
     нарисованное в E3.
4. Ручной выбор решения целиком сильнее всех правил. Он запоминается за
   позицией (по ID) и остаётся при переподборе, пока тип позиции не
   сменился (случай С15 раздела 9).

Признаки **разбираются из названий автоматически** при загрузке файла, но
только как предложение. Названия неоднозначны, и это видно на самих
файлах:

- «К» у вентилятора и фильтра значит «коробка», а у клапана «К24» —
  «клапан с пружинным возвратом 24 В»;
- одни и те же признаки в одном классе пишутся «влево», в другом —
  «Влево»;
- у одного нагревателя код «K» латинский, у остальных «К» кириллический;
- цифры после «_» у EC-вентиляторов означают число вентиляторов, у
  нагревателей — число ступеней, у узлов регулирующих — диапазон.

Поэтому администратор просматривает разбор и подтверждает его один раз.
Дальше признаки хранятся в каталоге явно, рядом с решением. Новое решение,
добавленное позже, разбирается так же.

Признаки хранятся в каталоге Flux, исходнике данных (5.0). При выгрузке
каталога в Excel они выходят отдельными столбцами, по столбцу на признак
класса. Если такую таблицу загрузить обратно, разбор названий уже не
нужен.

**Признаки настраиваются в каталоге, а не зашиты в код.** Администратор
заводит признак класса («Способ пуска»), его варианты («ПП, ЗТ, ПЧИ…»),
подсказку и вид (из подбора ОВ / профиль проекта / раскладка). Так же
настраиваются словарь обозначений (лист «Обозначения») и правила 5.3.
Новый класс решений или новый признак не требует правки программы.

### 5.3 Правила: признак из подбора ОВ

Правило отвечает: «как из данных позиции Flux получить ответ на признак».
Правила ведутся в каталоге по классам:

| Класс | Признак | Источник во Flux | Правило |
|---|---|---|---|
| Клапаны | Напряжение | Характеристика привода «Напряжение питания» | 24 → «24»; 220/230 → «230» |
| Клапаны | Тип привода | Вид привода (`equipKind`) и модель каталога | «С возвратной пружиной» → К; «Без пружины» → КР; сигнал 0–10 В → КПР |
| Клапаны | Число приводов | Число подпозиций ПРИВОД у клапана | 1 → «», 2 → «2», 3 → «3» |
| Вентилятор | EC | Вид двигателя | «EC» → класс «Вентилятор ЕС» |
| Вентилятор ЕС | Число вентиляторов | Число подпозиций ВЕНТИЛЯТОР в блоке | 1…12 |
| Вентилятор | Фазы | Напряжение двигателя | 230 → ПП230; 380/400 → 3Ф |
| Вентилятор | Защита двигателя | Характеристика «Термозащита» | PTC → РТС; термоконтакт → ТК |
| Фильтры | Двойной | Число ступеней фильтрации в блоке | 2 → «2 шт» |

Тип позиции Flux связан с основным классом классификатора таблицей:
ВЕНТИЛЯТОР → «Вентилятор» / «Вентилятор ЕС», КЛАПАН → «Клапаны», ФИЛЬТР →
«Фильтры», НАГРЕВАТЕЛЬ → «Нагреватель», ОХЛАДИТЕЛЬ → «Охладитель»,
РЕКУПЕРАТОР → «Теплоутилизатор», УВЛАЖНИТЕЛЬ → «Увлажнители», ОБВЯЗКА →
«Узел регулирующий», ДАТЧИК → «Датчики», УСТАНОВКА → «Начало установки»
и «Конец установки». Связь правится в каталоге: типы Flux
(`equipment/classes.ts`) и классы файла называются по-разному и
меняются независимо.

**Какой узел Flux становится решением.** Решение ставится на позицию того
уровня, где в составе Flux стоит изделие целиком: на вентилятор (а не на
его двигатель), на клапан (а не на привод). Подпозиции (двигатель,
привод, датчик) — это изделия внутри блока, и в них пишутся атрибуты.
Если в блоке Flux несколько вентиляторов, а решение EC-класса рассчитано
на «N вентиляторов», ставится одно решение на блок с N = числу
вентиляторов, а не N решений.

### 5.4 Изделия внутри решения

Колонка «Список изделий» перечисляет, что лежит в блоке: «Двигатель
3Ф+PTC; Внешний контакт NC //авария; …; Датчик 4–20 мА». Сейчас она
заполнена у 3 решений из 471.

Каждое изделие блока бывает одного из видов:

| Вид | Пример | Атрибуты |
|---|---|---|
| **Соответствует позиции Flux** | Двигатель ↔ подпозиция ДВИГАТЕЛЬ; привод ↔ подпозиция ПРИВОД | Из Flux (MOTOR_*, DRIVE_*, GLOBAL_*). `GLOBAL_ID_IN_PROJECT` = ID позиции Flux |
| **Есть только у КИП** | Датчик перепада давления, реле, термостат | Тег и общие атрибуты — от владельца-узла; INST_*, SIGNAL_* вводит КИП в E3Flux, хранятся во Flux. ID — составной: ID узла Flux + номер изделия в блоке |
| **Служебное** | Внешние контакты, клеммы | Только служебные атрибуты |

Состав блока по правилам (`e3/recipe.ts`) выводится из решения, его признаков и
таблицы IO: правило называет роль изделия, строку IO и сколько штук; результат
показывает «Состав блока» в окне подбора. У решения можно задать состав
вручную — он сильнее правил.

Сопоставление «изделие блока ↔ подпозиция Flux» задаётся в карточке
решения: по роли (двигатель, привод), а при нескольких одинаковых — по
порядку. Мост может прочитать состав блока из базы E3 и предложить
сопоставление сам, но подтверждает его администратор.

### 5.5 Атрибуты

Колонки «Списка атрибутов» и что из них берёт Flux:

| Колонка файла | Во Flux | Как используется |
|---|---|---|
| Наименование атрибута E3 («MOTOR_POWER») | Имя | Ключ: по нему пишется значение |
| Описание атрибута («MOTOR_Мощность») | Подпись | Видно инженеру в E3Flux |
| Носитель (Изделие, Блок, Лист, Пин) | Носитель | На чём писать: на изделие блока, на сам блок, на лист |
| Основной класс (Общий, Двигатели, КИП, Привод, Кабель…) | Класс атрибута | Набор атрибутов изделия: двигателю — Общий + Двигатели |
| Служебный (не менять!) | Служебный | Без «Да» Flux его не пишет: его считает скрипт E3 (номер на ФСА, итоги сигналов, номер листа). С «Да» — спорный случай, ниже |
| Скрипт, где применяется | Справка | Видно в карточке атрибута |
| Комментарии (свой, ВЕЗА, ВЕЗА2), дата изменения | Справка | Видно в карточке |
| Первая колонка без заголовка («Да» у 108 строк) | Заполняет Flux | «Да» — значение приходит из Flux; пусто — Flux атрибут не трогает |

**Кто заполняет атрибут — первый столбец файла.** «Да» в столбце без
заголовка значит «значение приходит из Flux». Пусто — Flux атрибут не
трогает: его заполняет скрипт E3 или инженер в E3, либо он остаётся пустым.
Это поле каталога «Заполняет Flux», и загрузка берёт его из файла.

| | Атрибутов | Что это |
|---|---|---|
| **«Да» — заполняет Flux** | 108 | Общие (теги, названия, марка, модель, описание), двигатели, нагреватели, освещение и климат, силовая техника, комплектные изделия, «чёрный ящик», КИП, КИП ЗРА, сигналы и привод |
| Пусто, служебный | 21 | Номер на ФСА, итоги и резерв сигналов подвала, листы. Считают скрипты E3 |
| Пусто, не служебный | 27 | Кабели (`CBL_*`, 15), кабельные вводы (`CBLENT_*`, 4), клеммы КИП (`INST_CLAMP_1/2`), резерв сигналов ПЛК, формат листа, шифр документа, IP, `GLOBAL_BLOCK_NAME`, `GLOBAL_ID_IN_PROJECT`. Заполняются в E3 |

**Откуда Flux берёт значение для атрибута с «Да».** Источник ставится в
каталоге у каждого из 108:

| Источник | Атрибуты | Откуда значение |
|---|---|---|
| **Тег и состав** | `Device Designation` (служебное поле E3, а не атрибут), `GLOBAL_TAG_UNIT`, `GLOBAL_TAG_UNIT_SHORT`, `GLOBAL_UNIT_NAME`, `GLOBAL_TAG_NODE`, `GLOBAL_NODE_NAME`, `GLOBAL_TAG_DEVICE_SHORT`, `GLOBAL_DEVICE_NAME`, `GLOBAL_DESCRIPTION_*` | Тег позиции, тег узла-владельца, тег установки (`equipment/composition.ts`: «родитель — тег ближайшего тегированного владельца»). Уровни E3 «установка → узел → устройство» совпадают с деревом тегов Flux |
| **Характеристики подбора ОВ** | `MOTOR_*`, `ELH_*`, `LC_*`, `PEQ_*`, `COMPRO_*`, `BLACKB_*` (мощность, напряжение, род тока, токи, косинус, КПД) | Характеристика позиции по коду (`sourceGroup`/`sourceKey`) с преобразованием |
| **Каталог** | `GLOBAL_BRAND`, `GLOBAL_MODEL`, `GLOBAL_ARTICLE`, `GLOBAL_MANUFACTURER`, `GLOBAL_MATERIAL`, `GLOBAL_CLIMATE_VERSION`, `GLOBAL_EXP_VERSION`, `INSTSCV_*` | Модель каталога, привязанная к позиции |
| **Проект** | `GLOBAL_TAG_TITLE`, `GLOBAL_TITLE_NAME` (титул, здание) | Реквизиты проекта или установки |
| **Данные КИП во Flux** | `INST_*` (диапазоны, уставки, единицы, присоединения, обогрев, HART), `SIGNAL_*` (тип и характеристика сигнала, тег сигнала, клеммы), `DRIVE_*`, `Clamp_Recommendation` | У ОВ этих данных нет. Их вводит инженер КИП **в E3Flux**, и они хранятся во Flux за позицией, а не только в E3: при повторной выгрузке и переподборе они не теряются. Значения по умолчанию — из профиля проекта (5.6), из типового решения (тип сигнала привода известен по решению: пружинный клапан — DI 2, DO 1 по «Таблице IO») или из модели датчика в каталоге |

Атрибут с «Да», для которого источник ещё не задан или значения нет,
E3Flux показывает пустым с пометкой «нет данных», а не пропускает молча.
Обязательность (выгрузка без него запрещена) — отдельная отметка
каталога, по умолчанию выключена.

**Что не сходится в файле и требует решения владельца** (раздел 13):

- **12 атрибутов отмечены и «Да», и «Служебный (не менять!)»:**
  `GLOBAL_TAG_UNIT` (обе строки), `GLOBAL_DEVICE_TYPE`, `Device
  Designation`, `GLOBAL_TAG_TITLE`, `!Dev_OpisaniePR_AI/AO/DI/DO`
  («генерится скриптом»), `SIGNAL_TYPE`, `SIGNAL_TAG`,
  `Clamp_Recommendation`. Кто главнее, если Flux записал значение, а скрипт
  E3 его пересчитал, **настраивается в каталоге у каждого атрибута**
  (решение владельца: «Нужно чтобы можно было все это настроить»):
  - «Пишет Flux, скрипт не трогает» — при повторной выгрузке значение
    скрипта перезаписывается значением Flux;
  - «Пишет Flux только первый раз» — дальше значение в E3 главнее;
  - «Пишет скрипт» — Flux не пишет, только показывает, что посчитал
    скрипт;
  - «Спросить» — при расхождении E3Flux показывает оба значения.
  По умолчанию для этих 12 — «Спросить», пока администратор не выберет.

**Настраивается всё, что в файле задано столбцом.** У каждого атрибута
в каталоге правятся: «Заполняет Flux» (столбец «Да»), «Служебный»,
источник значения, преобразование, обязательность, правило спора со
скриптом и с ручной правкой в E3 (С8, С19). Значения из файла — только
начальные.
- **`GLOBAL_ID_IN_PROJECT` без «Да»,** хотя по описанию это «индивидуальный
  сквозной номер (ID) изделия в проекте» — то самое место для ID позиции
  Flux (раздел 9.1). Владелец ответит позже. До ответа ID изделия
  пишется в отдельный атрибут `FLUX_ID`; переход на
  `GLOBAL_ID_IN_PROJECT` — смена одной настройки каталога.

Преобразования для значений из Flux: единицы (Вт ↔ кВт), округление,
разделитель дробной части, словарь значений (вид «С возвратной пружиной» →
`DRIVE_…` «Пружина»), род тока («AC 50Гц / AC 60Гц / DC», как в
комментарии к `MOTOR_CURRENT_TYPE`), обрезка до длины с предупреждением,
шаблон из нескольких источников, «если пусто — подставить».

**Слева в E3Flux видны уже преобразованные значения** — ровно то, что
ляжет в атрибуты. Рядом мелко — исходное значение и название
характеристики Flux.

### 5.6 Профиль автоматизации проекта

Решения КИП, одинаковые для всей установки или всего проекта, задаются
один раз, а не в каждой позиции:

- пуск двигателей вентиляторов: ПП / ЗТ / УППИ / УППВ / ПЧИ / ПЧВ — можно
  с порогом: «до 7,5 кВт — ПП, больше — ПЧИ»;
- контроль вентиляторов и фильтров: датчик 4–20 мА / реле перепада / без;
- дополнительные коробки на корпусе: да / нет;
- сервисный выключатель, освещение секций, концевые выключатели клапанов
  (КП1 / КП2), обогрев приводов;
- значения по умолчанию для атрибутов КИП (`SIGNAL_SIGNAL_CHAR` 4–20 мА и т. п.).

Профиль хранится за проектом Flux. У установки можно переопределить
отдельные пункты. Профиль правит инженер КИП прямо в E3Flux. Изменение
профиля показывает, сколько позиций подберутся иначе, до сохранения.

### 5.7 Загрузка из файла

Оба файла загружаются в каталог так же, как другие таблицы
(`flux-data-safety`):

1. Выбрать файл. Листы и столбцы распознаются по заголовкам. Для нового
   формата сопоставление показывается для правки и запоминается как
   профиль (`ImportProfile`).
2. **План:** сколько решений или атрибутов новых, изменённых и
   неизменных; какие есть в каталоге, но нет в файле; разбор признаков из
   названий (5.2) — на подтверждение; ошибки по строкам.
3. Для отсутствующих в файле — выбор: оставить / снять. По умолчанию —
   оставить. Выгруженное в E3 решение снять нельзя, пока оно стоит в
   схемах.
4. Запись одной партией. Снимок «до» — в `CatalogRevision`, откат
   возвращает всю загрузку.
5. У классификатора есть номер версии. Запись выгрузки в E3 помнит, по
   какой версии подбиралось (случай С14).

**Что загрузка найдёт в нынешних файлах.** Это не ошибки владельца, а
обычное состояние живой таблицы, и загрузка должна их показать, а не
молча проглотить:

| Файл | Что | Сколько |
|---|---|---|
| Классификатор | Повторяющиеся названия схем при разных ID: «Начало_1УР», «Конец_1УР» | 2 |
| Классификатор | «Список изделий» заполнен | 3 из 471 |
| Классификатор | Пробелы в начале и конце значений («Вентилятор с реле перепада давления ») | несколько классов |
| Классификатор | Латинская «K» вместо кириллической в признаке нагревателя | 1 |
| Атрибуты | Один атрибут дважды: `GLOBAL_TAG_UNIT`, `GLOBAL_DEVICE_TYPE` (в комментарии ВЕЗА: «Удалить, есть на строке 5») | 2 |
| Атрибуты | `GLOBAL_BLOCK_NAME` дважды с разным носителем (Блок и Изделие), во втором — пробел в конце имени | 1 |
| Атрибуты | В комментариях: «Надо создать», «Удалить» — атрибут ещё не заведён или выводится | несколько |
| Атрибуты | `Device Designation` — служебное поле E3, а не атрибут: пишется другим вызовом | 1 |
| Атрибуты | «Да» (заполняет Flux) и «Служебный (не менять!)» одновременно | 12 |
| Атрибуты | `GLOBAL_ID_IN_PROJECT` — «сквозной ID изделия», но без «Да» | 1 |

Повтор с одинаковым именем загрузка не сливает молча: строки
показываются рядом, и выбирает человек.

**Что уже сделано (справочник атрибутов, без экрана).** Логика — `e3/attributes.ts`,
маршруты — `server/routes/e3Attributes.ts` (`/api/catalog/e3-attributes`: чтение,
`plan`, `apply`, `item`, `revisions`, `undo`), проверки — `scripts/test-e3-attributes.ts`
и `scripts/test-e3-attributes-http.ts`. Справочник — одна настройка каталога
`e3_attributes` с версией: запись по старой версии получает 409, каждая запись
оставляет снимок «до» в `CatalogRevision`. Файл обновляет только свои поля
(подпись, носитель, класс, «Служебный», «Да», скрипт, комментарии); источник,
типы оборудования и правило спора — настройки Flux, их файл не трогает, а
правленное руками (`edited`) не перезаписывает. **Отличие от абзаца выше:**
повтор имени разбор пока не показывает рядом, а берёт первую строку и пишет
замечание («взята строка N»). В выгрузку атрибуты идут столбцами `e3:<имя>`
(`src/lib/exportSpec.ts`, `src/lib/equipmentExchange.ts`).

### 5.8 Сверка с базой E3

Вкладка «Связь с базой E3» работает, только когда подключён E3. Мост
читает из базы E3 блоки, компоненты и определения атрибутов. Каталог
показывает:

- решения каталога, блока которых нет в базе E3, и блоки базы E3, которых
  нет в каталоге — их можно добавить в каталог одной кнопкой (название и
  состав берутся из базы E3, признаки дописывает администратор);
- атрибуты из списка, которых нет в определениях базы E3 («Надо
  создать»): записать их E3 не даст;
- атрибуты связи Flux, которых нет в базе E3 (раздел 9.1).

Списки из базы E3 кешируются на сервере Flux с датой. Каталог можно
править на компьютере без E3, и ошибки видны по последнему снимку.

### 5.9 Таблица IO и группы продукции

- **Таблица IO** (сигналы DI/DO/AI/AO по видам устройств) нужна только для
  счёта сигналов; имя вставляемого блока она не задаёт (оно — название схемы
  решения, см. 5.1). Даёт E3Flux посчитать сигналы установки до выгрузки: «П1: DI 14, DO 7, AI 6, AO 3».
  Это то же, что потом посчитает скрипт подвала в `!Dev_Total_*`. Видно
  заранее — хватит ли контроллера. Итог по установке — необязательный шаг,
  этап после G. **Уже сделано (этап B):** лист читается и хранится в каталоге
  (раздел «Таблица IO»), по нему рецепт блока считает сигналы одного блока —
  «Состав блока» в окне подбора (см. «Автоматическое построение блоков» в
  разделе 13).
- **Группы продукции** (MR-коды ВЕЗА) помогают узнать вид установки по
  марке («ВЕРОСА» → центральный кондиционер) и подобрать «Начало
  установки». Используются как подсказка, не как правило.

## 6. Окно E3Flux

Три колонки по общему правилу «навигация → рабочая область → карточка»
(`docs/methodology/01-design.md`). Отдельная программа рабочего стола, как
«Выгрузка данных» у Оборудования: без модального фона, сворачивается и
переносится на второй монитор, рядом с E3.

### 6.1 Шапка

`E3Flux · проект Flux` · **состояние связи с E3** (точка и подпись: «E3
2025 · Корпус 3 — ВК · лист 12, А3» / «E3 не запущен» / «открыто два E3 —
выбрать») · «Обновить из Flux» · «Демонстрация» · главная кнопка
**«Выгрузить в E3.series»**.

### 6.2 Слева: что выгружать

- Переключатель вида: **«По установкам»** (установка → моноблок → узел →
  подпозиции, как в Оборудовании) / **«По типам»** (все клапаны, все
  вентиляторы проекта — удобно выгружать однотипное разом).
- Поиск по тегу, названию, обозначению E3, названию типового решения.
- Над списком — **профиль автоматизации** установки одной строкой («ПЧ в
  шкафу · датчики 4–20 · КП2 · коробки») со ссылкой на правку (5.6).
- Строка узла: название, тег, подобранное типовое решение и состояние:

| Знак | Состояние | Значит |
|---|---|---|
| ○ | Не в схеме | Ещё не выгружался в этот проект E3 |
| ● | В схеме | Выгружен, с тех пор не менялся |
| ◐ | Изменился | Во Flux изменился после выгрузки (переподбор, новый тег, профиль, классификатор) |
| ✕ | Снят | Во Flux снят, а в схеме ещё стоит |
| ? | Нужен ответ | Не хватает признака, чтобы выбрать одно решение |
| ! | Нельзя выгрузить | Решения нет, или блока нет в базе E3 |
| ⇄ | Правлен в E3 | В E3 значение атрибута отличается от выгруженного |

- Раскрытие узла — изделия типового решения (двигатель, датчик, привод) и
  их атрибуты с «Да» с готовыми значениями. Пустые помечены «нет данных».
- Флажок у строки — «брать в выгрузку». Установка отмечается целиком, и
  отметку можно снять с отдельных узлов (например, шумоглушитель: для
  него типового решения нет и не нужно).
- Позиции Flux без типового решения по природе (шумоглушитель, секция,
  камера) в список выгрузки не попадают, а видны свёрнутой строкой
  «не участвуют в схеме: 3».

### 6.3 Середина: холст листа

См. раздел 7.

### 6.4 Справа: свойства выбранного

- **Типовое решение:** ID и название («08.01.38 ·
  Клапан_К230_КП2_ПОК_ОП»), описание, ссылка на PDF; **признаки** — по
  строке на признак: ответ и откуда он («230 — характеристика
  „Напряжение“ привода», «КП2 — профиль проекта»). Любой ответ можно
  поменять, и решение тут же пересчитывается. «Выбрать другое решение» —
  список решений класса с описаниями и отличиями от текущего.
- **Атрибуты** изделий решения — только с «Да»: имя E3, значение,
  источник. Пустые значения КИП вводит здесь же, и они сохраняются во
  Flux за позицией. Значение из Flux можно переопределить; переопределение
  помечается «вручную».
- **Обозначение** в E3: тег позиции; проверка на повтор в проекте E3.
- **Связь:** в каком проекте E3 и на каком листе узел уже стоит, когда
  выгружен, кем, по какой версии позиции и какой версии классификатора.

### 6.5 Где начинать

- «Оборудование» → установка или позиция → «Выгрузить в E3.series» —
  E3Flux открывается с этим выбором.
- «Пуск» → E3Flux — с последним проектом и пустым выбором.
- Карточка позиции, строка «В схеме E3: Корпус 3 — ВК, лист 12, −M1 ·
  изменилась после выгрузки» — открывает E3Flux на этой позиции.

## 7. Холст

- **Лист в масштабе листа E3.** Формат, рамка и рабочее поле читаются из
  E3 (`status`). Координаты холста — миллиметры листа E3, с тем же началом
  отсчёта и той же сеткой. То, что стоит на холсте в точке (120, 85), в E3
  встанет в (120, 85).
- **Занятое на листе** (рамка, штамп, подвал, то, что инженер уже
  нарисовал в E3) показывается серыми областями (`sheetOccupancy`).
  Положить туда блок нельзя: холст предупредит.
- **Раскладка вручную:** перетащить узел слева на холст, двигать,
  выравнивать. Привязка к сетке E3. Поворот — не вращением, а выбором
  варианта решения «Влево», если он есть в классификаторе.
- **Несколько изделий:** можно добавить вторую установку или отдельное
  изделие. Каждая установка — своя группа, её можно двигать целиком.
- **Не помещается:** холст показывает переполнение и предлагает «Перенести
  на новый лист» (вкладка листа над холстом). Новый лист создаётся в E3
  только при выгрузке, с форматом текущего.
- **До демонстрации** блок на холсте — прямоугольник своего габарита
  (из кеша; если ещё не известен — условный) с названием решения и тегом.
- **«Демонстрация»** заменяет прямоугольники настоящими блоками (7.2).
- **Уже выгруженное** на холсте берётся из E3 (`readBound`): если инженер
  сдвинул блок в E3, на холсте он стоит там же. Источник положения —
  E3, а не запись Flux.

### 7.1 «Разложить»: по ходу воздуха

Функциональная схема автоматизации рисуется так, как идёт воздух в
установке, — это видно на листе «PID на тестовую систему»: слева
воздухозаборный клапан, дальше фильтр, нагреватель, охладитель,
вентилятор, справа выход. «Разложить» повторяет это:

- **Порядок** — порядок узлов в составе установки Flux (`sourceOrder`:
  расчёт ВЕЗА перечисляет секции по ходу воздуха). Инженер может
  переставить узлы в списке, и порядок запомнится за установкой.
- **Начало и конец.** Слева ставится «Начало установки», справа — «Конец
  установки». Вариант выбирается по составу: одна линия — «1УР»; приток и
  вытяжка — «2УР»; есть рекуператор — «_Р» (`Начало_2УР_ПВ_Р`).
- **Две линии.** У двухуровневой установки приток — верхняя линия слева
  направо, вытяжка — нижняя справа налево. Для вытяжной линии берётся
  вариант решения «Влево», если он есть. Если нет — блок ставится как
  есть, а в списке видно «нет варианта „Влево“».
- **Общие узлы** двух линий (рекуператор, двухуровневые решения
  «Двухуровневая схема = Да») ставятся между линиями.
- **Шаг** между блоками — по их габаритам из кеша, с отступом под
  обозначения. Блоки, которые инженер поставил руками, «Разложить» не
  двигает.

### 7.2 Демонстрация

Задача — нарисовать блок так, как его нарисует E3, не трогая лист
инженера. Варианты:

| Вариант | Как | За | Против |
|---|---|---|---|
| **А. Временный лист** | Мост создаёт в открытом проекте скрытый лист, ставит блоки, выгружает изображение и габариты, удаляет лист | Блок настоящий, из той же базы и версии | В проекте E3 на секунду появляется лист. Если E3 упадёт посреди демонстрации, лист останется (мост удаляет его при следующем подключении по служебному имени) |
| Б. Второй E3 | Отдельный экземпляр E3 с пустым проектом | Проект инженера не трогается | Вторая лицензия E3 и время запуска |
| В. Свои картинки | Flux хранит изображения схем (как лист «Схемы» в файле классификатора) | Не нужен E3 | Расходятся с базой E3: это ровно то, от чего владелец хочет уйти |

**Предлагается А с кешем.** Изображение и габарит блока сохраняются на
сервере Flux по ключу «база E3 + решение + версия». Второй раз тот же блок
не запрашивается: демонстрация установки, где все решения уже
встречались, идёт без обращения к E3. Атрибуты и обозначения поверх блока
холст рисует сам: их места (текстовые узлы) берутся из того же ответа.
Типовых решений 471, так что кеш со временем покрывает почти всё.

Демонстрация не обязательна. Выгружать можно и без неё: тогда раскладка
считается по габаритам блоков из кеша или по условным.

## 8. Выгрузка

### 8.1 Перед выгрузкой — проверка и план

Кнопка «Выгрузить в E3.series» сначала показывает **план**, а не пишет
сразу (`flux-data-safety`):

- проект E3 тот же, что при подготовке (по `FLUX_PROJECT`), лист тот же
  и открыт на запись;
- у каждого узла выбрано одно типовое решение, и оно есть в базе E3;
- обязательные атрибуты заполнены; пустые атрибуты с «Да» перечислены;
- служебные атрибуты не пишутся, кроме тех, где настройка каталога разрешает (5.5);
- обозначения не повторяются с уже существующими в проекте E3;
- холст не пересекает занятые области;
- **что будет сделано:** поставить N блоков, обновить атрибуты у M,
  заменить K решений, удалить L (удаление — только отмеченное инженером,
  раздел 9.3).

Ошибки блокируют выгрузку; предупреждения — нет.

### 8.2 Запись

Мост выполняет план по шагам в таком порядке: листы → блоки типовых
решений на места → обозначения изделий → атрибуты с «Да» → атрибуты
связи. После каждого блока мост сообщает, что сделано, а Flux записывает
это в журнал выгрузки.

После выгрузки инженер запускает свои скрипты E3 (ФСА, подвал, таблица
TAGов), как сейчас: они досчитают номера, итоги сигналов и листы. Запуск
скриптов из E3Flux — возможное продолжение, если владелец захочет.

- **Атрибуты связи пишутся последними.** Блок без `FLUX_BLOCK`
  означает, что запись не дошла до конца. Повтор находит такие блоки по
  отметке выгрузки и дописывает их, а не ставит вторые.
- **Обрыв посреди выгрузки** (E3 закрыли, E3 упал, Flux закрыли): запись
  выгрузки остаётся «прервана, сделано 7 из 12». При следующем открытии
  E3Flux предлагает «Продолжить» или «Убрать сделанное». Повтор по
  ключам связи не создаёт дублей.
- **Отмена выгрузки:** «Убрать из E3 то, что поставила эта выгрузка».
  Удаляются только блоки, поставленные ею, и только если инженер их не
  трогал после выгрузки: не провёл к ним провода, не правил. Иначе такой
  блок показывается в отчёте, и решает инженер. На отмену средствами
  E3 Flux не полагается: история отмены E3 через COM ненадёжна, и
  инженер мог успеть сделать что-то своё.
- **E3 занят** (открыт диалог, идёт пересчёт): COM отвечает «занято»; мост
  ждёт и повторяет. Через 30 секунд — сообщение «E3 не отвечает: закройте
  открытые окна E3» с кнопкой «Повторить».

### 8.3 После выгрузки

- Отчёт: что создано и где, что пропущено и почему.
- Запись в журнале Flux (`ActionLog`) и в истории позиции: «Выгружена в
  E3: Корпус 3 — ВК, лист 12, −M1».
- В Оборудовании у позиций появляется строка «В схеме E3». ОВ видит, что
  его подбор уже ушёл в схему КИП, и что переподбор этой позиции коснётся
  чужой работы.

## 9. Связь и переподбор

### 9.1 Как Flux узнаёт своё в E3

Атрибуты связи в E3:

| Атрибут | На чём | Значение | Есть в списке владельца |
|---|---|---|---|
| `FLUX_ID` или `GLOBAL_ID_IN_PROJECT` | Изделие | ID позиции Flux (раздел 1). Для изделий блока, которых нет во Flux (датчик КИП), — ID узла и номер изделия в блоке: `<ID узла>#2` | Какой из двух — ответ владельца позже; выбирается настройкой каталога (5.5) |
| `GLOBAL_BLOCK_ID` | Блок | ID типового решения («08.01.38») | Есть, служебный: его несёт сам блок из базы E3 |
| `FLUX_BLOCK` | Блок | ID узла Flux, на который поставлен блок | Завести — решение владельца «Да» |
| `FLUX_VER` | Блок | Версия узла и номер выгрузки | Завести — «Да» |
| `FLUX_PROJECT` | Проект E3 | uuid связи «проект E3 ↔ проект Flux» | Завести — «Да» |

`GLOBAL_BLOCK_ID` говорит, **какое** решение стоит, но не **чьё**: два
одинаковых клапана установки — два блока с одним `GLOBAL_BLOCK_ID`. Поэтому
у блока нужен свой атрибут с ID узла Flux. Недостающие атрибуты
(`FLUX_BLOCK`, `FLUX_VER`, `FLUX_PROJECT` и, до ответа владельца,
`FLUX_ID`) заводит администратор базы E3; без них выгрузка запрещена (5.8).

**Главный ключ — атрибуты связи, а не номер объекта E3.** Номер объекта
E3 меняется при копировании листа и переносе в другой проект, а атрибут
переезжает вместе с блоком. Мост перед каждой работой читает все блоки с
`FLUX_BLOCK` и изделия с ID Flux (`readBound`). Это и есть
картина «что сейчас в схеме».

Во Flux (общая база) хранится, **что было отправлено:**

```
E3Project      id, fluxProjectId, key (FLUX_PROJECT), name, path,
               e3Version, partsDb, lastSeenAt

E3Export       id, e3ProjectId, sheet, by, at, state
               (PLANNED | RUNNING | DONE | INTERRUPTED | UNDONE),
               classifierVersion, profileJson, planJson, reportJson

E3Binding      id, e3ProjectId, elementId (ID узла Flux),
               solutionId (ID типового решения), answersJson (ответы
               на признаки и откуда каждый), manualSolution, designation,
               sheet, x, y, rotation  — где поставили при выгрузке,
               sentVersion            — версия позиции на момент выгрузки,
               sentAttrsJson          — какие значения записали (по изделиям),
               overridesJson          — ручные значения инженера КИП,
               state (PLACED | REMOVED_IN_FLUX | DELETED_IN_E3 | DETACHED),
               lastExportId
               уникально: (e3ProjectId, elementId)
```

Одна позиция может стоять в нескольких проектах E3 (разные разделы,
ревизии). У каждого проекта своя связь.

Данные КИП (уставки, сигналы, диапазоны — атрибуты с «Да» без источника у
ОВ) хранятся не в `E3Binding`, а за самой позицией Flux, в её
характеристиках отдельной группой «КИП». Они нужны и без E3: их видно в
карточке позиции, в «Паспорте тега» и в выгрузке в Excel. Заполненная книга
атрибутов («Атрибуты проекта» → «Загрузить Excel») кладёт значения именно
туда; ключ строки — ID позиции и тег, ошибки ключей видны в плане.

### 9.2 Три стороны сравнения

Каждая повторная выгрузка сравнивает три состояния позиции:

- **Отправлено** — `E3Binding` (что Flux записал в прошлый раз);
- **Сейчас во Flux** — позиция, её подбор и атрибуты по текущим правилам;
- **Сейчас в E3** — `readBound`.

Из этого видно, кто что менял: Flux (переподбор), E3 (рука инженера КИП)
или оба. Двух сторон не хватило бы: без «отправлено» нельзя отличить
переподбор от ручной правки в E3.

### 9.3 Все случаи

| # | Что произошло | Что предлагает E3Flux | По умолчанию |
|---|---|---|---|

Если внешние выводы совпадают — провода переподключаются. Если нет — висящие провода перечисляются в отчёте | Заменить, с отчётом |

(8.1): «обновить 5 атрибутов у 3 изделий, заменить 1 блок, удалить 0».

### 9.4 Уведомления

- Позиция, стоящая в схеме E3, изменилась во Flux → уведомление
  (`Notification`) тому, кто выгружал: «П1: изменились 3 позиции,
  выгруженные в Корпус 3 — ВК». Одно уведомление на импорт, а не на
  каждую позицию.
- При импорте у ОВ предпросмотр показывает: «5 позиций этой установки уже
  в схеме КИП». Это не запрет, а предупреждение, что переподбор заденет
  чужую работу.

## 11. Права

- **Открыть E3Flux и выгружать** — новое право `e3.export`. По умолчанию
  у роли КИП.
- **Править типовые решения, признаки и атрибуты** — право каталога
  (`catalog.manage`) или отдельное `e3.catalog`. Это вопрос владельцу
  (раздел 13).
- **Профиль автоматизации проекта и данные КИП позиций** — право
  `e3.export`: это работа инженера КИП, а не администратора каталога.
- **Видеть «В схеме E3» в Оборудовании** — все, кто видит оборудование.
- Сервер проверяет право на каждом маршруте записи. Запись закупки, где
  право сейчас не проверяется, уже числится в плане как известная
  дыра — повторять её не надо.

### Решения владельца 8 октября 2026 и разбор образцов

**Решение владельца дословно:** «Да оба» — Flux строит и ФСА, и схему
соединений.

**Образец схемы соединений** (PDF, 10 листов A3):

- колонка на каждый прибор; три яруса сверху вниз: «приборы в поле»,
  «коробки HJB» (ряд клемм, экраны, резерв «Spare»), «шкаф» (клеммники XT,
  шина FE);
- сквозные метки цепей `тег-01` / `тег-02`;
- над колонкой шапка-таблица: параметр RU/EN, позиционное обозначение,
  тип/марка;
- жилы с цветами BK/WT; шифр и марка кабеля повёрнуты на 90°;
- полный штамп 185×55 на первом листе, сокращённый на остальных;
- межлистовых ссылок нет; разбиение на листы автоматическое, «Лист N из M».

**Чего для схемы соединений не хватает во Flux:**

- модель кабелей (шифр, марка, жилы, цвета), коробок и клеммников с номерами
  клемм и резервом, привязка позиции к коробке и шкафу;
- раскладка колонками по ярусам с шагом от ширины клеммного ряда;
- разбиение на листы;
- двуязычные и повёрнутые надписи.

В проекте-образце эти данные лежат в атрибутах устройств `dip_cable_*`,
`dip_SH_tag`, `.CABLENAME`, `.CABLETYPE`, `WireNumber`.

**Выгрузка проекта E3** (`.e3d`, текстовый формат E3 2023, UTF-16; секции
`$D`/`$F`, пустое поле = значение из предыдущей записи). Без E3 из неё
извлекаются:

- компоненты-шаблоны (DBCOMP/DBCIRC/DBPINS);
- символы с графикой, пинами и габаритом (DBSYMBOL/DBSYMGRA/DBSYMTXT/DBSYMPIN);
- размещения на листах (CBCELLS, TRAFORMS);
- цепи, провода, кабели (CBNET, CBSIGNAL, CBCABLE, CBCABWIR).

Это закрывает нехватку габаритов блоков без кеша из E3. Чего в выгрузке
нет: производителя и артикула, атрибутов на компонентах (только на
устройствах), блоков-изделий (CBBLOCK пуст). В образце 27 компонентов
(`клапан_*`, `датчик_*`, `БХК_тип_JBP-*`, `клеммы_в_шкафу_*`,
`внешние_сигналы_*`); `Клапан_К24_КП2` среди них нет. Вставка по имени в E3
возможна, только если компонент есть в базе E3 или в открытом проекте.

**Ещё открыто:** можно ли хранить в репозитории каталог шаблонов,
извлечённый из проекта (без самого файла проекта); источник данных о
кабелях — атрибуты `dip_*` или отдельный журнал.

**Решение владельца: единица вставки — блок (готовый фрагмент схемы `.e3p` /
подсхема базы), а не отдельный символ.** Кандидаты вызовов: `Job.ImportDrawing` /
`ImportDrawingEx` для файла, `Job.LoadPart` + `Sheet.PlacePart` для подсхемы из
базы — проверяются пробой (`tools/e3-probe`, режим «только разместить»).


### Автоматическое построение блоков — план (8 октября 2026)

Цель владельца: «E3Flux сам всё определяет: по характеристикам оборудования
целиком сам определяет из базы, как должен выглядеть блок, и размещает по
порядку на листе». Все данные по E3 Flux берёт по API (решение владельца), а не
из `components.mdb`/`symbols.mdb` и не из `.e3d`.

**Цепочка:** оборудование установки во Flux (узлы и характеристики) → решение
классификатора (есть: `e3/solutionSelect.ts`) → РЕЦЕПТ блока → изделия и символы
из базы E3 → раскладка по ходу воздуха (есть: `e3/layout.ts`) → показ на холсте
Flux → вставка в E3 мостом → атрибуты.

**Ключевая мысль.** Готовых `.e3p` по классификатору нет (ни одной ссылки),
поэтому блок Flux собирает сам: рецепт — список изделий с ролями и сигналами,
выводимый правилами из характеристик узла; имя вставляемого блока в E3 — название
схемы решения (решение владельца, 5.1).
Число сигналов DI/DO/AI/AO берётся из листа «Таблица IO» классификатора:
пружинный клапан с бк 2DI/1DO — `клапан_DIx2_DOx1`; 3-позиционный 2DI/2DO —
`клапан_DIx2_DOx2`; плавный 2DI/1AI/1AO; электродвигатель без ЧРП 2DI/1DO; с
ЧРП 2DI/1DO/1AI/1AO; датчики PT/TT — 1AI, TS/PS — 1DI и т. д. Вентилятор — по
коду пуска из листа «Обозначения» (ПП, ЗТ, УПП, ПЧ, ЕС, К, РТС, БРНО, СВ). Если
для решения появится `.e3p`, рецепт ссылается на файл, а мост вставляет его
через `Job.ImportDrawing`.

**Этапы:**

- **A. Каталог изделий и символов — только через COM API.** (а) Список имён: из
  выделенного инженером в базе E3 (`Application.GetDatabaseTreeSelectedComponents`,
  `GetDatabaseTreeSelectedSymbols`, `GetDatabaseTableSelectedComponents`; те же
  методы редактора базы `e3DbeApplication`) и из компонентов открытого проекта
  (`Job.GetAllComponentIds`). Полного списка базы в API нет: инженер выделяет
  нужные строки или папки. (б) По каждому имени — свойства, атрибуты, выводы и
  символы через Component-/Dbe-объекты. (в) Габарит символа — `Symbol.Load` и
  чтение области (`GetArea`/`GetPlacedArea`) без размещения, иначе на временном
  листе. Чтение mdb и `.e3d` — только запасной путь для разработки. Проверяется
  разделом «Каталог по API» пробы (`-CatalogOnly`): отдаёт ли выделенная папка всё
  содержимое, читается ли габарит без размещения. Импорт во Flux как справочник.
- **B. Рецепты блоков:** модель (решение классификатора → изделия с ролями) и
  правила вывода из характеристик узла; чтение листа «Таблица IO» (сейчас не
  читается); правки рецептов в интерфейсе каталога.
  Решение владельца 8 октября 2026: источник значения атрибута задаётся ПО
  ТИПУ ОБОРУДОВАНИЯ — один раз для типа (например, «Клапан воздушный»:
  GLOBAL_DEVICE_TYPE ← характеристика «Тип привода»), и действует для всех
  позиций этого типа во всех проектах. Если для типа не задано — общий
  источник атрибута (как сейчас, `E3Attribute.source`). Модель:
  `E3Attribute.sourceByClass: Record<classId, E3Source>` поверх `source`;
  экран в каталоге: выбор типа → таблица «атрибут E3 → откуда для этого
  типа», список предлагает только характеристики этого типа. Логику можно
  уточнять по ходу.
  Итог сухого прогона загрузки файлов владельца: классификатор 471/471
  распознано (159 на подтверждение — «К» у клапанов как коробка, цифра у

  **Сделано 8 октября (часть 2): таблица IO, рецепт, признаки новых классов.**
  Лист «Таблица IO» читается (`e3/ioTable.ts`): 26 строк со значащими сигналами
