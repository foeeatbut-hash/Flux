# Загрузка оборудования и E3Flux — выгрузка схем в E3.series

Проект, 7 октября 2026. Две части, и вторая стоит на первой:

1. **Загрузка данных.** У каждой позиции проекта с первой загрузки есть свой
   ID: у установки, у элемента внутри неё и у элемента внутри элемента, даже
   если тега ещё нет. Этот ID не переходит к другому изделию при повторной
   загрузке. Сейчас это не так — разбор ниже.
2. **E3Flux.** Программа внутри Flux для отдела КИПиА. Она берёт подобранное
   отделом ОВ оборудование, по классификатору подбирает каждой позиции её
   место в базе E3, пересчитывает характеристики в атрибуты E3, показывает
   схему на холсте и выгружает её в открытый E3.series. При переподборе
   выгружает схему заново и по ID заменяет то, что уже было выгружено.

Классификатор и список атрибутов владелец приложил к сообщению, но файлы до
сессии не дошли. Формат правил ниже описан так, чтобы любой из этих файлов
лёг в него без переделки. Когда файлы придут, столбцы сверяются с
разделом 5 и вписываются туда примером.

## Часть 1. Загрузка данных: ID позиции

### 1.1 Как сейчас

Импорт (`server/equipmentImport.ts`) узнаёт позицию по пути из имён:

```
установка (по имени, с поправкой на опечатку раскладки)
  └ моноблок (по имени внутри установки)
      └ блок (по коду: «бл2.1»)
          └ подпозиция (по пути: «бл2.1/вентилятор1/двигатель1»)
```

При первом появлении пути заводится запись с новым uuid. При повторной
загрузке тот же путь находит ту же запись, и в неё пишутся новые
характеристики. Вложенность держится полем `parentElementId`, глубина любая.

Значит, ID без тега уже выдаётся на всех уровнях. Беда в другом: ID
привязан к **пути в файле**, а не к **изделию**. Пока путь не меняется, это
незаметно. Перед связью с E3 это надо исправить: схема КИП будет держаться
за ID, и если ID переедет на другое изделие, вместе с ним переедет схема.

### 1.2 Где это ломается

| # | Что случилось в расчёте | Что делает импорт сейчас | Чем плохо |
|---|---|---|---|
| Д1 | В установку вставили блок, коды сдвинулись: бывший «бл2.1» стал «бл2.2» | В «бл2.1» записываются характеристики нового блока | Тег, история и будущая связь с E3 переходят от фильтра к нагревателю. Проверки на смену типа нет: `detectTypeMismatch` вызывается только в старом разборе Excel (`server/excelParser.ts`), новый импорт её не зовёт |
| Д2 | Из двух вентиляторов блока убрали первый | «вентилятор2» исчезает, «вентилятор1» получает данные второго | Номер экземпляра выдаётся по порядку в файле, и данные сдвигаются на одну позицию |
| Д3 | Позиция пропала из нового расчёта | Ничего: запись остаётся как была, без отметки | Нельзя отличить действующее оборудование от снятого. Старый разбор помечал такие позиции `ORPHANED_TAG`, новый — нет |
| Д4 | Установку переименовали («П1» → «П1.1»), это не опечатка | Заводится новая установка, старая остаётся рядом | Теги и связи остаются на старой, у новой их нет, и снятой старая не помечена |
| Д5 | В двух файлах одной категории есть установки с одинаковым именем | `matchSystem` ищет только по имени внутри категории | Две разные установки сливаются в одну. Выгрузка в Excel их уже различает по ID, а импорт — нет |
| Д6 | Блок без параметров установки | Служебный блок `__unit__` не заводится | У установки нет записи-позиции, и связать с E3 саму установку (шкаф, щит управления) не через что |

### 1.3 Правило

**ID выдаётся изделию один раз и навсегда.** Его получает любая позиция
любого уровня: установка, моноблок, блок, подпозиция и её подпозиции. Тега
для этого не нужно. ID не используется повторно и не передаётся другому
изделию. Тег, история, ручные правки, связь с каталогом и связь с E3
привязаны к ID, а не к коду и не к тегу.

Код из файла («бл2.1») — это **адрес**, а не ID. Адрес меняется, когда
расчёт пересобирают. ID при этом остаётся прежним.

### 1.4 Сопоставление при повторной загрузке

Для каждой позиции нового файла импорт ищет запись по шагам, от надёжного к
приблизительному. На первом найденном шаге поиск заканчивается.

1. **Ключ источника.** Если в файле у узла есть свой постоянный
   идентификатор, он запоминается при первой загрузке и сравнивается при
   следующих. В выгрузках САПР ВЕЗА сейчас такого ключа не видно. Шаг
   нужен на будущее и для файлов, которые Flux сам выгружал и получает
   обратно.
2. **Тег из файла.** Тег в файле есть, и в проекте он уже стоит на позиции
   этой установки — значит, это она, даже если код другой. Так ловится Д1
   для тегированных позиций.
3. **Адрес** (как сейчас) — **с проверкой, что изделие то же.** Тип или
   роль совпадают, ключевые характеристики близки (подпись — как у
   `CatalogLearn`: тип, вид, типоразмер, мощность). Если по адресу теперь
   стоит изделие другого типа, позиция с ним не сливается.
4. **Поиск переехавших.** Позиция пропала с одного адреса, а на другом
   появилась позиция того же типа с близкими характеристиками. Импорт
   предлагает связать их: «Фильтр ФВК переехал с бл2.1 на бл2.2».

Шаги 3 и 4 только **предлагают**. Решение принимает инженер в предпросмотре
импорта (`server/equipmentPlan.ts`), по правилам `flux-data-safety`. Каждая
спорная позиция показывается в плане отдельной строкой с вариантами:

| Вариант | Что значит | Когда стоит по умолчанию |
|---|---|---|
| **То же изделие** | Новые данные пишутся в прежнюю запись (ID, тег и связь с E3 сохраняются) | Тип совпадает, характеристики близки |
| **Переподобрано** | Прежняя запись снимается, заводится новая, и между ними ставится связь «заменено на» | Тип тот же, характеристики далеки (другой типоразмер) |
| **Другое изделие** | Прежняя запись снимается, новая заводится без связи | Тип другой |

«Переподобрано» отличается от «другого изделия» для E3: позицию в схеме
можно заменить на месте, и проводка не переделывается (раздел 9).

### 1.5 Пропавшие позиции

Позиция, которой нет в новом файле, **не удаляется**. Она получает
состояние «снята» (`status = 'REMOVED'`, дата и партия импорта, которой
снята):

- в дереве оборудования она видна серой, за переключателем «показать
  снятые»;
- тег остаётся, в «Тегах» отмечается «оборудование снято»;
- если позиция есть в схеме E3, E3Flux показывает её к удалению из схемы
  (раздел 9);
- если позиция вернулась в расчёт (откатили переподбор), запись
  возвращается с тем же ID;
- **отмена импорта** (`ImportBatch`) возвращает снятые этой партией
  позиции.

Ручные позиции (`manual = true`) снятыми не становятся: файл их не знает.

### 1.6 Установка, моноблок и номера экземпляров

- **Установка — тоже позиция.** Служебный блок `__unit__` заводится всегда,
  даже без параметров: на него вешаются тег установки и связь с E3. Так
  закрывается Д6. Предпросмотр должен считать так же, иначе план и запись
  разойдутся — об этом комментарий в `importEquipmentToDB`.
- **Переименование установки (Д4)** — в плане отдельная строка: «В файле
  нет П1, появилась П1.1 с тем же составом — это она?». Да — запись
  переименовывается, ID прежний.
- **Одинаковые имена (Д5):** установка ищется по имени **и** имени файла,
  если в категории уже есть две с таким именем. Если сопоставить нельзя,
  план просит выбрать.
- **Номер экземпляра (Д2):** «вентилятор1» и «вентилятор2» сопоставляются
  не по номеру, а по шагам 2–4: тегу, типоразмеру, характеристикам. Номер
  остаётся подписью для человека.

### 1.7 Версия позиции

У `ComponentElement` уже есть `version`. Её надо поднимать при **любом**
принятом изменении: характеристик, типа, тега, состава, ручной правки.
Сейчас она растёт только при обновлении характеристик в режиме
`immediate`. E3Flux сравнивает «какую версию выгрузили» с «какая сейчас» и
по этому сравнению показывает «изменилась после выгрузки».

### 1.8 Проверки части 1

Новый набор `scripts/test-equipment-identity.ts` — повторная загрузка на
настоящих выгрузках ВЕЗА с правкой:

- сдвиг кодов (Д1): ID следует за изделием, а не за кодом;
- удаление первого из двух вентиляторов (Д2);
- пропажа позиции → «снята»; возврат → тот же ID; отмена партии → снятие
  отменено (Д3);
- переименование установки (Д4) и две установки с одним именем (Д5);
- установка без параметров получает запись (Д6);
- первая загрузка без единого тега: ID есть на всех уровнях, тег,
  поставленный потом, ложится на нужный ID;
- план и запись совпадают по каждому случаю (как сейчас сверяет
  `test-equipment-plan`).

## Часть 2. E3Flux

## 2. Кто что делает

| Кто | Где | Что делает |
|---|---|---|
| Отдел ОВ | Flux, «Оборудование» | Загружает расчёты, подбирает оборудование, ставит теги. Про E3 не знает ничего |
| Администратор каталога (КИП) | Flux, «Каталог» → «E3» | Ведёт классификатор (какая позиция E3 у какого изделия) и атрибуты (какое значение куда пишется). Загружает их из файла |
| Инженер КИПиА | Flux → E3Flux, рядом открыт E3.series | Выбирает установку или изделие, проверяет подбор, раскладывает на холсте, выгружает в E3, потом достраивает схему в E3 руками |
| E3.series | Компьютер инженера КИП | Своя база компонентов и символов. Принимает команды Flux через COM |

## 3. Сценарий целиком

1. ОВ загрузил расчёт и подобрал оборудование: установка П1 с клапаном,
   фильтром, нагревателем и вентилятором. Теги поставлены, характеристики
   есть.
2. Инженер КИП открывает E3.series, свой проект и пустой лист.
3. Во Flux — «Оборудование» → установка П1 → **«Выгрузить в E3.series»**
   (или «Пуск» → E3Flux). Открывается окно E3Flux с выбранной установкой.
4. E3Flux подключается к запущенному E3 и показывает в шапке:
   «E3.series 2025 · проект „Корпус 3 — ВК“ · лист 12 (А3)».
5. Слева — установка П1 и её состав. У каждой позиции видны название, тег,
   что подобрано из базы E3 и атрибуты E3 со значениями.
6. Инженер нажимает «Разложить» (или перетаскивает позиции сам). На
   холсте справа появляются рамки позиций на листе в масштабе 1:1 к листу
   E3.
7. **«Демонстрация»**: Flux спрашивает у E3, как выглядит каждый символ, и
   холст рисует настоящие символы, обозначения и подписи атрибутов.
8. Инженер правит: меняет подобранную позицию, двигает символы, добавляет
   второе изделие или вторую установку.
9. **«Выгрузить в E3.series»**: в E3 на открытом листе появляются
   устройства с компонентами, символами, обозначениями и заполненными
   атрибутами, на тех же местах, что на холсте. У каждого устройства —
   служебный атрибут с ID позиции Flux.
10. Flux сохраняет запись выгрузки: что, куда, с какими значениями.
11. Через неделю ОВ переподбирает вентилятор. В карточке позиции и в
    E3Flux появляется «изменилось после выгрузки в E3». Инженер КИП
    открывает E3Flux, видит разницу «было → стало» и выгружает заново.
    Меняется только то, что изменилось. Положение символов и проводка,
    которую инженер нарисовал руками, остаются.

## 4. Устройство

```
┌──────────── Flux: окно E3Flux (renderer) ──────────────┐
│ установки и позиции │ холст листа │ свойства позиции   │
└──────────┬───────────────────────────────┬─────────────┘
           │ HTTP (как все разделы)        │ IPC (только настольная версия)
┌──────────▼──────────────┐     ┌──────────▼───────────────────────────┐
│ Сервер Flux, общая база │     │ Electron main → мост E3              │
│ • оборудование, теги    │     │ долгоживущий помощник (C#),          │
│ • классификатор E3      │     │ как нативный помощник Проводника     │
│ • атрибуты E3           │     │ (electron/nativeShellSource.ts)      │
│ • связи и выгрузки      │     └──────────┬───────────────────────────┘
└─────────────────────────┘                │ COM: CT.Application
                                ┌──────────▼───────────┐
                                │ E3.series у инженера │
                                └──────────────────────┘
```

- **С E3 говорит только компьютер инженера.** Сервер Flux к E3 не
  подключается: E3 стоит на рабочем месте, а сервер у каждого сотрудника
  свой, база общая.
- **Мост — долгоживущий помощник,** а не PowerShell на каждую команду.
  COM-вызовов на одну установку сотни, и запуск PowerShell на каждый
  растянул бы выгрузку на минуты. Шаблон уже есть: C# через Add-Type в
  `electron/nativeShellSource.ts`, тот же «нативный помощник этапа A» из
  `docs/explorer-windows11.md`.
- **Мост ничего не решает.** Он выполняет простые команды: «найди
  компонент», «создай устройство», «поставь символ», «запиши атрибут»,
  «прочитай атрибуты устройств с FLUX_ID». Подбор, сравнение и план
  считаются в общем модуле `e3/` — чистом TypeScript без COM, по примеру
  `equipment/`. Поэтому они проверяются в контейнере без E3.
- **Браузерная версия** (без Electron) открывает E3Flux только для
  подготовки: подбор, атрибуты, раскладка без демонстрации. Кнопки
  «Демонстрация» и «Выгрузить» неактивны, с объяснением «нужна настольная
  версия Flux на компьютере с E3.series».

### 4.1 Команды моста

Минимальный набор. Точные имена методов COM сверяются на установленной
версии E3 до начала этапа C (раздел 13).

| Команда | Что делает в E3 | Зачем |
|---|---|---|
| `status` | Какие E3 запущены, версия, открытый проект, активный лист, формат листа | Шапка E3Flux и проверки перед выгрузкой |
| `projectKey` | Читает или ставит атрибут проекта `FLUX_PROJECT` (uuid) | Узнавать проект E3 надёжнее, чем по пути к файлу: путь меняется при копировании и переносе |
| `listParts` | Компоненты и символы базы E3 (имя, версия, класс) | Проверка классификатора, выбор вручную |
| `attrDefs` | Определения атрибутов базы E3 | Проверка списка атрибутов |
| `preview` | Ставит символы на временный лист, выгружает их изображение и удаляет лист | «Демонстрация» |
| `sheetOccupancy` | Габариты того, что уже стоит на листе | Холст показывает занятые места |
| `readBound` | Все устройства с `FLUX_ID`: обозначение, лист, координаты, компонент, символ, атрибуты | Повторная выгрузка, сверка ручных правок |
| `apply` | Выполняет план выгрузки по шагам и после каждого шага сообщает, что сделано | Выгрузка |

### 4.2 Где лежит код

Расписывается по `flux-architecture` перед этапом A. Набросок:

- `e3/` — общий чистый модуль: правила классификатора, расчёт атрибутов,
  раскладка, план выгрузки и сверка;
- `server/routes/e3*.ts` — классификатор, атрибуты, связи, выгрузки;
- `electron/e3Bridge*.ts` — мост и его C#-источник;
- `src/screens/e3flux/` — окно программы;
- страница `docs/methodology/03-programs/e3flux.md` — пишется до
  раскладки в коде, по шаблону раздела 03.

## 5. Каталог: классификатор и атрибуты E3

В «Каталоге» появляется раздел **«E3.series»** с тремя вкладками:
«Классификатор», «Атрибуты», «Связь с базой E3». Обе таблицы ведутся
вручную и загружаются из файла.

### 5.1 Классификатор: что ставить в схему

Одно правило отвечает на вопрос: «Если во Flux такое изделие, что ставить
в E3».

**Условие** (все заданные поля должны совпасть):

| Поле | Пример | Откуда во Flux |
|---|---|---|
| Тип | Привод | `equipClass` / угадывание (`equipment/classes.ts`) |
| Вид | С возвратной пружиной | `equipKind` |
| Роль в составе | ПРИВОД | `role` (`equipment/roles.ts`) |
| Тип владельца | Клапан | Тип родителя по `parentElementId` |
| Изготовитель, семейство | НЕМАН, LF… | Привязка к каталогу |
| Условия по характеристикам | Напряжение = 24 В; Мощность ≤ 4 кВт; Сигнал = 0–10 В | Характеристики позиции по коду (`sourceGroup`/`sourceKey`), в единицах каталога |

**Результат:**

| Поле | Пример | Что это в E3 |
|---|---|---|
| Компонент базы E3 | `LF24-SR` вер. 1 | Изделие из базы компонентов E3 |
| Символ или фрагмент схемы | `ACT_SPRING_0-10V` | Что рисуется на листе. Фрагмент — готовый кусок схемы из нескольких символов (двигатель + термоконтакт + клеммник) |
| Буквенный код | `M`, `YV`, `BK` | Код по ГОСТ для обозначения |
| Правило обозначения | `{тег}` или `={установка}-{код}{номер}` | Как назвать устройство в E3 |
| Размер на листе | Из символа, при демонстрации | Для раскладки |
| Куда на листе | Группа «Силовые», «Датчики», «Приводы» | Для автоматической раскладки |
| Дочерние позиции | «Двигатель → датчик PTC ставится отдельным символом» / «входит в фрагмент двигателя» | Не рисовать позицию дважды |

**Как выбирается правило.** Подходящие правила сравниваются по точности:
правило с изготовителем точнее правила только с типом, правило с условием
по характеристикам точнее правила без него. Побеждает самое точное.

- Подошло одно правило — оно ставится, а в свойствах позиции написано,
  почему: «Привод, пружина, 24 В, 0–10 В → правило №14».
- Два правила одинаково точны — подбор **не угадывает**: позиция
  помечается «нужен выбор», показываются оба варианта.
- Не подошло ни одно — «нет правила», и прямо оттуда можно перейти в
  классификатор и добавить правило с уже заполненным условием.
- Ручной выбор инженера КИП сильнее любого правила. Он запоминается за
  позицией (по ID) и остаётся при переподборе, пока тип позиции не
  сменился. Если тип сменился, ручной выбор снимается с предупреждением.

### 5.2 Атрибуты: что писать в схему

Две таблицы.

**Определения атрибутов** — копия того, что есть в базе E3:

| Имя в E3 | Подпись | На чём | Тип | Длина | Обязателен |
|---|---|---|---|---|---|
| `Power` | Мощность | Устройство | Число | — | Да |

**Сопоставление** — откуда значение, для каждого типа изделия свой набор:

| Тип | Атрибут E3 | Источник во Flux | Преобразование | Пример |
|---|---|---|---|---|
| Двигатель | `Power` | Характеристика «Мощность» | кВт, 2 знака, запятая | `5,50` |
| Двигатель | `Voltage` | Характеристика «Напряжение» | как есть | `400` |
| Двигатель | `Description` | Шаблон | `Двигатель вентилятора {тег владельца}, {Мощность} кВт` | … |
| Любой | `Tag` | Тег позиции | — | `П1-М1` |
| Любой | `Unit` | Тег установки | — | `П1` |
| Привод | `Spring` | Вид | словарь: «С возвратной пружиной» → `Да` | `Да` |

Источники: характеристика (по коду, а не по подписи — подпись переименуют,
код останется: см. комментарий к `sourceGroup` в
`server/equipmentParser.ts`), тег, тег владельца, тег установки, название,
изготовитель и модель из каталога, проект, константа, шаблон из нескольких
источников.

Преобразования: единицы (Вт ↔ кВт, м³/ч ↔ л/с), округление, разделитель
дробной части, словарь значений, обрезка до длины атрибута E3 с
предупреждением, «если пусто — подставить».

**Слева в E3Flux показываются уже преобразованные значения,** то есть
ровно то, что ляжет в атрибуты. Рядом мелко — исходное значение и
название характеристики во Flux, чтобы при «5,50» было видно, что взято из
«Мощность двигателя, 5.5 кВт».

### 5.3 Загрузка из файла

Классификатор и атрибуты загружаются из Excel/CSV так же, как другие
таблицы каталога:

1. Выбрать файл. Столбцы распознаются по заголовкам. Если формат новый,
   сопоставление столбцов показывается для правки и запоминается как
   профиль (`ImportProfile`).
2. **План:** сколько правил новых, изменённых и неизменных; какие правила
   есть в каталоге, но нет в файле; в каких строках ошибки (нет компонента
   в базе E3, непонятное условие, неизвестный тип).
3. Для правил, которых нет в файле, — выбор: оставить / снять. По
   умолчанию — оставить.
4. Запись одной партией. Снимок «до» сохраняется в `CatalogRevision`,
   откат возвращает всю загрузку.
5. У классификатора есть номер версии. Запись выгрузки в E3 помнит, по
   какой версии подбиралось. При новой версии E3Flux показывает: «Правила
   изменились: 3 позиции в схеме теперь подобрались бы иначе».

Правила, правленные руками после загрузки, отмечаются. Повторная загрузка
файла показывает их отдельно и молча не перезаписывает (как `edited` у
семейств каталога).

### 5.4 Сверка с базой E3

Вкладка «Связь с базой E3» работает, только когда подключён E3. Мост
читает список компонентов, символов и определений атрибутов. Каталог
показывает:

- правила, ссылающиеся на компонент или символ, которого нет в базе E3;
- атрибуты, которых нет в определениях E3: записать их E3 не даст;
- служебные атрибуты Flux, которых нет в базе E3 (раздел 9.1). Без них
  выгрузка невозможна, и администратор E3 должен их завести.

Списки из базы E3 кешируются на сервере Flux с датой. Классификатор можно
править на компьютере без E3, и ошибки там видны по последнему снимку.

## 6. Окно E3Flux

Три колонки по общему правилу «навигация → рабочая область → карточка»
(`docs/methodology/01-design.md`). Отдельная программа рабочего стола, как
«Выгрузка данных» у Оборудования: без модального фона, сворачивается и
переносится на второй монитор, рядом с E3.

### 6.1 Шапка

`E3Flux · проект Flux` · **состояние связи с E3** (точка и подпись: «E3
2025 · Корпус 3 — ВК · лист 12, А3» / «E3 не запущен» / «открыто два E3 —
выбрать») · «Обновить из Flux» · «Демонстрация» · главная кнопка
**«Выгрузить в E3.series»**.

### 6.2 Слева: что выгружать

- Переключатель вида: **«По установкам»** (установка → моноблок → блок →
  подпозиции, как в Оборудовании) / **«По типам»** (все клапаны, все
  приводы, все двигатели проекта).
- Поиск по тегу, названию, обозначению E3.
- Строка позиции: название, тег, подобранный компонент E3 и состояние:

| Знак | Состояние | Значит |
|---|---|---|
| ○ | Не в схеме | Ещё не выгружалась в этот проект E3 |
| ● | В схеме | Выгружена, с тех пор не менялась |
| ◐ | Изменилась | Во Flux изменилась после выгрузки (переподбор, новый тег, правило) |
| ✕ | Снята | Во Flux снята, а в схеме ещё стоит |
| ! | Нужен выбор | Нет правила, или подошли два, или не хватает обязательного атрибута |
| ⇄ | Правлена в E3 | В E3 значение атрибута отличается от выгруженного |

- Раскрытие строки — атрибуты E3 с готовыми значениями.
- Флажок у строки — «брать в выгрузку». Установка отмечается целиком, и
  отметку можно снять с отдельных позиций (например, без фильтра: его
  на схеме КИП нет).
- Позиции, которые классификатор рисует внутри фрагмента владельца
  (датчик PTC внутри символа двигателя), отдельной строкой на холст не
  попадают и видны как «входит в фрагмент двигателя».

### 6.3 Середина: холст листа

См. раздел 7.

### 6.4 Справа: свойства выбранного

- **Подбор:** правило и почему оно выбрано; список других подходящих
  правил; «Выбрать другое из базы E3» — поиск по компонентам базы.
- **Атрибуты:** имя E3, значение, источник. Значение можно переопределить
  для этой выгрузки. Переопределение запоминается за позицией и помечается
  «вручную».
- **Обозначение** в E3: по правилу или вручную; проверка на повтор в
  проекте E3.
- **Связь:** в каком проекте E3 и на каком листе позиция уже стоит, когда
  выгружена, кем, по какой версии позиции.

### 6.5 Где начинать

- «Оборудование» → установка или позиция → «Выгрузить в E3.series» —
  E3Flux открывается с этим выбором.
- «Пуск» → E3Flux — с последним проектом и пустым выбором.
- Карточка позиции, строка «В схеме E3: Корпус 3 — ВК, лист 12, −M1 ·
  изменилась после выгрузки» — открывает E3Flux на этой позиции.

## 7. Холст

- **Лист в масштабе листа E3.** Формат, рамка и рабочее поле читаются из
  E3 (`status`). Координаты холста — миллиметры листа E3, с тем же началом
  отсчёта и той же сеткой. То, что стоит на холсте в точке (120, 85), в E3
  встанет в (120, 85).
- **Занятое на листе** (рамка, штамп, то, что инженер уже нарисовал в E3)
  показывается серыми областями (`sheetOccupancy`). Положить туда позицию
  нельзя: холст предупредит.
- **Раскладка вручную:** перетащить позицию слева на холст, двигать,
  поворачивать с шагом 90°, выравнивать. Привязка к сетке E3.
- **«Разложить»:** установка раскладывается по группам классификатора
  («Силовые», «Приводы», «Датчики»), в порядке состава и слева направо.
  Позиции, которые инженер поставил руками, «Разложить» не двигает.
- **Несколько изделий:** можно добавить вторую установку или отдельное
  изделие. Каждая установка — своя группа, её можно двигать целиком.
- **Не помещается:** холст показывает переполнение и предлагает «Перенести
  на новый лист» (вкладка листа над холстом). Новый лист создаётся в E3
  только при выгрузке, с форматом текущего.
- **До демонстрации** позиция на холсте — прямоугольник размера символа
  (если размер ещё не известен — условный) с обозначением и тегом.
- **«Демонстрация»** заменяет прямоугольники настоящими символами (7.1).
- **Уже выгруженное** на холсте берётся из E3 (`readBound`): если инженер
  сдвинул символ в E3, на холсте он стоит там же. Источник положения —
  E3, а не запись Flux.

### 7.1 Демонстрация

Задача — нарисовать символ так, как его нарисует E3, не трогая лист
инженера. Варианты:

| Вариант | Как | За | Против |
|---|---|---|---|
| **А. Временный лист** | Мост создаёт в открытом проекте скрытый лист, ставит символы, выгружает изображение, удаляет лист | Символ настоящий, из той же базы и версии | В проекте E3 на секунду появляется лист. Если E3 упадёт посреди демонстрации, лист останется (мост удаляет его при следующем подключении по служебному имени) |
| Б. Второй E3 | Отдельный экземпляр E3 с пустым проектом | Проект инженера не трогается | Вторая лицензия E3 и время запуска |
| В. Свои картинки | Flux хранит упрощённые изображения символов | Не нужен E3 | Расходятся с базой E3: это ровно то, от чего владелец хочет уйти |

**Предлагается А с кешем.** Изображение символа сохраняется на сервере
Flux по ключу «база E3 + символ + версия». Второй раз тот же символ не
запрашивается: демонстрация установки, где все символы уже встречались,
идёт без обращения к E3. Атрибуты и обозначения поверх символа холст
рисует сам: их места (текстовые узлы символа) берутся из того же ответа.

Демонстрация не обязательна. Выгружать можно и без неё: тогда раскладка
считается по размерам символов из кеша или по условным.

## 8. Выгрузка

### 8.1 Перед выгрузкой — проверка и план

Кнопка «Выгрузить в E3.series» сначала показывает **план**, а не пишет
сразу (`flux-data-safety`):

- проект E3 тот же, что при подготовке (по `FLUX_PROJECT`), лист тот же
  и открыт на запись;
- у каждой позиции есть компонент и символ из базы E3;
- обязательные атрибуты заполнены;
- обозначения не повторяются с уже существующими в проекте E3;
- холст не пересекает занятые области;
- **что будет сделано:** создать N устройств, обновить M, заменить K,
  удалить L (удаление — только отмеченное инженером, раздел 9.3).

Ошибки блокируют выгрузку; предупреждения — нет.

### 8.2 Запись

Мост выполняет план по шагам в таком порядке: листы → устройства и
компоненты → символы на места → обозначения → атрибуты → служебные
атрибуты. После каждой позиции мост сообщает, что сделано, а Flux
записывает это в журнал выгрузки.

- **Служебные атрибуты пишутся последними.** Устройство без `FLUX_ID`
  означает, что запись не дошла до конца. Повтор находит такие устройства
  по временной метке выгрузки и дописывает их, а не создаёт вторые.
- **Обрыв посреди выгрузки** (E3 закрыли, E3 упал, Flux закрыли): запись
  выгрузки остаётся «прервана, сделано 7 из 12». При следующем открытии
  E3Flux предлагает «Продолжить» или «Убрать сделанное». Повтор по
  `FLUX_ID` не создаёт дублей.
- **Отмена выгрузки:** «Убрать из E3 то, что поставила эта выгрузка».
  Удаляются только устройства, созданные ею, и только если инженер их не
  трогал после выгрузки: не провёл к ним провода, не правил. Иначе такое
  устройство показывается в отчёте, и решает инженер. На отмену средствами
  E3 Flux не полагается: история отмены E3 через COM ненадёжна, и
  инженер мог успеть сделать что-то своё.
- **E3 занят** (открыт диалог, идёт пересчёт): COM отвечает «занято»; мост
  ждёт и повторяет. Через 30 секунд — сообщение «E3 не отвечает: закройте
  открытые окна E3» с кнопкой «Повторить».

### 8.3 После выгрузки

- Отчёт: что создано и где, что пропущено и почему.
- Запись в журнале Flux (`ActionLog`) и в истории позиции: «Выгружена в
  E3: Корпус 3 — ВК, лист 12, −M1».
- В Оборудовании у позиций появляется строка «В схеме E3». ОВ видит, что
  его подбор уже ушёл в схему КИП, и что переподбор этой позиции коснётся
  чужой работы.

## 9. Связь и переподбор

### 9.1 Как Flux узнаёт своё в E3

Служебные атрибуты в E3 (их заводит администратор базы E3; без них
выгрузка запрещена — 5.4):

| Атрибут | На чём | Значение |
|---|---|---|
| `FLUX_PROJECT` | Проект E3 | uuid связи «проект E3 ↔ проект Flux» |
| `FLUX_ID` | Устройство | ID позиции Flux (раздел 1) |
| `FLUX_VER` | Устройство | Версия позиции, которую выгрузили |
| `FLUX_EXPORT` | Устройство | ID выгрузки |

**Главный ключ — `FLUX_ID` в E3, а не номер устройства E3.** Номер
устройства E3 меняется при копировании листа и переносе в другой проект, а
атрибут переезжает вместе с устройством. Мост перед каждой работой читает
все устройства с `FLUX_ID` (`readBound`). Это и есть картина «что сейчас в
схеме».

Во Flux (общая база) хранится, **что было отправлено:**

```
E3Project      id, fluxProjectId, key (FLUX_PROJECT), name, path,
               e3Version, partsDb, lastSeenAt

E3Export       id, e3ProjectId, sheet, by, at, state
               (PLANNED | RUNNING | DONE | INTERRUPTED | UNDONE),
               classifierVersion, planJson, reportJson

E3Binding      id, e3ProjectId, elementId (ID позиции),
               ruleId, manualRule, component, symbol, designation,
               sheet, x, y, rotation  — где поставили при выгрузке,
               sentVersion            — версия позиции на момент выгрузки,
               sentAttrsJson          — какие значения записали,
               overridesJson          — ручные значения инженера КИП,
               state (PLACED | REMOVED_IN_FLUX | DELETED_IN_E3 | DETACHED),
               lastExportId
               уникально: (e3ProjectId, elementId)
```

Одна позиция может стоять в нескольких проектах E3 (разные разделы,
ревизии). У каждого проекта своя связь.

### 9.2 Три стороны сравнения

Каждая повторная выгрузка сравнивает три состояния позиции:

- **Отправлено** — `E3Binding` (что Flux записал в прошлый раз);
- **Сейчас во Flux** — позиция, её подбор и атрибуты по текущим правилам;
- **Сейчас в E3** — `readBound`.

Из этого видно, кто что менял: Flux (переподбор), E3 (рука инженера КИП)
или оба. Двух сторон не хватило бы: без «отправлено» нельзя отличить
переподбор от ручной правки в E3.

### 9.3 Все случаи

| # | Что произошло | Что предлагает E3Flux | По умолчанию |
|---|---|---|---|
| С1 | Во Flux изменились характеристики, подбор тот же | Обновить изменившиеся атрибуты | Обновить |
| С2 | Изменился компонент, символ тот же (другая мощность двигателя) | Заменить компонент на месте: положение, обозначение и провода остаются | Заменить |
| С3 | Изменился символ или фрагмент (привод без пружины → с пружиной) | Поставить новый символ на место старого. Если выводы совпадают — провода переподключаются. Если нет — висящие провода перечисляются в отчёте | Заменить, с отчётом |
| С4 | Позиция снята во Flux | В E3 не удалять молча: показать «снята во Flux». Инженер выбирает: удалить / оставить и отвязать / оставить как есть | Оставить, пометить атрибутом `FLUX_STATUS = снята` |
| С5 | Во Flux новая позиция в выгруженной установке | В списке «не в схеме», на холсте — предложенное место рядом с группой | Не выгружать без отметки |
| С6 | Переподобрано (новый ID, связь «заменено на» — 1.4) | Заменить в E3 старую позицию новой на том же месте, как С3 | Заменить |
| С7 | Изменился тег | Обновить атрибуты с тегом. Обозначение E3 меняется, только если оно строится по тегу | Обновить |
| С8 | Инженер КИП правил атрибут в E3 | «В E3: 5,0 · отправляли: 5,50 · во Flux: 5,50» — оставить значение E3 / записать значение Flux | Оставить значение E3 |
| С9 | Атрибут правили и в E3, и во Flux | Показать все три значения и спросить | Не трогать до решения |
| С10 | Инженер сдвинул символ в E3 | Положение берётся из E3, на холсте символ стоит там же | Не двигать |
| С11 | Инженер удалил устройство в E3 | «Удалено в E3»: выгрузить снова / считать, что на схеме не нужно (связь DETACHED, больше не предлагать) | Не восстанавливать |
| С12 | Инженер скопировал устройство в E3 (у копии тот же `FLUX_ID`) | «Два устройства с одним ID»: какое главное; второе отвязать | Спросить до любой записи |
| С13 | Проект E3 скопирован (новая ревизия): у копии тот же `FLUX_PROJECT` | Распознать копию: путь другой, а ключ тот же. Предложить «это новый проект — завести свою связь» (новый ключ, связи скопировать) / «тот же проект переехал» | Спросить |
| С14 | Изменился классификатор: позиция подобралась бы иначе | Показать «по новым правилам: …». Без согласия инженера не менять | Не менять |
| С15 | Ручной выбор правила, а у позиции сменился тип | Ручной выбор снять, показать новый подбор | Новый подбор |
| С16 | Позиция стала «нужен выбор» (нет правила, не хватает атрибута) | Выгружать её нельзя, остальные — можно | Пропустить её |
| С17 | ОВ переподбирает, пока КИП выгружает | Выгрузка идёт по снимку на момент нажатия «Выгрузить». После неё позиции видны как «изменилась» | Снимок |
| С18 | Две выгрузки одной установки в один проект E3 одновременно (два инженера КИП) | Вторая видит, что проект E3 занят выгрузкой (запись RUNNING), и ждёт | Ждать |

Всё, что E3Flux меняет в уже выгруженном, проходит через тот же план
(8.1): «обновить 5 атрибутов у 3 устройств, заменить 1 компонент,
удалить 0».

### 9.4 Уведомления

- Позиция, стоящая в схеме E3, изменилась во Flux → уведомление
  (`Notification`) тому, кто выгружал: «П1: изменились 3 позиции,
  выгруженные в Корпус 3 — ВК». Одно уведомление на импорт, а не на
  каждую позицию.
- При импорте у ОВ предпросмотр показывает: «5 позиций этой установки уже
  в схеме КИП». Это не запрет, а предупреждение, что переподбор заденет
  чужую работу.

## 10. Подключение к E3: все состояния

| Состояние | Что видит инженер | Что можно |
|---|---|---|
| Flux в браузере, не настольный | «Выгрузка в E3 — только в настольной версии Flux» | Подбор, атрибуты, раскладка |
| Не Windows | То же | То же |
| E3 не запущен | «E3.series не запущен» · «Проверить снова» | Подбор, раскладка, демонстрация из кеша |
| E3 запущен, проект не открыт | «Откройте проект в E3» | То же |
| Открыто несколько E3 | Список: версия, проект | Выбрать |
| Проект открыт впервые для Flux | «Связать проект E3 с проектом Flux „…“?» → ставится `FLUX_PROJECT` | Всё после согласия |
| Проект E3 уже связан с другим проектом Flux | «Этот проект E3 связан с проектом Flux „…“» | Переключиться на тот проект или перевязать (с предупреждением) |
| Нет активного листа | «Откройте лист» или «Создать новый лист при выгрузке» | Всё |
| Лист или проект только для чтения (взят другим, заблокирован) | Причина словами | Подготовка без выгрузки |
| Версия E3 не проверена с Flux | Предупреждение с версией | Всё, на свой риск |
| В базе E3 нет служебных атрибутов | «Администратор базы E3 должен завести атрибуты FLUX_…» со списком | Подготовка без выгрузки |
| База компонентов E3 не та, по которой сверен классификатор | «Компоненты из классификатора не найдены: N» | Выбрать вручную |
| E3 занят диалогом | «E3 занят: закройте открытые окна E3» | Повторить |
| E3 закрылся во время работы | Связь серым, выгрузка «прервана» (8.2) | Продолжить после запуска |

## 11. Права

- **Открыть E3Flux и выгружать** — новое право `e3.export`. По умолчанию
  у роли КИП.
- **Править классификатор и атрибуты** — право каталога (`catalog.manage`)
  или отдельное `e3.catalog`. Это вопрос владельцу (раздел 13).
- **Видеть «В схеме E3» в Оборудовании** — все, кто видит оборудование.
- Сервер проверяет право на каждом маршруте записи. Запись закупки, где
  право сейчас не проверяется, уже числится в плане как известная
  дыра — повторять её не надо.

## 12. Этапы

Каждый этап — отдельный PR.

| Этап | Что | Проверки в контейнере |
|---|---|---|
| **A. ID позиции** | Часть 1 целиком: каскад сопоставления, «снята», `__unit__` всегда, версия, план с вариантами | `test-equipment-identity`, план = запись |
| **B. Каталог E3** | Классификатор и атрибуты: модель, таблицы, загрузка из файла с планом и откатом, расчёт подбора и атрибутов (`e3/`) | Подбор по точности, ничья → «нужен выбор», преобразования, загрузка/откат |
| **C. Мост** | Помощник C#, команды `status`, `projectKey`, `listParts`, `attrDefs`, `readBound`; сверка с базой E3 | Только разбор ответов. **Сам мост — на компьютере с E3** (раздел 13) |
| **D. Окно E3Flux** | Три колонки, состояния позиций, холст листа, ручная раскладка и «Разложить», страница программы | Раскладка, зонд `test-design-live` |
| **E. Демонстрация** | `preview`, кеш изображений, символы на холсте | Кеш, отрисовка из кеша |
| **F. Выгрузка** | План, запись по шагам, журнал, продолжение, отмена | План и сверка «три стороны» на подставном мосте |
| **G. Переподбор** | Случаи С1–С18, уведомления, «В схеме E3» в Оборудовании | Каждый случай — проверка на подставном мосте |

Подставной мост — объект с теми же командами, который хранит «проект E3» в
памяти. На нём в контейнере проверяется вся логика F и G. Настоящий E3
нужен только для проверки самого моста и приёмки.

## 13. Нужно от владельца

1. **Файлы классификатора и атрибутов** — до сессии не дошли. Без них
   этап B делается на формате из раздела 5, и столбцы сверяются потом.
2. **Версия E3.series** у отдела КИП и **доступ к компьютеру с E3** для
   этапа C: имена методов COM, экспорт изображения символа и поведение при
   «занят» проверяются только на настоящем E3.
3. **Решения:**
   - демонстрация через временный лист в проекте инженера (вариант А) — да
     или нет;
   - позиция, снятая во Flux, в E3 по умолчанию остаётся с пометкой (С4) —
     или удаляется;
   - при споре атрибута (С8) по умолчанию главнее значение из E3 — или из
     Flux;
   - кто правит классификатор: те же, кто каталог, или отдельное право;
   - нужны ли в E3Flux провода и клеммы (сейчас проект их не создаёт:
     выгружаются устройства, символы и атрибуты; провода рисует инженер в
     E3).
4. **Пример схемы КИП** (лист E3 в PDF), нарисованной руками, — по нему
   настраиваются «Разложить» и группы на листе.
