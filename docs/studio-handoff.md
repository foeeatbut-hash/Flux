# Flux Studio — задание на разработку

Задание для внешнего исполнителя (другой ИИ-агент или программист). Пишется
для того, кто впервые открывает репозиторий. Владелец — заказчик, приёмку
каждого PR делает руководитель разработки Flux.

Репозиторий: https://github.com/foeeatbut-hash/Flux

## 0. Прочитать до начала

1. `AGENTS.md` — постоянные правила репозитория (подготовка, проверки,
   экономия контекста, что нельзя коммитить). Обязательно.
2. `docs/roadmap/modules.md` — **сам план Flux Studio** (решения владельца от
   29 октября и 4 ноября 2026, устройство, этапы 1–11). Это главный документ;
   здесь — только порядок работ и критерии приёмки.
3. Навыки `.claude/skills/flux-architecture`, `flux-style`, `flux-verify`,
   `flux-data-safety` — где класть код, стиль и токены оформления, как
   проверять, правила записи в базу.
4. `docs/methodology/01-design.md` (разделы 5 и 8) — компоненты интерфейса и
   проверочный список; новые экраны делаются по нему.

## 1. Что строим (коротко)

**Flux Studio** — программа разработчика, в которой **любой разработчик**
делает свою подпрограмму (модуль) для Flux. Модуль выкладывается через общую
базу и сразу появляется у всех Flux — без выпуска нового portable.

Решения владельца, которые нельзя нарушать:

- **Данные Flux — только на чтение.** Модуль читает любые данные Flux
  (проекты, оборудование с параметрами, теги, спецификации, каталог, файлы
  Проводника, ВДР) через договор, но **ничего во Flux не правит**. Данные в
  окне модуля актуальны: оболочка передаёт события «данные изменились».
- **Одна универсальная оболочка во Flux.** Модуль сам объявляет, где
  появляется («Пуск», карточка оборудования, карточка тега). Под каждый модуль
  portable не меняется.
- **Цепочка доверия.** Flux запускает только выпуск, подписанный ключом
  разработчика, чей сертификат подписан ключом владельца (корень зашит в exe,
  как `electron/updateKey.ts`). Запись в таблицу модулей SQL-запросом в обход
  подписи не запускается.
- **Изоляция.** Чужой код не видит cookie, `localStorage`, IPC, сеть Flux.
- **Первый настоящий модуль — E3Flux** (связь с E3.series): мост к E3 (COM)
  остаётся во Flux, логика E3Flux — в модуле. Это этап 11, не раньше.

## 2. Порядок PR

Каждый пункт — **отдельный PR в `main`**, маленький и проверенный. Не
начинать следующий, пока предыдущий не принят.

| PR | Этапы плана | Что | Готово, когда |
|---|---|---|---|
| 1 | 1 + 2 | Договор v1 (только чтение), универсальная оболочка, изоляция и мост, пример-модуль, события «данные изменились» | см. раздел 3 |
| 2 | 3 | Выпуски модулей в базе (`ModuleRelease`/`ModuleChunk` по образцу `server/updates.ts`), подпись, сертификаты, отзыв, кэш проверенных | выпуск без подписи, с изменённым куском или отозванным ключом не запускается; прошлая проверенная версия продолжает работать |
| 3 | 4 | Права `module.develop`, `module.publish` (по образцу `catalog.*`), каналы «тестовый/рабочий», откат | права проверяются сервером; откат возвращает прошлую версию у всех |
| 4 | 5 | Flux Studio как вторая цель сборки в том же CI и с тем же номером версии; вход, ключ разработчика в `safeStorage`, тестовая база с образцами, публикация | Studio собирается в CI вместе с Flux; разработчик публикует пример-модуль в тестовый канал, Flux его запускает |
| 5 | 6–7 | Проверка связок, панель разработчика, методология дизайна внутри Studio | по плану |
| 6 | 11 | Перенос E3Flux в модуль: мост к E3 как возможность договора | после ответа владельца на вопросы раздела 5 |

Этапы 8–10 (перенос другой логики, Python/WebAssembly, отдельный процесс) —
только по отдельному решению владельца.

## 3. PR 1 подробно

**Договор v1** (версионированный, JSON Schema на каждое сообщение):
- чтение: проект, позиция оборудования (параметры, состав, тег), тег,
  спецификация, каталог — минимум, нужный примеру;
- событие от оболочки: «открыт из карточки», «проект сменился», «данные
  изменились» — по существующим `entity:changed` (`server/entityChanged.ts`) и
  живым обновлениям; модуль перечитывает;
- записи нет: сообщение-запись отклоняется оболочкой.

**Универсальная оболочка:** окно модуля, место в «Пуске», вход из карточки
оборудования и тега по объявлению модуля. Интерфейс — по методологии.

**Изоляция и мост:** протокол `flux-module://`, `<iframe sandbox>` **другого
источника**, своя CSP, `postMessage` с проверкой источника и схемы (образец —
`src/lib/officeBridge.ts`, но у него нет `sandbox` и тот же источник: для
чужого кода этого мало), Web Worker с пределом времени для расчёта. Белый
список IPC (`electron/ipcAllow.ts`) модулям ничего не открывает.

**Пример-модуль:** простой модуль на TypeScript, написанный вручную, —
показывает выбранную позицию оборудования и её параметры, обновляется при их
изменении. Пока модуль кладётся в репозиторий как фикстура (выпуски — PR 2).

**Проверки** (наборы `scripts/test-*.ts`, по `flux-verify`):
- модуль не читает cookie и `localStorage` Flux, не вызывает IPC, не ходит в
  сеть; сообщение не по схеме отбрасывается; попытка записи отклоняется;
  зависший расчёт останавливается по времени;
- правка позиции во Flux доходит до открытого модуля;
- снимки окна модуля в обеих темах (`flux-verify`).
- Каждая новая проверка должна **падать без правки** — показать это в PR.

## 4. Правила работы

- Ветка от свежего `main`, имя `studio/<коротко>`; force-push не использовать.
- Тексты коммитов, PR, комментариев — по-русски, про «почему»
  (`flux-style`). Имя модели — нигде в коммитах, PR и коде.
- Кто меняет программу, обновляет её страницу в
  `docs/methodology/03-programs/`; внедрённый этап отмечается в
  `docs/roadmap/modules.md` (раздел «Внедрено») и в `docs/plan.md`.
- Готовность — только после зелёного CI для последнего коммита, включая
  Windows. Что не проверено (Windows вручную, E3) — прямо написать в PR.
- Не расширять задачу: нашёл проблему вне PR — записать в PR как находку, не
  чинить попутно.

## 5. Решения, которые ждут владельца

По умолчанию работаем по рекомендации; владелец может поменять.

1. Связи «позиция ↔ блок в схеме E3»: собственное хранилище модуля или
   существующие таблицы с правом писать только в них. *Рекомендация:*
   существующие таблицы, запись модулю — только в них (нужно к PR 6).
2. Выкладка новых версий модуля: сразу всем или через тестовый канал.
   *Рекомендация:* через тестовый (нужно к PR 3).

## 6. Как сдавать

PR в `main` черновиком с разделами: что сделано и почему; чем проверено
(наборы, снимки, CI); что не проверено; находки. Приёмку делает руководитель
разработки Flux: проверяет код, прогоняет наборы и смотрит снимки; замечания —
в PR.
