# Подразделения: филиалы, отделы, права и обновления по структуре

Статус: проект, ждёт решений владельца (раздел 9). Кода ещё нет.

## 1. Зачем

Компания работает в нескольких городах. Сейчас все сотрудники — один плоский
список: права даются по роли или лично, обновления назначаются по списку
устройств, настройки — глобальные или личные. Нужно:

- распределять людей по подразделениям при создании, импорте и потом;
- давать права, настройки и обновления подразделению целиком;
- поручать управление подразделением его руководителю, не делая его
  администратором всей компании;
- видеть и фильтровать всё по подразделениям: людей, устройства и версии,
  лицензии, журнал.

## 2. Что есть сейчас

- `User.department` — свободный текст. Его пишет только импорт, а экран
  «Сотрудники» его не показывает. Справочника подразделений нет.
- Права: `Role.permissions` и `User.permissions`, JSON вида
  `{feature: {enabled, until, mode}}`. Решает `shared/appPolicy.ts → decide()`:
  личное, затем роль, затем отказ. Ключи `admin.*` даёт только явная запись.
- Настройки: `AppSetting(key, userId|null)` — глобальные или личные.
- Проекты: `ProjectMember(projectId, userId)`. Проект без участников виден всем.
- Обновления: кампании по устройствам, фильтр — только на клиенте (список
  «Сотрудников»). Делегирование от Owner ограничивает число устройств и срок.
- Лицензии: по логину, без группировки.
- Журнал действий, уведомления, общие ящики: без подразделений.

## 3. Модель данных

Все таблицы — в трёх схемах Prisma и `ddl.ts` (SQLite, PostgreSQL, MariaDB).
Новые поля только добавляются, существующие не ломаются.

**Department** — узел дерева:
`id, name, shortName, kind ('company'|'branch'|'division'|'group'), city?,
timezone (IANA, например 'Asia/Novosibirsk'), parentId?, sortOrder, archivedAt?,
createdAt, createdBy`.

- Корень «Компания» создаётся сам. Филиал (город) содержит отделы, отдел —
  группы. Глубину ограничивает только здравый смысл; в интерфейсе нужно 2–3
  уровня.
- Подразделение не удаляют, а отправляют в архив. Пока в нём есть люди или
  проекты, архивация требует перевода людей.

**User.departmentId** — основное подразделение (одно). Старое текстовое
`department` остаётся и показывается как подсказка при переносе.

**UserDepartmentLink** `(userId, departmentId, kind: 'extra')` — доступ к
другим подразделениям: командированный, совместитель. Наследование прав идёт
только от основного подразделения, а дополнительные дают видимость.

**DepartmentAdmin** `(departmentId, userId, scopes JSON, until?)` — кто
управляет подразделением. Области: `users` (заводить и править людей),
`access` (права подразделения), `updates`, `projects`, `settings`, `logs`.
Действует на подразделение и всё его поддерево.

**DepartmentPolicy** `(departmentId, permissions JSON, settings JSON,
defaults JSON, updatedBy, updatedAt)`:

- `permissions` — тот же формат PermMap, но без ключей `admin.*`;
- `settings` — значения по умолчанию для людей подразделения: тема, язык,
  тихие часы, адрес сервера, почта и т. д.;
- `defaults` — роль и права для новых сотрудников подразделения, шаблон
  логина, срок доступа.

**UserDepartmentHistory** `(userId, from, to, by, at, reason)` — история
переводов, для проверки и отчёта.

В записи журнала действий и в устройстве обновлений хранится снимок
`departmentId` на момент события, чтобы отчёт за прошлый месяц не менялся
после перевода человека.

## 4. Как решаются права

Новый порядок в `decide()`, одном для окна и сервера:

1. профиль (активен, срок), платформа, владелец — как сейчас;
2. личное DENY или ALLOW;
3. **подразделение**: политика основного подразделения, затем его
   родителей вверх по дереву, ближайший уровень сильнее;
4. роль;
5. по умолчанию — отказ.

Подразделение может и выдать возможность, и запретить её. Например, филиалу
в Новосибирске закрыть «Каталог», а ОВиК дать «E3Flux». Личное по-прежнему
сильнее всего: исключение для одного человека не требует нового отдела.
Ключи `admin.*` подразделение не выдаёт, их дают только Owner и
администратор компании.

На экране прав рядом с каждой возможностью видно, откуда пришло решение:
«лично», «ОВиК (Новосибирск)», «роль Инженер ОВиК», «по умолчанию».

Настройки разрешаются тем же порядком: личное → подразделение вверх по
дереву → глобальное → встроенное по умолчанию.

## 5. Кто чем управляет

| Кто | Что может |
|---|---|
| Owner | всё; выпускает лицензии и делегирование обновлений |
| Администратор компании (ADMIN, 1 уровень) | всё дерево, назначает руководителей подразделений |
| Администратор подразделения (`DepartmentAdmin`) | только своё поддерево и только в выданных областях |
| Сотрудник | видит своё подразделение и коллег; ничего не правит |

Правила для администратора подразделения:

- заводит людей только в своё поддерево; переводит только внутри него (в
  чужое — запрос администратору компании);
- выдаёт роли не выше своей и уровнем ниже своего (`Role.level`); не выдаёт
  `admin.*`;
- назначает обновления только устройствам своих людей и в пределах
  делегирования, выданного ему Owner (лимит устройств и срок — как сейчас,
  плюс поле «подразделение» в делегировании);
- видит журнал только своего поддерева, если ему выдана область `logs`.

Сервер проверяет каждое изменение по поддереву. Скрытой кнопки на клиенте
недостаточно.

## 6. Экраны

**«Сотрудники» → новая вкладка «Подразделения».** Слева дерево (город → отдел),
справа выбранное подразделение:

- шапка: название, город, часовой пояс, руководители, число людей и устройств;
- вкладки: «Люди», «Права», «Настройки», «По умолчанию для новых»,
  «Администраторы», «Обновления»;
- действия: создать подразделение (внутри выбранного), переименовать,
  перенести перетаскиванием в дереве, отправить в архив (с переводом людей).

**Вкладка «Список» сотрудников:**

- колонка «Подразделение» и фильтр-дерево слева, свёртываемое;
- поиск ищет и по подразделению;
- массовое действие «Перевести в подразделение…» для отмеченных строк;
- создание сотрудника: поле «Подразделение» (по умолчанию — выбранное в
  фильтре), а роль и права подставляются из `defaults` подразделения;
- импорт: колонка «Подразделение» сопоставляется со справочником. Новых
  подразделений предпросмотр предлагает создать (галочкой, по правилам
  flux-data-safety: план → предпросмотр → применение → откат).

**Перенос текущих данных.** Однократный мастер «Разложить сотрудников по
подразделениям». Он берёт уже имеющиеся тексты `User.department`, предлагает
создать подразделения и разложить людей, показывает предпросмотр, применение
можно откатить.

## 7. Подразделения в других программах

- **Обновления.**
  - Кампания выбирает подразделения, а не только устройства. Сервер сам
    раскрывает их в устройства и проверяет права назначающего.
  - Кольца выпуска: «пилотное подразделение → филиал → вся компания».
  - Окно установки задаётся по местному времени подразделения, например
    «после 19:00 по Новосибирску».
  - Версии и отставание видны по подразделениям.
- **Лицензии.** Обзор и запрос лицензий по подразделениям: сколько выдано,
  у кого истекают.
- **Проекты.** У проекта необязательное «ведущее подразделение». Участником
  можно добавить подразделение целиком: новые люди отдела получают доступ
  сами, переведённые — теряют.
- **Уведомления и чат.** Рассылка «всему подразделению». По желанию —
  автоматическая группа чата подразделения.
- **Почта.** Общий ящик можно открыть подразделению (сейчас общие ящики
  видны всем).
- **Журнал.** Фильтр по подразделению; администратор подразделения видит
  только своё.
- **Время.** Часы, сроки и события показываются по поясу сотрудника.
  Подразделение задаёт пояс по умолчанию.

## 8. Этапы

1. **Справочник и распределение.**
   - Таблицы `Department`, `User.departmentId`, история переводов.
   - Вкладка «Подразделения» (дерево, создать, переименовать, перенести, архив).
   - Колонка, фильтр и массовый перевод в «Списке».
   - Подразделение в создании сотрудника и импорте; мастер переноса старых
     текстов.
2. **Права и настройки по подразделению.** `DepartmentPolicy`, новый шаг в
   `decide()` (окно и сервер), показ происхождения решения, `defaults` для новых.
3. **Администраторы подразделений.** `DepartmentAdmin`, проверки поддерева на
   сервере для людей, прав и журнала.
4. **Обновления по подразделениям.** Выбор подразделений в кампании, кольца,
   окна по местному времени, отчёт версий. Поле подразделения в
   делегировании Owner.
5. **Остальные программы.** Проекты и почта для подразделения, рассылки,
   лицензии по подразделениям.

Каждый этап — отдельный PR со своими проверками: решение `decide()`
проверяется набором, поддерево — тестом на трёх СУБД.

## 9. Решения владельца (нужны до этапа 1)

1. **Глубина.** «Компания → город (филиал) → отдел» — достаточно, или нужны
   группы внутри отделов?
2. **Несколько подразделений.** У человека одно основное плюс дополнительные
   только для доступа, или полноценно несколько?
3. **Видимость между филиалами.** Сотрудник видит коллег других городов в
   списке, чате и присутствии? Предложение: людей видят все, проекты — по
   участию, как сейчас.
4. **Администраторы подразделений.** Разрешать им заводить людей и выдавать
   роли (не выше своей), или только смотреть и назначать обновления?
5. **Обновления.** Нужны ли окна установки по местному времени и пилотное
   подразделение?
