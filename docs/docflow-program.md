# Программа «Документооборот»

Статус: этап 1 реализован в PR #138, этап 2 — план; задание и критерии —
раздел 12. Устройство первого этапа — [страница программы](methodology/03-programs/docflow.md).
Решения владельца — 5 ноября 2026.

Решения владельца (5 ноября 2026), на которых построен документ:

1. «Документооборот» (ДО) — **отдельная программа**, «Менеджмент» остаётся
   отдельно. Настройки документооборота переезжают из «Менеджмента» в ДО.
2. **Документ — это и есть файл в Проводнике.** В имени файла записано,
   к какому проекту он относится, тип документа, ревизия, заказ и т. д.
   Строка ВДР — запись об этом файле в реестре.
3. Связать файл со строкой ВДР можно **из ДО** и **из Проводника** (правой
   кнопкой). Из Проводника человек сам называет файл и привязывает; если
   имя не сходится со строкой — связать нельзя, видно почему. Из ДО: если
   имя файла некорректное — ДО показывает ошибки и предлагает
   переименовать в правильное (или человек исправляет сам).
4. Старые свойства, которые накладывались на файл (теги и т. п.), и старый
   «Проводник проекта» — **просто удалить**: сейчас ими не пользуются; другие
   функции программы при этом не должны сломаться.
5. Настройки документооборота **у каждого проекта свои** и переносятся из
   проекта в проект.
6. Комплект документов по типу оборудования (приточная установка ВЕРОСА →
   E02, C32, C01 …) **задаётся в ДО**; типы оборудования берутся из
   **Каталога**.
7. Есть **общий каталог** и **каталог проекта**.
8. Формирование документов — **пока без внутреннего заполнения** данными;
   заполнение проработаем позже.
9. Замечания заказчика приходят **отдельным файлом (возврат)**. В ДО у строки
   указывают путь к скачанному файлу — ДО сам **перемещает** его в папку
   возвратов, назначенную в настройках, и ставит ссылку. В Реестре всё —
   ссылками: столбцы строки, затем «Файл», затем «Возврат». Так же из ДО
   назначаются и сами файлы документов. Назначать файлы и возвраты может
   только тот, кому это право выдал администратор.
10. Автосвязь: **всегда спрашивать**. Копия при выпуске — **пока нет**, решим
    позже. Право на каталог проекта — **кому назначит администратор** в
    «Сотрудниках».
11. Внедрение — **не дробить на много этапов**.

Предшественники: [docflow-integration.md](docflow-integration.md) (этапы
0 и A сделаны в #133; этот документ заменяет его этапы B–G и раздел 5),
[vdr-docflow-design.md](vdr-docflow-design.md) (что такое ВДР). Сервер — единый
обработчик выпусков и сверки ([roadmap/offline-work.md](roadmap/offline-work.md)).

## 1. Понятия — один словарь

| Понятие | Что это |
|---|---|
| **Документ** | файл в папке проекта. Его имя по **маске проекта** несёт шифр: проект, заказ, тип документа (код ВДР, напр. E02), номер, ревизию, при желании тег |
| **Строка ВДР** | запись о документе в реестре: шифры (подрядчик/заказчик/поставщик), наименование RU/EN, тип, теги, стадия, ответственный, сроки, история ревизий. Сервер, `DocRegisterItem` |
| **Ревизия** | A, B, C… (на рассмотрение) → 0, 1, 2… (окончательные). **Каждая ревизия — свой файл** (ревизия есть в имени); строка ВДР хранит, какой файл какой ревизии |
| **Файл замечаний** | файл, который вернул заказчик; привязывается к выданному файлу ревизии (раздел 7.3) |
| **Маска имени** | правило проекта, как из имени файла читаются шифр, тип, ревизия и т. д. и как имя собирается из строки ВДР |
| **Комплект** | какие типы документов нужны для типа оборудования (класса Каталога) — задаётся в ДО |
| **Настройки ДО проекта** | статусы, ревизии, коды, типы документов, маски, папки, комплекты, сроки, подписанты |

Главное правило: **имя файла и строка ВДР должны совпадать по маске.** ДО и
Проводник проверяют это при связывании и показывают расхождения; поэтому у
файла нет отдельных «свойств» — всё про него видно из имени и строки ВДР.

## 2. Программы и где что

**«Документооборот»** — новый раздел в «Пуске» (`/docflow`, свой значок),
вкладки:
- **Реестр (ВДР)** — то, что сейчас `VdrPanel`, плюс файлы ревизий, выпуск,
  замечания;
- **По тегам** — для каждого тега проекта: какие документы нужны по
  комплекту, какие есть, что выпущено (раздел 6);
- **Выпуски** — история выпусков проекта;
- **Сверка с папкой** — расхождения между папкой проекта и реестром (раздел
  4.3);
- **Настройки** (кто вправе) — по проекту, с переносом (раздел 5).

**«Менеджмент»** — остаются закупки и управление проектом. Старые адреса
`/management?tab=vdr`, `?tab=docflow`, `?vdr=` ведут в ДО (перенаправление,
ссылки в уведомлениях не ломаются).

Права: `docflow.view`, `docflow.edit`, **`docflow.files`** (назначать файлы и
возвраты строкам — решение владельца: только кому выдал администратор),
`docflow.issue`, `docflow.settings`, `docflow.delete` (вместо `vdr.*`;
переводятся один к одному, роли не теряют того, что имели; `docflow.files` по
умолчанию — только администратору). Права выдаёт администратор в
«Сотрудниках».

## 3. Проводник ↔ документооборот

### 3.1 Папки проекта

«Привязать папку» (есть) расширяется: у привязанной папки — **проект** и
**назначение**: «Рабочая» (документы в работе), «Выпуск» (выданные),
**«Возвраты»** (файлы замечаний заказчика — их туда кладёт ДО, 7.3),
«Входящие» (прочее от заказчика: исходные данные). Структура внутри — по
маске папок проекта (раздел 5). Ключ — как сейчас, `locationKey` сетевой
папки.

### 3.2 Что видно в Проводнике (папка проекта, вид «Таблица»)

- новые столбцы (включаются в «Просмотреть»): **Шифр**, **Тип**, **Ред.**,
  **Статус** (точка и слово), **В реестре** (наименование строки ВДР или
  «—»);
- значок у имени, если имя **не по маске** проекта (подсказка — что именно
  не так: «нет ревизии», «неизвестный тип „E2“»);
- фильтры: «В реестре», «Нет в реестре», «Имя не по маске»;
- **«Сведения»** (правая панель) для файла из реестра — строка ВДР: шифр,
  наименование, тип, теги, ревизия этого файла и последняя ревизия
  документа, статус, ответственный, срок, история ревизий с файлами, файлы
  замечаний; кнопки «Открыть в ДО», «Выпустить…» (раздел 7).

### 3.3 Меню правой кнопки (файл в папке проекта)

Новый подраздел меню **«Документооборот ▸»**:
- **Связать со строкой ВДР…** — выбор строки проекта (поиск по шифру,
  названию, тегу; сверху — строки, чей шифр совпадает с именем файла).
  **Проверка имени**: шифр, тип и ревизия из имени по маске сравниваются со
  строкой. Если не сходится — **связать нельзя**, окно показывает
  расхождения по полям («в имени тип C32, в строке E02»); человек
  переименовывает файл сам (F2) и пробует снова. Если ревизия в имени новая
  для строки — файл становится файлом этой ревизии (черновик ревизии).
- **Добавить в реестр…** — новая строка ВДР, поля заполнены из имени по
  маске (шифр, тип, ревизия), наименование и теги — ввести; имя не по маске —
  сначала исправить.
- **Назначить возвратом к…** (для файла замечаний) — раздел 7.3.
- **Открыть в ДО**, **Выпустить…**, **Отвязать** (связь — в истории).
- Для папки: **«Сверить с реестром»** — открывает «Сверку с папкой» по этой
  папке.

### 3.4 Перетаскивание

Файл из Проводника на строку Реестра ДО → «Привязать к строке» с той же
проверкой имени (3.3 / 4.2). Работает и между окнами Flux.

### 3.5 Слежение за файлом

- **Переименовали / перенесли в Windows** — связь держится по ключу папки и
  отпечатку содержимого; новое имя снова проверяется по маске: перестало
  сходиться — строка показывает «имя файла не совпадает со строкой» с
  выбором «вернуть имя» / «отвязать».
- **Изменили после выпуска** — файл помечается «изменён после выпуска ред. B».
- **Удалили** — строка показывает «файл ред. B удалён», связь в истории.

### 3.6 Что удаляется

Сейчас этим не пользуются — удаляется без мастера переноса, но так, чтобы
остальная программа работала:
- **локальные свойства файла** — теги, проекты, ревизия, ответственный
  (`electron/filesystem/state.ts`, `WindowsFileMetadata`; правка в
  `PropertiesWindow`): убрать вывод и правку, хранение и команды моста
  `setMetadata`; проверить и поправить всех, кто их читает (поиск,
  сведения, свойства, копирование свойств, корзина, наборы проверок);
  история действий с файлом в Проводнике остаётся;
- **статусы файла D/C/B/A** (`FileItems.tsx`) — заменяются статусом строки
  ВДР;
- **`DocRegisterItem.fileNodeId`** (файл замечаний из серверного архива) —
  поле и вывод; замечания — раздел 7.3;
- упоминания «Проводник проекта» (`guide/engine.ts`, `MailThread.tsx`,
  `mailLink.ts`) — заменить на «папка проекта в Проводнике».
Серверный архив (`FileNode`, `/api/files`) этим планом **не** удаляется: у него
другие потребители (`dropUpload`, `fileBytes`, `saveToWindows`, `MdFileHost`,
`OfficeHome`, `Archives`) — их переводит пункт «Отказ от серверного архива» в
`plan.md`. ДО на архив не опирается.

## 4. Связь файла и строки ВДР

### 4.1 Два пути, оба с проверкой имени

1. **Из Проводника** — человек сам называет файл по маске и привязывает
   (3.3, 3.4). Не сходится — не привязывается, показаны расхождения.
2. **Из ДО** — в Реестре в столбце **«Файл»** у строки → «Назначить файл…»:
   выбор файла по пути (в папке проекта или где угодно, например в
   «Загрузках») или перетаскивание. Если имя некорректное — ДО показывает
   ошибки по полям и предлагает **«Переименовать в {правильное имя}»**
   (предпросмотр) или «Исправлю сам» (окно ждёт, пока имя станет
   правильным). Если файл лежит **вне рабочей папки проекта**, ДО
   **перемещает** его в рабочую папку по маске структуры (что и куда —
   показано до подтверждения; отмена — журналом отмены Проводника).
   Право — `docflow.files`.

Автоматически ничего не связывается: если имя файла совпало со строкой, ДО
**предлагает** связать (в «Сверке с папкой» и уведомлением), человек
подтверждает (решение владельца — всегда спрашивать).

### 4.2 Проверка имени

По маске проекта из имени читаются поля (шифр, тип, номер, ревизия, тег …) и
сравниваются со строкой ВДР. Результат — список: совпало / не совпало / нет в
имени / неизвестное значение (тип не из настроек, ревизия не по схеме).
Блокируют связь: другой шифр, другой тип, ревизия не по схеме. Предупреждения
(связать можно): нет необязательного поля.

### 4.3 «Сверка с папкой»

Сравнение рабочей папки проекта и реестра (то, что раньше неудачно названо
«файлы без документа»):

| Группа | Что это | Что сделать |
|---|---|---|
| Есть в реестре, файла нет | у строки нет файла текущей ревизии | «Привязать файл…» |
| Файл есть, в реестре нет | имя по маске, но такой строки ВДР нет | «Добавить в реестр» / «Связать с …» (если шифр совпал со строкой, но файл не привязан) |
| Имя не по маске | файл в рабочей папке, имя не читается | «Переименовать» / «Не документ» |
| Расходится | файл привязан, но имя и строка разошлись | «Вернуть имя» / «Переименовать по строке» / «Отвязать» |

«Не документ» исключает служебные файлы (можно сохранить правило: `*.bak`,
`~$*`). Сверка запускается кнопкой и при открытии папки проекта (без
изменений — только показывает).

## 5. Настройки документооборота проекта

В ДО → «Настройки» выбранного проекта:

| Раздел | Что | Пример |
|---|---|---|
| Статусы | список, порядок, цвет точки, какие разрешают выпуск | В работе → На проверке → Согласован → Выдан → Замечания → Принят; Аннулирован |
| Ревизии | схема по стадиям и причинам | A, B, C… для IFR; 0, 1, 2… для CEF; «V» — аннулирован |
| Причины выпуска | коды и названия | IFR, IFI, IFU, CEF, VOID |
| Коды рассмотрения | код заказчика → следующий статус | 1 принято, 2 с замечаниями, 3 отклонено, 4 для сведения |
| Типы документов | код ВДР, наименование RU/EN, стадия П/Р, шаблон файла | E02 «Общий вид», C32 «Опросный лист» |
| Маски | имени файла (поля и разделители), шифра, структуры папок | `{заказ}-{тип}-{номер}_{ред}` |
| Папки | рабочая, выпуск, **возвраты**, входящие и структура внутри каждой | возвраты: `Возвраты/{тип}/{шифр}/{ред}` |
| Комплекты | по классам оборудования из Каталога (раздел 6) | Приточная установка → E02, C32, C01 |
| Сроки | вехи проекта, сроки по типам документов, рабочий календарь | C32 — «Старт» + 10 раб. дней |
| Подписанты | разработал / проверил / утвердил / нормоконтроль | |
| Колонки ВДР | колонки, порядок, экспорт в формат заказчика | |

**Маска** настраивается конструктором: поля по порядку с разделителями,
примеры имён — сразу видно, как разберётся «3700-B01-E02-001_B.pdf»; проверка
на файлах папки проекта до сохранения.

**Перенос между проектами.** «Скопировать из проекта…» → источник → галочки
по разделам → **предпросмотр различий** → применить; отмена одним действием.
«Сохранить как шаблон» / «Создать из шаблона». Глобальный `DocStandard`
становится шаблонами; у проекта — своя копия, не ссылка; видно «скопировано
из ЗапСиб PDH2, 05.11.2026».

**Правка во время работы** не переименовывает существующие файлы; для них —
«Сверка с папкой» покажет, что разошлось.

## 6. Комплекты документов по типам оборудования

### 6.1 Тип оборудования у тега — из Каталога

Тип оборудования — **класс Каталога** (`CatalogClass`, напр. «Приточная
установка»). Сейчас у тега надёжного типа нет (`Equipment.type` —
AHU/FAN/VALVE…, категория — у системы), поэтому: `Equipment.catalogClassId`,
заполняется из выбранной модели Каталога, из импорта XML/бланка, вручную в
карточке; пока не задан — по соответствию `Equipment.type → класс` в
настройках ДО проекта.

### 6.2 Комплект задаётся в ДО

В настройках ДО проекта, раздел «Комплекты»: слева — классы оборудования из
Каталога, справа — комплект класса:

| Поле | Значение |
|---|---|
| Тип документа | из типов документов проекта (E02, C32, C01 …) |
| Стадия | П, Р или обе |
| Единица | на тег / на установку (группу тегов) / на проект |
| Обязательность | обязательный / по требованию заказчика / необязательный |
| Ответственная роль | должность по умолчанию |
| Срок | от какой вехи и сколько рабочих дней |
| Условие | по параметру оборудования (напр. «есть привод» → паспорт привода) |

Комплекты — часть настроек проекта, переносятся вместе с ними и через
шаблоны.

### 6.3 «По тегам»

Вкладка ДО и блок «Документы» в карточке тега: для тега с классом — нужные
типы и состояние каждого: нет строки / строка без файла / в работе / на
проверке / выдан ред. B / замечания / принят / не нужен в проекте. Сводка:
«Нужно 46 · есть 31 · выдано 12 · просрочено 3».

**«Создать недостающие строки»** — план → предпросмотр (строки, шифры и имена
по маске, ответственные, сроки) → применить → отмена (`flux-data-safety`);
повтор не создаёт дублей (ключ: тег + тип + единица).

**Новый тег в проекте** (вручную, импортом, из Каталога) — ДО показывает
подсказку «Для AHU-3 по комплекту нужно 3 документа — Создать строки / Позже».
Сам строки не создаёт. **Тег сняли** — его строки помечаются «тег снят»,
решает человек.

## 7. Выпуск и замечания

### 7.1 Выпуск

«Выпустить…» — у строки или выбранных строк Реестра, из «По тегам», из
Проводника. Право `docflow.issue`. Только при связи (номер ревизии выдаёт
сервер).

Окно выпуска:
1. Документы — для каждого: файл ревизии (по имени), причина (IFR…), дата.
2. **Проверки**: у строки есть файл этой ревизии; имя по маске и совпадает
   со строкой; статус разрешает выпуск; ревизия следующая по схеме; файл не
   правится сейчас коллегой.
3. «Выпустить» → сервер в одной транзакции записывает ревизии (как этап 0),
   статус «Выдан», дату; файл ревизии фиксируется (отпечаток) — правка после
   этого помечает «изменён после выпуска ред. B».

Копия в папку «Выпуск», заполнение штампа и сопроводительное письмо — **не
сейчас**, решение владельца позже (раздел 13).

### 7.2 Конструктор

Выпуск спецификаций Конструктора (`BuilderScreen` → `IssuePanel`) пока
остаётся как есть; объединение с выпуском ДО — после решения о копиях и
заполнении (раздел 13).

### 7.3 Возвраты (замечания заказчика)

Заказчик присылает замечания **отдельным файлом** — это **возврат** к
выданной ревизии. Человек скачивает его куда угодно (например, в «Загрузки»).

**Назначить возврат** (право `docflow.files`):
- в Реестре в столбце **«Возврат»** у строки → «Назначить возврат…» → выбрать
  файл по пути (или перетащить); выбрать, к какой выданной ревизии он
  относится (по умолчанию — последняя выданная), код рассмотрения (из
  настроек), дата получения;
- или в Проводнике на файле → «Документооборот ▸ Назначить возвратом к…» →
  выбрать строку.

**Что делает ДО:**
1. показывает, куда переместит: папка возвратов проекта по маске
   (`Возвраты/{тип}/{шифр}/{ред}/`), имя файла сохраняется (одинаковое имя —
   «(2)», как в Windows);
2. после подтверждения **перемещает** файл туда (отмена — журналом отмены
   Проводника) и ставит ссылку на него в столбце «Возврат» этой ревизии;
3. код рассмотрения задаёт следующий статус (принят / замечания → нужна
   следующая ревизия);
4. у выданного файла в «Сведениях» виден его возврат, у файла возврата — к
   какому выданному файлу он относится.

Файлов возврата у ревизии может быть несколько (замечания, размеченный PDF,
письмо) — столбец показывает первый и «+2». Сроки ответа на замечания — от
даты получения возврата.

### 7.4 Реестр — всё ссылками

Строка Реестра: столбцы данных строки (шифры, наименование, тип, теги,
ревизия, статус, ответственный, сроки — набор по «Колонкам ВДР» проекта),
затем **«Файл»** — ссылка на файл текущей ревизии (щелчок — открыть,
правой — «Показать в Проводнике», «Назначить другой…», «История файлов по
ревизиям»), затем **«Возврат»** — ссылка на файл возврата последней выданной
ревизии (те же действия). Пусто — кнопка «Назначить…» (видна только при праве
`docflow.files`). Файл не найден — ссылка красная с причиной
(«перемещён», «удалён») и «Найти…».

## 8. Создание файлов документов

**Пока без внутреннего заполнения данными** (решение владельца). «Создать
файл» у строки ВДР (или пакетно по тегу в «По тегам»):
- берёт **шаблон типа документа** из настроек проекта (пустой docx/xlsx,
  бланк) или пустой файл нужного формата;
- кладёт в рабочую папку проекта по маске структуры, **с правильным именем по
  маске** (шифр, тип, ревизия первой версии);
- сразу связывает со строкой; повторное нажатие не плодит копии («файл ред. A
  уже есть — открыть»).
Заполнение данными тега и оборудования (через привязки Flux Office) —
отдельная проработка позже.

## 9. Каталог проекта и общий каталог

- **Общий каталог** — как сейчас (`CatalogClass`, `CatalogFamily` …): классы,
  модели, параметры, бланки. Классы — источник типов оборудования для ДО.
- **Каталог проекта** — у проекта свой слой поверх общего:
  - **взять из общего** — позиция проекта ссылается на позицию общего и
    закреплённую ревизию; параметры можно **переопределить** для проекта
    (напр. характеристики привода в этом типе проектов) — видно, что
    изменено, «Сбросить к общему», «Обновить до новой ревизии общего» (с
    разницей);
  - **своя позиция** — только в этом проекте;
  - **поднять в общий** — через обычную публикацию Каталога (право
    `catalog.*`).
- В Оборудовании при выборе модели — источник «Каталог проекта» / «Общий»;
  по умолчанию проектный, если там есть.
- Хранение: `CatalogFamily.projectId` (пусто — общий), `basedOnFamilyId` +
  `basedOnRevision`, переопределения — разница к `dataJson`; проектная
  позиция не видна в других проектах.
- Право правки каталога проекта — `catalog.project`, выдаёт администратор в
  «Сотрудниках».
- Перенос настроек проекта может включать каталог проекта (галочка).

## 10. Без связи и одновременная работа

- Связи, строки, настройки — через сервер со сверкой версий (этап 0 сделан
  для ВДР); без связи — по [offline-work.md](roadmap/offline-work.md) (журнал

- Двое связали один файл с разными строками — второй получает понятный отказ

## 12. Задание

Исполнитель — внешний (правила — `AGENTS.md`, данные — навык
`flux-data-safety`, оформление — `docs/methodology/01-design.md`). **Два
этапа**, каждый — один PR в `main` с коммитом на шаг; после каждого шага
сборка и проверки шага зелёные; каждая новая проверка падает без правки.

### Этап 1 — ДО, Проводник, настройки проекта

1. Программа ДО (`/docflow`, Пуск), вкладки Реестр / По тегам (каркас) /
   Выпуски / Сверка с папкой / Настройки; перенос `VdrPanel` и
   `DocflowSettings`; перенаправления старых адресов; права `docflow.*` с
   переводом `vdr.*`; «Менеджмент» — без этих вкладок.
2. Настройки ДО **проекта** (раздел 5) с конструктором маски, переносом между
   проектами и шаблонами; глобальный `DocStandard` → шаблоны (миграция с
   предпросмотром).
3. Связь файл ↔ строка ВДР на сервере (`DocFileLink`: строка, ревизия, роль
   «файл ревизии» / «замечания», к какому файлу относятся замечания, ключ
   папки + путь, отпечаток); назначения папок; **проверка имени по маске**
   (4.2) — общий модуль для Проводника и ДО; право `docflow.files`.
4. Проводник: столбцы, значок «не по маске», фильтры, «Сведения» со строкой
   ВДР, меню «Документооборот ▸» (3.3), перетаскивание, слежение (3.5); ДО:
   столбец «Файл» со ссылкой и «Назначить файл…» (путь, переименование,
   перемещение в рабочую папку), «Сверка с папкой».
5. Удалить старое (3.6) так, чтобы остальное работало; обновить
   `explorer.md`, `management.md`, новая страница `docflow.md` в
   `docs/methodology/03-programs/`, справка.

**Готово:** файл со строкой связывается из Проводника и из ДО; несходящееся
имя не даёт связать и показывает расхождения; из ДО неправильное имя
исправляется переименованием с предпросмотром; переименование в Windows
перепроверяется; настройки одного проекта переносятся в другой с
предпросмотром и отменой; старые ссылки на ВДР открываются; снимки обеих тем;
наборы Проводника, где были локальные свойства, проходят.

### Этап 2 — Комплекты, каталог проекта, файлы, выпуск, замечания

1. Класс Каталога у оборудования (6.1); соответствие `Equipment.type → класс`
   в настройках ДО проекта.
2. Комплекты в настройках ДО (6.2), «По тегам» и блок в карточке тега (6.3),
   «Создать недостающие строки» с планом и отменой, подсказка при новом теге.
3. Каталог проекта (раздел 9) и право `catalog.project` в «Сотрудниках».
4. Создание файлов по шаблону с именем по маске (раздел 8), пакетно по тегу.
5. Выпуск (7.1), возвраты (7.3) — столбец «Возврат», назначение по пути с
   перемещением в папку возвратов.

**Готово:** у приточной установки в проекте видно, что нужны E02, C32, C01 и
что выдано; недостающие строки создаются с предпросмотром и не дублируются;
файл создаётся по шаблону в нужной папке с правильным именем и связанным;
выпуск пачки записывает ревизии одной транзакцией, повтор не плодит ревизий;
файл возврата из «Загрузок» назначается по пути, перемещается в папку
возвратов, в Реестре появляется ссылка, статус меняется по коду; каталог
проекта переопределяет параметр, не трогая общий.

Проверки обоих этапов: серверные наборы на SQLite и схема на трёх СУБД (CI
`security-db`), интерфейсные наборы Проводника и ДО, снимки обеих тем;
Windows (переименование, сетевые папки) — CI и вручную владельцем.
