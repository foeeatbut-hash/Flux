# Программа «Документооборот»

Статус: план, задание исполнителю — раздел 12 · 5 ноября 2026

Решения владельца (5 ноября 2026), на которых построен документ:

1. «Документооборот» — **отдельная программа**, «Менеджмент» остаётся
   отдельно. Настройки документооборота переезжают из «Менеджмента» в саму
   программу.
2. Файлы и документы связываются в обе стороны: файл из Проводника — со
   строкой ВДР, строка ВДР — с файлом; у файла автоматически появляются шифр,
   наименование, ревизия, статус.
3. Старые способы накладывать на файл теги и прочие свойства и старый
   «Проводник проекта» — пересмотреть и убрать, если мешают; всё строится
   заново вокруг документа.
4. Настройки документооборота (ревизии, статусы, коды и т. д.) **у каждого
   проекта свои**; их можно переносить из проекта в проект.
5. Комплект документов по типу оборудования (например, приточная установка
   ВЕРОСА → E02, C32, C01 …) задаётся в **Каталоге**, регулируется в проекте;
   тег с таким оборудованием в проекте показывает, какие документы нужны и что
   уже выпущено.
6. Есть **общий каталог** и **каталог проекта**: в проект можно взять позицию
   из общего или завести свою (например, характеристики привода для этого
   типа проекта).
7. Подробно продумать **выпуск документов** и **формирование бланков**.
8. Внедрение — **не дробить на много этапов**.

Предшественники: [docflow-integration.md](docflow-integration.md) (этапы
0 и A сделаны в #133; этот документ заменяет его этапы B–G и раздел 5),
[vdr-docflow-design.md](vdr-docflow-design.md) (что такое ВДР). Сервер — единый
обработчик выпусков и сверки ([roadmap/offline-work.md](roadmap/offline-work.md)).

## 1. Понятия — один словарь

| Понятие | Что это | Где живёт |
|---|---|---|
| **Документ** | одна строка ВДР: шифры (подрядчик/заказчик/поставщик), наименование RU/EN, тип документа (код ВДР, напр. E02), теги, стадия, ответственный, сроки | сервер, `DocRegisterItem` |
| **Ревизия документа** | A, B, C… (на рассмотрение) → 0, 1, 2… (окончательные); у каждой: причина, дата, файлы, замечания | сервер, `DocRegisterItemRevision` |
| **Файл документа** | файл в папке проекта, привязанный к документу с ролью: основной, исходник (native), замечания заказчика, скан с подписями | сервер хранит ссылку, файл — в Windows |
| **Тип документа** | код (E02), наименование, стадия, правила имени и шаблон | настройки проекта |
| **Комплект** | какие типы документов нужны для типа оборудования | Каталог (общий) + поправки проекта |
| **Настройки документооборота проекта** | всё, что раньше было в «Стандарте»: статусы, ревизии, коды, маски, папки, комплекты, сроки, подписанты, шаблоны | сервер, у проекта |
| **Выпуск** | событие «ревизия X документа(ов) выдана»: номер — только сервер, файлы замораживаются, формируется сопроводительное письмо | сервер |

Главное правило: **свойства файла — это свойства его документа**. У файла нет
своих тегов, ревизии и статуса; он их показывает из документа. Поэтому они не
расходятся.

## 2. Программы и где что

**«Документооборот»** — новый раздел в «Пуске» (`/docflow`, свой значок),
вкладки:
- **Реестр (ВДР)** — то, что сейчас `VdrPanel`, плюс файлы, ревизии, выпуск;
- **По тегам** — для каждого тега проекта: какие документы нужны по
  комплекту, какие есть, что выпущено (раздел 6);
- **Выпуски** — история выпусков и сопроводительные письма проекта;
- **Неразобранное** — файлы в папках проекта без документа и предложения
  связать (раздел 4.3);
- **Настройки** (кто вправе) — всё, что сейчас «Настройки документооборота» в
  «Менеджменте», но уже **по проекту**, с переносом (раздел 5).

**«Менеджмент»** — остаются закупки и управление проектом (вехи, сроки,
сводки). Старые адреса `/management?tab=vdr`, `?tab=docflow`, `?vdr=` ведут в
«Документооборот» (перенаправление, ссылки в уведомлениях не ломаются).

Права: `docflow.view`, `docflow.edit` (документы и файлы), `docflow.issue`
(выпуск), `docflow.settings`, `docflow.delete` (вместо `vdr.*`; `vdr.*`
переводятся один к одному, роли не теряют того, что имели).

## 3. Проводник ↔ документы

### 3.1 Папки проекта

«Привязать папку» (есть) расширяется: у привязанной папки — **проект** и
**назначение**: «Рабочая» (документы в работе), «Выпуск» (выданные ревизии,
только чтение для всех, кроме выпуска), «Входящие» (от заказчика: замечания,
исходные данные). Внутри рабочей — структура по маске настроек проекта
(стадия / раздел / тип документа, раздел 5). Ключ — как сейчас, `locationKey`
сетевой папки; путь у каждого свой, сервер хранит ключ и путь внутри.

### 3.2 Что видно в Проводнике

В папке проекта (скриншот владельца, вид «Таблица»):
- новые столбцы (включаются в «Просмотреть»): **Шифр**, **Ред.**, **Статус**
  (точка и слово), **Документ** (наименование); у несвязанного — пусто;
- строка над списком, как «Недоступных объектов пропущено»: **«Файлов без
  документа: 5 — Разобрать»** (открывает «Неразобранное» с этой папкой);
- фильтры: «Связанные», «Без документа», «Изменены после выпуска»;
- **«Сведения»** (правая панель) для связанного файла — карточка документа:
  шифр, наименование, тип, теги, ревизия и статус, ответственный, срок,
  история ревизий с файлами, кнопки «Открыть в Документообороте», «Выпустить
  ревизию…»; для несвязанного — «Связать с документом…», «Создать документ из
  файла…».

### 3.3 Меню правой кнопки (файл в папке проекта)

- **Связать с документом…** — выбор строки ВДР проекта: поиск по шифру,
  названию, тегу; сверху — подсказки (совпадение шифра в имени, тег в имени,
  похожее наименование); роль файла (основной / исходник / замечания / скан);
  галочка **«Переименовать по шифру»** с предпросмотром имени по маске.
- **Создать документ из файла…** — новая строка ВДР, поля заполнены из имени
  по маске (шифр, ревизия, наименование), тип и теги — выбрать; затем связь.
- **Открыть в Документообороте**, **Выпустить ревизию…** (раздел 7),
  **Отвязать от документа** (файл остаётся, связь — в истории).
- Для папки: «Связать все файлы…» — пакетный разбор по маске с таблицей
  предложений.

### 3.4 Перетаскивание

Файл из Проводника на строку Реестра → «Прикрепить к документу» (роль по
умолчанию — основной). Строку Реестра в папку Проводника → «Создать файл
документа здесь» (раздел 8). Работает и между окнами Flux.

### 3.5 Что происходит со старым

- **Локальные свойства файла** (`electron/filesystem/state.ts`,
  `WindowsFileMetadata`: теги, проекты, ревизия, ответственный; правка в
  `PropertiesWindow`) — **убираются** как источник правды. Перенос:
  одноразовый мастер «Перенести свойства файлов» — для каждого файла с
  локальными свойствами предлагает документ (по ревизии, тегам, имени) или
  «оставить без документа»; что не перенесено — показывается списком и
  удаляется после подтверждения. История файла остаётся (только чтение).
- **Статусы D/C/B/A** (`FileItems.tsx`) — заменяются едиными статусами
  документа (раздел 5).
- **Серверный архив** (`FileNode`, `/api/files`, `/api/folders`, «Архив
  Flux»): документооборот на него **не опирается**. `DocRegisterItem.fileNodeId`
  (файл замечаний) переносится в «Файлы документа» с ролью «замечания» (если
  файл архива доступен — выгрузить в папку «Входящие» проекта). Остальные
  потребители архива (`dropUpload`, `fileBytes`, `saveToWindows`, `MdFileHost`,
  `OfficeHome`, `Archives`) — вне этого плана, их переводит пункт «Отказ от
  серверного архива» в `plan.md`.
- **«Проводник проекта»** как отдельный экран уже удалён; фраза осталась в
  `guide/engine.ts`, `MailThread.tsx`, `mailLink.ts` — заменить на «папка
  проекта в Проводнике».

### 3.6 Когда файл меняется сам

- **Переименовали / перенесли в Windows** — связь держится по ключу папки и
  отпечатку содержимого (sha256 первых и последних МБ + размер + время):
  Flux находит файл и обновляет путь; не нашёл — документ показывает «файл
  не найден», предлагает найти.
- **Изменили после выпуска** — файл помечается «изменён после выпуска ред. B»;
  выданная копия лежит в «Выпуске» нетронутой (раздел 7).
- **Удалили** — документ показывает «файл удалён», связь в истории.

## 4. Связь файла и документа — как именно

### 4.1 Три пути, все равноправны

1. **Из документа** — «Создать файл» (раздел 8): файл сразу появляется в
   нужной папке, с правильным именем, связан. **Основной путь** — меньше
   ручной работы и ошибок.
2. **Из Проводника** — «Связать с документом…» / «Создать документ из
   файла…» (3.3) или перетаскивание (3.4).
3. **Сам** — файл с именем по маске проекта, появившийся в рабочей папке:
   точное совпадение шифра → связывается сам (переключатель в настройках
   проекта, по умолчанию включён), иначе — в «Неразобранное» с подсказкой.

### 4.2 Что задаётся файлу при связи

Имя (если «Переименовать по шифру»), шифр, наименование, ревизия, статус,
теги, проект — **из документа**. Свойства в самом файле Office (основные
свойства docx/xlsx, поля штампа) заполняются через существующие источники
`vdr.*` (`server/officeSources.ts`) при открытии во Flux Office и при выпуске.
Ручная правка этих полей в Проводнике не делается — правится документ.

### 4.3 «Неразобранное»

Список файлов рабочих папок проекта без документа: имя, папка, кто положил,
когда; подсказка (оценка совпадения), действия «Связать», «Создать документ»,
«Не документ» (исключить: служебный файл; правило можно сохранить по маске,
напр. `*.bak`, `~$*`).

## 5. Настройки документооборота проекта

Открываются в «Документообороте» → «Настройки» выбранного проекта. Разделы:

| Раздел | Что | Пример |
|---|---|---|
| Статусы | список, порядок, цвет точки, какие разрешают выпуск | В работе → На проверке → Согласован → Выдан → Замечания → Принят; Аннулирован |
| Ревизии | схема номеров по стадиям и причинам | A, B, C… для IFR; 0, 1, 2… для CEF; «V» — аннулирован |
| Причины выпуска | коды и названия | IFR, IFI, IFU, CEF, VOID |
| Коды рассмотрения | код заказчика → действие | 1 принято, 2 с замечаниями, 3 отклонено, 4 для сведения |
| Типы документов | код ВДР, наименование RU/EN, стадия П/Р, шаблон файла, маска шифра | E02 «Общий вид», C32 «Опросный лист» |
| Маски | шифра документа, имени файла, структуры папок | `{проект}-{тег}-{тип}-{№}`, `{шифр}_{ред}_{наим}.{ext}`, `{стадия}/{тип}` |
| Комплекты | поправки проекта к комплектам Каталога (раздел 6) | для этого проекта AHU без C01 |
| Сроки | вехи проекта, сроки по типам документов от вехи, рабочий календарь | C32 — веха «Старт» + 10 раб. дней |
| Подписанты | разработал / проверил / утвердил / нормоконтроль по разделам | |
| Колонки ВДР | какие колонки и в каком порядке, экспорт в формат заказчика | |
| Выпуск | куда кладётся выпуск, формат копии (PDF + исходник), шаблон сопроводительного письма | |
| Автоматика | связывать файл сам при совпадении шифра; предлагать строки по комплекту | |

**Перенос между проектами.** «Скопировать настройки из проекта…» → выбор
проекта-источника → галочки по разделам → **предпросмотр различий** (что
добавится, что заменится) → применить; отмена одним действием. «Сохранить
как шаблон» / «Создать из шаблона» — шаблоны компании (замена глобального
`DocStandard`: он превращается в шаблоны, у проекта — своя копия, не
ссылка). У проекта видно «скопировано из ЗапСиб PDH2, 05.11.2026».

**Правка во время работы.** Изменение маски или схемы ревизий не
переписывает существующие документы и файлы; для уже существующих —
отдельное действие «Привести к маске» с предпросмотром.

## 6. Комплекты документов по типам оборудования

### 6.1 Откуда берётся тип у тега

Сейчас у тега надёжного «типа» нет (`Tag.equipmentId → Equipment.type`:
AHU/FAN/VALVE…, категория — у системы). Вводится **класс Каталога у
оборудования**: `Equipment.catalogClassId` (класс — `CatalogClass`, напр.
«Приточная установка»). Заполняется: из выбранной модели Каталога (у модели
класс есть), из импорта XML/бланка (правило «тип Веза → класс»), вручную в
карточке. Пока не задан — по таблице соответствия `Equipment.type → класс` в
настройках проекта.

### 6.2 Комплект в Каталоге

В Каталоге у класса — вкладка **«Документы»**: какие типы документов нужны
оборудованию этого класса:

| Поле | Значение |
|---|---|
| Тип документа | код и наименование (E02 «Общий вид», C32 «Опросный лист», C01 …) |
| Стадия | П, Р или обе |
| Единица | на тег / на установку (группу тегов) / на проект |
| Обязательность | обязательный / по требованию заказчика / необязательный |
| Шаблон | бланк класса (опросный лист), шаблон docx/xlsx, генератор Конструктора |
| Ответственная роль | должность по умолчанию |
| Срок | от какой вехи и сколько рабочих дней |
| Условие | по параметру модели (напр. «есть привод» → паспорт привода) |

Пример: класс «Приточная установка» (ВЕРОСА): E02 Общий вид (на тег, П+Р),
C32 Опросный лист (на тег, П), C01 Паспорт (на тег, Р), E05 Схема автоматики
(если «автоматика ВЕЗА»).

### 6.3 Поправки проекта

В настройках проекта, раздел «Комплекты»: для каждого класса — комплект из
Каталога и поправки этого проекта: убрать тип, добавить свой, поменять
единицу, срок, ответственного, шаблон. Видно, что из Каталога, а что
изменено в проекте; «Сбросить к Каталогу».

### 6.4 «По тегам»

Вкладка «Документооборот → По тегам» и блок «Документы» в карточке тега:
для каждого тега с классом — список нужных по комплекту типов и состояние
каждого:

| Состояние | Что значит |
|---|---|
| нет строки | документа в ВДР ещё нет |
| строка, нет файла | заведён, файла нет |
| в работе / на проверке | есть файл, статус |
| выдан ред. B | последний выпуск |
| замечания | пришли замечания, нужна следующая ревизия |
| принят | закрыт |
| не нужен в проекте | исключён поправкой проекта |

Сверху — сводка по проекту: «Нужно 46 · есть 31 · выдано 12 · просрочено 3».
Действие **«Создать недостающие строки»** — план → предпросмотр (какие
строки, шифры по маске, ответственные, сроки) → применить → отмена
(`flux-data-safety`); повтор не создаёт дублей (ключ: тег + тип + единица).

**Когда тег появляется в проекте** (вручную, импортом XML, из Каталога) —
документооборот показывает «Для AHU-3 по комплекту нужно 3 документа —
Создать / Позже» (сам строки не создаёт, если в настройках проекта не
включено «создавать сразу»). **Тег сняли** — его строки помечаются «тег
снят», решает человек (не удаляются).

## 7. Выпуск документов

### 7.1 Кто и откуда

«Выпустить» — у строки или выбранных строк Реестра, из «По тегам», из
Проводника («Выпустить ревизию…»). Право `docflow.issue`. Только при связи
(номер ревизии выдаёт сервер, [offline-work.md](roadmap/offline-work.md) 7.1).

### 7.2 Окно выпуска

1. Документы (одна или пачка) — для каждого: текущая ревизия → **следующая**
   (по схеме проекта), причина (IFR…), основной файл и исходник.
2. **Проверки перед выпуском** — блокирующие и предупреждения: нет основного
   файла; файл не найден; статус не разрешает выпуск; не заполнены
   подписанты; шифр не по маске; файл изменён коллегой и не сохранён;
   позиции оборудования в документе изменились после последнего
   заполнения (Office: полоса «устарело»).
3. Что будет: номера ревизий, имена файлов в «Выпуске», сопроводительное
   письмо.
4. «Выпустить» → сервер в одной транзакции выдаёт номера ревизий (как этап
   0), записывает ревизии; Flux:
   - заполняет поля штампа и свойства файла (ревизия, дата, подписанты) через
     `vdr.*`;
   - кладёт **копию** в папку «Выпуск» проекта:
     `{Выпуск}/{дата}_{№ письма}/{шифр}_{ред}.pdf` + исходник (по настройке),
     только чтение; запоминает отпечаток;
   - переводит статус в «Выдан», дату выпуска — в ВДР;
   - формирует **сопроводительное письмо** (трансмиттал) по шаблону проекта:
     список документов, ревизии, причины, кол-во листов — docx/pdf, тоже в
     «Выпуск».
5. После выпуска рабочий файл свободен для следующей ревизии; правка
   помечает «изменён после выпуска ред. B».

### 7.3 Ответ заказчика

«Внести ответ» у выпуска или строки: код рассмотрения (из настроек),
файл замечаний (роль «замечания», в «Входящие»), дата. Код задаёт следующий
статус (принят / замечания → следующая ревизия). Сроки ответа — от даты
выпуска.

### 7.4 Конструктор

Выпуск спецификаций Конструктора (`BuilderScreen` → `IssuePanel`, снимок
выпуска) переходит на тот же выпуск: Конструктор формирует файл документа
(раздел 8), выпускает — «Документооборот». Снимок выпуска Конструктора
остаётся как содержимое файла (чтобы переиздание давало тот же документ).

## 8. Формирование документов и бланков

«Создать файл» у строки (или у нескольких, у тега в «По тегам»):
- **источник** — шаблон типа документа из настроек проекта, иначе из
  комплекта Каталога: бланк класса (`BlankTemplate`, опросный лист),
  docx/xlsx-шаблон, генератор Конструктора (спецификация), паспорт;
- **данные** — тег, оборудование и его параметры, модель Каталога (общего или
  проекта), реквизиты проекта и ВДР — через привязки Flux Office (как
  «Заполнить» сейчас);
- **куда** — рабочая папка проекта по маске структуры, имя по маске;
- **результат** — файл связан с документом как основной, статус «В работе»;
  повторное нажатие не плодит копии («файл уже есть — открыть / пересоздать
  в новую версию»).

Пакетно: «Создать файлы для тега AHU-3» — все документы комплекта сразу.
Обновление данных в уже созданном файле — существующий предпросмотр
«Обновить» Office.

## 9. Каталог проекта и общий каталог

- **Общий каталог** — как сейчас (`CatalogClass`, `CatalogFamily` …): типы,
  модели, параметры, бланки, теперь и комплекты документов.
- **Каталог проекта** — у проекта свой слой поверх общего:
  - **взять из общего** — позиция проекта ссылается на позицию общего
    каталога и закреплённую ревизию; можно **переопределить** параметры для
    проекта (напр. характеристики привода в этом типе проектов) — видно,
    что изменено, «Сбросить к общему», «Обновить до новой ревизии общего» (с
    разницей);
  - **своя позиция** — только в этом проекте (не в общем);
  - **поднять в общий** — своя или изменённая позиция проекта предлагается в
    общий каталог (право `catalog.*`, через обычную публикацию Каталога).
- В Оборудовании при выборе модели — источник «Каталог проекта» / «Общий»;
  по умолчанию проектный, если там есть.
- Комплекты документов и бланки тоже могут быть проектными (раздел 6.3).
- Модель хранения: `CatalogFamily.projectId` (пусто — общий),
  `basedOnFamilyId` + `basedOnRevision`, переопределения — разница к
  `dataJson`; ограничение: проектная позиция не видна в других проектах.
- Перенос настроек проекта (раздел 5) может включать и каталог проекта
  (галочка «каталог проекта»).

## 10. Без связи и одновременная работа

- Связи файлов, свойства, строки — через сервер со сверкой версий (этап 0
  сделан для ВДР); без связи — по [offline-work.md](roadmap/offline-work.md):
  журнал действий, каталог расхождений (п. 26 «свойства файла» = связь
  файл-документ, п. 28 выпуск без связи — отказ).
- Двое связали один файл с разными документами — второй получает понятный
  отказ «файл уже связан с …» с выбором.
- Выпуск — только при связи, номера — только сервер.

## 12. Задание

Исполнитель — внешний (правила — `AGENTS.md`, данные — навык
`flux-data-safety`, оформление — `docs/methodology/01-design.md`). **Два
этапа**, каждый — один PR в `main` с коммитом на шаг; после каждого шага
сборка и проверки шага зелёные; каждая новая проверка падает без правки.

### Этап 1 — Документооборот, Проводник, настройки проекта

1. Программа «Документооборот» (`/docflow`, Пуск), вкладки Реестр / По тегам
   (каркас) / Выпуски / Неразобранное / Настройки; перенос `VdrPanel` и
   `DocflowSettings`; перенаправления старых адресов; права `docflow.*` с
   переводом `vdr.*`; «Менеджмент» — без этих вкладок.
2. Настройки документооборота **проекта** (раздел 5) с переносом между
   проектами и шаблонами; глобальный `DocStandard` → шаблоны (миграция с
   предпросмотром).
3. Связь файл ↔ документ на сервере (`DocFileLink`: документ, ревизия,
   роль, ключ папки + путь, отпечаток), назначения папок (рабочая / выпуск /
   входящие).
4. Проводник: столбцы, строка «Файлов без документа», фильтры, «Сведения» с
   карточкой документа, меню 3.3, перетаскивание 3.4, слежение 3.6,
   «Неразобранное» и автосвязь 4.1(3).
5. Убрать старое (раздел 11): локальные свойства с мастером переноса,
   D/C/B/A, `fileNodeId`; обновить `explorer.md`, `management.md`, новую
   страницу `docflow.md` в `docs/methodology/03-programs/`, справку.

**Готово:** файл связывается с документом тремя путями; у файла видны шифр,
ревизия, статус из документа; переименование в Windows связь не рвёт;
настройки одного проекта переносятся в другой с предпросмотром и отменой;
старые ссылки на ВДР открываются; снимки обеих тем.

### Этап 2 — Комплекты, каталог проекта, формирование и выпуск

1. Класс Каталога у оборудования (6.1) с заполнением из модели, импорта и
   вручную; соответствие `Equipment.type → класс` в настройках проекта.
2. Комплекты в Каталоге (6.2), поправки проекта (6.3), «По тегам» и блок в
   карточке тега (6.4), «Создать недостающие строки» с планом и отменой,
   подсказка при появлении тега.
3. Каталог проекта (раздел 9): взять из общего с переопределением, своя
   позиция, поднять в общий; выбор источника в Оборудовании.
4. Формирование файлов документов и бланков (раздел 8), пакетно по тегу.
5. Выпуск (раздел 7): окно с проверками, транзакция номеров на сервере,
   копия в «Выпуск», штамп и свойства, сопроводительное письмо, ответ
   заказчика; Конструктор выпускает через него (7.4).

**Готово:** у приточной установки в проекте видно, что нужны E02, C32, C01 и
что выдано; недостающие строки создаются с предпросмотром и не дублируются;
файл создаётся по шаблону в нужной папке с правильным именем; выпуск пачки
выдаёт ревизии одной транзакцией, кладёт копии и письмо, повтор не плодит
ревизий; каталог проекта переопределяет параметр привода, не трогая общий.

Проверки обоих этапов: серверные наборы на SQLite и схема на трёх СУБД (CI
`security-db`), интерфейсные наборы Проводника и Документооборота, снимки
обеих тем; Windows (переименование, сетевые папки) — CI и вручную владельцем.
