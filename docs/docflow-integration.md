# Документооборот: связь ВДР, проекта, Проводника, оборудования и шаблонов

Проект (только проектирование, кода пока нет). Основание — слова владельца
(28 октября 2026): перенести настройки документооборота в Менеджмент и
проработать их детально; привязать документооборот к Проводнику, проекту и
остальному так, чтобы всё распознавалось и привязывалось само, а сроки в
ВДР вносились автоматически; при создании ВДР по типам оборудования
создавались нужные документы (чертежи, бланки и т. д.).

Предшественник — `docs/vdr-docflow-design.md` (первая постановка ВДР:
реестр, ревизии, уведомления). Здесь — то, чего в ней не было: вехи, комплекты
по типам оборудования, Проводник Windows как место файлов, привязка по id.

Состояние на ревизию 40289d1. Шаг 0 уже сделан: лист «Документооборот»
переехал из Настроек в Менеджмент, вкладка «Настройки документооборота»
(`?tab=docflow`, `src/components/management/DocflowSettings.tsx`). Дальше
вкладка растёт по этому документу.

## 0. Принципы

1. **Связь по id, а не по тексту.** Строка ВДР ссылается на тег, файл и
   проект по идентификаторам; строка вроде «AHU-2» в JSON — только
   отображаемая копия. (В `docs/plan.md` это уже записано как отложенное:
   «Связь тегов с ВДР — вернуть по id тега, а не по коду».)
2. **Программа предлагает, человек подтверждает.** Любая массовая запись
   (комплект документов, пересчёт сроков, привязка файлов) идёт через
   план → предпросмотр → применение → откат (`flux-data-safety`). Молча
   ничего не создаётся и не удаляется.
3. **Ручное сильнее автоматического.** Дата, привязка и номер, которые
   человек поправил, помечаются «закреплено» и больше не пересчитываются.
4. **Файлы живут в Windows.** Сервер не хранит файлы и пути; он хранит
   ключ папки, имя внутри неё и хеш (как уже сделано для привязок папок
   проектов). Серверный архив файлов (`FileNode`) выводится из программы,
   и новая связь на него опираться не должна.
5. **Одна цепочка ревизий.** Ревизия строки ВДР, ревизия файла и выпуск
   бланка — один факт, записанный в одном месте и показанный в трёх.

### 1.2 Главные разрывы (по важности)

1. Нет вех проекта → нечем автоматически считать сроки.
2. Нет правил «тип оборудования → набор документов» → ВДР заводится руками
   или импортом таблицы заказчика.
3. Теги в строке — текст; переименование или удаление тега рвёт связь молча.
4. Строка не связана с файлом в Проводнике Windows; `fileNodeId` мёртв.
5. Шифр и маски есть, но ни одна часть программы по ним файлы не узнаёт.
6. Ответственный — человек, а не должность; ответственных по должностям
   программа не знает, пока должности не заведены.
7. Две-три параллельные истории ревизий (строка, бланк, документ).

## 2. Целевая модель

### 2.1 Схема связей

```
Project ──< ProjectMilestone (вехи: дата, закреплена ли)
   │
   ├──< DocRegister (ВДР; standardId; stage; folderKey)
   │        │  └──< DocRegisterItem (документ) ──< DocRegisterItemRevision
   │        │          │   ├─ plannedDate / plannedMode / milestoneId / offset
   │        │          │   ├─ kitRuleId, originKey  ← откуда строка
   │        │          │   ├──< DocRegisterItemTag >── Tag ── Equipment(type/category)
   │        │          │   ├──< DocFileLink >── файл Windows (ключ папки + имя + sha256)
   │        │          │   └─ docId → ConstructorDoc / selectionListId → SelectionList
   │        │          └─ responsiblePositionId → Position ── (сотрудники проекта)
   │        └─ DocGenerationBatch (план/применение/откат)
   │
   ├──< ProjectFolderBinding (есть: ключ сетевой папки ↔ проект)
   └──< DocInboxItem (файлы без пары / конфликты)

DocStandard ──< DocKitRule (тип оборудования → вид документа, срок, должность…)
```

### 2.2 Ключи привязки

| Что связываем | Ключ | Почему |
|---|---|---|
| строка ↔ тег | `Tag.id` (+ копия `identifier` для показа) | переживает переименование тега; ответ на отложенный пункт плана |
| строка ↔ тип оборудования | `DocKitRule.equipmentKind` = id категории оборудования (`equip_categories`); необязательно `catalogClassCode` | категория — то, что уже выбирает человек в Оборудовании; соответствие классу каталога хранится в правиле, а не угадывается |
| строка ↔ правило комплекта | `DocRegisterItem.kitRuleId` + `originKey` = `ruleId:tagId` (или `ruleId:group`/`ruleId:project`) | идемпотентность: повторный запуск не создаёт дубль, правка правила находит «свои» строки |
| строка ↔ файл | `DocFileLink`: `folderKey` (sha256 нормализованного сетевого пути папки, как в `ProjectFolderBinding.locationKey`) + `relName` + `sha256` + `size` | путь в базу не пишется; у каждого клиента свой диск, но ключ одинаков; хеш переживает переименование |
| строка ↔ документ программы | `docId` (Конструктор), `selectionListId` (опросный лист) | уже существуют / добавляется одно поле |
| строка ↔ ответственный | `responsiblePositionId` → `Position`; `assigneeId` остаётся как «назначен конкретно» | должность задаёт правило, человек выводится из состава проекта |
| реестр ↔ папка | `DocRegister.folderKey` (+ `folderRel`) — подпапка реестра внутри привязанной папки проекта | |

### 2.3 Эскиз Prisma

Эскиз, не готовая миграция. Правила таблиц Flux: ручной SQL для SQLite в
`server/localSchema.ts`, ленивое создание для PostgreSQL в
`server/routes/vdr.ts` (`ensureTables`), три варианта `prisma/schema*.prisma`
(`flux-architecture`, проверка схемы профиля). Все новые поля у существующих
таблиц — с безопасным значением по умолчанию, чтобы старые базы читались.

```prisma
// Веха проекта: от неё считаются сроки строк ВДР.
model ProjectMilestone {
  id        String    @id @default(uuid())
  projectId String
  code      String    // CONTRACT | KICKOFF | ISSUE_P | ISSUE_R | ORDER | DELIVERY | своя
  title     String
  date      DateTime? // не задана — зависящие сроки не считаются, а показываются «ждёт веху»
  locked    Boolean   @default(false) // дата договорная: сдвиг только с подтверждением
  sort      Int       @default(0)
  updatedById String?
  updatedAt DateTime  @updatedAt
  @@unique([projectId, code])
}

// Должность (справочник). Основная и дополнительные должности человека —
// отдельная связь; User.position остаётся для показа.
model Position {
  id        String  @id @default(uuid())
  name      String
  departmentId String?
  archivedAt DateTime?
}
model UserPosition {
  userId     String
  positionId String
  primary    Boolean @default(false)
  @@id([userId, positionId])
}

// Правило комплекта: «для оборудования этого типа нужен такой документ».
model DocKitRule {
  id              String  @id @default(uuid())
  standardId      String  // правила принадлежат стандарту: у заказчиков разные комплекты
  equipmentKind   String  // id категории оборудования; "*" — на проект целиком
  catalogClassCode String? // класс каталога для опросного листа/паспорта
  vdrCode         String  // вид документа из vdrTypes стандарта (C01, E02, K32…)
  titleRuTpl      String  // «Габаритный чертёж {tag}», подстановки из тега
  titleEnTpl      String  @default("")
  numberMask      String  @default("") // пусто — маска стандарта
  scope           String  @default("PER_TAG") // PER_TAG | PER_GROUP | PER_PROJECT
  stage           String  @default("R") // P | R | PR (обе)
  required        Boolean @default(true)
  positionId      String? // ответственная должность
  milestoneCode   String  @default("")  // от какой вехи
  offsetDays      Int     @default(0)   // отрицательное — «до вехи»
  offsetKind      String  @default("WORKDAYS") // WORKDAYS | CALENDAR
  generator       String  @default("NONE") // NONE | CONSTRUCTOR | BLANK | SELECTION | PASSPORT
  generatorRef    String? // id шаблона Конструктора / бланка
  autoDraft       Boolean @default(false) // сразу создать черновик документа
  language        String  @default("")
  sort            Int     @default(0)
  disabledAt      DateTime?
  @@index([standardId, equipmentKind])
}

// Новые поля DocRegister: stage String @default(""), folderKey String @default(""),
//   folderRel String @default("")
// Новые поля DocRegisterItem:
//   stage String @default(""), required Boolean @default(true),
//   kitRuleId String?, originKey String @default(""), source String @default("MANUAL") // KIT|IMPORT|MANUAL
//   plannedDate DateTime?, plannedMode String @default("MANUAL") // AUTO | MANUAL (закреплена)
//   milestoneCode String @default(""), offsetDays Int @default(0), offsetKind String @default("WORKDAYS")
//   responsiblePositionId String?, selectionListId String?
//   @@index([registerId, originKey])

model DocRegisterItemTag {
  itemId        String
  tagId         String
  tagIdentifier String // копия для показа и для восстановления при удалении тега
  @@id([itemId, tagId])
  @@index([tagId])
}

// Файл, привязанный к ревизии строки. Путь не хранится.
model DocFileLink {
  id        String   @id @default(uuid())
  itemId    String
  revision  String
  folderKey String
  relName   String
  sha256    String   @default("")
  size      Int      @default(0)
  source    String   @default("MANUAL") // AUTO | MANUAL
  state     String   @default("WORKING") // WORKING | REVIEW | ISSUED | SUPERSEDED
  linkedById String?
  linkedAt  DateTime @default(now())
  @@index([itemId])
  @@index([folderKey, relName])
}

// Очередь «неразобранное»: файлы в папке реестра без пары или со спором.
model DocInboxItem {
  id        String   @id @default(uuid())
  projectId String
  registerId String?
  folderKey String
  relName   String
  sha256    String   @default("")
  parsedJson String  @default("{}") // что узнали: шифр, ревизия, язык, вид
  candidatesJson String @default("[]") // подходящие строки с оценкой
  reason    String   // NO_MATCH | AMBIGUOUS | CONFLICT | OLDER_REVISION | BAD_NAME
  state     String   @default("NEW") // NEW | LINKED | IGNORED
  resolvedById String?
  createdAt DateTime @default(now())
  @@index([projectId, state])
}

// Операция над ВДР: план, применение, откат (по образцу SelectionBatch).
model DocGenerationBatch {
  id        String   @id @default(uuid())
  registerId String
  kind      String   // KIT_INITIAL | KIT_NEW_EQUIPMENT | KIT_RULE_CHANGED | RECALC_DATES | FILE_SCAN
  planJson  String   // что будет сделано (предпросмотр)
  appliedJson String @default("{}") // что сделано: id созданных, прежние значения изменённых
  state     String   @default("PLANNED") // PLANNED | APPLIED | UNDONE | PARTLY_UNDONE
  createdById String?
  createdAt DateTime @default(now())
  appliedAt DateTime?
  undoneAt  DateTime?
}
```

Миграция существующих данных: `equipmentTags` (JSON) разбирается в
`DocRegisterItemTag` по `Tag.identifier` в проекте строки; не найденные теги
остаются в JSON и показываются в очереди «теги без id» — не теряются.
Поле `equipmentTags` не удаляется до отдельного решения.

### 2.4 Где что в интерфейсе

- Менеджмент → «Настройки документооборота» (общее для программы):
  «Стандарты» (есть), «Комплекты документов» (правила, этап C),
  «Вехи по умолчанию» (шаблон набора вех нового проекта), «Структура
  папок» и «Распознавание» (маски, этап E).
- Менеджмент → «ВДР» (по проекту): реквизиты реестра получают блок
  «Стадия», «Папка», «Вехи проекта»; кнопки «Дополнить по комплекту»,
  «Пересчитать сроки», «Проверить папку»; вкладка/фильтр «Неразобранное».
- Вехи проекта правятся в ВДР (рядом с реквизитами), а не в «Проектах»:
  там владелец отложил «настройки проекта своими значениями».
- Оборудование и теги: в паспорте тега и в строке оборудования показ
  «Документы: 4 из 6 выпущено» со ссылкой в ВДР (обратная связь).
- Проводник: у файла в привязанной папке в свойствах Flux видно «ВДР:
  код · ревизия · статус», у папки реестра — счётчик «не разобрано».

## 3. «Тип оборудования → набор документов»

### 3.1 Справочник комплектов

Правило комплекта (`DocKitRule`) — строка таблицы в настройках
документооборота, внутри стандарта (у разных заказчиков разные комплекты).
Колонки экрана:

| Колонка | Смысл | Пример |
|---|---|---|
| Тип оборудования | категория (AHU, FAN, VALVE, CURTAIN, свои) или «весь проект» | AHU |
| Вид документа | код из каталога типов стандарта | C01 Габаритный чертёж |
| Масштаб | на каждый тег / на группу / на проект | на каждый тег |
| Наименование | шаблон с подстановками `{tag}`, `{kind}`, `{wbs}`, `{dept}` | Габаритный чертёж {tag} |
| Шифр | маска; пусто — маска стандарта | `{contract}-{wbs}-{po}-{type}-{seq}` |
| Стадия | П, Р или обе | Р |
| Обязательность | обязательный / по требованию | обязательный |
| Ответственная должность | из справочника должностей | Ведущий инженер ОВ |
| Срок | веха + смещение + рабочие/календарные дни | Выдача Р − 10 раб. дн. |
| Как создать документ | нет / шаблон Конструктора / бланк каталога / опросный лист / паспорт | опросный лист класса «Вентилятор» |
| Язык | ru / en / оба | ru+en |

Примеры (наполняет владелец, это иллюстрация формата, а не требование):

| Тип | Документы комплекта |
|---|---|
| AHU (центральный кондиционер) | C01 габаритный чертёж; E02 опросный лист; K32 технический паспорт; схема автоматики; руководство по эксплуатации; программа и методика испытаний |
| FAN (вентилятор) | C01 чертёж; E02 опросный лист; K32 паспорт; характеристика вентилятора |
| VALVE (клапан) | E02 опросный лист (бланк-заказ каталога); K32 паспорт |
| Проект целиком | A01 сам реестр; B01 график изготовления; общая спецификация |

### 3.2 Когда строки появляются

Триггеры (все — только через предпросмотр):

1. **Создание реестра** («Новый реестр»): выбирается стандарт и стадия,
   программа собирает теги проекта по категориям и предлагает полный комплект.
2. **Появление оборудования**: после импорта оборудования или создания тега
   сервер не создаёт строк сам, а ставит проектный флаг «есть неохваченное
   оборудование» и уведомляет ответственного менеджера реестра
   (`managerId`): «3 новых тега, предложено 12 документов» → кнопка ведёт в
   предпросмотр. Так же работает «Дополнить по комплекту» вручную.
3. **Правка правила** (добавили документ в комплект AHU): предлагается
   добавить его всем существующим AHU-тегам. Уже выпущенные реестры
   затрагиваются только после подтверждения.
4. **Удаление/снятие тега с оборудования:** строки не удаляются; их
   метка меняется на «оборудование снято», человек решает сам
   (аннулировать ревизией V, оставить, удалить вручную).

### 3.3 Алгоритм плана

1. Собрать область: теги проекта (по `equipmentId → Equipment.type`/
   категории), стадия реестра.
2. Для каждого тега найти действующие правила (`equipmentKind`, `stage`,
   не отключены).
3. Для каждой пары (правило, тег/группа) вычислить `originKey`.
4. Сверить с существующими строками реестра:
   - по `originKey` → «уже есть» (пропустить; если правило изменилось —
     показать «отличается: срок, должность», предложить обновить только
     незакреплённые поля);
   - по (`vdrCode` + тег) у строки без `originKey` (импортирована от
     заказчика) → «похоже на существующую»: предложить **принять её за
     строку комплекта** (проставить `kitRuleId`, не создавать дубль);
   - иначе → «создать».
5. Построить шифр по маске; при совпадении с существующим номером —
   конфликт, строка не создаётся, а помечается в плане красным.
6. Вычислить `plannedDate` (раздел 4); нет вехи — «срок ждёт веху».
7. Определить ответственного: должность → человек (раздел 6.3).
8. Показать план.

### 3.4 Предпросмотр, применение, откат

- **Предпросмотр** (диалог, одна таблица): сгруппировано по тегам;
  счётчики «создать N · уже есть M · похоже K · конфликт L»; у каждой
  строки галочка (по умолчанию стоит у «создать»), редактируемые
  наименование, шифр, срок, ответственный; итог внизу, кнопка «Создать N
  документов». Без галочек запись не идёт.
- **Применение**: одна транзакция; записывается `DocGenerationBatch`
  (`appliedJson`: id созданных строк и прежние значения изменённых). Если
  документ-источник (`generator ≠ NONE`) — создаётся не сразу, а отдельной
  кнопкой «Сформировать документы» (или `autoDraft` в правиле).
- **Откат** («Отменить операцию» в журнале реестра): удаляются только
  строки этой операции, которые после неё **не менялись** (сверка
  `updatedAt` и отсутствие файлов/ревизий/замечаний); изменённые остаются, и
  откат честно пишет «3 из 12 не отменены, потому что их уже правили».
  Удаление по фрагменту имени/шифра запрещено — только по id из
  `appliedJson`.
- Минимальные требования `flux-data-safety`: сухой прогон на сервере
  (`POST …/plan`), применение по `batchId` (`POST …/apply`), журнал,
  откат; кнопка недоступна, пока план не получен свежим (метка версии
  реестра, чтобы не применить устаревший план).

## 4. Сроки

### 4.1 Вехи

`ProjectMilestone` у проекта. Набор по умолчанию (настраивается во вкладке
«Вехи по умолчанию»): Договор (T0) → Старт проектирования → Выдача стадии
П → Выдача стадии Р → Заказ оборудования → Поставка. Даты вносит менеджер
проекта; пока даты нет, зависящие сроки пусты.

### 4.2 Расчёт

`plannedDate = веха.date ± offsetDays` в рабочих днях
(`offsetKind = WORKDAYS`) или календарных. Рабочие дни — по
производственному календарю: настройка программы (`AppSetting`) со
списком праздников и переносов, по умолчанию — календарь РФ и выходные
Сб/Вс; календарь подразделения (`Department.timezone`) задаёт часовой
пояс «конца дня». Смещение и веха записываются в строку (`milestoneCode`,
`offsetDays`, `offsetKind`) — пересчёт работает и после правки правила
(строка помнит, как её считали).

Два срока в строке — разные вещи, и это закрепляется в названиях:

| Поле | Смысл | Кто ставит |
|---|---|---|
| `plannedDate` | плановая дата выдачи текущей ревизии | комплект + веха (AUTO) или человек (MANUAL) |
| `dueDate` (есть) | срок ответа на замечания заказчика | код рассмотрения из стандарта (как сейчас) |

Просрочено — `status ∈ {DRAFT, READY}` и `plannedDate < сегодня`, либо
`status = REMARKS` и `dueDate < сегодня`. `/api/vdr/attention` берёт
действующий срок по этому правилу.

### 4.3 Пересчёт при сдвиге вехи

1. Человек меняет дату вехи → сервер строит план `RECALC_DATES`:
   «сдвиг Выдачи Р на +14 дн. затронет 38 строк; 5 закреплены вручную; 7
   уже выданы и не меняются».
2. Предпросмотр (та же таблица: было → станет). Применение — отдельной
   кнопкой, откат — через `DocGenerationBatch`.
3. Пересчитываются только `plannedMode = AUTO` и статус `DRAFT/READY`.
   Выданные и принятые не трогаются никогда.
4. Ручная правка даты в карточке строки переводит `plannedMode` в
   `MANUAL` («закреплено», значок замка); возврат — кнопка «Считать по
   вехе».
5. Веха с `locked` (договорная) двигается только с подтверждением и записью
   причины в журнал.

### 4.4 Уведомления

| Когда | Кому | Канал |
|---|---|---|
| за 7 и за 1 рабочий день до `plannedDate` и `dueDate` | ответственный (человек из должности) | `notifyUser` «ДОКУМЕНТЫ» + строка в календаре (`source:'vdr'`, уже есть) |
| в день срока без «На проверке» | ответственный | то же |
| +3 рабочих дня просрочки | ответственный + менеджер реестра (`managerId`) | то же, с пометкой «эскалация» |
| сдвиг вехи | менеджер реестра и ответственные затронутых строк | сводное одно уведомление, не по строке |
| новое оборудование без документов | менеджер реестра | одно уведомление на операцию |

Ежедневная серверная задача (раз в сутки, рано утром по времени
подразделения); дедупликация — запись «уже уведомлён: строка, порог, дата»
в `meta` строки (или отдельная таблица `DocNotifyLog`, если `meta` станет
тесна), чтобы повторный запуск и перезапуск сервера не слали второй раз.
Сводка на Главной (`/api/vdr/attention`) остаётся.

## 5. Проводник: распознавание и привязка файлов

### 5.1 Исходные условия

- Проводник — окна Windows с мостом `windowsFiles`; сервер видит только то,
  что сообщает клиент. Привязку «папка → проект» уже ведёт журнал
  `ProjectFolderBinding` (ключ сетевой папки). Папка проекта и подпапка
  реестра внутри неё — единственное место, которое программа просматривает
  автоматически. Весь диск и личные папки не сканируются.
- Путь в базу не пишется (решение уже действует для привязок): хранятся
  `folderKey` + относительное имя + хеш.
- В браузере без моста Проводника нет: функции файлов выключены, остальное
  (строки, сроки, комплекты) работает.

### 5.2 Структура папок

Маска структуры в настройках («Структура папок»), по умолчанию:

```
<папка проекта>/<стадия П|Р>/<реестр>/<вид документа C01 — Габаритные чертежи>/
    <шифр>_<рев>_<язык>.<расширение>        ← по fileNameMask стандарта
```

- Кнопка «Создать папки по реестру» строит план: какие подпапки создать
  (по видам документов реестра), чего не хватает, какие имена недопустимы
  в Windows (символы, длина пути до 260). Предпросмотр → создание через мост
  (`windowsFiles`) → запись `DocGenerationBatch` для отката (откат удаляет
  только пустые созданные папки).
- Создаются только пустые папки и только внутри привязанной папки проекта;
  существующие файлы не двигаются и не переименовываются.

### 5.3 Как файл узнаётся

Каскад, от надёжного к слабому; на каждом шаге считается оценка (0–100):

1. **Хеш**: файл уже привязан (тот же `sha256`) — ничего не делать.
2. **Имя по `fileNameMask`**: разбор `{docNo}_{rev}_{lang}` в шифр, ревизию,
   язык; шифр ищется среди номеров трёх сторон (`contractorNo`, `ownerNo`,
   `vendorNo`) строк реестра.
3. **Папка**: имя родительской папки содержит код вида (C01…) — подсказка
   для строк с тем же видом и тегом в имени.
4. **Свойства файла**: шифр в свойствах документа (Word/Excel — основные
   свойства, PDF — заголовок/метаданные) — этап позже, после первого
   выпуска; штамп внутри PDF не читаем (дорого и хрупко).
5. **Тег в имени** (`AHU-2`) + вид по слову в имени («чертёж», «опросный») —
   слабый признак, сам по себе не привязывает.

Авто-привязка — только при оценке ≥ 90 (шифр совпал ровно и строка
единственная) и без конфликта; всё остальное — предложение человеку.

### 5.4 Ревизии файла и строки

- Ревизия в имени файла = ревизия строки. Новая ревизия файла
  (`…_B_ru.pdf` при строке в `A`) предлагается как «следующая ревизия
  строки»: человек нажимает «Выпустить ревизию B» — вызывается существующее
  `issue-revision` (причина по стандарту), и новая ревизия строки получает
  `DocFileLink` с этим файлом. Файл предыдущей ревизии получает `SUPERSEDED`.
- Ревизия строки без файла допустима (бумажный документ, ссылка) — предупреждение
  «ревизия без файла», не запрет.
- История ревизий строки (`DocRegisterItemRevision`) получает ссылку на
  `DocFileLink` и источник (`SelectionIssue`, `OfficeDocumentRevision`, если
  ревизия пришла оттуда) — три истории показываются одним списком
  «Учёт ревизий».

### 5.5 Статусы

Сводка соответствия; единый словарь предлагается в вопросе владельцу
№ 4, пока — таблица перевода, без смены существующих значений.

| Строка ВДР | Файл (статус Flux) | Смысл |
|---|---|---|
| `DRAFT` | `D` черновик | в работе |
| `READY` | `C` на проверке | внутренняя проверка пройдена/идёт; готов к выдаче |
| (нет) | `B` согласован | согласован внутри; в строке выражается как `READY` + отметка «согласован внутри» |
| (выдача) | `A` выдан | отправлен заказчику; фиксируется `issueDate` и ревизия |
| `REMARKS` | — | заказчик вернул замечания; срок `dueDate` |
| `ACCEPTED` | — | принят заказчиком |

Смена статуса файла в Проводнике предлагает смену статуса строки (и
наоборот), но не делает её молча, если это «шаг назад» (выдан → черновик).

### 5.6 Конфликты и «неразобранное»

`DocInboxItem` — очередь по проекту (счётчик на папке реестра и в шапке
ВДР). Причины и действия:

| Причина | Пример | Действия человека |
|---|---|---|
| `NO_MATCH` | файл с шифром, которого нет в реестре | «Добавить строку в ВДР» (форма из имени файла), «Привязать к…», «Игнорировать» (запомнить хеш) |
| `AMBIGUOUS` | шифр подходит двум строкам (общий тег) | выбрать строку из списка кандидатов |
| `CONFLICT` | у ревизии уже привязан другой файл (разный хеш) | оставить старый / заменить (старый → `SUPERSEDED`) / оба — новая ревизия |
| `OLDER_REVISION` | ревизия ниже текущей в строке | привязать как архивную / игнорировать |
| `BAD_NAME` | имя не по маске, но тег и вид угадываются | показать предположение, привязать вручную, предложить переименовать (само не переименовывается) |

Проверка запускается: при открытии ВДР, по событию наблюдателя за папкой
(в Проводнике он уже есть), кнопкой «Проверить папку»; результат — только
чтение, запись в очередь и привязка при оценке ≥ 90. Программа не
переименовывает, не перемещает и не удаляет файлы пользователя.

## 6. Синхронизация, события, права

### 6.1 События

| Событие | Есть | Кто шлёт | Кто слушает |
|---|---|---|---|
| `vdr:changed` | да | любой маршрут записи ВДР (`announceVdrChange`) | открытая ВДР, Главная, E3Flux, панель Flux Office |
| `tag:updated`, `tag:linked` | да | запись тега | ВДР (обновить копию `tagIdentifier`) |
| `milestone:changed` | нет | запись вехи | ВДР, Календарь |
| `vdr:inbox` | нет | проверка папки | ВДР, Проводник (счётчик) |
| `equipment:added` | нет | импорт/создание тегов (серверный хук) | серверный сборщик предложений комплекта → уведомление менеджеру |

Новые события идут тем же путём `emitProjectEvent` (только членам проекта),
а не в общую рассылку. У `vdr:changed` добавляется поле причины
(`reason: 'kit' | 'dates' | 'files'`) — клиенту не надо перечитывать то,
чего это не касается. Несохранённые поля карточек и реквизитов остаются
локальными черновиками (как сейчас).

### 6.2 Целостность связей

- Тег переименован: `DocRegisterItemTag.tagIdentifier` обновляется по
  `tag:updated`; шифр строки не меняется сам (предложение «обновить»).
- Тег удалён: связь остаётся с пометкой, строка не удаляется (3.2).
- Проект удалён: каскад по правилам проектов, плюс чистка журнала привязок
  папок (она уже есть) — и новых таблиц.
- Файл исчез из папки: `DocFileLink` не удаляется, помечается «файл не
  найден» при следующей проверке.

### 6.3 Должности и ответственные

Сейчас у сотрудника одна строка `User.position`; владелец вводит основную и
дополнительные должности. Проект исходит из будущего справочника `Position`
+ `UserPosition (primary)` (эскиз выше); пока справочника нет, правило
хранит название должности строкой, а сопоставление идёт по `User.position`
(регистр не учитывается). Это зависимость от соседней работы, а не её
подмена: форма справочника — решение того, кто её делает.

Ответственный по должности выводится так:

1. сотрудники **проекта** (`ProjectMember`) с этой должностью (основной или
   дополнительной);
2. если один — он; если несколько — первый по меньшей нагрузке (число
   открытых строк в проекте), с предложением заменить в предпросмотре;
3. если никого — строка создаётся без ответственного и попадает в
   список «нет ответственного» (счётчик в шапке ВДР), уведомление уходит
   менеджеру реестра;
4. `assigneeId` (конкретный человек) всегда сильнее должности; смена
   сотрудника на должности предлагает перенести его открытые строки
   (план + предпросмотр).

### 6.4 Права

| Действие | Кто | Право |
|---|---|---|
| Править стандарты, комплекты и маски | администратор | `vdr.standards` (риск) |
| Править вехи проекта | менеджер проекта, администратор | новое `vdr.milestones` (по умолчанию MANAGER, ADMIN) |
| Создавать/дополнять строки по комплекту, пересчитывать сроки | менеджер, администратор | `vdr.manage` |
| Править свою строку, привязывать файл, менять свой статус | ответственный по строке | участие в проекте + назначение |
| Разбор «неразобранного» | менеджер, ответственный по виду | `vdr.manage` или назначение |
| Откат операции | автор операции, администратор | `vdr.manage` |
| Видеть реестр | члены проекта | как сейчас (`canSeeProject`) |

Сервер проверяет эти права на каждом маршруте (сейчас часть маршрутов
сверяет роли вручную; приведение к `vdr.*` — часть этапа A).

Вехи и сроки** | `ProjectMilestone`, `plannedDate/plannedMode`, рабочий календарь, пересчёт с предпросмотром и откатом, уведомления и серверная задача, календарь | сдвиг вехи показывает план и не трогает закреплённые/выданные; повторный запуск не шлёт дубли; просрочка в сводке считается по новому правилу |

## 8. Вопросы владельцу

Для каждого — предлагаемый ответ; пока владелец не ответил, работаем по нему.

1. **Вехи.** Какие вехи нужны? *По умолчанию:* Договор, Старт
   проектирования, Выдача П, Выдача Р, Заказ оборудования, Поставка; даты
   вносит менеджер проекта, набор можно менять.
2. **Рабочие дни.** Считать по производственному календарю РФ (праздники и
   переносы) или только Пн–Пт? *По умолчанию:* календарь РФ, праздники
   правятся в настройках.
3. **Сроки: плановая дата или только срок ответа?** Нужны ли оба поля
   (выдача и ответ на замечания)? *По умолчанию:* оба, как в разделе 4.2.
4. **Единые статусы документа.** Свести словари файла (D/C/B/A) и строки
   (DRAFT/READY/REMARKS/ACCEPTED) в один из шести: В работе → На проверке
   → Согласован внутри → Выдан → Замечания → Принят? *По умолчанию:* да, но
   этапом F, до него — таблица перевода из 5.5.
5. **Кто пополняет справочник комплектов.** Только администратор или
   ведущие по отделам? *По умолчанию:* администратор; отдельный проход по
   типам оборудования вместе с владельцем.
6. **Откуда брать начальный комплект.** Нужны ли готовые наборы для
   AHU/FAN/VALVE/CURTAIN от первого пуска? *По умолчанию:* да, пример из 3.1
   как «стандартный комплект ЗапСиб/PDH2», правится.
7. **Стадии П/Р.** Один реестр на обе стадии (поле «стадия» в строке) или
   отдельный реестр на каждую? *По умолчанию:* один реестр, стадия в строке,
   фильтр в таблице.
8. **Единица комплекта.** Документы по каждому тегу или по группе
   (установка → её теги)? *По умолчанию:* по умолчанию «на каждый тег»,
   в правиле можно выбрать «на группу» (установка) и «на проект».
9. **Сколько человек на должности.** Если на должности несколько человек
   проекта — кого назначать? *По умолчанию:* наименее загруженного, с
   подтверждением в предпросмотре; нет никого — строка без ответственного
   и уведомление менеджеру.
10. **Должности.** Дождаться справочника основных/дополнительных должностей
    или начать со строкой `User.position`? *По умолчанию:* начать со строки,
    перейти на справочник, когда он появится (этап C готовит переход).
11. **Автосоздание документов.** Создавать черновик документа сразу при
    создании строки или только по кнопке «Сформировать»? *По умолчанию:*
    только по кнопке; в правиле можно включить автосоздание.
12. **Привязка файлов.** Привязывать сам при совпадении шифра (оценка ≥ 90)
    или всегда спрашивать? *По умолчанию:* сам при точном совпадении
    шифра, остальное — через «неразобранное»; вся автопривязка отключается
    одним переключателем реестра.
13. **Структура папок.** Подходит ли `стадия / реестр / вид документа`?
    Есть ли у заказчиков свои обязательные структуры? *По умолчанию:*
    маска в настройках, стартовая — как в 5.2.
14. **Где правятся вехи.** В ВДР рядом с реквизитами или в «Проектах»?
    *По умолчанию:* в ВДР (в «Проектах» настройки проекта отложены).
15. **Откат комплекта.** Допустимо ли, что откат не удаляет строки,
    которые успели править? *По умолчанию:* да (безопасно), с понятным
    списком «не отменено».
16. **Снятое оборудование.** Что делать со строками удалённого тега:
    только пометка или автоматически аннулировать (ревизия V)? *По
    умолчанию:* только пометка, решает человек.
17. **E3.series.** Нужна ли связь строки ВДР со схемой в E3 (привязка
    `E3Binding`, ссылка «схема выпущена»)? *По умолчанию:* позже, после
    этапа F; ключи (тег по id) этому не мешают.
18. **Личные папки.** Просматривать ли личные папки сотрудника на предмет
    файлов ВДР? *По умолчанию:* нет, только привязанная сетевая папка
    проекта.
