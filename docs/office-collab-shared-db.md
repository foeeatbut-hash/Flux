# Совместная правка Flux Office через общую базу

## Жалоба владельца 29.09

Два сотрудника открыли один файл Word или Excel с общего стола. Правки
друг у друга не появляются. При сохранении программа спрашивает «сохранить
мои правки рядом / открыть свежую версию». Файл лежит на общем столе, значит
правка может быть только совместной, и таких вопросов быть не должно.

## Причина

В отделе нет сервера программы. Общая у всех только база PostgreSQL, а
встроенный сервер поднимает программа каждого сотрудника (README, «Где лежат
данные и где сервер»). Правило оттуда: **всё, что живёт в памяти сервера, у
каждого своё.**

Совместная правка Flux Office целиком построена в памяти сервера:

| Что | Где | Что выходит, когда серверов два |
|---|---|---|
| Комната файла: кто в файле, кто держатель | `server/officeRooms.ts`, `officeRooms` | каждый сидит в комнате один, каждый себе держатель |
| Общий Y-документ Word, засев, исходник сеанса | `server/officeCollab.ts`, `collab` | у каждого свой Y, свой засевающий, свой исходник |
| Журнал правок Таблицы, номера, `savedSha` | `server/officeSheetCollab.ts`, `sheetBook` | у каждого свой журнал и своя «последняя запись» |
| Рассылка `office:y`, `office:x-op`, `office:saved`, курсоры | комнаты socket.io | доходит только до окон своего же сервера |

Отсюда оба симптома.

1. **Правки не видны.** Они уходят на свой сервер, и тот рассылает их
   собственным окнам, то есть никому.
2. **Вопрос «сохранить рядом».** Оба окна считают себя держателем и
   записывают файл со сверкой хеша. Второй получает 409 или 423, и
   `OfficeHost` показывает диалог конфликта. У Таблицы сверка идёт с
   `sheetBook.savedSha` своего сервера: запись не проходит, и Таблица
   сообщает об ошибке.

На одной машине (проверки в контейнере, `test-office-collab-live`) всё
работает, потому что сервер там один. Поэтому проверки поломку не ловили.

## Решение: общая шина через базу

Правила сеанса остаются прежними: держатель пишет файл, правят все, порядок
правок Таблицы задаёт сервер. Меняется только хранилище: всё, что должно быть
общим, переезжает из памяти в общую базу. Память каждого сервера остаётся
кэшем, который можно восстановить из базы.

### Таблицы (`ensureTables` из `server/ddl.ts` и все три схемы Prisma)

- **`OfficeSession`**, один на файл:
  - `fileId` PK, `app`, `key`;
  - `baseData` (blob) и `baseSha`: исходник сеанса, общий для всех серверов;
  - `savedSha`, `savedSeq`, `lastSeq` (int);
  - `seeded` (bool), `seederSocket`, `seederAt`;
  - `snapshot` (blob) и `snapshotSeq`: сжатое состояние Y, чтобы опоздавшему
    не проигрывать весь журнал;
  - `createdAt`, `updatedAt`.
- **`OfficeEvent`**, журнал сеанса:
  - PK (`fileId`, `seq`);
  - `sessionKey`;
  - `kind`: `y` | `x` | `aware` | `saved` | `save-request` | `roster`;
  - `fromSocket`, `toSocket` (null — всем);
  - `data` (blob), `createdAt`.
  - Номер `seq` выдаётся в транзакции через
    `UPDATE OfficeSession SET lastSeq = lastSeq + 1`. Блокировка строки
    одинаково работает в PostgreSQL, MariaDB и SQLite. Номера идут подряд и
    фиксируются по порядку, поэтому читатель «всё после N» ничего не
    пропустит. Автоинкремент такого не обещает: при параллельных вставках
    меньший номер может зафиксироваться позже большего.
- **`OfficePeer`**, участник:
  - `socketId` PK, `fileId` (индекс), `serverId`, `clientId`, `userId`;
  - `name`, `color`, `mayWrite`, `app`, `since`;
  - `beatAt` (удар сердца раз в 5 с), `lostAt`.
- **`OfficeHolder`**, держатель для личных файлов и PDF, где правит один:
  - `fileId` PK, `socketId`, `clientId`, `userId`, `name`, `lostAt`, `freed`;
  - захват через условный `UPDATE` или вставку с проверкой.

### Правила (прежние, только общие для всех серверов)

- **Держатель общего файла** вычисляется из `OfficePeer` одинаково на любом
  сервере: самый ранний по `since` живой участник с `mayWrite`. Живой —
  `beatAt` свежее 15 с, либо тот же `clientId` вернулся в пределах
  `GRACE_MS`. Сервер, который упал и не снял своих участников, перестаёт
  считаться через 15 с.
- **Сеанс Документа.**
  - Строку `OfficeSession` создаёт первый сервер; при гонке второй
    перечитывает её. Ключ и исходник у всех одни.
  - Засевающего назначает условный `UPDATE … WHERE seeded = false AND
    (seederSocket IS NULL OR seederAt устарел)`.
  - Y-состояние для `office:y-want` берётся так: `snapshot` плюс события `y`
    после `snapshotSeq`. Снимок пересчитывается после каждой записи
    держателя; события до него удаляются.
- **Таблица.**
  - `office:x-op` получает номер из той же транзакции, `office:x-want`
    читает журнал из базы.
  - `savedSha` и `savedSeq` лежат в `OfficeSession`, сверка при записи идёт
    с ними.
- **Запись файла** (`writeOfficeFile`, `holderOf`) спрашивает держателя у
  общей комнаты, а не у памяти.
- **`drop`**: сервер сам записал файл (откат, «Обновить поля», английская
  версия), и строка сеанса вместе с событиями удаляется. У остальных
  серверов ключ сеанса сменится, и окна переоткроют файл, как сейчас.
- **Уборка.** Сеанс без живых участников дольше `IDLE_MS`, в котором всё
  записано, удаляется любым сервером. События `aware` старше минуты
  удаляются.

### Доставка

- У каждого сервера свой `serverId` (uuid при старте).
- Насос: для каждого файла, где есть его сокеты, он берёт события
  `seq > lastSeen[fileId]` и раздаёт своим окнам:
  - автору (`fromSocket`) событие не отдаётся;
  - адресное событие (`toSocket`) отдаётся только адресату.
- Будит насос:
  - в PostgreSQL — `LISTEN flux_office` на отдельном клиенте `pg`,
    `NOTIFY flux_office, '<fileId>'` после фиксации. Задержка — десятки мс;
  - всегда, и для MariaDB, — опрос раз в 700 мс;
  - в SQLite сервер один, поэтому насос будится сразу из того же процесса.
- Своим окнам сервер по-прежнему рассылает мгновенно через socket.io.
  Насос раздаёт только чужое, то есть события, у которых `serverId`
  отправителя не свой. Для этого в `OfficeEvent` нужна колонка
  `fromServer`.
- Состав комнаты (`office:roster`) каждый сервер собирает из `OfficePeer`
  и рассылает своим окнам:
  - при событии `roster`, которое пишется на вход, выход и обрыв;
  - раз в удар сердца.

### Окно: никаких вопросов в общем файле

- В общем файле (`roster.collab`) диалог конфликта не показывается никогда.
  - Держатель получил 409, потому что держатель сменился и файл уже записал
    другой. Окно берёт свежий хеш (`/meta`) и записывает ещё раз:
    содержимое общее, и в нём уже есть всё записанное.
  - Получил 423: это не держатель. Молча отдать запись держателю через
    `save-request`.
- Ctrl+S соавтора остаётся просьбой держателю, как сейчас. Но теперь
  просьба доходит через шину.

## Шаги

1. `server/officeBus.ts` — таблицы, `serverId`, номера, насос,
   LISTEN/NOTIFY, опрос, уборка. Модуль не знает ни Word, ни Excel.
2. `officeRooms`, `officeCollab`, `officeSheetCollab` и `officeHostApps`
   переходят на шину. Правила остаются в классах книг (их проверяет
   `test-office-rooms`), состояние уходит в базу. `server.ts` не растёт:
   подключение — в `officeSockets.ts`.
3. `OfficeHost` и `OfficeAppHost`: в общем файле нет диалога конфликта,
   409 и 423 обрабатываются без вопросов.
4. Проверки:
   - `scripts/test-office-bus.ts` — **два сервера на одной PostgreSQL**
     (кластер `initdb` во временной папке, `PORT=3000` и `PORT=3001`);
   - `test-office-collab-live` и `test-office-sheets-collab-live`: второй
     сотрудник подключён ко второму серверу (`FLUX_API2`). Буквы у обоих,
     файл записан один раз, диалога нет, в файле правки обоих;
   - `npm run check` зелёный.
5. README, раздел «Как это устроено в отделе»: третья поломка того же рода и
   как она исправлена. Этот файл дополняется итогом.

## Итог (29.09)

### Что сделано

- **Шина** — `server/officeBus.ts`: таблицы `OfficeSession`, `OfficeEvent`,
  `OfficePeer`, `OfficeHolder` (все три схемы Prisma, подстраховка `ddl.ts`),
  `serverId`, номера событий через `UPDATE lastSeq` в транзакции, насос с
  `LISTEN/NOTIFY` (PostgreSQL) и опросом 700 мс, удар сердца 5 с, уборка.
  `server/officeIo.ts` — отдача событий окнам этого сервера (проверкам вместо
  сокета подставляется своя).
- **Комната** — `OfficeRoomBook` остался чистыми правилами; `OfficeRoomHub`
  грузит комнату из базы, применяет правило и записывает итог: участников каждый
  сервер про своих, держателя — сравнением `version`.
- **Документ** — `CollabShared`: исходник, ключ, засев (условный `UPDATE`),
  снимок Y и журнал в базе; Y сервера — кэш, собираемый из снимка и журнала.
- **Таблица** — `SheetShared`: журнал правок — события вида `x`, номер общий.
  Правки идут окнам из насоса, в том числе окнам своего же сервера: по приходу
  две правки могли бы обогнать друг друга, а окно отбрасывает старше применённой.
- **Запись** — держатель и `savedSha` спрашиваются у базы (`holderOf` теперь
  асинхронный). Таблица сама повторяет запись, если держатель успел смениться,
  и передаёт просьбу настоящему держателю.
- **Окно** — у общего файла диалога нет: 409 повторяется с хешем, который записал
  сам сеанс (сервер отвечает `bySession`), 423 уходит держателю через шину.
- **Отступления от плана.** В `OfficeHolder` добавлены `collab`, `freed`,
  `version`, `color`; в `OfficeSession` — `dataSeq`; в `OfficeEvent` — `id` (схема
  не умеет составной `@@id`, вместо него `@@unique([fileId, seq])`) и
  `fromServer`. `OfficePeer.lostAt` не нужен: потерянный участник из списка
  уходит, а ждущий держатель живёт в `OfficeHolder.lostAt`.

### Чем проверено

- Два сервера Flux на одной PostgreSQL 16 (`PORT=3000` и `3001`, база из
  `db-setup/flux-postgres-init.sql`), два браузера, второй сотрудник на втором
  сервере:
  - до исправления `test-office-collab-live` — 13 провалов (правок не видно,
    «Правите вместе» нет, файл без правок обоих, держатель не найден), 
    `test-office-sheets-collab-live` — 18;
  - после — обе проверки зелёные целиком: Документ 30, Таблица 27 проверок.
- `scripts/test-office-bus.ts` — 206 проверок с `FLUX_PG` (104 на SQLite): номера
  подряд при 80 параллельных вставках с двух серверов, один держатель в 12 файлах
  при одновременном входе, уход, обрыв, возврат окна через другой сервер, смерть
  сервера, засев и обмен Y, журнал Таблицы, сброс сеанса, уборка; правка доходит
  до другого сервера за ~50 мс (медиана).
- `test-office-rooms` дополнен загрузкой комнаты из базы, `test-ddl` сверяет
  таблицы с тремя схемами Prisma.

### Найденные по дороге дефекты

- Адаптер SQLite (better-sqlite3): запрос вне транзакции выполняется внутри
  открытой, и созданная им строка откатывается вместе с ней. Строку сеанса теперь
  создаём до транзакции.
- Два соединения better-sqlite3 в одном процессе виснут друг на друге, поэтому
  «два сервера на SQLite» проверяются через один клиент (сервер там один).
- Автомиграция общей базы не создаёт неявные связующие таблицы (`_FileMainTags`,
  `_ComponentElementToTag`…): на пустой PostgreSQL без `flux-postgres-init.sql`
  загрузка файла отвечает 500. Не исправлено, вне этого задания.
- При первом запуске на пустой базе засев данных идёт параллельно с созданием
  таблиц («Equipment does not exist» в журнале). Не исправлено.
- Наблюдатель за диалогом в живых наборах и `innerText` полосы без таймаута:
  проба ждала 30 с на каждый опрос и «падала» минутами.
- Устаревшее в README («живое редактирование только в пределах одного
  сервера», `server/collab.ts` уже нет) исправлено.

### Не проверено

- MariaDB: живой базы нет; SQL и схема сверены тестом `test-ddl`, опрос вместо
  `LISTEN` общий с PostgreSQL. Рассинхрон часов машин больше нескольких секунд не
  моделировался иначе как сдвигом часов в проверке.
