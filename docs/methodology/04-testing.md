# Проверки каждой программы Flux

Правила приняты к внедрению 4 октября 2026. Подробные сценарии, матрицы
и критерии — в [исходном стандарте](../testing-standard-proposal-2026-10-04.md).
Этот раздел делает их обязательными для новой функции и исправления старой.
Паспорта существующих программ переводятся поэтапно; пробелы отображаются
в отчёте и не считаются успешными проверками.

## Объём проверки — по размеру правки

Объём доказательства соразмерен правке. Полный контракт на исправление
одной строки съедает время и контекст, а дефектов не находит больше, чем
узкая регрессия: поломку ловит набор, который её воспроизводит, а не
количество прогнанных наборов.

| Уровень | Когда | Что обязательно |
|---|---|---|
| Малая правка | исправление или доработка внутри одного раздела, новых действий и связей нет | узкая регрессия на саму поломку; наборы своего раздела (`npm run check -- <слово>`); `tsc --noEmit`; для интерфейса — замер раздела зондом и один снимок в двух темах |
| Новая функция | новое действие, связь между программами, новый экран | весь контракт ниже: паспорт, проверка на нужном слое, полная приёмка интерфейса |
| Выпуск | сборка exe | полный `npm run check -- --live`, `vite build`, `build:electron`, критичные сценарии |

Что не урезается ни на каком уровне:

- регрессия пишется вместе с исправлением — без неё поломка возвращается, и
  второй разбор дороже сэкономленного;
- правка, которая пишет в базу, проверяется по skill `flux-data-safety`
  целиком, малой она не бывает;
- правка общего кода (`src/components`, `src/store`, `src/lib`, `server/`)
  проверяется наборами всех разделов, которые его используют;
- полный `npm run check` — один раз перед пул-реквестом.

Паспорт действия в `verification/manifests/` заводится на новое действие.
Исправление существующего паспорт обновляет, только если изменился
ожидаемый результат.

## Обязательный контракт действия

Каждая кнопка, команда меню, клавиатурный способ запуска, перетаскивание,
переключатель и фоновая операция получают постоянный ID и ожидаемый результат.
Реестр хранится в `verification/manifests/*.json`, формат описан
[отдельно](../testing/manifest-format.md). Все существующие межпрограммные
связи получают источник, получателя, права, версию данных и сценарий передачи.

Для новой функции обязательны:

1. Паспорт действия: способ запуска, роли, исходное состояние, результат,
   отмена/повтор/ошибка и применимые связи.
2. Проверка на нужном слое: чистая функция, компонент, реальный API/БД,
   браузер, native Windows либо сам portable. Подмена зависимости фиксируется.
3. Независимое ожидаемое значение; для сохранения — повторное чтение
   фактических данных, закрытие и открытие. Для совместной работы — второй клиент.
4. Узкий тест регрессии вместе с исправлением. Нужный набор повторяется
   после правки; соседние наборы расширяются по зависимостям.
5. Снимок/геометрия для изменения интерфейса и проверка его доступности.
   Новая кнопка без проверяемого результата — незавершённая функция.

Нельзя подменять ожидаемое значение результатом той же функции, нажимать
все кнопки без сценария, обновлять снимки автоматически при провале или
считать успешную сборку доказательством работы интерфейса.

## Команды и область результата

```bash
npm run check:verification                # сам механизм проверок и новые регрессии
npm run check:coverage                    # маршруты, действия и исходные контролы
npm run check:programs -- --list           # заявленные наборы и зависимости
npm run check:programs -- --run --group engineering --report /tmp/flux-verification.json
```

Успех инвентаризации означает, что реестры согласованы. Обнаруженный JSX-
контрол не равен уникальной функции, а подсчёт контролов не означает, что
каждая кнопка была нажата и проверена. Динамические меню, iframe-редакторы
и native-контролы требуют дополнительной проверки. Непривязанные сценарии
и неисполненные ручные проверки видны отдельно.

Прошедший набор подтверждает только его перечисленные утверждения на
указанном слое. Вывод `PASS` unit-набора не превращает всю программу в
проверенную на Windows. Итог действия может оставаться PARTIAL/UNTESTED;
ручной сценарий без доказательства остаётся NOT_RUN.

## Безопасность стенда и исполнение

Используются временные файлы, синтетические профили и отдельная тестовая БД.
Наборы, зависящие от внешнего тестового API/БД, требуют явной метки
изолированного стенда и своих prerequisites. Корпоративная конфигурация
не используется как fallback. Прямое подключение компании проверяется
на MariaDB; доказательства других движков не переносятся на неё автоматически.

Общие порты, БД, пользователи, файлы и ограничения объявляются ресурсами.
Наборы с конфликтующим ресурсом выполняются по очереди, измерения
быстродействия — отдельно. Платформа, отсутствие зависимости и skip
отражаются в отчёте; exit 0 после пропуска не считается полноценным PASS.
Неизвестный отказ инфраструктуры не выдаётся за дефект программы или успех.

Артефакты содержат версию/стенд, шаг, ожидаемое/фактическое, снимок/trace
и ID синтетической операции. Пароли, токены, vault и данные сотрудников
не публикуются. Ручные сценарии и неполная инвентаризация имеют обозначенный
следующий шаг, а не скрываются ради зелёного результата.

## Приёмка интерфейса и выпуска

Обе темы, узкое/широкое окно, длинные данные и состояние ошибки обязательны
для нового экрана и для выпуска; для малой правки интерфейса хватает замера
изменённого раздела зондом и снимка в двух темах (см. уровни выше).
Проверяются читаемость, реальная геометрия, доступность кнопок, клавиатура,
фокус, контраст, скролл и устойчивость размеров. Намеренное
перекрытие окна/меню не считается дефектом само по себе.

Windows отдельно проверяет DPI и реальные дисплеи, рабочую область,
панель задач, файлы/UNC и события ОС. Эмулированные bounds не заменяют
физическую конфигурацию. Для недоступного стенда сохраняется ограничение.
Производительность измеряется по активным операциям с объёмом данных,
стендом и сопоставимым baseline; idle rAF не доказывает плавность ввода.

Потеря данных, обход прав/подписи, неработающее сохранение и недоступные
основные действия блокируют выпуск. Обязательный критичный сценарий без
доказательства также не позволяет объявить выпуск готовым. Прошедший CI
самого механизма проверок не является разрешением выпуска всего Flux.
Проверяемый portable и публикуемый portable совпадают по SHA-256.

Исключения имеют причину, ответственного, срок и альтернативное доказательство;
критичные проверки не исключаются только для получения зелёного отчёта.
Массовое добавление паспортов — основа работы, а не завершение всех проверок.
