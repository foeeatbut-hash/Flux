# Модули Flux

Назначение — запускать программы, объявленные в манифестах модулей, в общей оболочке Flux.

## Что на экране и раскладка

Модуль открывается по маршруту `/module/<id>` в обычной раме окна Flux. Манифест объявляет места запуска: «Пуск», карточку выбранной позиции оборудования и карточку тега. В карточках кнопка появляется только для объявленного места. Оформление окна следует общим правилам оболочки и поддерживает обе темы.

## Логика

PR 1 реализует этапы 1–2 плана Flux Studio. Встроенный пример находится в `modules/fixtures/equipment-inspector`: пакет содержит `manifest`, `form` и `logic`. До PR 2 используется только встроенная фикстура; загрузчика выпусков из базы пока нет. Для dev-режима перед запуском нужен `vite build`: он создаёт файлы модуля, без сборки их запросы возвращают 404.

Договор v1 предоставляет только чтение: текущий проект, позицию оборудования с параметрами, тегами и составом, тег, спецификацию (строки Тегов) и минимальные данные каталога (семейства). Запись во Flux из модуля не предусмотрена. События `opened`, `project-changed` и `changed` сообщают об открытии, смене проекта и изменении данных; модуль перечитывает данные через договор.

Привязки `flux.*` заполняет оболочка независимо от логики модуля. Логика подписывается на обновления через `flux.on('changed', ...)`; `state` хранит собственное состояние окна между пересчётами, а `calc.out` — результаты логики. При смене контекста состояние сбрасывается. Общие GET-запросы разделяются всеми открытыми модулями одного сеанса/API; локальный снимок одного пересчёта остаётся неизменным. `entity:changed`, возврат фокуса и восстановление связи сбрасывают общий кэш до уведомления окон.

Содержимое загружается по протоколу `flux-module://` в iframe с непрозрачным источником и `sandbox="allow-scripts"`. CSP запрещает сеть и `eval`. Схемы сообщений находятся в `modules/schemas.ts` (`messageSchemas`); расчёт выполняется в Worker с пределом времени 30 секунд. Без подписчиков Worker завершается по `done`. При подписчиках он отвечает на ping раз в секунду; отсутствие ответа за 3 секунды завершает поток. Состояние и calc.out вместе ограничены 256 КиБ UTF-8, размер проверяется также между событиями. Через 60 секунд Worker освобождает globalThis; следующий расчёт восстанавливает последний завершённый снимок. После фонового сбоя показывается сообщение, перезапуск отложен до нового события, чтобы неисправный setup не запускался бесконечным циклом.

## Проверки

`test-modules-contract` проверяет строгие схемы, происхождение сообщений,
запрет записи и отмену старых ответов. `test-modules-data` проверяет проекции
и отказы чтения с подставным HTTP. `test-modules-native` запускает настоящий
Electron с рабочим preload и протоколом, временную SQLite и штатные маршруты
оборудования: правка через API и `entity:changed` меняет открытый модуль.
Профиль и передача socket-события в тесте синтетические; полный вход,
корпоративная SQL-база и работа двух компьютеров им не подтверждаются.
Набор также проверяет изоляцию, время Worker, геометрию и снимки при 1440/1024
в обеих темах. CI Windows — `.github/workflows/verify-modules.yml`.

Изменения доставляются событиями сокета и при возврате фокуса. Единственный
общий запасной таймер раз в две минуты работает только при отключённом сокете.
При смене проекта контекст карточки сбрасывается, старые ответы не выдаются.
Отказ чтения очищает содержимое, вместо него не показываются подставные данные.

Предел 30 секунд останавливает Worker через `terminate()`. Жёсткий лимит
памяти отдельного Worker браузерный API не предоставляет; это ограничение
PR 1, а не реализованная квота. Внешних подключений, загрузчика выпусков,
сертификатов и редактора Studio в этом PR нет.

`form.json` проверяется при сборке по схемам данных договора: неизвестный ресурс, поле или колонка останавливают сборку с указанием пути. Динамические state/calc.out принадлежат модулю. Наборы `modules-worker`, `modules-form`, `modules-refresh` проверяют жизненный цикл, ошибки формы и общий кэш/события. Жёсткая квота heap браузерного Worker не заявляется.
