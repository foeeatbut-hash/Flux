# Модули Flux

Назначение — запускать программы, объявленные в манифестах модулей, в общей оболочке Flux.

## Что на экране и раскладка

Модуль открывается по маршруту `/module/<id>` в обычной раме окна Flux. Манифест объявляет места запуска: «Пуск», карточку выбранной позиции оборудования и карточку тега. В карточках кнопка появляется только для объявленного места. Оформление окна следует общим правилам оболочки и поддерживает обе темы.

## Логика

PR 1 реализовал этапы 1–2 плана Flux Studio, PR #139 — этап 2 (выпуски из базы, права, каналы, Flux Store, обращения по подпрограммам; описание — разделы ниже). Встроенный пример находится в `modules/fixtures/equipment-inspector`: пакет содержит `manifest`, `form` и `logic`; выпуски, выложенные в базу, загружаются поверх встроенной фикстуры. Для dev-режима перед запуском нужен `vite build`: он создаёт файлы модуля, без сборки их запросы возвращают 404.

Договор v1 предоставляет только чтение: текущий проект, позицию оборудования с параметрами, тегами и составом, тег, спецификацию (строки Тегов) и минимальные данные каталога (семейства). Запись во Flux из модуля не предусмотрена. События `opened`, `project-changed` и `changed` сообщают об открытии, смене проекта и изменении данных; модуль перечитывает данные через договор.

Привязки `flux.*` заполняет оболочка независимо от логики модуля. Логика подписывается на обновления через `flux.on('changed', ...)`; `state` хранит собственное состояние окна между пересчётами, а `calc.out` — результаты логики. При смене контекста состояние сбрасывается. Общие GET-запросы разделяются всеми открытыми модулями одного сеанса/API; локальный снимок одного пересчёта остаётся неизменным. `entity:changed`, возврат фокуса и восстановление связи сбрасывают общий кэш до уведомления окон.

Содержимое загружается по протоколу `flux-module://` в iframe с непрозрачным источником и `sandbox="allow-scripts"`. CSP запрещает сеть и `eval`. Схемы сообщений находятся в `modules/schemas.ts` (`messageSchemas`); расчёт выполняется в Worker с пределом времени 30 секунд. Без подписчиков Worker завершается по `done`. При подписчиках он отвечает на ping раз в секунду; отсутствие ответа за 3 секунды завершает поток. Состояние и calc.out вместе ограничены 256 КиБ UTF-8, размер проверяется также между событиями. Через 60 секунд Worker освобождает globalThis; следующий расчёт восстанавливает последний завершённый снимок. После фонового сбоя показывается сообщение, перезапуск отложен до нового события, чтобы неисправный setup не запускался бесконечным циклом.

## Выпуски из базы и проверка владельцем (этап 2, шаг а)

Модуль из общей базы запускается только выпуском с подписью владельца.
Разработчик присылает запрос на публикацию — весь пакет (исходники,
`manifest.json`, `form.json`, примеры, `build/runtime.js`), подписанный
ключом из сертификата владельца. Владелец в разделе «Запросы на публикацию» Studio — Владелец (`studio/owner/console`, во Flux этого
экрана больше нет) смотрит файлы и разницу с прошлым выпуском, изменения разрешений и «Связь с Flux»,
пробует подпрограмму на тестовой базе в изоляции, оставляет замечания к строкам, возвращает, правит сам,
отклоняет или выпускает. Подпись ставит главный процесс Studio — Владелец ключом издателя из хранилища
владельца (`studio/owner/src/moduleSigning.ts`), после собственного диалога подтверждения; окно пароль
не вводит. Главный процесс Flux проверяет каждый выпуск сам (`modules/trust/verify.ts`) и держит кэш
проверенных (`electron/moduleCache.ts`); протокол `flux-module://` отдаёт модуль из базы только из этого
кэша. Там же — «Выпуски и каналы» (перевод в рабочий канал, откат, отзыв, тестовый канал) и
«Сертификаты разработчиков» (запросы, выдача, отзыв); устройство окна и таблица «функция → где → чем
проверено» — [страница Studio](studio.md).

## Права, каналы и откат (этап 2, шаг б)

Права `module.develop` (присылать код владельцу) и `module.publish` (просить
рабочий канал сразу) закрыты по умолчанию; роль «Разработчик»
(`MODULE_DEVELOPER`) выдаёт только первое. Проверяет сервер, а не окно. Без
`module.publish` запрос идёт только в тестовый канал. «Что нового» в запросе
обязательно. Тестовый канал виден назначенным владельцем людям
(`AppSetting modules.testers`, панель «Тестовый канал» в разделе владельца):
сервер не отдаёт его остальным, Flux запускает выпуск разрешённого канала.
Владелец может перевести тот же тестовый выпуск в рабочий канал: отдельное
неизменяемое назначение `FLUXMODCHANNEL1` подписано ключом владельца и связано
с SHA-256 исходной подписи выпуска. Подпись, версия и пакет выпуска не
меняются. Назначения хранятся отдельными строками `AppSetting` и проверяются
сервером и кэшем; ограничения отката применяются к эффективному каналу.

Откат — подписанное владельцем назначение «канал не выше версии X»
(`FLUXMODPIN1`): Flux хранит его, как отзывы, без связи, из двух записей
действует позднее. Тот же ключ `keys.update`, что и для обновлений Flux
(решение владельца 6 ноября 2026), приставки подписей разные.

## Flux Store (этап 2, шаг в)

Раздел «Store» (`/store`, `src/screens/StoreScreen.tsx`, части в
`src/components/store/`): витрина (карусель «Рекомендуем», ряды, поиск с
подсказками, категории), страница подпрограммы (шапка сжимается при прокрутке
в полосу за 160 мс, снимки, описание, отзывы, что нового, разрешения,
требования, история версий), «Библиотека» и «Загрузки» (обновления по решению
человека, автообновление — настройка, по умолчанию выключено, свой
переключатель у подпрограммы, «Вернуть предыдущую версию»), «Админ» (допуск,
закрепление версии, обязательные для должностей, журнал). Вид — исключение
из `01-design.md`: стекло окна `.fx-glass`, при выключенной прозрачности фон
сплошной; движение отключается по `prefers-reduced-motion`.

Устройство. Витрина собирается сервером из выпусков и манифеста
(`server/moduleListings.ts`, блок `store` в `manifest.json`: категория,
описание, цвет, требования, зависимости, должности, снимки). Политика —
таблицы `ModuleStoreEntry`, `ModuleInstall`, `ModuleStoreLog`,
`ModuleReview`; доверия в них нет. Ставится человеку: сервер хранит список
для других его компьютеров, но запускает Flux только то, что человек выбрал в
файле выбора главного процесса (`electron/moduleSelection.ts`) и что прошло
проверку подписи (`ModuleCache.resolve`). Разрешения, показанные в окне,
сверяются с проверенным манифестом (`permissionsDigest`). Отозванная версия
сама откатывает установленную на прошлую неотозванную. Последние 3 версии и
выбранная хранятся в кэше: возврат работает без связи.

Открытое окно удерживает запущенную версию, пока человек не нажмёт
«Перезапустить» после обновления; расчёт на прежней версии не прерывается
самой установкой. Отзыв выпуска или ключа, подписанное ограничение канала,
потеря допуска и удаление прекращают недопустимый запуск без ожидания кнопки.
Постоянные данные модуля и их копирование перед обновлением,
относятся к следующим этапам; подключения к внешним программам — этап 3б (раздел ниже).

## Обращения по подпрограммам (этап 2, шаг г)

В панели обращения можно выбрать Flux или установленную подпрограмму; активная
подпрограмма подставляется автоматически. Рядом с адресатом сказано, что
заголовок и описание видит разработчик, а данные проектов ему не передаются.
Это одно обращение с общей историей.
Разработчик видит обращения своих выпусков по действующему сертификату;
пакет для него строится из разрешённых полей и не включает данные проектов.
Переадресация меняет получателя. В Store и похожие обращения попадают только
известные проблемы, последнюю отметку которых подтвердил разработчик этой
подпрограммы с действующим сертификатом; одной отметки администратора мало.
Известные проблемы показываются с обходом, «У меня тоже» учитывает затронутых. Обезличенные счётчики сбоев
принимаются только для существующего подписанного выпуска, группируются
по версии за последние 30 дней и показываются в Store. Расписки старше 30
дней удаляет часовая уборка; при чтении они уже не учитываются. Предел —
30 новых пакетов за минуту и 100 событий в пакете; повтор принятого пакета
не тратит предел. Когда доступен подходящий
выпуск с исправлением, автор видит «Исправлено» и переход к обновлению.
Графики и полноценная вкладка разработчика остаются работой Studio.


## Языки логики и пределы исполнения (этап 3а)

Языки ровно эти (решение владельца 7 ноября 2026): TypeScript/JavaScript,
Python (Pyodide) и WebAssembly для C, C++, Rust, Go (TinyGo) и C#. Других нет.
Для оболочки любая логика — чёрный ящик «вход JSON → выход JSON по схеме договора»
(`{state, calc:{out}}`); язык задаёт `manifest.json` (`language`, для `.wasm` ещё
`sourceLanguage`, `platform`), те же поля подписаны в выпуске. Файл логики обязан
соответствовать языку (`logic/main.ts`, `main.py`, `main.wasm`) — проверка до
подписи владельца, `modules/trust/execution.ts`. Подпись и так покрывает пакет
побайтно: изменённый `.py` или `.wasm` не запускается. Код: `modules/engine/`.

* **Обмен.** Числа — float64; целое больше 2^53 − 1 передаётся строкой, в тексте
  с порядком (`1e150`) оно остаётся float64; NaN и бесконечность — ошибка `NUMBER`.
  Результат проверяется по схеме до показа (мост и подпрограмма, `modules/engine/json.ts`).
  Часов нет, случайность только от `seed` входа (WASI `random_get`, `random` в Python,
  `Math.random` в TypeScript `compute`); каждый расчёт — чистая среда.
* **WebAssembly** (`modules/engine/wasm.ts`, `wasmInspect.ts`). Файл разбирается до
  компиляции: импортов только `flux.*` и урезанный WASI, максимум памяти записан в
  файле (реактор до 64 МиБ, WASI-команда .NET до 128 МиБ). Два способа вызова:
  реактор (`flux_alloc/flux_run/flux_output`: C, C++, Rust, Go) и WASI-команда
  (stdin → stdout: C#). Каждый расчёт — новый экземпляр. Компиляция одна на выпуск
  (в окне, готовый модуль передаётся Worker'у); дисковый кэш невозможен — Chromium
  не хранит `WebAssembly.Module` в IndexedDB, а V8 и так компилирует лениво (мс).
* **Python** (`modules/engine/python.ts`). Одна среда Pyodide на все подпрограммы в
  скрытом iframe `flux-module://_compute/` (непрозрачный источник, CSP без сети,
  `wasm-unsafe-eval` и `connect-src 'self'` только здесь). Pyodide ставится
  пакетом npm в `dist/modules/_compute/pyodide` при сборке — в portable, не из интернета.
  Загрузка при первом Python-расчёте; выгрузка после N минут без вызовов (настройка
  `flux.modules.pythonIdleMinutes`, по умолчанию 5) одним отложенным вызовом. У каждой
  подпрограммы своя область имён и свои копии разрешённых модулей (только публичные имена,
  без вложенных модулей: подмена `math.sqrt` другой подпрограмме не видна, `json.codecs.sys`
  не существует), список разрешённых модулей, нет `open`. `random` и `statistics` собственные
  (чистый Python, без `os`/`sys`; зерно из входа), поэтому `random._os` не существует. Это защита
  от ошибок: функции стандартной библиотеки остаются общими, и через `func.__globals__` достижим
  настоящий `sys` — от злого кода Python в одном интерпретаторе не изолировать, границу держит
  песочница (проверено побегом из фильтра импортов). **numpy 2.2.5** входит в сборку (колесо в
  `vendor/pyodide`, SHA-256 сверяется с `pyodide-lock.json` при сборке, +2,8 МБ), грузится лениво —
  только если подпрограмма его импортирует, без сети; отдаётся настоящий, один на все подпрограммы,
  зерно входа ставится в глобальный `numpy.random`, `default_rng()` пишите с зерном. Лицензии:
  Pyodide — MPL-2.0 (файлы не изменены), numpy — BSD-3-Clause (`vendor/pyodide/README.md`).
* **Один расчёт Python за раз — жёсткая гарантия.** Очередь окна даёт Python одну полосу, но порядок
  очереди не гарантия: два расчёта в одной среде не идут вместе, потому что `SerialLane`
  (`modules/engine/serial.ts`) стоит и в самой среде (`PythonEnvironment.run`, включая await'ы загрузки
  пакетов), и в обёртке хоста окна (выгрузка, перезапуск, остановка по времени одного не пускают второй
  вперёд; таймер второго стартует в его очередь). Копии модулей создаются заново на каждый расчёт, так что
  восстанавливать между расчётами нечего. Среда своя у каждого окна Flux. Вторая подпрограмма ждёт
  ровно столько, сколько держит среду первая (в Electron: подмена `math.sqrt` и цикл 296 мс → вторая
  закончила на 298 мс).
* **Пределы** (`modules/engine/scheduler.ts`, `src/services/moduleCompute.ts`). Всё вне
  главного потока. Одновременно не больше «ядра − 1, не более 4» расчётов; открытое окно
  раньше фонового, фоновым оставлен слот открытому; Python — одна полоса; очередь и число
  расчётов одной подпрограммы ограничены (`BUSY`). Время 30 с на расчёт (Worker/среда
  останавливаются и пересоздаются), память — максимум `WebAssembly.Memory` (для Pyodide
  подменяется на 512 МиБ), результат до 256 КиБ. Приоритет потока ОС Worker'у из веба не
  задать: «пониженный приоритет» — очередь и ожидание паузы окна. В простое нет таймеров-опросов.
  Вложенные Worker'ы запретить нечем в CSP (`worker-src blob:` нужен самому Worker'у логики), поэтому
  пролог (`modules/runtime/prologue.ts`) убирает `Worker`/`SharedWorker` до кода подпрограммы — в
  TypeScript-Worker и в Worker Python (`js.Worker`). Закрытая подпрограмма снимает ожидающие
  расчёты с очереди, выпуски, ушедшие из кэша проверенных, — свои источники и скомпилированные модули.
* **Контрольные примеры** (`examples/controls.json`, до 8 примеров, допуск `abs`/`rel`).
  При первом запуске выпуска на компьютере окно прогоняет их тем же путём, что и расчёт;
  расхождение результата — подпрограмма не запускается, событие `controls` в счётчики сбоев;
  разовая ошибка расчёта (время, память) не закрывает выпуск навсегда: проверка повторяется до
  трёх раз подряд, кнопка «Проверить снова» сбрасывает любой итог. Главный процесс запоминает итог (`electron/moduleControls.ts`, ключ — хеш подписи и версия
  Electron) и перестаёт отдавать код выпуска.
* **Примеры** — `modules/fixtures/` (README с тулчейнами): один расчёт на семи языках,
  результат совпадает бит в бит.

Проверки: `test-modules-languages`, `-wasm`, `-python`, `-parity`, `-scheduler`,
`-compute`; в настоящем Electron — `test-modules-compute-native` (подписанные выпуски,
изоляция хоста Python, пределы, контрольные при первом запуске; Windows в CI).

## Подключения к внешним программам и журнал подпрограмм (этап 3б)

Подпрограмма объявляет подключения в `manifest.json` (`connections`, до 8): `id`, `kind`
(`com` с `progId`, `http` или `ws` с `url` без пути и `pathPrefix`), `app` (понятное имя программы),
`does` (что будет делать, простыми словами) и `access` (`read`, `write`, `send`). Объявление входит в
подписанный выпуск; схема отвергает адрес с путём или учётными данными, запрещённый COM-объект
(`WScript.Shell`, `Shell.Application`, `MSXML2.*` и подобные: запуск программ и сеть в обход адресов
закрыты решением владельца) и технические тексты вместо человеческих. Разрешение — только это
объявление в выпуске, подписанном владельцем; то, что подпрограмма «просит» во время работы, сверяется
с ним главным процессом (`modules/connections/model.ts`, `electron/moduleConnections.ts`).

* **Сквозной канал.** Логика на TypeScript зовёт `connect.http/ws/com` (сырой вызов — `connect.call`);
  мост проверяет форму сообщения схемой (адреса в вызове нет вовсе, только путь внутри префикса), окно
  передаёт вызов в главный процесс (`modules:connect`), тот снова проверяет форму, выпуск, объявление,
  политику, решение человека и пределы. HTTP: метод, путь с запросом, заголовки (cookie, host, origin и
  управление соединением запрещены), тело; ответ — статус, заголовки без `set-cookie`, тело. Редиректы
  не выполняются: ответ 3xx возвращается как есть, а следующий вызов проверяется заново. WebSocket:
  открыть, послать, получить (очередь до 100 сообщений и 512 КиБ), закрыть. COM: открыть объект по
  имени, вызвать метод, прочитать и записать свойство по имени с аргументами JSON; объект в ответе
  приходит номером `{$com: n}`, ref-параметр — `{$out: true}` (ответ `{ret, out}`), чужой номер — отказ.
  Подключения открывает логика на TypeScript; расчёт на Python и WebAssembly (чистая функция «JSON → JSON»)
  получает их результат входом через `state`. Прямой вызов подключений из Python/WASM — отдельная задача этапа 4.
* **Адрес.** Имя разрешается в главном процессе, **все** адреса имени проверяются (`address.ts`), соединение
  идёт на проверенный адрес (подмена DNS между проверкой и подключением невозможна). Внутренние адреса и
  localhost открыты, только если объявлены явно (адрес-литерал, `localhost` — только петля, или `internal`);
  адреса метаданных облака и «этот компьютер» закрыты всегда.
* **Пределы на подпрограмму.** 20 вызовов в секунду, 4 одновременно, 4 открытых подключения, 512 КиБ
  на тело и ответ, 15 с на вызов (ожидание сообщения WebSocket — до 25 с), 64 COM-объекта на
  подключение. Превышение — `LIMIT`/`TIMEOUT` и событие `connection` в счётчиках сбоев (как и `DENIED`).
* **COM.** Во Flux нет моста к E3 в главном процессе (этап C `e3-integration.md` не сделан), поэтому
  общий способ — долгоживущий помощник Windows PowerShell поздним связыванием (`InvokeMember`, как в
  пробе E3, раздел 4.3 документа): значения разворачиваются из PSObject, у объекта не зовётся `GetType()`.
  **Белый список:** открывается только ProgID, объявленный в выпуске, подписанном владельцем; имя сравнивается без
  версии (`Name.1` = `Name`). Опасные объекты (оболочка и запуск программ, файловая система, ADODB/CDO, приложения
  Office, WMI, HTTP-клиенты) закрыты даже при объявлении: нужен флаг `allowDangerous` — он в подписанном выпуске,
  отмечен в описании («опасный объект») и входит в разрешение, которое спрашивается у человека. Главный процесс
  проверяет это на каждом вызове. Объект в ответе помощник регистрирует, только если его тип не из списка опасных
  (иначе ошибка, номер не выдаётся). **Помощник у каждой подпрограммы свой:** таймаут или сбой одной не трогает
  объекты других, номера объектов сквозные и после перезапуска не повторяются, при выходе помощника учёт
  открытых объектов обнуляется. Вызовы одной подпрограммы идут по очереди (очередь до 8), до 1000 вызовов в секунду
  и до 4096 живых объектов; лишние объекты в ответе освобождаются сразу, все — при закрытии окна. Пакет `com-batch`
  (до 200 вызовов за один обход, остановка на первой ошибке) нужен для скорости E3. Аргументы до 64 КиБ, ответ до 512 КиБ.
  **Замер** (1000 вызовов `GetBaseName`, Windows CI): см. описание PR. Другие ОС и проверки подменяют бэкенд
  (`ComBackend`, `scripts/fixtures/fakeCom.ts`). Пример использует настоящий `Scripting.FileSystemObject`
  (с флагом; только `GetBaseName` и `BuildPath`: диск не читается и не пишется).
* **Запрос у человека** (`ConnectionPrompt`): закрытие окна подпрограммы при открытом запросе ничего не запоминает (спросим снова), три ответа, «Подробнее», «Для специалиста». Решения хранит
  `electron/moduleGrants.ts` (файл `grants.json`), привязаны к человеку, подпрограмме, подключению и **тексту
  разрешения** (адрес и вид доступа): новая версия с новым адресом или доступом «изменять» спрашивает
  снова. Политика администратора (`/api/modules/connection-policy`, правила по ролям) приходит в окно и
  в главный процесс, сильнее выбора человека и хранится рядом с решениями — работает без связи. Управление —
  Store (страница подпрограммы) и «Настройки → Подпрограммы».
* **Журнал** (`modules/journal/model.ts`): запись — подпрограмма, версия, человек, вид, уровень, событие,
  короткая метка, итог, длительность, объём. Кольцо на компьютере (`electron/moduleJournal.ts`: 5000
  записей, 14 дней, частота записей от окна ограничена), пачки на сервер (`/api/modules/journal`, 30 пачек в
  минуту, 200 записей, идемпотентно по id, человек берётся из сеанса, записи неизвестных подпрограмм и вне срока
  отвергаются; ключ строки привязан к человеку, чужой номер занять нельзя; не больше 20 000 записей от человека в сутки), срок 30 дней и 200 000 строк (часовая уборка). Смотрят владелец и администратор (с именами,
  фильтры, CSV), разработчик — только свои подпрограммы, без людей и без отбора по человеку, а **строки `flux.log` — без текста** (уровень, время, факт): текст пишет сама подпрограмма, и в общем журнале его видят только владелец и администратор; разработчик увидит строки, только если человек сам приложил журнал к обращению (строки видны человеку до отправки). Таблица
  `ModuleJournal` — во всех трёх схемах Prisma.
* **В запросе владельца** разница подключений выделена («новое: подключение к …») и показаны тексты так, как
  их увидит человек; в окне установки Store — подключения словами и мелко адрес.

Проверки: `test-modules-connections` (72: объявление, адреса и DNS, HTTP/WebSocket/COM, решения, пределы,
журнал — на настоящих локальных серверах), `test-modules-journal` (31: приём, права, обезличивание, срок,
политика, разница запроса; SQLite), `test-modules-connections-native` (31 в настоящем Electron на Windows и
Linux: подписанные выпуски, окно запроса в обеих темах, примеры HTTP и COM, границы, журнал, раздел «Разрешения»
и журнал на экране). Снимки — артефакт CI (`artifacts/modules-shots`), в git их нет. Не проверено на этом
этапе: E3 вживую и работа помощника COM с реальным E3 — у владельца.

## Страница программы (договор v2)

Второй вид интерфейса рядом с формой: свой экран кодом. Кадр тот же (`<iframe sandbox="allow-scripts">`, `flux-module://<id>/ui/…`),
CSP свой: ресурсы только из пакета, без сети, без eval, без `'unsafe-inline'`; `canvas`, SVG, WebGL, `data:`/`blob:` картинки работают.
Страница видит только `flux.*` (клиент поставляет Flux, `/_flux/flux.v1.js`; набор оформления — `/_flux/flux-ui.v1.css`, необязателен).
Окно Flux показывает «Программа не отвечает» с перезапуском, если страница молчит 30 с (считается только страница с клиентом flux.v1.js и только у видимого окна); свои окна программы открываются как
обычные окна Flux (`flux.windows.open`). Что есть на экране — то, что нарисовал разработчик; требования методологии к цветам и мерам
проверяют снимки обеих тем и владелец, автоматически — только использование токенов темы.

## Проверки

`test-modules-page` проверяет страницу программы: пакет и подпись, адреса, мост и настоящий кадр Chromium (каждая попытка выйти за
границы — сеть, родитель, хранилища, eval, встроенные скрипт и стиль, окно — закрыта; мутации ослабленного CSP замечены).
`test-modules-contract` проверяет строгие схемы, происхождение сообщений,
запрет записи и отмену старых ответов. `test-modules-data` проверяет проекции
и отказы чтения с подставным HTTP. `test-modules-native` запускает настоящий
Electron с рабочим preload и протоколом, временную SQLite и штатные маршруты
оборудования: правка через API и `entity:changed` меняет открытый модуль.
Профиль и передача socket-события в тесте синтетические; полный вход,
корпоративная SQL-база и работа двух компьютеров им не подтверждаются.
Набор также проверяет изоляцию, время Worker, геометрию и снимки при 1440/1024
в обеих темах. CI Windows — `.github/workflows/verify-modules.yml`.

Изменения доставляются событиями сокета и при возврате фокуса. Единственный
общий запасной таймер раз в две минуты работает только при отключённом сокете.
При смене проекта контекст карточки сбрасывается, старые ответы не выдаются.
Отказ чтения очищает содержимое, вместо него не показываются подставные данные.

Предел 30 секунд останавливает Worker через `terminate()`. Жёсткий лимит
памяти отдельного Worker браузерный API не предоставляет; это ограничение
PR 1, а не реализованная квота. Внешних подключений и редактора Studio нет; выпуски,
сертификаты и отзывы проверяют `test-modules-trust` и `test-modules-publishing`; права, каналы и откат — `test-modules-channels`, перевод выпуска — `test-modules-promotion`; Store (сервер, выбор установленного, возврат без связи) — `test-modules-store`, экран — `test-modules-store-ui` (нужен свой Vite и `FLUX_CHROME`).

`form.json` проверяется при сборке по схемам данных договора: неизвестный ресурс, поле или колонка останавливают сборку с указанием пути. Динамические state/calc.out принадлежат модулю. Наборы `modules-worker`, `modules-form`, `modules-refresh` проверяют жизненный цикл, ошибки формы и общий кэш/события. Жёсткая квота heap браузерного Worker не заявляется.
