# Flux Studio (программа разработчика и сборка владельца)

Состояние: этап 4а (две сборки и перенос Flux Owner). Содержимое для
разработчика — этап 4б, разделы владельца внутри общего окна — 4в. План —
[roadmap/modules.md](../../roadmap/modules.md), задание —
[studio-handoff.md](../../studio-handoff.md).

## Две сборки из одного кода

Решение владельца (9 ноября 2026): программ две — Flux для пользователей и Flux
Studio для разработчиков. Отдельного Flux Owner больше нет, всё, что он умел,
живёт в Studio — Владелец.

| Сборка | Файл | Что внутри | Кто получает |
|---|---|---|---|
| Studio | `FluxStudio.exe` | оболочка разработчика: подключение к базе, вход, «Подпрограммы» | разработчики |
| Studio — Владелец | `FluxStudio-Владелец.exe` | та же оболочка + раздел «Лицензии и обновления Flux» (бывший Flux Owner) | только владелец |

Номер версии у Flux, Studio и Studio — Владелец один: корневой `package.json`,
другого источника у сборок нет (`studio/build.cjs` берёт его оттуда).

**Кода владельца в сборке разработчика физически нет.** Раздел подключается только
точкой входа сборки владельца (`studio/entry-owner.ts`) и собирается отдельными
файлами (`owner/main.cjs`, `ui/`); у разработчика нет ни этих файлов, ни
IPC-канала `owner:action`. Проверка `scripts/check-studio-bundle.ts` смотрит на
готовый пакет, а не на исходники: файл из `studio/owner` в карте сборки esbuild,
каталоги раздела в пакете, метки кода владельца (подпись лицензий и обновлений,
вход владельца, форматы хранилища) в тексте любого файла и в `app.asar`.
`scripts/test-studio-bundle.ts` доказывает, что проверка падает: подключённый к
сборке разработчика модуль владельца, метка в готовом пакете, метка в asar.
Каждая метка обязана встречаться в сборке владельца, иначе она мёртвая.

Сборка владельца собирается только по ручному запуску
(`build-studio-owner.yml`, `workflow_dispatch`), артефакт хранится 7 дней и не
попадает ни в общие выпуски, ни в обновления разработчиков. Закрытых ключей в
сборке нет: хранилище лежит на компьютере владельца
(`~/.flux-owner/vault.flux-owner`, формат и путь прежние — перевыпуск лицензий и
смена закреплённых ключей не нужны; прежнее хранилище, созданное кодом до
переноса, лежит в тестовых данных и открывается проверкой).

## Вход разработчика

Подключение: адрес общей MariaDB / MySQL вводится в окне и нигде не
сохраняется (содержит пароль базы); рядом с Studio должен лежать Flux того же
выпуска (`Flux-<версия>-x64.exe`) — он запускает локальный обработчик на
loopback (`studio/shared/database-runtime.cjs`, общий с разделом владельца).
Вход — логин и пароль Flux. **Право проверяет сервер** (`server/routes/studio.ts`,
`GET /api/studio/session`): пускает только вход владельца или пользователя с
**явным** правом `module.develop` (личным или от должности, действующим и не
просроченным). Общая проверка прав Flux (`userCan`) здесь намеренно не
используется: она отдаёт администратору любое право, кроме `admin.*`, а в Studio
администратор без явно выданного права получает 403 и подсказку. Токен сессии живёт только
в главном процессе, окно его не видит. Раздел «Подпрограммы» показывает свои
подпрограммы (последняя версия, состояние последней отправки, число отправок),
не больше 200; число отправок считает база.

## Окно

Одно окно, левое меню разделов («Подпрограммы», у владельца ещё «Управление →
Лицензии и обновления Flux», который открывает окно прежнего Flux Owner),
справа раздел. Экраны: «Подключение», «Вход», «Подпрограммы» (список и пустое
состояние). Оформление — токены на `:root`, светлая и тёмная тема по системе,
фоны сплошные, без прозрачности; фокус виден, поля подписаны. Проверка —
`scripts/test-studio-ui.ts` (замеры и снимки обеих тем, снимки уходят
артефактом CI `studio-screenshots`).

## Редакторы подпрограммы (этап 4б-2)

Каталог `studio/renderer/editors/`, вход — `index.tsx` (`<Editors moduleId draft onChange />`, тип
`ModuleDraft` в `types.ts`). Вкладки: «Форма» (палитра, структура, свойства, предпросмотр),
«form.json» (текст), «Код», «Договор», «Правила».

- Один источник истины для формы — `formStore.ts`: визуальная правка переписывает текст, правка
  текста обновляет форму, но только если текст прошёл разбор и схему; иначе остаётся последняя
  верная форма, а ошибки показаны с номером строки (`jsonText.ts`, `formSchema.ts`). Привязки,
  которых нет в договоре, форму не отвергают, а отмечаются красной точкой и в списке замечаний.
- Предпросмотр рисует настоящий `modules/runtime/form.ts` (второго набора разметки нет) в светлой и
  тёмной теме и в окне 360 px. Форма расширена необязательными полями ввода (`unit`, `allowed`,
  `min`/`max`, `required`, `placeholder`, `hint`, `visibleIf`); Flux их пока не рисует — это
  описание ввода для редактора и проверок, прежние формы остаются верными.
- Код: CodeMirror 6 из npm (без CDN), в теневом корне: Studio открывается с CSP `style-src 'self'`,
  а CodeMirror в обычном документе ставит `<style>`. Из договора создаётся настоящий `contract.d.ts`
  (`contractTypes.ts`; компилятор TypeScript проверяет его в тесте); в окне работает лёгкая проверка и
  автодополнение (`codeSupport.ts`) — компилятор в окно не входит (размер, закрытая сеть). Для
  остальных языков — подсветка и справка «какой JSON приходит и уходит».
- Ajv в окне не запускается (`new Function` против CSP без `unsafe-eval`): схема формы проверяется
  своим разбором `miniSchema.ts`, согласие с Ajv закреплено тестом; `dataSchemas` вынесены из
  `modules/schemas.ts` в `modules/dataSchemas.ts`, чтобы не тянуть Ajv в окно.
- Методология внутри: «когда применять» и пример у компонентов палитры, правила текста и список
  раздела 8 берутся из `docs/methodology/01-design.md` скриптом
  `scripts/gen-studio-editor-methodology.ts` (файл `methodology.generated.ts`; тест падает, если
  документ изменился, а выписка нет). `checkFormDesign(form, { contract? })` — автоматические
  проверки раздела 8 по описанию формы (цвета из токенов, подписи, меры, узкое окно, числа вправо,
  моноширинный только для кодов); её вызывает «Проверка перед отправкой».
- Стенд для браузерных проверок: `studio/renderer/editors/harness/` (страница с образцом черновика).

| Функция Flux Owner | Где теперь | Чем проверено |
|---|---|---|
| Подключение к общей базе по URI, без сохранения пароля | `studio/shared/database-runtime.cjs`, действие `connect` в `studio/owner/src/main.cjs` | `studio/shared/test-database-runtime.cjs`, `studio/owner/scripts/test.cjs` |
| Локальный API на loopback (`Flux-<версия>-x64.exe --flux-company-server`) | там же; версия Flux = версия Studio | те же + `studio/owner/scripts/test-network.cjs` |
| Хранилище ключей (создание, пароли, запасной ключ, импорт, экспорт, полная копия) | `studio/owner/src/vault.cjs`, `setup.cjs`; путь `~/.flux-owner/vault.flux-owner`, формат `FLUXOWNER1` | `test.cjs`; `scripts/test-studio-owner-section.ts` (хранилище прежнего кода открывается теми же ключами); `scripts/test-verification-identity-owner.ts` |
| Вход владельца (подпись одноразового вызова) | `connect` → `/api/owner/challenge`, `/api/owner/login` | `test.cjs`, `scripts/test-owner-auth.ts` |
| Лицензии: выпуск, отзыв, запрос | `signing.cjs`, `vendor/license-core.ts`; `request`, `issue`, `revoke`, `publishRevocation` | `test.cjs` |

Список из 30 действий главного процесса прежний; их проверки живут в перенесённом
`studio/owner/scripts/test.cjs` (он собирает настоящий `main.cjs` и вызывает действия).
Намеренные изменения: закрытие окна владельца только запирает хранилище, программа
остаётся; окно открывается из меню Studio. Оболочка и раздел подключаются к базе каждый
своим локальным обработчиком — это осознанно: у них независимые сессии и отключение.
